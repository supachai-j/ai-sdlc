Frontend Implementation

ฝั่งหน้าบ้านมีปัญหาเฉพาะตัวที่ฝั่งหลังบ้านไม่มี — โค้ดที่ผิดอาจดูถูกในสกรีนช็อต โมดูลนี้ว่าด้วยการปิดช่องนั้นด้วยลูปตรวจที่ agent ทำเองได้

9 บทเรียน3 ชั่วโมง2 แล็บต้องผ่าน M04 · M05 ก่อน
ใจความของทั้งโมดูล

งาน FE ที่มอบให้ agent แล้วได้ผลดี คืองานที่มีภาษากลางให้อ้างอิง — design token ชื่อ component และเกณฑ์ที่ตรวจอัตโนมัติได้ ถ้าไม่มีสามอย่างนี้ คุณกำลังสั่งด้วยคำบรรยายความรู้สึก

06.01

ลำดับที่ข้ามไม่ได้

งาน FE มีปัญหาเฉพาะตัวที่ฝั่ง BE ไม่มี — โค้ดที่ผิดอาจดูถูกในสกรีนช็อต แล้วเราก็ผ่านมันไป จนกว่าจะมีคนกดจริงแล้วพัง

ทางแก้ไม่ใช่ดูให้ละเอียดขึ้น แต่คือทำให้มันมีภาษากลางให้อ้างอิง แล้วตรวจด้วยเกณฑ์แทนสายตา — ลำดับ token → component → page → flow มีไว้เพื่อสร้างภาษานั้น

Figure 1 · ลำดับนี้ไม่ใช่เรื่องความเป็นระเบียบ แต่แต่ละขั้นให้ คำศัพท์ กับขั้นถัดไป

อ่านเพิ่มจากต้นทาง

  1. Effective context engineering — ทำไมชื่อที่อ้างอิงได้ถึงมีค่ากว่าคำบรรยาย anthropic.com/engineering
  2. Claude Code best practices — การให้บริบทงาน FE แบบที่ agent ใช้ต่อได้ anthropic.com/engineering
06.02

Design system ในฐานะบริบท

ส่งภาพอย่างเดียวแล้วบอกว่า "ทำตามนี้" คือการบังคับให้ agent เดาค่าจากพิกเซล ผลที่ได้คือค่าที่ใกล้เคียงแต่ไม่ตรง แล้วกระจายไปทั่วจนเก็บกวาดยาก

Figure 2 · ค่าดิบที่กระจายอยู่ตรวจไม่ได้ด้วย grep — ส่วนชื่อ token ตรวจได้

ทำให้เป็นเกณฑ์เชิงกลได้ทันที

พอทุกอย่างมีชื่อ คุณเขียนเกณฑ์ตรวจได้เลยโดยไม่ต้องใช้คน — grep หาค่าสีดิบในไฟล์ component แล้วต้องได้ศูนย์

อันนี้คือตัวอย่างที่ดีของเกณฑ์ deterministic ตาม M12.03 และเป็นเหตุผลที่แล็บ A ของโมดูลนี้เอาไปใส่ชุดวัดได้ทันที

อ่านเพิ่มจากต้นทาง

  1. WCAG 2.2 Quick Reference — เกณฑ์คอนทราสต์ที่ token ของคุณต้องผ่าน ทั้งธีมสว่างและมืด w3.org/WAI
  2. Writing tools for agents — หลักการเดียวกัน: ชื่อที่ชัดทำให้เลือกถูก anthropic.com/engineering
06.03

เส้นแบ่ง server/client ที่พลาดบ่อยที่สุด

เฟรมเวิร์กสมัยใหม่แยกโค้ดที่รันบนเซิร์ฟเวอร์กับบนเบราว์เซอร์ และเส้นนี้คือจุดที่ agent พลาดมากที่สุดในงาน FE ทั้งหมด

ที่แย่คือ มันมักพลาดแบบที่ "แก้แล้วผ่าน" ทันที — ซึ่งเป็นทางแก้ที่ผิด

Figure 3 · ข้อที่ build พังคือข้อที่โชคดี · ข้อที่เงียบคือข้อที่ต้องระวัง

วิธีกันที่ได้ผลกว่าการเขียนกฎยาว ๆ

ใส่ไว้ใน project memory สั้น ๆ ว่า "ถ้าจะเปลี่ยน component จาก server เป็น client ให้หยุดแล้วอธิบายเหตุผลก่อน"

เพราะการเปลี่ยนนี้มักเป็นการหลบปัญหา ไม่ใช่การแก้ปัญหา และเป็นจุดที่คนควรตัดสิน ไม่ใช่ปล่อยให้ agent เลือกทางที่ทำให้ build ผ่านเร็วที่สุด

อ่านเพิ่มจากต้นทาง

  1. Server and Client Components — เส้นแบ่งจริง ๆ อยู่ตรงไหน และอะไรข้ามได้ข้ามไม่ได้ nextjs.org
  2. Memory — ที่สำหรับเขียนกฎ "หยุดถามก่อน" ให้ agent เห็นทุกครั้ง docs.claude.com
06.04

State และ data fetching

สองเรื่องนี้อยู่ด้วยกันเพราะความผิดพลาดส่วนใหญ่เกิดที่รอยต่อของมัน — ข้อมูลถูกดึงผิดที่ แล้ว state ก็เลยอยู่ผิดที่ตามไปด้วย

Figure 4 · agent มักเขียนแบบบน เพราะอ่านง่ายกว่า — และไม่มีอะไรแดงให้รู้ว่าช้า

แพตเทิร์นagent ทำถูกagent ชอบทำผิด
ดึงข้อมูลใกล้จุดที่ใช้ใช่ ถ้าบอกโครงไว้ชัดยกไปไว้ชั้นบนสุดแล้วส่งผ่านหลายชั้น
แยก server state กับ UI stateทำได้เมื่อมีตัวอย่างใน repoยัดทุกอย่างลง state ก้อนเดียว
จัดการ loading / errorเขียนครบถ้าอยู่ใน specทำแต่ happy path ถ้าไม่ได้สั่ง
ทำข้อมูลสดหลังแก้ไขทำได้รีเฟรชทั้งหน้าแทนอัปเดตเฉพาะจุด
อาการที่ไม่มี error แต่ช้าลงเรื่อย ๆ

พอ agent วางการดึงข้อมูลเป็นลำดับที่ต้องรอกันไปเรื่อย ๆ หน้าจะทำงานถูกทุกอย่าง แต่ช้าขึ้นทุกครั้งที่เพิ่มของ ไม่มีอะไรแดง ไม่มีเทสต์แตก และไม่มีใครสังเกตจนกว่าจะมีคนบ่น

ทางกันคือใส่เพดานเวลาโหลดเป็นเกณฑ์ในเทสต์ ตามหลักเดียวกับ budget ใน M03.07 — ถ้าไม่มีตัวเลขกำกับ ความช้าจะสะสมโดยไม่มีใครรับผิดชอบ

สิ่งที่ควรใส่ใน project memory

ระบุให้ชัดว่าโปรเจกต์นี้ใช้อะไรจัดการ server state และห้ามเพิ่มตัวใหม่โดยไม่ถาม

ไม่งั้น agent จะเลือกวิธีที่มันคุ้นเคยที่สุด ซึ่งอาจเป็นคนละตัวกับที่ทีมใช้อยู่ แล้วคุณจะได้สองระบบในโปรเจกต์เดียว โดยที่แต่ละอันก็ทำงานได้ถูกต้องของมัน

อ่านเพิ่มจากต้นทาง

  1. Server and Client Components — ที่ทางของการดึงข้อมูลในแต่ละฝั่ง nextjs.org
  2. Largest Contentful Paint — ตัวเลขที่เอาไปตั้งเป็นเพดานในเทสต์ได้ web.dev
06.05

Visual verification loop

อันนี้คือสิ่งที่เปลี่ยนงาน FE กับ agent จาก "ส่งไปแล้วลุ้น" เป็นลูปปิดที่มันตรวจงานตัวเองได้ก่อนถึงมือเรา

หัวใจไม่ได้อยู่ที่การถ่ายภาพนะครับ — อยู่ที่มันมี spec ให้เทียบ ถ้าไม่มีเกณฑ์ การให้มันดูภาพตัวเองก็แค่ทำให้มันมั่นใจขึ้น ไม่ได้ทำให้ถูกขึ้น

Figure 5 · การอ่าน console จับบั๊กได้มากกว่าการดูภาพ — แต่คนมักสั่งแค่ให้ถ่ายภาพ

จุดที่ลูปนี้ล้มเสมอถ้าไม่ระวัง

agent จะรายงานว่า "ผ่านหมดครับ" ทั้งที่ยังไม่ผ่าน ไม่ใช่เพราะโกหก แต่เพราะมันสรุปจากภาพที่ดูโอเค

วิธีกันคือบังคับให้แนบหลักฐานต่อข้อ — ภาพไหน บรรทัด console ไหน ตามวินัยหลักฐานใน M04.05 ข้อไหนไม่มีหลักฐานถือว่ายังไม่ได้ตรวจ

อ่านเพิ่มจากต้นทาง

  1. Playwright — Best Practices — การขับเบราว์เซอร์แบบที่ผลไม่แกว่ง ใช้เป็นฐานของลูปนี้ playwright.dev
  2. Claude Code best practices — การให้ agent ตรวจงานตัวเองก่อนส่งกลับ anthropic.com/engineering
06.06

Accessibility เป็นเกณฑ์ที่ตรวจอัตโนมัติได้

ข้อดีของการวางเรื่องนี้เป็น acceptance criteria คือมันเป็นหนึ่งในไม่กี่เรื่องคุณภาพ UI ที่เครื่องตัดสินได้จริง — เลยเอาไปใส่ชุดวัดได้ตรง ๆ

แล้วมันยังเป็นข้อที่ agent ทำได้ดีถ้าสั่ง และลืมสนิทถ้าไม่สั่ง

Figure 6 · สี่ข้อนี้ตรวจด้วยเครื่องมืออัตโนมัติได้ทั้งหมด · ใส่ CI แล้วมันกลายเป็นสิ่งที่ agent ต้องทำให้ผ่าน

อ่านเพิ่มจากต้นทาง

  1. WCAG 2.2 Quick Reference — เกณฑ์ทางการ พร้อมระดับ A / AA / AAA w3.org/WAI
  2. Playwright — Best Practices — การเลือก element ด้วย role และข้อความที่ผู้ใช้เห็น ซึ่งช่วยทั้งเทสต์และ a11y พร้อมกัน playwright.dev
06.07

UI ที่ผ่านสายตาแต่พังจริง

Figure 7 · สองในห้าข้อแก้ได้ด้วยการเตรียม fixture ให้เหมือนของจริงมากขึ้น ไม่ต้องเขียนกฎเพิ่มเลย

รูปแบบที่เจอซ้ำ

สาเหตุร่วมของหลายข้อคือ ข้อมูลทดสอบสวยเกินจริง — ชื่อสั้น รูปมีครบ ไม่มีเคสว่าง

การเตรียม fixture ที่มีเคสว่าง เคสข้อความยาว และเคสพัง ให้ผลมากกว่าการเขียนกฎเพิ่มใน prompt เพราะมันเปลี่ยนสิ่งที่ agent เห็น ไม่ใช่แค่สิ่งที่เราขอ

อ่านเพิ่มจากต้นทาง

  1. Cumulative Layout Shift — ตัววัด layout shift ที่เอาไปตั้งเป็นเกณฑ์ได้ web.dev
  2. Playwright — Best Practices — การเตรียมข้อมูลทดสอบใหม่ทุกรอบ ไม่ให้ state ค้างข้ามเทสต์ playwright.dev
06.08 · แล็บ A

สร้าง component library จาก design token

  1. กำหนด token ให้ครบก่อน — สี ระยะ ตัวอักษร มุม เงา พร้อมชื่อที่ใช้อ้างอิงได้
  2. ให้ agent สร้าง 5 component จาก token โดยห้ามใช้ค่าดิบ
  3. ตรวจด้วยเกณฑ์เชิงกล — grep หาค่าสีดิบในไฟล์ component ต้องได้ศูนย์
  4. ทุก component ต้องผ่านการตรวจ accessibility อัตโนมัติ
เกณฑ์ผ่าน

เกณฑ์ “ไม่มีค่าดิบ” ตรวจด้วย grep ได้ ทำให้แล็บนี้เอาไปใส่ชุดวัดของ M12 ได้ทันทีโดยไม่ต้องใช้คนตัดสิน

06.09 · แล็บ B

สร้าง flow สามหน้าพร้อมรอบ visual verification

  1. เขียน spec ของ flow ให้ทุกข้อตรวจได้ (ใช้วิธีจาก M04.01)
  2. ให้ agent สร้างครบสามหน้าพร้อมสถานะ loading, empty, error
  3. บังคับให้มันเปิดเบราว์เซอร์ตรวจเอง ทั้งจอกว้างและจอแคบ
  4. ให้มันรายงานว่า spec ข้อไหนยังไม่ผ่าน ก่อนที่คุณจะดู
จุดที่แล็บนี้มักล้ม

agent จะรายงานว่า “ผ่านหมด” ทั้งที่ยังไม่ผ่าน วิธีกันคือให้มันแปะภาพและบรรทัด console มาเป็นหลักฐานต่อข้อ ตามวินัยหลักฐานใน M04.05 ไม่ใช่ให้สรุปลอย ๆ
