ใจความของทั้งโมดูล

เมื่อคนเขียนโค้ดแล้วเขียนเทสต์ เทสต์สะท้อนความเข้าใจของคนคนนั้น เมื่อ agent เขียนทั้งคู่ เทสต์สะท้อนสิ่งที่โค้ดทำ ไม่ใช่สิ่งที่โค้ดควรทำ ความต่างนี้คือทั้งโมดูล

ที่มา

TDD ถูกคิดมาเพื่อคนที่ไม่มีวินัย — ซึ่งตรงกับ agent พอดี

เรื่องตลกร้ายของโมดูลนี้คือ วิธีแก้ปัญหาเทสต์ที่ agent เขียน ถูกคิดไว้ตั้งแต่ก่อนมี LLM 20 ปี

และเหตุผลที่มันได้ผลกับ agent ก็เป็นเหตุผลเดียวกับที่มันได้ผลกับคนเป๊ะ ๆ

Figure 0 · agent ไม่ได้สร้างปัญหาใหม่ มันแค่ทำให้ปัญหาเดิมเกิดเร็วขึ้นจนวินัยของคนตามไม่ทัน

1978ความคิดที่ว่าเทสต์เองก็ต้องถูกทดสอบ

Mutation testing เสนอโดย DeMillo, Lipton และ Sayward ในปี 1978 บนคำถามที่ตรงมาก — เรารู้ได้ยังไงว่าชุดเทสต์ทำงานจริง คำตอบของพวกเขาคือ จงใจแก้โค้ดให้ผิดทีละจุด แล้วนับว่าเทสต์จับได้กี่จุด ถ้าแก้ให้ผิดแล้วเทสต์ยังเขียว แปลว่าเทสต์นั้นไม่ได้ตรวจอะไรเลย

เกือบ 50 ปีต่อมา นี่ยังเป็นคำตอบที่ดีที่สุดสำหรับคำถามใน 11.02 ว่า coverage 100% แปลว่าอะไรกันแน่

1999–2002TDD และสมมติฐานที่มันตั้งอยู่

Kent Beck ทำให้ test-driven development เป็นที่รู้จักผ่าน Extreme Programming และหนังสือ Test-Driven Development: By Example (2002) วงจร red → green → refactor บังคับให้เกณฑ์ความสำเร็จถูกเขียนก่อนที่จะรู้ว่าคำตอบหน้าตายังไง

สมมติฐานของ TDD คือ คนขี้เกียจและมีอคติเข้าข้างงานตัวเอง — พอเขียนโค้ดเสร็จแล้ว เทสต์ที่เขียนตามหลังจะสะท้อนสิ่งที่โค้ดทำ ไม่ใช่สิ่งที่โค้ดควรทำ

ซึ่งเป็นคำอธิบายที่แม่นยำมากสำหรับ agent — มันไม่ได้ขี้เกียจ แต่มันเห็นโค้ดที่เพิ่งเขียนอยู่ใน context แล้วเขียนเทสต์ที่ยืนยันสิ่งนั้น ผลออกมาเหมือนกันเป๊ะ

  2. Mutation testing — งานปี 1978 ของ DeMillo, Lipton, Sayward และพัฒนาการหลังจากนั้น wikipedia.org
  3. Test-driven development — ไทม์ไลน์ การรับมาใช้ และข้อวิจารณ์ที่มีต่อมัน wikipedia.org

11.08 · แล็บประจำโมดูล

วัด precision และ recall ของ review agent กับบั๊กที่ปลูกไว้

เป้าหมายคือได้ตัวเลขจริงว่าเครื่องมือรีวิวของคุณจับได้กี่เปอร์เซ็นต์ และเตือนผิดบ่อยแค่ไหน แทนความรู้สึกว่า “ก็ดูช่วยได้นะ”

ขั้นตอน

  1. ปลูกบั๊ก 20 ตัว ใน repo จริง — คละแบบ: เคสขอบ, off-by-one, ผลข้างเคียง, race, จัดการ error หาย
  2. บันทึกไว้ว่าบั๊กแต่ละตัวอยู่ไฟล์ไหนบรรทัดไหน นี่คือเฉลย
  3. รัน review agent สามรอบ
  4. คำนวณ recall (จับได้กี่ตัวจาก 20) และ precision (ที่รายงานมา ถูกจริงกี่เปอร์เซ็นต์)
  5. เพิ่มสเตจ verification แล้ววัดซ้ำ
เกณฑ์ผ่าน
  • มีตัวเลข precision กับ recall จริง ไม่ใช่ความรู้สึก
  • บอกได้ว่าบั๊กประเภทไหนที่มันจับไม่ได้เลย — ข้อนี้มีค่ากว่าตัวเลขรวม
  • วัดผลของสเตจ verification ได้ว่าเปลี่ยน precision ไปเท่าไร และแลกกับ recall เท่าไร
ผลที่มักเจอ

recall มักดีกว่าที่คาด แต่ precision แย่กว่าที่คาดมาก และปัญหาจริงคือ precision เพราะ finding ปลอมกินเวลาคนและกัดกร่อนความเชื่อถือจนไม่มีใครใช้เครื่องมือนี้ต่อ
