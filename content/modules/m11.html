AI Coding Agent SDLC · Phase 04 · Module 11

Testing และ QA

agent เขียนเทสต์ได้เร็วมาก ซึ่งเป็นทั้งข้อดีและปัญหา เพราะเทสต์ที่ผ่านไม่ได้แปลว่าโค้ดถูก โมดูลนี้ว่าด้วยการได้เทสต์ที่จับบั๊กจริง ไม่ใช่เทสต์ที่ยืนยันว่าบั๊กยังอยู่

8 บทเรียน2.5 ชั่วโมง1 แล็บต้องผ่าน M04 · M05 ก่อน
ใจความของทั้งโมดูล

เมื่อคนเขียนโค้ดแล้วเขียนเทสต์ เทสต์สะท้อนความเข้าใจของคนคนนั้น เมื่อ agent เขียนทั้งคู่ เทสต์สะท้อนสิ่งที่โค้ดทำ ไม่ใช่สิ่งที่โค้ดควรทำ ความต่างนี้คือทั้งโมดูล

11.01

กับดักของเทสต์ที่ agent เขียน

รูปแบบอาการทำไมอันตราย
ล็อกพฤติกรรมผิดไว้รันโค้ด ดูผล เขียนเทสต์ยืนยันผลนั้นเทสต์เขียวตลอด บั๊กอยู่ถาวรและถูกปกป้อง
mock จนไม่เหลืออะไรทุก dependency ถูกแทนทดสอบว่า mock ทำงาน ไม่ได้ทดสอบโค้ด
ยืนยันสิ่งที่ไม่มีความหมายเช็คว่าฟังก์ชันถูกเรียกรีแฟกเตอร์แล้วแดงทั้งที่พฤติกรรมเหมือนเดิม
ทดสอบแต่ทางที่สำเร็จไม่มีเคสว่าง เคสพัง เคสขอบบั๊กจริงเกือบทั้งหมดอยู่ในทางที่ไม่ได้ทดสอบ
รูปแบบแรกคืออันตรายที่สุด

มันสร้างเทสต์ที่ปกป้องบั๊ก ครั้งหน้าที่มีคนแก้บั๊กนั้นถูกต้อง เทสต์จะแดง แล้วคนจะคิดว่าตัวเองแก้ผิด แล้วย้อนกลับ นี่คือวิธีที่บั๊กกลายเป็นสเปคโดยไม่มีใครตั้งใจ

11.02

Coverage โกหกอย่างไร

ตัวเลขความครอบคลุมวัดว่าโค้ดถูกรันระหว่างเทสต์ ไม่ได้วัดว่าถูกตรวจสอบ ความต่างนี้ใหญ่ขึ้นมากเมื่อ agent เป็นคนเขียน เพราะมันไล่ทำให้ตัวเลขสวยได้เร็วกว่าคน

// coverage 100% แต่ไม่ได้ตรวจอะไรเลย
test("คำนวณยอดรวม", () => {
  const r = calculateTotal(items);
  expect(r).toBeDefined();          // ผ่านแม้ผลจะผิดทุกกรณี
});
ตัววัดที่ดีกว่า

Mutation testing — แก้โค้ดให้ผิดโดยตั้งใจ แล้วดูว่าเทสต์จับได้กี่จุด ตัวเลขนี้โกหกยากกว่ามาก ถ้าแก้โค้ดให้ผิดแล้วเทสต์ยังเขียว แปลว่าเทสต์ชุดนั้นไม่ได้ทำงาน ไม่ว่า coverage จะเท่าไร

11.03

เทสต์ในฐานะ spec

ทางแก้ที่ตรงที่สุดสำหรับปัญหาทั้งหมดในบท 11.01 คือสลับลำดับ — เขียนเทสต์ก่อน แล้วให้ agent ทำให้ผ่าน

โค้ดก่อนเทสต์เทสต์ก่อนโค้ด
เทสต์สะท้อนอะไรสิ่งที่โค้ดทำสิ่งที่ควรทำ
บั๊กที่ถูกล็อกไว้เกิดบ่อยเกิดไม่ได้
เกณฑ์เสร็จกำกวมชัดเจน — เทสต์เขียว
เอาไปใช้ในชุดวัดได้ไหมไม่ได้ได้ทันที
ผลพลอยได้ที่มีค่าที่สุด

เทสต์ที่เขียนก่อนคือ เกณฑ์ red→green ของ M12.03 พอดี ทุกงานที่คุณทำแบบนี้ กลายเป็นงานในชุดวัดได้ฟรีโดยไม่ต้องทำงานเพิ่ม

11.04

Property-based และ fuzz

พื้นที่ที่ agent ได้เปรียบคนชัดเจนที่สุด เพราะการคิดคุณสมบัติที่ต้องจริงเสมอ และการสร้างอินพุตแปลก ๆ จำนวนมาก เป็นงานที่มันทำได้ดีและคนขี้เกียจทำ

// แทนที่จะเขียนเคสทีละอัน ให้ระบุคุณสมบัติที่ต้องจริงเสมอ
สำหรับตะกร้าใด ๆ:
  ยอดรวม >= 0
  ลบสินค้าแล้วเพิ่มกลับ → ยอดรวมเท่าเดิม
  ลำดับการเพิ่มสินค้าไม่มีผลต่อยอดรวม
  ส่วนลดไม่ทำให้ยอดติดลบ
วิธีสั่งที่ได้ผล

อย่าสั่งว่า “เขียนเทสต์เพิ่ม” ให้สั่งว่า “บอกคุณสมบัติที่ต้องจริงเสมอสำหรับฟังก์ชันนี้มา 10 ข้อ แล้วเขียนเทสต์ที่ตรวจแต่ละข้อ” คำสั่งแบบหลังได้เทสต์ที่จับบั๊กจริง คำสั่งแบบแรกได้เทสต์ที่เพิ่มตัวเลข coverage

11.05

E2E ที่ไม่ flaky

เทสต์ E2E ที่แดงบ้างเขียวบ้างแย่กว่าไม่มีเทสต์ เพราะมันสอนให้ทุกคนเพิกเฉยต่อสีแดง แล้ววันที่แดงจริงก็ไม่มีใครสนใจ

สาเหตุความไม่แน่นอนวิธีแก้ที่ถูกวิธีแก้ที่ผิดแต่คนชอบทำ
รอเวลาแทนรอสภาวะรอจนกว่าองค์ประกอบจะพร้อมเพิ่มเวลา sleep
ข้อมูลค้างจากรอบก่อนเตรียมข้อมูลใหม่ทุกรอบสั่งให้รันเรียงลำดับ
พึ่งบริการภายนอกจริงบันทึกไว้แล้วเล่นซ้ำลองใหม่สามครั้ง
อิงตำแหน่งหรือคลาส CSSอิงบทบาทและข้อความที่ผู้ใช้เห็นอัปเดตตัวเลือกทุกครั้งที่ UI ขยับ
รูปแบบร่วมของคอลัมน์ขวา

ทุกวิธีแก้ที่ผิดคือการซ่อนอาการแทนที่จะแก้เหตุ และ agent จะเสนอวิธีเหล่านี้เป็นอันดับแรกเสมอเพราะมันทำให้เทสต์เขียวได้เร็วที่สุด คุณต้องบอกไว้ล่วงหน้าว่าห้ามใช้

11.06

ออกแบบ review agent ให้หาบั๊กจริง

review agent ที่สั่งลอย ๆ ว่า “ช่วยรีวิวโค้ดนี้” จะคืนรายการเรื่องสไตล์ยาวเหยียดที่ไม่มีใครอ่าน ต้องออกแบบให้มันหาสิ่งที่คนพลาด

ควรให้หาไม่ควรให้หา
เงื่อนไขที่ทำให้พังจริง พร้อมอินพุตตัวอย่างชื่อตัวแปร การจัดรูปแบบ
เคสขอบที่ไม่ได้จัดการสิ่งที่ linter จับได้อยู่แล้ว
สมมติฐานที่ไม่ได้เขียนไว้ความชอบส่วนตัวเรื่องโครงสร้าง
ผลข้างเคียงที่มองไม่เห็น“น่าจะเพิ่มคอมเมนต์”
ข้อบังคับที่เปลี่ยนคุณภาพมากที่สุด

บังคับว่าทุก finding ต้องมี สถานการณ์ที่ทำให้พังจริง — อินพุตอะไร แล้วได้ผลผิดยังไง ข้อบังคับข้อเดียวนี้ตัด finding ประเภทเดาไปได้เกือบหมด เพราะถ้าเขียนสถานการณ์ไม่ได้ แปลว่ายังไม่รู้ว่ามันพังจริงไหม

11.07

Verification pass

ก่อนรายงาน finding ให้คน ต้องมีขั้นยืนยันเสมอ เหตุผลเป็นเรื่องเศรษฐศาสตร์ของความสนใจ — รายงานผิดสามครั้ง แล้วคนจะเลิกอ่านรายงานที่สี่ แม้ครั้งที่สี่จะถูก

  1. สเตจแรกหา finding ให้กว้างไว้ก่อน
  2. สเตจสองรับ finding ทีละข้อ โดยไม่เห็นเหตุผลของสเตจแรก
  3. สเตจสองพยายามยืนยันจากโค้ดจริง แล้วตัดสินว่ายืนยันได้หรือเป็นการเตือนผิด
  4. รายงานเฉพาะที่ยืนยันได้ พร้อมหลักฐาน

ข้อ 2 คือหัวใจ ถ้าสเตจสองเห็นเหตุผลของสเตจแรก มันจะเห็นด้วยตาม — เหตุผลเดียวกับกฎความเป็นอิสระใน M10.05

11.08 · แล็บประจำโมดูล

วัด precision และ recall ของ review agent กับบั๊กที่ปลูกไว้

เป้าหมายคือได้ตัวเลขจริงว่าเครื่องมือรีวิวของคุณจับได้กี่เปอร์เซ็นต์ และเตือนผิดบ่อยแค่ไหน แทนความรู้สึกว่า “ก็ดูช่วยได้นะ”

ขั้นตอน

  1. ปลูกบั๊ก 20 ตัว ใน repo จริง — คละแบบ: เคสขอบ, off-by-one, ผลข้างเคียง, race, จัดการ error หาย
  2. บันทึกไว้ว่าบั๊กแต่ละตัวอยู่ไฟล์ไหนบรรทัดไหน นี่คือเฉลย
  3. รัน review agent สามรอบ
  4. คำนวณ recall (จับได้กี่ตัวจาก 20) และ precision (ที่รายงานมา ถูกจริงกี่เปอร์เซ็นต์)
  5. เพิ่มสเตจ verification แล้ววัดซ้ำ
เกณฑ์ผ่าน
  • มีตัวเลข precision กับ recall จริง ไม่ใช่ความรู้สึก
  • บอกได้ว่าบั๊กประเภทไหนที่มันจับไม่ได้เลย — ข้อนี้มีค่ากว่าตัวเลขรวม
  • วัดผลของสเตจ verification ได้ว่าเปลี่ยน precision ไปเท่าไร และแลกกับ recall เท่าไร
ผลที่มักเจอ

recall มักดีกว่าที่คาด แต่ precision แย่กว่าที่คาดมาก และปัญหาจริงคือ precision เพราะ finding ปลอมกินเวลาคนและกัดกร่อนความเชื่อถือจนไม่มีใครใช้เครื่องมือนี้ต่อ
