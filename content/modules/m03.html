AI Coding Agent SDLC · Phase 00 · Module 03

เศรษฐศาสตร์ของ Token และโมเดล

ต้นทุนไม่ใช่รายละเอียดปลีกย่อย มันคือสิ่งที่ตัดสินว่าเวิร์กโฟลว์ของคุณใช้ได้กับทีม 20 คน หรือแค่กับคุณคนเดียว โมดูลนี้ทำให้การตัดสินใจเรื่องโมเดลกลายเป็นเลขคณิต ไม่ใช่ความเชื่อ

8 บทเรียน2.5 ชั่วโมง1 แล็บต้องผ่าน M01 · M02 ก่อน
ใจความของทั้งโมดูล

คำถามที่ถูกไม่ใช่ “โมเดลไหนถูกกว่า” แต่คือ “ต้นทุนต่องานที่เสร็จเท่าไร” โมเดลที่ราคาต่อ token ถูกกว่าครึ่งหนึ่งแต่ต้องวนสามรอบ แพงกว่าเสมอ

03.01

บัญชี token สี่ช่อง

เกือบทุกคนที่เริ่มคิดเรื่องต้นทุนจะคิดว่ามีสองราคา — ค่าสิ่งที่ส่งเข้าไป กับค่าสิ่งที่ได้กลับมา ความเข้าใจนี้ไม่ผิดแต่ไม่ครบ และช่องที่หายไปคือช่องที่ประหยัดได้มากที่สุด

ช่องคืออะไรราคาเทียบ input ปกติ
Inputสิ่งที่ส่งเข้าไปแบบไม่ cacheฐาน 1×
Outputสิ่งที่โมเดลผลิต รวมส่วนที่ใช้คิดแพงกว่าหลายเท่า
Cache writeครั้งแรกที่เขียนบริบทลง cacheแพงกว่า input เล็กน้อย
Cache readอ่านซ้ำจาก cacheถูกกว่า input มาก

ทำไมสองช่องหลังถึงเปลี่ยนเกม

ย้อนกลับไปที่ M01.01 — บริบทถูกส่งซ้ำทุกรอบ ถ้าคุณคิดด้วยบัญชีสองช่อง งานที่วน 20 รอบกับบริบทตั้งต้น 50K จะคิดเป็น input 1 ล้าน token

แต่ถ้าบริบทตั้งต้นนั้นติด cache ได้ สิ่งที่เกิดขึ้นคือจ่ายราคาเขียนครั้งเดียว แล้วจ่ายราคาอ่านซึ่งถูกกว่ามากอีก 19 ครั้ง ผลต่างของบิลไม่ใช่หลักสิบเปอร์เซ็นต์ แต่เป็นหลายเท่า

และมันฟรี

สิ่งที่ทำให้คันโยกนี้พิเศษกว่าคันโยกอื่นในโมดูลนี้คือ มันไม่แลกอะไรเลย ไม่ได้ลดคุณภาพ ไม่ได้ลดความสามารถ ไม่ต้องเปลี่ยนโมเดล แค่จัดลำดับบริบทให้ส่วนที่นิ่งอยู่หน้า คันโยกอื่นทุกตัวมีของแลก คันโยกนี้ไม่มี จึงควรทำก่อนเสมอ

ช่อง output ที่คนประเมินต่ำ

output แพงกว่า input หลายเท่าต่อ token ซึ่งฟังดูไม่สำคัญเพราะ output มักสั้นกว่า input มาก แต่มีสองอย่างที่ทำให้มันโตกว่าที่คิด — ส่วนที่โมเดลใช้คิดก่อนตอบก็นับเป็น output และงานที่ให้เขียนไฟล์ยาว ๆ ก็คือ output ล้วน ๆ

ผลในทางปฏิบัติคือ งานสองงานที่บริบทเท่ากัน อาจมีบิลต่างกันมากถ้างานหนึ่งให้เขียนโค้ดเยอะ และการปรับ effort ลง (บท 03.06) กระทบช่องนี้โดยตรง

ตัวเลขแรกที่ควรไปดู

เกือบทุกเครื่องมือรายงานตัวเลขสี่ช่องนี้ต่อคำขอ ถ้าคุณยังไม่เคยเปิดดู ให้ไปดูตอนนี้ สิ่งที่คนมักพบคือ cache read เป็นศูนย์ ซึ่งแปลว่าจ่ายราคาเต็มทุกรอบมาตลอด โดยไม่รู้ตัว บทถัดไปว่าด้วยการแก้ข้อนี้

03.02

Prompt caching เชิงลึก

Cache ทำงานด้วยหลักการเดียวที่ต้องเข้าใจให้แม่น — prefix match ระบบเทียบว่าคำขอใหม่มีส่วนต้นตรงกับที่เคยเห็นแค่ไหน แล้วใช้ซ้ำได้ถึงจุดที่เริ่มต่างกัน หลังจุดนั้นคิดราคาเต็มทั้งหมด

คำว่า “ส่วนต้น” หมายถึงต้นจริง ๆ ตามลำดับไบต์ ไม่ใช่เชิงความหมาย ถ้าอักขระตัวที่ 3 ต่างกัน ทุกอย่างตั้งแต่ตัวที่ 3 เป็นต้นไปคือของใหม่หมด แม้เนื้อหาที่เหลือจะเหมือนเดิมทุกประการ

ลำดับที่บริบทถูกประกอบ

บริบทถูกต่อกันตามลำดับ tools → system → messages ซึ่งแปลว่า อะไรที่ไม่นิ่งในสามอย่างนี้ จะทำลาย cache ของทุกอย่างที่อยู่หลังมัน

ผลที่ตามมามีน้ำหนักมาก — ถ้ารายการเครื่องมือของคุณไม่นิ่ง (เช่น MCP server ตัวหนึ่งตอบช้าบ้าง จนบางรอบมีเครื่องมือไม่ครบ) คุณจะเสีย cache ของ system prompt และประวัติทั้งหมด ทั้งที่สองส่วนนั้นไม่ได้เปลี่ยนเลย 

// ผิด — timestamp อยู่ต้น system prompt ทำลาย cache ทั้งก้อนทุกรอบ
system: `เวลาปัจจุบัน ${new Date()}
คุณคือผู้ช่วยเขียนโค้ด...(อีก 4000 token)`

// ถูก — ของนิ่งอยู่หน้า ของเปลี่ยนอยู่ท้ายสุด
system: `คุณคือผู้ช่วยเขียนโค้ด...(อีก 4000 token)`   // ← cache ได้
messages: [{ role: "user", content: `เวลาปัจจุบัน ${new Date()}
${question}` }]
กฎเดียวที่ครอบคลุมทุกกรณี

เรียงจากนิ่งที่สุดไปเปลี่ยนบ่อยที่สุด — system prompt และกฎของทีมอยู่หน้า บริบทของงานอยู่กลาง คำถามและอะไรที่เปลี่ยนทุกครั้งอยู่ท้ายสุด

กฎข้อนี้ฟังดูเล็ก แต่มันตัดสินว่าคุณจ่ายราคาเต็มหรือราคาถูกในทุกรอบของทุกงานที่ทำต่อจากนี้

ข้อจำกัดที่ต้องรู้

  • มีขนาดขั้นต่ำ — บริบทที่สั้นเกินเกณฑ์จะไม่ถูก cache เลย ซึ่งเป็นพฤติกรรมปกติ ไม่ใช่บั๊ก
  • มีอายุ — ทิ้งไว้นานเกินแล้ว cache หลุด รอบถัดไปต้องเขียนใหม่
  • แยกตามโมเดล — เปลี่ยนโมเดลกลางทางคือเริ่ม cache ใหม่ทั้งหมด (ดูกับดักในบท 03.04)
03.03

ตัวทำลาย cache แบบเงียบ

สิ่งเหล่านี้ทำให้ cache ไม่ติดโดยไม่มี error ไม่มี warning บิลแค่แพงกว่าที่ควรเป็นสามเท่าเงียบ ๆ

  • เวลาหรือวันที่ใน system prompt — เปลี่ยนทุกคำขอ ทำลายทุกอย่างหลังมัน
  • JSON ที่ลำดับ key ไม่คงที่ — เนื้อหาเหมือนกันแต่ไบต์ต่าง cache ไม่ติด
  • รายการเครื่องมือที่ไม่นิ่ง — MCP server ที่ตอบช้าบ้างเร็วบ้างจนบางรอบมีเครื่องมือไม่ครบ
  • ID สุ่มหรือเลขรันต่อคำขอ ที่ถูกใส่ไว้ต้นบริบท
  • บริบทสั้นเกินขั้นต่ำ — ต่ำกว่าเกณฑ์แล้วระบบไม่ cache ให้ ซึ่งเป็นพฤติกรรมปกติ ไม่ใช่บั๊ก
วิธี audit ที่ใช้เวลาห้านาที

ยิงคำขอเดิมสองครั้งติดกัน แล้วดูตัวเลข cache read ในรอบที่สอง ถ้าเป็นศูนย์ แปลว่ามีตัวทำลายอยู่ ให้ไล่ตัดของที่ไม่นิ่งออกจากส่วนต้นทีละอย่างจนตัวเลขขึ้น ทำครั้งเดียวได้ผลถาวร

03.04

Model routing เชิงเศรษฐศาสตร์

โมเดลระดับบนสุดกับระดับกลางต่างกันหลายเท่าต่อ token คำถามคือเมื่อไหร่ส่วนต่างนั้นคุ้ม

ลักษณะงานควรใช้เหตุผล
วางแผน ตัดสินใจสถาปัตยกรรม รีวิวระดับบนผิดแล้วแพงกว่าค่า token มาก
แก้โค้ดตามแผนที่ชัดแล้วระดับกลางงานกำหนดแน่นอน ตรวจได้ด้วยเทสต์
ค้นหา อ่านสรุป งานกลไกระดับล่างปริมาณเยอะ ความยากต่ำ
งานที่ยังไม่รู้ว่ายากแค่ไหนระดับบนให้มันบอกเองว่ายากตรงไหน แล้วค่อยลด
กับดักของ cascade

การไล่จากโมเดลถูกไปแพงฟังดูประหยัด แต่ cache แยก namespace ตามโมเดล พอเปลี่ยนโมเดลกลางทาง cache ที่สะสมมาใช้ไม่ได้เลย ต้องจ่ายเขียนใหม่ทั้งก้อน ในงานที่บริบทใหญ่ cascade มักแพงกว่าการใช้โมเดลเดียวตลอด

03.05

ต้นทุนต่องานที่เสร็จ

ทุกการเปรียบเทียบต้นทุนที่ดูแค่ราคาต่อ token เป็นการเปรียบเทียบที่ผิดตั้งแต่ตั้งโจทย์ เพราะสิ่งที่คุณซื้อไม่ใช่ token คุณซื้องานที่เสร็จ และหน่วยทั้งสองไม่ได้แปรผันตรงกัน 

ต้นทุนจริงต่องาน = ค่า token ทั้งงาน
                 + (เวลาคนที่ต้องเข้าไปแก้ × ค่าแรง)
                 + (จำนวนครั้งที่ต้องสั่งใหม่ × ต้นทุนรอบใหม่)

ตัวอย่างที่กลับผลลัพธ์

สมมติเทียบสองโมเดลกับงานประเภทเดียวกัน 100 งาน

โมเดล A (ถูกกว่า)โมเดล B (แพงกว่า)
ค่า token ต่อครั้งที่ลอง$0.12$0.40
สำเร็จในรอบแรก55 งาน85 งาน
ต้องสั่งใหม่/แก้เอง45 งาน15 งาน
ค่า token รวม~$17~$46
เวลาคนที่ต้องเข้าไปแก้45 × 10 นาที = 7.5 ชม.15 × 10 นาที = 2.5 ชม.

ต่างกัน 29 ดอลลาร์ แลกกับเวลาคน 5 ชั่วโมง ซึ่งในเกือบทุกองค์กรคือการแลกที่คุ้มอย่างชัดเจน แต่ถ้าดูแค่บรรทัดแรกของตาราง คุณจะเลือกผิด

ตัวเลขเดียวที่ควรเก็บ ถ้าเก็บได้อย่างเดียว

ดอลลาร์ต่องานที่ผ่านเกณฑ์ — เอาค่าใช้จ่ายทั้งหมดหารด้วยจำนวนงานที่สำเร็จ ไม่ใช่จำนวนงานที่ลอง ตัวหารนี้คือจุดที่ทางเลือกซึ่งดูถูกกว่ามักแพ้

สังเกตว่าตัวเลขนี้ต้องมีนิยามของคำว่า “สำเร็จ” ที่ตรวจได้ ซึ่งเป็นเหตุผลที่โมดูลนี้ ต้องพึ่ง M12 ถ้าไม่มีเกณฑ์เชิงกล คุณจะคำนวณตัวหารไม่ได้เลย

ต้นทุนที่ไม่อยู่ในบิลแต่แพงที่สุด

พจน์ที่สองในสมการ — เวลาคน — มักใหญ่กว่าพจน์แรกหลายเท่า แต่ไม่มีใครเห็นเพราะมันไม่ได้ออกใบเสร็จ และมันโตแบบไม่เป็นเชิงเส้น เพราะการเข้าไปแก้งานที่ agent ทำค้างไว้ครึ่งทาง ใช้เวลามากกว่าการทำเองตั้งแต่ต้น ในหลายกรณี

03.06

Effort เป็นคันโยกก่อนเปลี่ยนโมเดล

ก่อนจะขยับโมเดล ให้ขยับ effort ก่อนเสมอ เพราะมันเปลี่ยนต้นทุนได้มากโดยไม่เสีย cache และไม่ต้องแก้โค้ด

  1. เริ่มที่ระดับกลางสำหรับงานประจำ แล้ววัด
  2. ขึ้นเฉพาะงานที่ตกบ่อย ไม่ใช่ขึ้นทั้งระบบ
  3. ลดสำหรับ sub-agent ที่ทำงานกลไก — นี่คือที่ที่ประหยัดได้เยอะโดยไม่กระทบผล
ลำดับคันโยกทั้งหมด เรียงจากคุ้มที่สุด
  1. ซ่อม cache ให้ติด — ฟรี ไม่เสียคุณภาพ
  2. ตัดบริบทที่ไม่ใช้ — ฟรี มักได้คุณภาพเพิ่ม (M02)
  3. ลด effort สำหรับงานง่าย — แลกเล็กน้อย
  4. ใช้ batch สำหรับงานที่ไม่รีบ — ถูกลงมาก แลกกับเวลา
  5. เปลี่ยนโมเดล — ทำท้ายสุด เพราะกระทบมากที่สุด
03.07

Task budget กับเพดานที่ agent รู้ตัว

มีสองวิธีคุมการใช้จ่าย และผลลัพธ์ต่างกันมาก

วิธีagent รู้ไหมผลเมื่อชนเพดาน
เพดานความยาวคำตอบไม่รู้ถูกตัดกลางประโยค งานเสียเปล่า
Task budgetรู้และเห็นว่าเหลือเท่าไรมันเร่งสรุปและปิดงานให้เรียบร้อย

ความต่างนี้สำคัญมากกับงานอัตโนมัติที่ไม่มีคนเฝ้า เพราะงานที่ถูกตัดกลางคันคือเงินที่จ่ายไปแล้วได้ศูนย์ ส่วนงานที่ปิดตัวเองอย่างเรียบร้อยยังได้ผลบางส่วนที่ใช้ต่อได้

03.08 · แล็บประจำโมดูล

ทำ cost profile หนึ่งสัปดาห์ แล้วหาสามคันโยก

เป้าหมายคือเปลี่ยนจาก “รู้สึกว่าแพง” เป็น “รู้ว่าเงินไปอยู่ตรงไหน” ซึ่งเกือบทุกครั้งผลจะไม่ตรงกับที่เดาไว้

ขั้นตอน

  1. เก็บข้อมูลทุกงานหนึ่งสัปดาห์ — ต้นทุน จำนวนรอบ token แยกสี่ช่อง และผลว่าสำเร็จหรือไม่
  2. จัดกลุ่มตามประเภทงาน แล้วหา ดอลลาร์ต่องานที่สำเร็จ ของแต่ละกลุ่ม
  3. หากลุ่มที่แพงที่สุด แล้วดูว่าเงินไปช่องไหน — output แพง? cache ไม่ติด? วนหลายรอบ?
  4. เลือกสามคันโยกตามลำดับในบท 03.06 ทำทีละอย่าง วัดผลทุกครั้ง
เกณฑ์ผ่าน
  • ตอบได้ว่างานประเภทไหนกินงบมากที่สุด และเพราะช่องไหน
  • ลดต้นทุนต่องานที่สำเร็จได้อย่างน้อย 25% โดยอัตราผ่านไม่ตก
