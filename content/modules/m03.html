เศรษฐศาสตร์ของ Token และโมเดล

ต้นทุนไม่ใช่รายละเอียดปลีกย่อย มันคือสิ่งที่ตัดสินว่าเวิร์กโฟลว์ของคุณใช้ได้กับทีม 20 คน หรือแค่กับคุณคนเดียว โมดูลนี้ทำให้การตัดสินใจเรื่องโมเดลกลายเป็นเลขคณิต ไม่ใช่ความเชื่อ

8 บทเรียน2.5 ชั่วโมง1 แล็บต้องผ่าน M01 · M02 ก่อน
ใจความของทั้งโมดูล

คำถามที่ถูกไม่ใช่ “โมเดลไหนถูกกว่า” แต่คือ “ต้นทุนต่องานที่เสร็จเท่าไร” โมเดลที่ราคาต่อ token ถูกกว่าครึ่งหนึ่งแต่ต้องวนสามรอบ แพงกว่าเสมอ

03.01

บัญชี token สี่ช่อง

คนส่วนใหญ่คิดว่ามีสองราคา — ค่าที่ส่งเข้าไป กับค่าที่ได้กลับมา ไม่ผิดครับ แต่ไม่ครบ และช่องที่หายไปคือช่องที่ประหยัดได้มากที่สุด

พอรู้ว่ามีสี่ช่อง วิธีมองบิลจะเปลี่ยนไปเลย

Figure 1 · สัดส่วนแท่งเป็นภาพคร่าว ๆ ไม่ใช่ตัวเลขจริง — ราคาจริงดูจากหน้า pricing เพราะเปลี่ยนตามรุ่น

ทำไมสองช่องหลังถึงเปลี่ยนเกม

ย้อนกลับไป M01.01 — context ถูกส่งซ้ำทุก round ถ้าคิดด้วยบัญชีสองช่อง งานที่วน 20 รอบด้วย context ตั้งต้น 50K ก็คือ input 1 ล้าน token

แต่ถ้า context ก้อนนั้นติด cache สิ่งที่เกิดขึ้นคือจ่ายราคาเขียนครั้งเดียว แล้วจ่ายราคาอ่านซึ่งถูกกว่ามากอีก 19 ครั้ง — ผลต่างของบิลไม่ใช่หลักสิบเปอร์เซ็นต์ แต่เป็นหลายเท่า

และมันฟรี

สิ่งที่ทำให้คันโยกนี้พิเศษกว่าตัวอื่นในโมดูลคือ มันไม่แลกอะไรเลย — ไม่ลดคุณภาพ ไม่ลดความสามารถ ไม่ต้องเปลี่ยน model แค่จัดลำดับ context ให้ของนิ่งอยู่หน้า

คันโยกอื่นทุกตัวมีของแลก ตัวนี้ไม่มี เพราะงั้นทำก่อนเสมอ

ช่อง output ที่คนประเมินต่ำ

output แพงกว่า input หลายเท่าต่อ token ซึ่งฟังดูไม่สำคัญเพราะ output มักสั้นกว่ามาก แต่มีสองอย่างที่ทำให้มันโตกว่าที่คิด — token ที่โมเดลใช้คิดก่อนตอบก็นับเป็น output และงานที่ให้เขียนไฟล์ยาว ๆ ก็คือ output ล้วน ๆ

ผลจริงคืองานสองงานที่ context เท่ากัน อาจมีบิลต่างกันมากถ้างานหนึ่งให้เขียนโค้ดเยอะ และการลด effort (บท 03.06) กระทบช่องนี้โดยตรง

ตัวเลขแรกที่ควรไปดูตอนนี้เลย

เกือบทุกเครื่องมือรายงานสี่ช่องนี้ต่อ request ถ้ายังไม่เคยเปิดดู ให้ไปดูเดี๋ยวนี้

สิ่งที่คนมักเจอคือ cache_read เป็นศูนย์ — แปลว่าจ่ายราคาเต็มทุกรอบมาตลอด โดยไม่รู้ตัว บทถัดไปว่าด้วยการแก้ข้อนี้

อ่านเพิ่มจากต้นทาง

  1. Pricing — ราคาจริงของทั้งสี่ช่องแยกตามรุ่น docs.claude.com
  2. Token counting — นับ token ก่อนยิงจริง เอาไว้ทำ cost profile ในแล็บท้ายบท docs.claude.com
03.02

Prompt caching เชิงลึก

Cache ทำงานด้วยหลักการเดียวที่ต้องเข้าใจให้แม่น — prefix match ระบบเทียบว่า request ใหม่มีส่วนต้นตรงกับที่เคยเห็นแค่ไหน แล้วใช้ซ้ำได้ถึงจุดที่เริ่มต่าง

คำว่า "ส่วนต้น" คือต้นจริง ๆ ตามลำดับ byte ไม่ใช่เชิงความหมาย — ถ้าตัวอักษรที่ 3 ต่าง ทุกอย่างตั้งแต่ตัวที่ 3 เป็นต้นไปคือของใหม่หมด แม้เนื้อหาที่เหลือจะเหมือนเดิมเป๊ะ

Figure 2 · สีส้ม = จ่ายราคาเต็ม · request 3 เปลี่ยนนิดเดียวตรงต้น แต่เสีย cache ของทั้งก้อน

ลำดับที่ context ถูกประกอบคือ tools → system → messages แปลว่าอะไรที่ไม่นิ่งในสามอย่างนี้ จะทำลาย cache ของทุกอย่างที่อยู่หลังมัน

ผลที่ตามมามีน้ำหนักมาก — ถ้ารายการ tool ของคุณไม่นิ่ง (เช่น MCP server ตัวหนึ่งตอบช้าบ้าง จนบางรอบมี tool ไม่ครบ) คุณจะเสีย cache ของ system prompt และ history ทั้งหมด ทั้งที่สองส่วนนั้นไม่ได้เปลี่ยนเลย 

// ผิด — timestamp อยู่ต้น system prompt ทำลาย cache ทั้งก้อนทุกรอบ
system: `เวลาปัจจุบัน ${new Date()}
คุณคือผู้ช่วยเขียนโค้ด...(อีก 4000 token)`

// ถูก — ของนิ่งอยู่หน้า ของเปลี่ยนอยู่ท้ายสุด
system: `คุณคือผู้ช่วยเขียนโค้ด...(อีก 4000 token)`   // ← cache ได้
messages: [{ role: "user", content: `เวลาปัจจุบัน ${new Date()}
${question}` }]
ข้อจำกัดที่ต้องรู้ ไม่งั้นงงว่าทำไมไม่ติด
  • มีขนาดขั้นต่ำ — context สั้นเกินเกณฑ์จะไม่ถูก cache เลย เป็นพฤติกรรมปกติ ไม่ใช่ bug
  • มีอายุ — ทิ้งไว้นานเกินแล้ว cache หลุด รอบถัดไปต้องเขียนใหม่
  • แยกตาม model — เปลี่ยน model กลางทางคือเริ่ม cache ใหม่ทั้งหมด (ดูกับดักในบท 03.04)
  • มีเพดานจำนวนจุด cache ต่อ request — วางไม่ได้ไม่จำกัด ต้องเลือกจุดที่คุ้ม

อ่านเพิ่มจากต้นทาง

  1. Prompt caching — prefix match · ลำดับ render · ขนาดขั้นต่ำ · อายุ cache · จำนวนจุดที่วางได้ docs.claude.com
  2. Claude Code best practices — การจัดโครง context ในงานจริงให้ส่วนนิ่งอยู่หน้า anthropic.com/engineering
03.03

ตัวทำลาย cache แบบเงียบ

หัวข้อนี้ผมอยากให้อ่านช้า ๆ หน่อย เพราะของพวกนี้ไม่ error ไม่ warning ไม่มีอะไรแดง บิลแค่แพงกว่าที่ควรเป็นสามเท่าเงียบ ๆ

Figure 3 · ตัวทำลายที่เจอบ่อย และวิธี audit ที่ใช้เวลาห้านาที

Engineering noteเคสที่ debug ยากที่สุดในลิสต์

tool list ไม่นิ่ง เป็นตัวที่หายากสุด เพราะโค้ดของคุณไม่ได้ผิดอะไรเลย ปัญหาอยู่ที่ MCP server ตัวหนึ่งบางครั้ง handshake ไม่ทัน แล้ว tool ของมันหายไปจากรายการรอบนั้น

ผลคือ cache หลุดเป็นบางรอบแบบสุ่ม — cache_read ไม่ได้เป็นศูนย์ตลอด แต่เป็นบ้างไม่เป็นบ้าง ซึ่งทำให้เข้าใจผิดว่า "ก็ติดอยู่นะ" ทั้งที่จ่ายเกินไปเยอะ

วิธีจับ

log ลำดับชื่อ tool ที่ส่งไปแต่ละ request แล้วเทียบ hash ข้ามรอบ ถ้า hash ไม่คงที่ทั้งที่ไม่ได้แก้อะไร — เจอตัวการแล้ว

ทางแก้คือเรียงชื่อ tool ให้คงที่ และถ้า server ตัวไหนไม่พร้อม ให้ตัดสินใจไปเลยว่าจะรอหรือจะไม่ใส่ — อย่าปล่อยให้ผลลัพธ์ขึ้นกับจังหวะ

JSON ที่ลำดับ key ไม่คงที่

อันนี้เจอบ่อยเวลาประกอบ context จาก object ในภาษาที่ไม่รับประกันลำดับ key หรือเวลา serialize จาก map เนื้อหาเหมือนกันทุกประการ แต่ byte ต่าง — cache ไม่ติด 

// ไม่ปลอดภัย — ลำดับ key อาจสลับ
JSON.stringify(config)

// ปลอดภัย — บังคับลำดับ
JSON.stringify(config, Object.keys(config).sort())

  1. Prompt caching — field ที่รายงาน cache read/write และวิธีอ่านค่าเพื่อ audit docs.claude.com
  2. Messages API reference — โครงสร้าง usage ที่มีตัวเลขทั้งสี่ช่อง docs.claude.com
03.04

Model routing เชิงเศรษฐศาสตร์

โมเดลระดับบนกับระดับกลางต่างกันหลายเท่าต่อ token คำถามคือเมื่อไหร่ส่วนต่างนั้นคุ้ม

คำตอบไม่ใช่ "ใช้ตัวถูกให้มากที่สุด" และไม่ใช่ "ใช้ตัวแพงไปเลยจบ" — มันขึ้นกับว่า ผิดแล้วแพงแค่ไหน ซึ่งต่างกันมากตามประเภทงาน

Figure 4 · แกนที่ตัดสินคือ "ผิดแล้วแพงแค่ไหน" ไม่ใช่ "งานยากแค่ไหน" — สองอย่างนี้ไม่เหมือนกัน

ลักษณะงานควรใช้เหตุผล
วางแผน · ตัดสินใจ architecture · reviewระดับบนผิดแล้วแพงกว่าค่า token มาก
แก้โค้ดตาม plan ที่ชัดแล้วระดับกลางงานกำหนดแน่นอน ตรวจได้ด้วย test
ค้นหา · อ่านสรุป · งานกลไกระดับล่างปริมาณเยอะ ความยากต่ำ
ยังไม่รู้ว่ายากแค่ไหนระดับบนให้มันบอกเองว่ายากตรงไหน แล้วค่อยลด
กับดักของ cascade

การไล่จากโมเดลถูกไปแพงฟังดูประหยัดมาก แต่ cache แยก namespace ตาม model พอเปลี่ยน model กลางทาง cache ที่สะสมมาใช้ไม่ได้เลย ต้องจ่ายเขียนใหม่ทั้งก้อน

ในงานที่ context ใหญ่ cascade มักแพงกว่าการใช้ model เดียวตลอด — และนี่คือเหตุผลที่ผมบอกใน M01.05 ว่าให้ปรับ effort ก่อนเปลี่ยน model เพราะ effort ยังอยู่ใน namespace เดิม

Sub-agent คือที่ที่ routing ได้ผลจริง

แทนที่จะ cascade กลางงาน ให้ใช้ model ต่างระดับกับ agent คนละตัว — ตัวหลักใช้ระดับบนเพื่อถือแผน ตัวลูกที่ไปอ่านไฟล์ 40 ไฟล์ใช้ระดับล่าง

แต่ละตัวมี context ของตัวเอง เลยมี cache namespace ของตัวเอง — ไม่ตีกัน ต่อกับ M10.02 เรื่อง orchestrator/worker โดยตรง

  2. Pricing — ส่วนต่างราคาจริงระหว่างรุ่น docs.claude.com
03.05

ต้นทุนต่องานที่เสร็จ

ทุกการเทียบต้นทุนที่ดูแค่ราคาต่อ token ผิดตั้งแต่ตั้งโจทย์ เพราะสิ่งที่เราซื้อไม่ใช่ token เราซื้องานที่เสร็จ และสองหน่วยนี้ไม่ได้แปรผันตรงกัน 

ต้นทุนจริงต่องาน = ค่า token ทั้งงาน
                 + (เวลาคนที่ต้องเข้าไปแก้ × ค่าแรง)
                 + (จำนวนครั้งที่ต้องสั่งใหม่ × ต้นทุนรอบใหม่)

Figure 5 · พจน์ที่สองในสมการมักใหญ่กว่าพจน์แรก แต่ไม่มีใครเห็นเพราะมันไม่ออกใบเสร็จ

ตัวเลขเดียวที่ควรเก็บ ถ้าเก็บได้อย่างเดียว

ดอลลาร์ต่องานที่ผ่านเกณฑ์ — เอาค่าใช้จ่ายทั้งหมดหารด้วยจำนวนงานที่สำเร็จ ไม่ใช่จำนวนงานที่ลอง ตัวหารนี้คือจุดที่ทางเลือกซึ่งดูถูกกว่ามักแพ้

สังเกตว่าตัวเลขนี้ต้องมีนิยามของ "สำเร็จ" ที่ตรวจได้ — เพราะงั้นโมดูลนี้ต้องพึ่ง M12 ถ้าไม่มีเกณฑ์เชิงกล คุณคำนวณตัวหารไม่ได้เลย

ต้นทุนที่โตแบบไม่เป็นเชิงเส้น

การเข้าไปแก้งานที่ agent ทำค้างไว้ครึ่งทาง ใช้เวลามากกว่าทำเองตั้งแต่ต้น ในหลายกรณี เพราะต้องอ่านสิ่งที่มันทำ เข้าใจว่ามันคิดอะไร แล้วค่อยตัดสินใจว่าจะแก้ต่อหรือทิ้ง

เพราะงั้นอัตราสำเร็จที่ต่างกัน 30% ไม่ได้แปลว่าเวลาคนต่างกัน 30% — มันต่างกันมากกว่านั้น

  2. Exploring Generative AI — บันทึกภาคสนามเรื่องเวลาที่หมดไปกับการตรวจและแก้งานของ AI martinfowler.com
03.06

Effort เป็นคันโยกก่อนเปลี่ยนโมเดล

ก่อนจะขยับ model ให้ขยับ effort ก่อน เพราะมันเปลี่ยนต้นทุนได้เยอะโดยไม่ต้องแก้โค้ด และยังอยู่ใน cache namespace เดิม — ต่างจากการเปลี่ยน model ที่ทำให้ cache ที่สะสมมาใช้ไม่ได้เลย

Figure 6 · สองข้อแรกฟรีจริง ๆ · ทำให้ครบก่อนค่อยไปข้อที่แลกอะไรบางอย่าง

ข้อควรรู้ที่คนมักเข้าใจผิด

effort ไม่ได้ "ฟรีต่อ cache" — ถ้าเปลี่ยนกลางบทสนทนา messages cache จะหลุด สิ่งที่มันดีกว่าการเปลี่ยน model คือไม่ได้ย้าย namespace ทั้งก้อน

เพราะงั้นถ้าจะปรับ ให้ปรับตั้งแต่ต้น session ไม่ใช่ปรับไปมาระหว่างทาง

  1. เริ่มที่ระดับกลางสำหรับงานประจำ แล้ววัด
  2. ขึ้นเฉพาะงานที่ตกบ่อย ไม่ใช่ขึ้นทั้งระบบ
  3. ลดสำหรับ sub-agentที่ทำงานกลไก — ประหยัดเยอะโดยไม่กระทบผล

อ่านเพิ่มจากต้นทาง

  1. Extended thinking — thinking token ถูกคิดเงินยังไง และ effort กระทบตรงไหน docs.claude.com
  2. Batch processing — คันโยกข้อ 4 · ส่งงานเป็นชุดสำหรับสิ่งที่ไม่ต้องการผลทันที docs.claude.com

ย้อนกลับไป M01.04 — เพดานความยาวที่ชนแล้วได้ max_tokens คือกรณีเดียวกับที่ทำให้ได้ไฟล์เขียนไม่จบ ส่วน task budget เป็นการบอกงบให้ agent รู้ตั้งแต่ต้น เพื่อให้มันบริหารเอง

ใช้คู่กัน ไม่ใช่เลือกอย่างเดียว

Task budget เอาไว้ให้มันบริหารตัวเอง · เพดานความยาว เอาไว้เป็นตาข่ายกันพัง ตั้งเพดานให้สูงพอที่จะไม่ชนในกรณีปกติ แล้วให้ budget เป็นตัวคุมจริง

ถ้าชนเพดานบ่อย แปลว่า budget ตั้งผิด ไม่ใช่ว่าเพดานต่ำไป

03.08 · แล็บประจำโมดูล

ทำ cost profile หนึ่งสัปดาห์ แล้วหาสามคันโยก

เป้าหมายคือเปลี่ยนจาก “รู้สึกว่าแพง” เป็น “รู้ว่าเงินไปอยู่ตรงไหน” ซึ่งเกือบทุกครั้งผลจะไม่ตรงกับที่เดาไว้

ขั้นตอน

  1. เก็บข้อมูลทุกงานหนึ่งสัปดาห์ — ต้นทุน จำนวนรอบ token แยกสี่ช่อง และผลว่าสำเร็จหรือไม่
  2. จัดกลุ่มตามประเภทงาน แล้วหา ดอลลาร์ต่องานที่สำเร็จ ของแต่ละกลุ่ม
  3. หากลุ่มที่แพงที่สุด แล้วดูว่าเงินไปช่องไหน — output แพง? cache ไม่ติด? วนหลายรอบ?
  4. เลือกสามคันโยกตามลำดับในบท 03.06 ทำทีละอย่าง วัดผลทุกครั้ง
เกณฑ์ผ่าน
  • ตอบได้ว่างานประเภทไหนกินงบมากที่สุด และเพราะช่องไหน
  • ลดต้นทุนต่องานที่สำเร็จได้อย่างน้อย 25% โดยอัตราผ่านไม่ตก
  • พิสูจน์ได้ว่าอัตราผ่านไม่ตกจริง ไม่ใช่แค่รู้สึก — ต้องใช้ชุดวัดจาก M12
ผลที่มักเจอ

ทีมส่วนใหญ่พบว่าค่าใช้จ่ายกระจุกอยู่ที่งานไม่กี่ประเภท และสาเหตุอันดับหนึ่งคือ cache ไม่ติดเพราะของไม่นิ่งอยู่ต้นบริบท ซึ่งแก้ครั้งเดียวจบและไม่แลกอะไรเลย
