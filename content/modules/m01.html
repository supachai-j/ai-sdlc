01.01

Agentic loop จริง ๆ คืออะไร

เอาแบบนี้นะ ถ้าเพื่อนถามผมว่า agent คืออะไร ผมจะตอบว่า — มันคือโปรแกรมที่ถามโมเดลว่า "จะทำอะไรต่อ" แล้วก็ทำตามนั้น วนไปเรื่อย ๆ จนโมเดลบอกว่าพอแล้ว

แค่นั้นจริง ๆ ครับ ไม่มีอะไรมากกว่านี้ ที่มันดูฉลาดจนน่าตกใจ ไม่ได้มาจากความซับซ้อนของโปรแกรม แต่มาจากการที่มันวนลูปนี้หลาย ๆ รอบ

ลูปนี้มีแค่สามขั้น ถาม → ทำ → บอกผล แล้ววนกลับไปถามใหม่

รูปที่ 1 · ลูปทั้งหมดของ agent เส้นสีส้มคือส่วนที่ทำให้มันดูฉลาด — มันได้ลองใหม่พร้อมข้อมูลที่เพิ่งได้มา

messages = [คำสั่งของคุณ]
while True:
    reply = model(messages, tools)      # ขั้น 1 — ถาม
    messages.append(reply)
    if reply.stop_reason != "tool_use":
        break                           # โมเดลไม่ขออะไรแล้ว จบ
    results = [run(call) for call in reply.tool_calls]   # ขั้น 2 — ทำ
    messages.append(results)            # ขั้น 3 — บอกผล

มาดูของจริงสั่งงานหนึ่งงาน เกิดอะไรขึ้นบ้าง

สมมติคุณพิมพ์ว่า “ฟังก์ชัน calculateTotal คำนวณผิดตอนตะกร้าว่าง ช่วยแก้ที” สิ่งที่เกิดขึ้นจริงหลังบ้านเป็นแบบนี้

รอบโมเดลขอโปรแกรมทำ
1ค้นคำว่า calculateTotalรัน grep ได้มา 3 บรรทัด
2ขอเปิดไฟล์ total.tsอ่านมา 120 บรรทัด
3ขอเปิดไฟล์เทสต์อ่านมาอีก 80 บรรทัด
4ขอแก้ไฟล์เขียนทับ สำเร็จ
5ขอรันเทสต์รัน ได้ผลมา 40 บรรทัด
6ไม่ขออะไรแล้ว บอกว่าแก้เสร็จออกจากลูป

จุดที่คนพลาดกันเยอะทุกรอบคุณส่งของเดิมไปใหม่ทั้งหมด

ตรงนี้แหละที่คนตกใจกันตอนรู้ — รอบที่ 6 ไม่ได้ส่งแค่ผลเทสต์นะครับ มันส่งทุกอย่างตั้งแต่รอบ 1 ไปใหม่หมด

คำสั่งของคุณ ผล grep ไฟล์ทั้งไฟล์ เทสต์ทั้งไฟล์ diff ที่แก้ ผลเทสต์ — ไปพร้อมกันอีกรอบ เพราะโมเดลไม่ได้จำอะไรได้เลย ต้องบอกใหม่ทุกครั้ง

รูปที่ 2 · แถบสีน้ำเงินคือของเดิมที่ถูกส่งซ้ำ สังเกตว่ามันโตขึ้นเรื่อย ๆ ส่วนของใหม่แต่ละรอบเล็กนิดเดียว

แปลว่าอะไรกับกระเป๋าเงินคุณ

ไฟล์ที่เปิดตอนรอบ 2 สมมติ 5,000 token คุณไม่ได้จ่ายครั้งเดียวนะ คุณจ่ายในรอบ 2, 3, 4, 5, 6 — ห้าครั้ง

งานที่วน 20 รอบก็คือจ่ายค่าไฟล์นั้นเกือบยี่สิบครั้ง นี่คือเหตุผลที่ M03 พูดเรื่อง cache เยอะมาก และทำไม M02 ถึงบอกว่าบริบทคืองบประมาณ ไม่ใช่ถังที่เทใส่ได้เรื่อย ๆ

เรื่องที่เข้าใจผิดกันบ่อย“มันจำได้ว่าเมื่อกี้ทำอะไร”

ไม่ได้จำครับ จำไม่ได้เลยสักนิด ที่มันดูเหมือนจำได้ เพราะโปรแกรมส่งประวัติทั้งหมดกลับเข้าไปให้ทุกครั้งต่างหาก

ฟังดูเป็นเรื่องเล็ก แต่มันเปลี่ยนวิธีคิดเยอะ — ถ้าข้อมูลไม่ได้อยู่ในกองที่ส่งไป มันไม่รู้ และถ้าเราตัดของเก่าทิ้ง มันลืมทันทีเหมือนไม่เคยเกิดขึ้น

พอเข้าใจข้อนี้ อาการอย่าง “คุยไปนาน ๆ แล้วมันเริ่มลืมสิ่งที่ตกลงกันไว้” จะเลิกดูลึกลับ กลายเป็นเรื่องที่เดาได้และแก้ได้

แล้วอะไรทำให้ agent ตัวหนึ่งเก่งกว่าอีกตัว

ในเมื่อลูปเหมือนกันหมด ความต่างมาจากสามอย่างรอบ ๆ ลูป และทั้งสามอย่างอยู่ในมือคุณ

  • เครื่องมือที่ให้ — ตัวที่รันเทสต์ได้ ตรวจงานตัวเองได้ ตัวที่รันไม่ได้ต้องเดาเอา
  • ข้อมูลที่ใส่ให้ — มันเห็นเท่าที่เราส่งไป ไม่มากไม่น้อยกว่านั้น
  • ขอบเขตที่วางไว้ — อะไรทำเองได้ อะไรต้องหยุดถาม

ทั้งหลักสูตรนี้คือการเล่นกับสามอย่างนี้ให้เป็นระบบ ไม่มีอย่างที่สี่จริง ๆ

ลองเองสัก 5 นาที

สั่งงานเล็ก ๆ กับ agent ที่คุณใช้อยู่ แล้วนับว่ามันเรียกเครื่องมือกี่ครั้งกว่าจะจบ เอาจำนวนรอบคูณขนาดบริบทคร่าว ๆ ดู ตัวเลขที่ได้มักทำให้คนอึ้ง และเป็นแรงจูงใจที่ดีที่สุดสำหรับ M02

  1. Tool use overview — เอกสารทางการว่าด้วยรูปแบบการขอใช้เครื่องมือและการส่งผลกลับ docs.claude.com
  2. Building effective agents — แยกให้เห็นว่า workflow กับ agent ต่างกันตรงไหน และเมื่อไหร่ควรใช้อะไร anthropic.com/engineering
01.02

กายวิภาคของ harness

ลูปในบทที่แล้วคือแก่น แต่ของที่คุณใช้จริงไม่ใช่ลูปเปล่า ๆ มันมีอีกห้าชั้นห่อไว้รอบนอก เราเรียกทั้งก้อนนี้ว่า harness

ที่ต้องรู้จักทั้งห้าชั้นไม่ใช่เพื่อความรู้รอบตัวนะครับ แต่เพราะ เวลามันทำอะไรแปลก ๆ คำถามที่ช่วยได้คือ "อาการนี้มาจากชั้นไหน" ไม่ใช่ "ทำไมโมเดลมันโง่จัง" — คำถามแรกพาไปเจอทางแก้ คำถามหลังพาไปเปลี่ยนโมเดลซึ่งมักไม่ใช่สาเหตุ

รูปที่ 3 · ลูปอยู่ตรงกลาง มีห้าชั้นห่อไว้ ชั้นสีส้มคือชั้นที่คนเจอปัญหาบ่อยที่สุด

ชั้นทำอะไรพังแล้วอาการเป็นยังไง
1 · System promptบอกบทบาทกับกฎทำผิด convention เดิม ๆ ทุกครั้งเหมือนกันหมด
2 · Tool registryรายการเครื่องมือหยิบเครื่องมือผิดตัวซ้ำ ๆ
3 · Context assemblerเลือกว่าจะส่งอะไรลืมของที่เพิ่งคุย วนทำงานเดิม
4 · Permissionอนุญาตหรือห้ามค้างรออนุมัติ หรือทำสิ่งที่ไม่ควรทำ
5 · Result rendererแปลงผลเป็นข้อความมั่นใจแต่ผิด

ชั้นที่ 3ชั้นที่คนบ่นถึงมากที่สุด

ชั้นนี้ตอบคำถามว่า “รอบนี้จะส่งอะไรเข้าไปบ้าง” ซึ่งฟังดูง่าย แต่พอคุยกันยาว ๆ จนใกล้เต็มที่ มันต้องเลือกว่าจะตัดอะไร สรุปอะไร เก็บอะไร

อาการคลาสสิกคือ “คุยไปสักพักมันเริ่มลืม” กับ “มันวนทำสิ่งที่ทำไปแล้ว” ทั้งคู่คือชั้นนี้ตัดของที่ยังต้องใช้ทิ้งไป M02 ทั้งโมดูลคือการจัดการชั้นนี้

ชั้นที่ 5ชั้นที่โดนโทษน้อยที่สุด แต่ผิดบ่อยที่สุด

ชั้นนี้ผมอยากเล่าให้ฟังหน่อย เพราะมันหลอกคนได้เก่งมาก

สมมติ agent สั่งรันเทสต์ แล้ว output ออกมา 3,000 บรรทัด เทสต์ที่แดงอยู่บรรทัดที่ 2,400 แต่ harness ตัดเหลือแค่ 200 บรรทัดแรกก่อนส่งเข้าโมเดล

โมเดลก็เลยเห็นแต่เทสต์ที่ผ่าน แล้วสรุปอย่างมั่นใจว่าเรียบร้อยดี คุณจะเห็นเป็น "มันตอบผิดแบบมั่นใจ" แล้วก็สรุปว่าโมเดลไม่เก่ง

แต่จริง ๆ โมเดลสรุปถูกแล้วนะ ถูกต้องตามข้อมูลที่มันได้รับ — ปัญหาอยู่ที่ท่อ ไม่ได้อยู่ที่คนอ่าน

เวลาเจอปัญหา ให้ไล่ตามนี้
  1. มันเห็นข้อมูลถูกไหม — ชั้น 3 กับ 5
  2. มันมีเครื่องมือที่เหมาะไหม — ชั้น 2
  3. มันโดนห้ามอะไรอยู่หรือเปล่า — ชั้น 4
  4. กฎที่เราให้ไปขัดกันเองไหม — ชั้น 1

สังเกตว่า “โมเดลไม่เก่งพอ” ไม่อยู่ในลิสต์ เพราะมันควรเป็นข้อสรุปสุดท้ายหลังตัดสี่ข้อบนทิ้งแล้ว และจากประสบการณ์ มันแทบไม่เคยเป็นคำตอบจริง ๆ

อ่านเพิ่มจากต้นทาง

  1. Effective context engineering for AI agents — ว่าด้วยชั้นที่ 3 โดยตรง ทั้งเรื่องเลือกอะไรเข้าบริบทและจัดการยังไงเมื่อยาวขึ้น anthropic.com/engineering
  2. Writing tools for agents — ว่าด้วยชั้นที่ 2 ออกแบบเครื่องมือและคำอธิบายยังไงให้ agent หยิบถูก anthropic.com/engineering
01.03

Tool-use protocol และกฎที่ห้ามผิด

ประโยคที่ว่า “agent เรียกใช้เครื่องมือ” ทำให้เข้าใจผิดนิดหนึ่ง เพราะโมเดลไม่ได้เรียกอะไรเลย มันทำได้อย่างเดียวคือผลิตข้อความออกมา สิ่งที่เกิดขึ้นจริงคือมันผลิตบล็อกข้อมูลที่มีโครงสร้าง ซึ่งบอกว่าอยากให้เรียกเครื่องมือชื่ออะไร ด้วย argument อะไร และแนบรหัสอ้างอิงมาด้วย แล้วโปรแกรมของคุณต่างหากที่เป็นคนรัน

ความต่างนี้สำคัญเพราะมันบอกว่าคุณคุมทุกอย่างที่เกิดขึ้นจริง โมเดลขอได้อย่างเดียว การรันหรือไม่รัน รันยังไง และรายงานผลกลับยังไง เป็นการตัดสินใจของโปรแกรมทั้งหมด 

// สิ่งที่โมเดลผลิตออกมา — แค่ข้อมูล ไม่ได้ทำอะไร
{ type: "tool_use", id: "call_a1", name: "read_file",
  input: { path: "src/billing/total.ts" } }

// สิ่งที่โปรแกรมส่งกลับเข้าไป — ต้องอ้าง id เดิม
{ type: "tool_result", tool_use_id: "call_a1",
  content: "export function calculateTotal(...) { ... }" }

กฎข้อที่ 1หนึ่งคำตอบมีหลายคำขอได้

เมื่อโมเดลเห็นว่างานหลายอย่างไม่ขึ้นต่อกัน มันจะขอพร้อมกันในคำตอบเดียว เช่นอ่านสามไฟล์รวดเดียว แทนที่จะอ่านทีละไฟล์แล้วรอผล พฤติกรรมนี้มีประโยชน์มากเพราะลดจำนวนรอบ ซึ่งลดทั้งเวลาและเงิน (ย้อนกลับไปดูตารางในบท 01.01 — จำนวนรอบคูณกับขนาดบริบทคือบิลของคุณ)

กฎข้อที่ 2ต้องส่งผลกลับครบทุกตัวใน message เดียว

นี่คือกฎที่ผิดแล้วไม่มีใครสังเกต และเป็นข้อที่ผมอยากให้จำที่สุดในบทนี้ ถ้าโมเดลขอสามอย่างพร้อมกัน คุณต้องรวมผลทั้งสามไว้ใน message เดียวแล้วส่งกลับ ไม่ใช่ส่งทีละอันสามครั้ง

ทำไมการส่งแยกถึงอันตรายกว่าที่ดู

เมื่อคุณส่งผลแยกกัน โครงสร้างบทสนทนาจะกลายเป็นว่าโมเดลขอสามอย่างแต่ได้กลับมาทีละอย่าง ในรอบถัดไปมันจะเรียนรู้จากรูปแบบนั้นว่าการขอพร้อมกันไม่ได้ผลดี แล้วค่อย ๆ เลิกขอแบบขนาน

อาการที่คุณจะเห็นคือ agent ที่ตอนแรกทำงานเร็ว แล้วช้าลงเรื่อย ๆ โดยไม่มี error ไม่มีอะไรแดง แค่ใช้รอบมากขึ้นและแพงขึ้น เป็นบั๊กที่ debug ยากมากถ้าไม่รู้ว่าจะมองหาอะไร

กฎข้อที่ 3เครื่องมือที่ล้มเหลวต้องส่งผลกลับ ห้ามเงียบ

เวลาคำสั่งล้มเหลว สัญชาตญาณของคนเขียนโปรแกรมคือ throw แล้วจบ แต่ในลูปนี้การไม่ส่งผลกลับ ทำให้โครงสร้างบทสนทนาเสียสภาพ — มีคำขอที่ไม่มีคำตอบ และโมเดลจะเดาว่าเกิดอะไรขึ้น

สิ่งที่ถูกคือส่งผลกลับพร้อมธงบอกว่าเป็น error แล้วให้โมเดลตัดสินใจว่าจะทำยังไงต่อ ซึ่งมันมักทำได้ดีอย่างน่าประหลาดใจ ถ้าข้อความ error บอกอะไรที่ใช้ได้

Error message คือช่องทางสอน agent ที่ถูกที่สุดที่มี

เทียบสองแบบนี้ — แบบแรกทำให้ agent เดาสุ่มแล้วลองใหม่สามรอบ แบบหลังทำให้มันแก้ถูกในรอบเดียว 

// ทำให้วนแก้ไปเรื่อย
ENOENT: no such file or directory

// ทำให้แก้ถูกทันที
ENOENT: ไม่พบ src/billing/index.ts
  ไฟล์ในโฟลเดอร์นี้: total.ts, tax.ts, discount.ts
  ถ้าต้องการ entry point ของ billing ให้ใช้ total.ts

ต้นทุนของการเขียน error แบบหลังคือครั้งเดียว ผลตอบแทนคือทุกครั้งที่ใคร — คนหรือ agent — เจอมัน เรื่องนี้เป็นแกนของ M05 ทั้งโมดูล

01.04

stop_reason ทุกค่า และการจัดการแต่ละแบบ

ทุกครั้งที่โมเดลตอบกลับ มันแนบค่ามาด้วยหนึ่งค่าที่บอกว่าทำไมถึงหยุดพูด ค่านี้เล็กมากแต่เป็นข้อมูลวินิจฉัยที่ดีที่สุดชิ้นเดียวที่คุณมี และเป็นสิ่งที่โค้ดต้องแยกกรณีให้ครบ เพราะการรวบว่า “ไม่ใช่ tool_use ก็แปลว่าเสร็จ” คือที่มาของบั๊กประเภทหนึ่งที่เจ็บมาก

ค่าแปลว่าต้องทำอะไร
end_turnพูดจบตามปกติออกจากลูป
tool_useขอใช้เครื่องมือรันแล้วส่งผลกลับ วนต่อ
max_tokensชนเพดานความยาว ถูกตัดกลางคันห้ามถือว่าเป็นคำตอบ — ต้องขอต่อหรือขยายเพดาน
pause_turnงานฝั่งเซิร์ฟเวอร์ยังไม่จบส่งกลับเข้าไปให้ทำต่อ
refusalถูกปฏิเสธด้วยเหตุผลด้านความปลอดภัยจัดการแยก อย่าลอง retry ซ้ำ ๆ

กรณีที่ต้องระวังที่สุดmax_tokens และไฟล์ที่เขียนไม่จบ

ทุกคำขอมีเพดานว่าโมเดลผลิตข้อความได้ยาวสุดเท่าไร เมื่อชนเพดาน มันไม่ได้สรุปให้จบ มันหยุดกลางประโยค แล้วแนบค่า max_tokens มาบอก

ปัญหาคือคำตอบที่ถูกตัดครึ่ง หน้าตาเหมือนคำตอบปกติทุกประการ ถ้าโค้ดของคุณเขียนแบบนี้ 

// บั๊กคลาสสิก — กลืน max_tokens เงียบ ๆ
if (reply.stop_reason === "tool_use") {
    runTools(reply)
} else {
    done(reply)          // ← max_tokens ก็มาตกที่นี่ แล้วถูกนับว่าเสร็จ
}

ผลคือคุณได้ไฟล์ที่เขียนไม่จบ ฟังก์ชันที่ปิดวงเล็บไม่ครบ หรือ JSON ที่ขาดปีกกาปิด แล้วขั้นตอนถัดไปก็ทำงานต่อบนของที่ไม่สมบูรณ์ นี่คือที่มาของอาการ “มันเขียนไฟล์มาแล้วพัง” จำนวนมากที่คนโทษว่าโมเดลสะเพร่า

สิ่งที่โค้ดต้องทำ

แยก max_tokens ออกมาเป็นกรณีของตัวเองเสมอ แล้วเลือกหนึ่งในสาม — ขอให้เขียนต่อจากจุดที่ค้าง ขยายเพดานแล้วสั่งใหม่ หรือรายงานว่างานไม่สมบูรณ์ สิ่งที่ห้ามทำคือเงียบแล้วใช้ผลนั้นต่อ

อีกสามค่าที่พบน้อยกว่าแต่ต้องมีที่ทาง

pause_turn เกิดกับงานที่ฝั่งเซิร์ฟเวอร์ทำค้างไว้และยังไม่เสร็จ วิธีจัดการคือส่งกลับเข้าไปให้ทำต่อ ไม่ใช่ถือว่าจบ ส่วน refusal คือกรณีที่คำขอถูกปฏิเสธด้วยเหตุผลด้านความปลอดภัย การ retry ซ้ำ ๆ ไม่ช่วยและเปลืองเปล่า ควรแยกออกมาให้คนดู

สุดท้าย end_turn คือค่าที่ทุกอย่างเรียบร้อย แต่มีข้อควรระวังหนึ่งข้อ — มันบอกว่าโมเดลพูดจบ ไม่ได้บอกว่างานสำเร็จ agent อาจตอบว่า “ผมแก้ไม่ได้ครับ” แล้วจบด้วย end_turn เหมือนกัน การตัดสินว่างานสำเร็จหรือไม่ต้องมาจากเกณฑ์ของคุณ ไม่ใช่จากค่านี้ — ซึ่งเป็นเหตุผลที่ M12 ยืนยันว่าต้องมีเกณฑ์เชิงกล

01.05

Thinking และ effort

โมเดลรุ่นใหม่คิดก่อนตอบได้ คือมันผลิตกระบวนการให้เหตุผลออกมาก่อน แล้วค่อยตอบ ส่วนนี้ถูกนับเป็น token ที่คุณจ่ายเหมือนกัน และคุมความลึกได้ผ่านค่าที่เรียกว่า effort

สิ่งที่คนมักเข้าใจว่า effort สูง = ฉลาดขึ้น ซึ่งไม่ผิด แต่พลาดประเด็นสำคัญกว่า — มันเปลี่ยนรูปแบบการทำงาน ไม่ใช่แค่คุณภาพ และรูปแบบที่เปลี่ยนไปมีผลต่อทั้งเวลาและเงิน

effort ต่ำeffort สูง
จำนวน tool callน้อยลง รวบมากขึ้นมากขึ้น สำรวจกว้างกว่า
คำพูดนำก่อนลงมือสั้น หรือไม่มีอธิบายเหตุผลก่อน
การตรวจงานตัวเองน้อยย้อนกลับไปตรวจบ่อย
เหมาะกับงานซ้ำที่รู้ขั้นตอนแล้ว · sub-agentงานที่ผิดแล้วแพง · วางแผน · รีวิว

คำสั่งที่เคยช่วย แต่ตอนนี้เป็นตัวถ่วง

ในยุคที่โมเดลยังไม่คิดเองก่อนตอบ การเขียนใน prompt ว่า “ให้คิดทีละขั้นก่อนตอบ” ช่วยได้จริง และกลายเป็นคำแนะนำมาตรฐานที่ถูกคัดลอกต่อ ๆ กันมา

แต่กับโมเดลที่คิดเองอยู่แล้ว คำสั่งแบบนี้ไม่ได้ช่วยอะไร และในหลายกรณีทำให้แย่ลง เพราะมันไปแทรกแซงกระบวนการที่ทำงานได้ดีอยู่แล้ว บวกกับกินงบบริบททุกรอบ นี่คือตัวอย่างของสิ่งที่ M12.08 เรียกว่า prompt cruft — คำสั่งที่หมดอายุแล้วแต่ยังอยู่เพราะไม่มีใครกล้าลบ เนื่องจากพิสูจน์ไม่ได้ว่ามันไม่จำเป็น

ลำดับการปรับที่ถูกต้อง

เจอปัญหาคุณภาพ ให้ไล่ตามลำดับนี้ — บริบท → effort → โมเดล

  1. บริบท — มันเห็นข้อมูลที่ต้องใช้ครบไหม มีของรกที่ไม่เกี่ยวปนอยู่ไหม ฟรีและมักได้ผลมากที่สุด
  2. effort — ปรับได้ทันที ไม่เสีย cache ไม่ต้องแก้โค้ด
  3. โมเดล — แพงที่สุด กระทบมากที่สุด และเสีย cache ที่สะสมมา

คนส่วนใหญ่กระโดดไปข้อสามก่อน ซึ่งนอกจากแพงแล้วยังทำให้ไม่รู้ว่าปัญหาจริงคืออะไร เพราะถ้าเปลี่ยนโมเดลแล้วดีขึ้น คุณก็ยังไม่รู้ว่าเพราะโมเดลเก่งกว่า หรือเพราะบริบทของคุณแย่มาตลอด

01.06

Permission model

ชั้นสิทธิ์เป็นชั้นเดียวในห้าชั้นที่มีหน้าที่ปฏิเสธ ชั้นอื่นทำให้ agent ทำงานได้ ชั้นนี้ทำให้มันทำงานได้เท่าที่ควร และเพราะมันขวางทางเป็นครั้งคราว คนจึงมองมันเป็นความรำคาญที่ต้องกำจัด ซึ่งเป็นการมองผิดที่ราคาแพง

โหมดใช้เมื่อความเสี่ยง
askงานสำรวจ งานที่ยังไม่ไว้ใจต่ำ แต่ขัดจังหวะ
acceptEditsงานแก้ไฟล์ในขอบเขตที่รู้แล้วปานกลาง — แก้ไฟล์ได้เอง
allowlist เฉพาะคำสั่งโหมดที่ควรใช้เป็นค่าเริ่มต้นของทีมต่ำและคาดเดาได้
bypassเฉพาะใน container ที่ทิ้งได้สูงมาก — เท่ากับให้ shell เต็ม

ทำไม allowlist ถึงชนะทั้งสองขั้ว

โหมด ask ปลอดภัยแต่ทำให้คุณต้องนั่งกดอนุมัติจนเลิกใช้ ส่วนโหมดผ่านหมดสะดวกแต่ให้สิทธิ์เท่ากับ shell ทางออกที่ใช้ได้จริงอยู่ตรงกลาง — ระบุไปเลยว่าคำสั่งกลุ่มไหนรันได้โดยไม่ต้องถาม 

// อนุญาตเฉพาะสิ่งที่งานนี้ต้องใช้จริง
Read · Grep · Glob · Edit · Write
Bash(bun test:*)      // รันเทสต์ได้
Bash(bun run:*)       // รัน script ที่มีใน package.json ได้
Bash(git diff:*)      // ดู diff ได้
// สิ่งที่ไม่อยู่ในรายการ = ต้องถาม

ผลที่ได้คือ agent ทำงานลื่นไหลตลอดเส้นทางปกติ — แก้โค้ด รันเทสต์ ดู diff แก้ต่อ — โดยไม่ต้องขออนุญาตเลย แต่ถ้ามันจะทำอะไรนอกกรอบ เช่นเรียกอินเทอร์เน็ตหรือ push โค้ด มันต้องหยุดถาม คุณได้ความลื่นไหลของโหมดผ่านหมด โดยไม่ต้องรับความเสี่ยงของมัน

หนี้ที่มองไม่เห็นจนวันที่มันมาเก็บ

เหตุผลที่คนเปิดโหมดผ่านหมดมักไม่ใช่ความประมาท แต่เป็นความหงุดหงิดสะสม — โดนถามครั้งที่สิบในเช้าวันเดียวแล้วก็กดปิดไป

ปัญหาคือความเสี่ยงไม่ได้อยู่ที่ agent จะ “คิดชั่ว” ความเสี่ยงอยู่ที่มันอ่านเนื้อหาจากภายนอก — issue ที่ใครก็เปิดได้ README ของไลบรารี หน้าเว็บที่คุณให้ไปอ่าน — แล้วเนื้อหานั้นมีข้อความ ที่หน้าตาเหมือนคำสั่งฝังอยู่ ในโหมดผ่านหมด ไม่มีอะไรกั้นระหว่างข้อความนั้นกับ shell ของคุณ M13 ลงรายละเอียดว่าช่องทางเหล่านี้มีอะไรบ้างและปิดยังไง

ข้อสังเกตที่คนไม่ค่อยพูดถึง

สิทธิ์ที่คุณให้เป็นส่วนหนึ่งของสิ่งที่คุณกำลังวัด ไม่ใช่แค่การตั้งค่าความปลอดภัย agent ที่รันเทสต์ได้กับตัวที่รันไม่ได้ คือคนละระบบกัน ตัวแรกตรวจงานตัวเองได้ ตัวหลังต้องเดา

เวลาเปรียบเทียบสองเวิร์กโฟลว์ตาม M12 ถ้าสิทธิ์ต่างกัน คุณกำลังเทียบของสองอย่างที่ต่างกันมากกว่าที่ตั้งใจ — จึงต้องระบุสิทธิ์เป็นส่วนหนึ่งของนิยามแขนที่ทดสอบ

01.07

เจ็ดโหมดที่ agent ล้มเหลว

หลังจากดูปัญหาที่คนเจอจริงมาพอสมควร รูปแบบความล้มเหลวเกือบทั้งหมดตกอยู่ในเจ็ดแบบนี้ ประโยชน์ของการจำมันได้ไม่ใช่การท่องจำ แต่คือการที่อาการแต่ละแบบชี้ไปที่ชั้นที่ต่างกัน ทำให้คุณเลิกเดาแล้วเริ่มวินิจฉัยได้

โหมดอาการที่เห็นชั้นที่ต้องแก้
บริบทล้นลืมสิ่งที่เพิ่งตกลง วนทำงานเดิมcontext assembler
คำอธิบายเครื่องมือกำกวมเลือกผิดตัวซ้ำ ๆtool registry
error อ่านไม่รู้เรื่องแก้วนไปวนมาไม่ตรงจุดcodebase (M05)
ติดลูปทำสามอย่างสลับกันไม่จบเพดาน turn + เกณฑ์จบงาน
ค้นเกินจำเป็นอ่าน 40 ไฟล์ก่อนแก้ 1 บรรทัดโครงสร้าง repo (M05)
ลอยจากแผนเริ่มถูก แล้วค่อย ๆ ทำอย่างอื่นแผนที่ตรวจได้ (M04)
ตัดข้อมูลเงียบมั่นใจแต่ผิดresult renderer

สามแบบที่เจอบ่อยที่สุดและวิธีแยกออกจากกัน

บริบทล้น มีลายเซ็นชัด — มันทำถูกช่วงแรก แล้วเริ่มถามสิ่งที่ตอบไปแล้ว หรือแก้ไฟล์ที่เพิ่งแก้ไปกลับเป็นแบบเดิม จุดสังเกตคืออาการจะแย่ลงตามความยาวของบทสนทนา ถ้าเริ่มใหม่แล้วหาย นั่นแหละใช่

ค้นเกินจำเป็น ดูเผิน ๆ เหมือนความขยัน แต่มันคือสัญญาณว่าโครงสร้าง repo ไม่สื่อ ทุกไฟล์ที่มันเปิดผิดก่อนเจอไฟล์ที่ถูก คือหลักฐานว่าชื่อหรือที่อยู่เดาไม่ได้ ข้อดีคืออาการนี้วัดเป็นตัวเลขได้ตรง ๆ — นับจำนวนไฟล์ที่เปิดก่อนเจอที่ถูก แล้วใช้เป็นตัววัดว่า การปรับ repo ตาม M05 ได้ผลจริงไหม

ตัดข้อมูลเงียบ เป็นแบบที่วินิจฉัยยากที่สุดเพราะมันไม่มีอาการภายนอกเลย ผลลัพธ์ดูสมเหตุสมผล น้ำเสียงมั่นใจ แต่ข้อสรุปผิด วิธีจับคือตรวจสิ่งที่มันเห็น ไม่ใช่สิ่งที่มันพูด ถ้าเป็นไปได้ให้ดู output ดิบของคำสั่งที่มันรัน แล้วเทียบกับสิ่งที่มันสรุป ช่องว่างระหว่างสองอย่างนี้คือคำตอบ

คำถามเดียวที่ควรถามก่อนสรุปว่าโมเดลไม่เก่งพอ

“ถ้าผมเป็นคนที่เห็นข้อมูลเท่าที่มันเห็น ผมจะตอบต่างจากนี้ไหม”

ถ้าคำตอบคือไม่ ปัญหาไม่ได้อยู่ที่โมเดล แต่อยู่ที่ข้อมูลที่ไปถึงมัน ซึ่งเป็นชั้น 3 หรือชั้น 5 และเป็นสิ่งที่คุณแก้ได้ ในทางปฏิบัติคำตอบเป็น “ไม่” บ่อยกว่าที่คนคาดมาก

01.08 · แล็บประจำโมดูล

เขียน mini-harness ~150 บรรทัด

เป้าหมายไม่ใช่ได้เครื่องมือใช้งาน แต่คือทำลายความรู้สึกว่ามันเป็นเวทมนตร์ เมื่อคุณเขียนลูปเองแล้ว ทุกอาการแปลก ๆ หลังจากนี้จะมีที่ทางให้ชี้

ข้อกำหนดต้องมีครบทั้งห้าข้อ

  1. ลูป while ที่วนจนกว่า stop_reason จะไม่ใช่ tool_use และแยกกรณี max_tokens ออกมาชัด ๆ
  2. เครื่องมือสามตัว — อ่านไฟล์ เขียนไฟล์ และรันคำสั่ง
  3. Permission gate ที่เป็น allowlist ไม่ใช่ ask ทุกครั้ง
  4. รองรับ tool call หลายตัวในหนึ่งคำตอบ และส่งผลกลับครบใน message เดียว
  5. นับและพิมพ์จำนวน token กับต้นทุนสะสมทุกรอบ

  • สั่งงานที่ต้องใช้เครื่องมือสามรอบขึ้นไปแล้วทำสำเร็จ
  • จงใจให้เครื่องมือ error หนึ่งครั้ง แล้ว agent แก้ทางได้เองโดยไม่ค้าง
  • ตั้งเพดาน token ต่ำจนโดนตัด แล้ว harness ต้องรายงานว่าโดนตัด ไม่ใช่ทำเป็นว่าจบ
