AI Coding Agent SDLC · Phase 01 · Module 05

ออกแบบ Codebase ให้ Agent ทำงานได้

คุณภาพงานของ agent มาจากโครงสร้าง repo มากกว่ามาจาก prompt และความต่างที่สำคัญคือ โครงสร้างให้ผลถาวร ส่วน prompt ที่ปรับดีขึ้นให้ผลแค่ครั้งเดียว

8 บทเรียน2.5 ชั่วโมง1 แล็บต้องผ่าน M02 · M04 ก่อน
ใจความของทั้งโมดูล

ทุกครั้งที่ agent หาของไม่เจอ อ่าน error ไม่รู้เรื่อง หรือรันเทสต์ทั้งชุดเพื่อตรวจบรรทัดเดียว คุณจ่ายเงินและเวลาให้กับสิ่งที่แก้ครั้งเดียวจบได้

05.01

Legibility — อ่านรู้เรื่องสำหรับเครื่อง

โมดูลนี้ผมอยากเริ่มด้วยประโยคที่คนมักไม่เชื่อตอนแรก — คุณภาพงานของ agent มาจากโครงสร้าง repo มากกว่ามาจาก prompt

และที่สำคัญกว่าคือ โครงสร้างให้ผลถาวร ส่วน prompt ที่ปรับดีขึ้นให้ผลแค่ครั้งเดียว คุณปรับ prompt วันนี้ พรุ่งนี้เปิด session ใหม่ก็ต้องปรับใหม่ แต่ถ้าคุณตั้งชื่อไฟล์ให้สื่อ มันสื่อไปตลอดกับทุกคนและทุก agent

Figure 1 · ความรู้ฝั่งซ้ายอยู่ในหัวคน ไม่ได้อยู่ใน repo — agent เข้าถึงไม่ได้

codebase ที่คนอ่านรู้เรื่องกับที่เครื่องอ่านรู้เรื่อง ไม่ใช่สิ่งเดียวกัน คนเติมช่องว่างจากบริบทที่สะสมมาหลายเดือน — รู้ว่าไฟล์ไหนตายแล้ว รู้ว่าเทสต์ไหนแดงเป็นปกติ รู้ว่าต้องรันอะไรก่อน ส่วน agent เห็นเฉพาะสิ่งที่อยู่ตรงหน้า

ผลพลอยได้ที่มักใหญ่กว่าผลหลัก

ทุกอย่างในโมดูลนี้ช่วย dev ใหม่ พอ ๆ กับช่วย agent เพราะทั้งคู่ขาดบริบทที่คนเก่ามีเหมือนกัน

หลายทีมพบว่าเวลาที่ประหยัดจากการที่คนใหม่ไม่ต้องมาถาม มากกว่าเวลาที่ประหยัดจาก agent เสียอีก เพราะงั้นถ้าต้องขายงานนี้ให้หัวหน้า ขายว่าเป็น onboarding ไม่ใช่ AI

อ่านเพิ่มจากต้นทาง

  1. Claude Code best practices — การเตรียม repo ให้ agent ทำงานได้ดี anthropic.com/engineering
  2. Code Smell — กรอบคิดเรื่องสัญญาณที่บอกว่าโครงสร้างมีปัญหา ใช้ได้กับทั้งคนและ agent martinfowler.com
05.02

โครงไฟล์ที่ลดต้นทุนการค้นหา

agent จ่าย token ทุกครั้งที่หาไม่เจอ และมันหาแบบเดาจากชื่อ ไม่ใช่แบบจำที่ได้

เพราะงั้นโครงสร้างที่ดีวัดได้ด้วยคำถามเดียว — "จากชื่อฟีเจอร์ เดาที่อยู่ไฟล์ถูกในครั้งแรกไหม"

Figure 2 · ทุกไฟล์ที่เปิดผิดคือหลักฐานว่าชื่อหรือที่อยู่เดาไม่ได้ — และมันนับเป็นตัวเลขได้

  • จัดตาม domain ไม่ใช่ตามชนิดไฟล์ — billing/ ที่มีทั้ง logic, test, type รวมกัน ชนะการกระจายไป 3 โฟลเดอร์
  • ชื่อไฟล์บอกเนื้อหา — invoice-total.ts ชนะ helpers.ts เสมอ
  • อย่ามีทางเข้าหลายทางไปที่เดียวกัน — re-export ซ้อนหลายชั้นทำให้ agent ตามไม่จบ และ grep เจอแต่ตัวกลาง
  • ของที่ห้ามแตะต้องบอกที่ตัวมันเอง ไม่ใช่ในหัวคน
Barrel file — ของที่ดูดีแต่ทำร้าย agent

ไฟล์ index.ts ที่ re-export ทุกอย่างในโฟลเดอร์ ทำให้ import สวยขึ้นสำหรับคน แต่สำหรับ agent มันแปลว่า grep หาชื่อฟังก์ชันแล้วเจอแต่บรรทัด re-export ไม่เจอที่มันถูกนิยามจริง

ผลคือมันต้องไล่ตามอีกชั้นสองชั้น เสีย round เสีย token และบางทีก็หลงไปแก้ผิดไฟล์

อ่านเพิ่มจากต้นทาง

  1. Common workflows — วิธีที่ agent สำรวจ codebase จริง ซึ่งบอกว่าโครงแบบไหนช่วยมัน docs.claude.com
  2. Claude Code best practices — คำแนะนำเรื่องโครงสร้างและการตั้งชื่อ anthropic.com/engineering
05.03

Error message คือช่องทาง feedback

อันนี้คือการลงทุนที่ให้ผลตอบแทนสูงสุดในโมดูลนี้ และเป็นข้อที่ทีมส่วนใหญ่ไม่เคยคิดถึง

เพราะเราชินกับการมอง error ว่าเป็นสิ่งที่คนอ่านตอนของพัง แต่ในโปรเจกต์ที่มี agent ทำงานอยู่ error คือสิ่งที่มันอ่านตอนหลงทาง — และเป็นโอกาสเดียวที่เราจะชี้ทางได้โดยไม่ต้องอยู่ตรงนั้น

Figure 3 · ส่วนที่ 3 คือส่วนที่เปลี่ยนการวนแก้ 3 รอบให้เหลือรอบเดียว

สังเกตว่าเรามักรู้คำตอบอยู่แล้วตอนเขียน error — คนที่เขียนโค้ดตรวจสอบย่อมรู้ว่าค่าที่ถูกคืออะไร การเขียนมันลงไปใช้เวลาสิบวินาที แต่คนไม่เขียนเพราะคิดว่า "เดี๋ยวคนอ่านก็รู้เอง"

เริ่มจากตรงไหน — อย่าไล่แก้ทั้งโปรเจกต์

เก็บสถิติสองสัปดาห์ว่า error ตัวไหนที่ agent เจอบ่อยที่สุด แล้วแก้แค่สามตัวแรก

การกระจายมักเบ้มาก — error ไม่กี่ตัวกินสัดส่วนส่วนใหญ่ของการวนแก้ทั้งหมด แก้สามตัวได้ผลเกือบเท่าแก้ทั้งหมด

อ่านเพิ่มจากต้นทาง

  1. Writing tools for agents — ออกแบบ error ที่ส่งกลับให้ agent ใช้ตัดสินใจต่อได้ anthropic.com/engineering
  2. Tool use overview — การส่ง error result กลับเข้า loop อย่างถูกต้อง docs.claude.com
05.04

Test affordance

หลักการของบทนี้ฟังดูเหมือนเรื่อง performance แต่จริง ๆ เป็นเรื่องพฤติกรรม — ถ้ารันเทสต์เฉพาะจุดไม่ได้เร็ว agent จะเลิกรันแล้วเดาแทน

แล้วมันไม่ประกาศนะครับว่าเลิกรัน มันแค่ค่อย ๆ ข้ามไป แล้วเขียนคำตอบลงท้ายว่า "น่าจะทำงานได้แล้วครับ" — ซึ่งเราจะเห็นเป็นคุณภาพที่ตกโดยหาสาเหตุไม่เจอ

Figure 4 · agent ทำงานภายใต้แรงกดดันเดียวกับคน — ถ้าการตรวจสอบมีต้นทุนสูง มันจะถูกทำน้อยลง

ต่างจากคนตรงที่คนรู้ตัวว่ากำลังข้ามขั้นตอน ส่วน agent ไม่ได้รายงานให้เรารู้ ข้อนี้ทำให้มันเป็นปัญหาที่แก้ที่ต้นทางได้ผลกว่าแก้ที่ prompt มาก — การเขียนกฎว่า "ต้องรันเทสต์ทุกครั้ง" ไม่ได้ทำให้เทสต์เร็วขึ้น มันแค่เพิ่มบรรทัดที่ถูกละเลย

ทางลัดที่ทำให้แย่ลง

พอเทสต์ช้า ทางลัดที่คนเลือกคือบอก agent ว่า "ไม่ต้องรันเทสต์ เดี๋ยว CI รันเอง" ซึ่งย้ายการตรวจไปไว้หลังจากที่ agent จบงานไปแล้ว

ผลคือ agent เสียความสามารถในการวนแก้เองจนถูก และเราได้งานที่ต้องตีกลับ ซึ่งแพงกว่าการรอเทสต์ห้าวินาทีหลายเท่า — และเป็นการย้ายต้นทุนจากเครื่องมาที่คน

Engineering note · ทำให้เร็วได้ยังไงบ้าง
  • watch mode ที่รันเฉพาะไฟล์ที่เกี่ยว — ให้ agent เรียกได้แบบ one-shot ด้วย
  • แยก unit ออกจาก integration ให้ชัด แล้วให้ default คือ unit
  • อย่าให้ test setup แพง — ถ้าต้องยก container ทุกครั้ง ให้ทำ in-memory ไว้สำหรับ unit
  • ใส่คำสั่งไว้ใน project memory ไม่งั้น agent จะรันทั้งชุดเพราะไม่รู้ว่ามีทางลัด

อ่านเพิ่มจากต้นทาง

  1. Test Pyramid — เหตุผลว่าทำไมชั้นล่างต้องเร็วและเยอะ ซึ่งเป็นเงื่อนไขของบทนี้พอดี martinfowler.com
  2. Memory — ที่สำหรับเขียนคำสั่งรันเทสต์ให้ agent รู้จัก docs.claude.com
05.05

Type และ schema เป็น guardrail ที่ถูกที่สุด

Type ทำงานต่างจากกฎใน prompt ตรงจุดเดียวที่สำคัญมาก — มันบังคับได้ ไม่ใช่แค่ขอ และมันทำงานตอนที่ไม่มีใครดูอยู่

Figure 5 · แถบสีส้มคือต้นทุน context ที่จ่ายทุกรอบโดยไม่รับประกันผล

กฎที่ควรใช้คือ — อะไรที่ทำให้เป็น type ได้ อย่าเอาไปเขียนเป็นกฎใน prompt เพราะกฎใน prompt กินงบ context ทุกรอบ และยังไม่รับประกันว่าจะถูกทำตาม

ตัวอย่างการแปลงกฎเป็น type 
// กฎใน prompt — จ่ายทุกรอบ ไม่รับประกัน
"อย่าลืมเช็คว่า user ยัง active อยู่ก่อนส่ง email"

// เป็น type — ฟรี และเลี่ยงไม่ได้
type ActiveUser = User & { readonly _active: unique symbol }
function sendEmail(u: ActiveUser) { ... }
// ส่ง User ธรรมดาเข้าไป → compile ไม่ผ่าน ไม่ต้องหวังพึ่งความจำ

อ่านเพิ่มจากต้นทาง

  1. Hooks — การบังคับกฎด้วยเครื่องมือแทนการเขียนเป็นข้อความ docs.claude.com
  2. Code Smell — กรอบคิดว่าเมื่อไหร่ควรย้ายข้อตกลงไปอยู่ในโครงสร้างแทนในหัวคน martinfowler.com
05.06

Docs-as-context

ในโปรเจกต์ที่มี agent ทำงานอยู่ เอกสารเปลี่ยนสถานะ — จากของที่เขียนแล้วไม่มีใครอ่าน กลายเป็น input ที่ถูกอ่านทุกวัน ซึ่งเปลี่ยนวิธีเขียนไปด้วย

Figure 6 · ฝั่งขวาต่างจากฝั่งซ้ายตรงที่ "ทำตามได้ทันที" ไม่ใช่ "อ่านแล้วเข้าใจ"

เอกสารที่เป็นโทษ

เอกสารล้าสมัยแย่กว่าไม่มี เพราะ agent เชื่อมันและทำตาม โดยไม่มีสัญชาตญาณแบบคนที่จะรู้สึกว่า "เอ๊ะ อันนี้เก่าแล้วมั้ง"

ถ้าดูแลไม่ไหว ลบดีกว่าปล่อยไว้ และถ้าลบไม่ได้ ให้เขียนวันที่กับสถานะไว้บนหัวไฟล์ — ตรงกับกฎใน M15.03 ที่ว่าเอกสารต้อง "พังได้เมื่อผิด"

อ่านเพิ่มจากต้นทาง

  1. Memory — ที่ทางของเอกสารที่ต้องการให้ agent อ่านทุกครั้ง docs.claude.com
  2. Effective context engineering — เอกสารในฐานะ context ที่ต้องบริหาร ไม่ใช่ของที่ใส่ไว้เฉย ๆ anthropic.com/engineering

05.08 · แล็บประจำโมดูล

Audit repo จริง แล้วทำห้าการเปลี่ยนที่ลด token ต่องานลง 30%

แล็บนี้วัดผลได้ตรง ๆ และผลมักอยู่ได้นานกว่าทุกอย่างที่คุณทำในหลักสูตรนี้

ขั้นตอน

  1. วัดตั้งต้น — เลือกงานตัวแทนสามงาน รันแล้วบันทึก token ที่ใช้ จำนวนรอบ และจำนวนไฟล์ที่ agent เปิดอ่าน
  2. หาจุดรั่ว — ดูว่ามันเปิดไฟล์อะไรบ้างก่อนจะเจอที่ถูก ทุกไฟล์ที่เปิดผิดคือหลักฐานว่าโครงสร้างหรือชื่อไม่สื่อ
  3. เลือกห้าการเปลี่ยน จากรายการนี้ — คำสั่งรันเทสต์เฉพาะจุด · แก้ error สามข้อที่เจอบ่อยให้บอกวิธีแก้ · ตั้งชื่อไฟล์ที่กำกวมใหม่ · เขียนหัวไฟล์ให้ของ deprecated · ตัด project memory ที่พิสูจน์ไม่ได้ทิ้ง
  4. วัดซ้ำด้วยงานเดิม อย่างละ 3 ครั้ง
เกณฑ์ผ่าน
  • token ต่องานลดลงอย่างน้อย 30% โดยอัตราผ่านไม่ตก
  • จำนวนไฟล์ที่เปิดผิดก่อนเจอที่ถูก ลดลงชัดเจน
  • บอกได้ว่าการเปลี่ยนไหนให้ผลมากที่สุด — เกือบทุกครั้งคือข้อ test affordance
อย่าทำพร้อมกันทั้งห้า

ทำทีละอย่างแล้ววัด ไม่งั้นคุณจะรู้ว่ารวม ๆ ดีขึ้น แต่ไม่รู้ว่าเพราะอะไร แล้วครั้งหน้าในโปรเจกต์อื่นก็ต้องเดาใหม่หมด
