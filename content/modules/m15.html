15.04

Trust calibration

ความไว้ใจที่ถูกต้องไม่ใช่ตัวเลขเดียว แต่แตกต่างตามประเภทงาน และควรมาจากข้อมูลของทีมคุณเอง ไม่ใช่จากความรู้สึกหรือจากที่คนอื่นบอก

ระดับหมายความว่าเลื่อนขึ้นได้เมื่อ
ตรวจทุกบรรทัดอ่าน diff ทั้งหมดก่อนรับงานประเภทนี้ผ่านชุดวัดสม่ำเสมอ
ตรวจแบบสุ่มดูละเอียดบางส่วนอัตราพลาดต่ำต่อเนื่องหลายสิบงาน
เชื่อ gateดูแค่ผลของ gategate มี precision สูงพิสูจน์แล้ว
ตรวจย้อนหลังดูเป็นชุดรายสัปดาห์งานที่ผิดแล้วเสียหายต่ำและย้อนได้
สิ่งที่ทำให้การเลื่อนระดับไม่ใช่การเดา

ชุดวัดจาก M12 คือหลักฐานที่ทำให้บทสนทนาเรื่องนี้เปลี่ยนจาก “ผมว่ามันเชื่อได้แล้วนะ” เป็น “งานประเภทนี้ผ่าน 47 จาก 50 ในสามเดือน และสามที่ไม่ผ่านถูก gate จับได้ทั้งหมด”

15.05

วัฒนธรรม code review เมื่อ diff โตขึ้นสิบเท่า

เมื่อปริมาณโค้ดที่ต้องรีวิวโตขึ้นมาก การรีวิวแบบเดิมพังลงเงียบ ๆ — คนยังกด approve เท่าเดิม แต่อ่านจริงน้อยลงมาก ซึ่งแย่กว่าไม่รีวิว เพราะมันสร้างภาพลวงว่ามีการตรวจ

เปลี่ยนสิ่งที่รีวิว ไม่ใช่เร่งความเร็ว
ปล่อยให้เครื่องตรวจคนต้องตรวจ
รูปแบบ การตั้งชื่อโจทย์นี้ถูกต้องหรือเปล่า
type และสัญญาสมมติฐานที่ไม่ได้เขียนไว้
เทสต์ผ่านครบเทสต์ทดสอบสิ่งที่ถูกต้องไหม
ขอบเขต diffผลกระทบต่อส่วนอื่นที่ diff ไม่แสดง

คอลัมน์ขวาคือสิ่งที่เครื่องทำแทนไม่ได้ และเป็นสิ่งที่คุณค่าเพิ่มขึ้นเมื่อ agent เขียนโค้ดเยอะขึ้น การรีวิวจึงไม่ได้หายไป แต่เปลี่ยนเป้า

15.06

Attribution license และความเสี่ยงเชิงกฎหมาย

สิ่งที่ควรทำเป็นนโยบาย
  • ระบุในคอมมิตว่าสร้างโดย agent และใครอนุมัติ — สำคัญตอนตรวจสอบย้อนหลัง
  • สแกน license ของ dependency ที่ agent เพิ่มเข้ามา เป็น gate ใน CI
  • กำหนดว่าโค้ดของลูกค้าส่งเข้าโมเดลได้แค่ไหน — ข้อนี้มักถูกกำหนดโดยสัญญาที่มีอยู่แล้ว
  • เก็บบันทึกว่าใครใช้อะไรกับงานไหน ในระดับที่ตอบผู้ตรวจสอบได้

เรื่องเหล่านี้ต่างกันไปตามเขตอำนาจและตามสัญญาที่องค์กรคุณมีอยู่ หลักสูตรนี้ให้เช็คลิสต์ที่ต้องเอาไปคุยกับฝ่ายกฎหมาย ไม่ใช่คำแนะนำทางกฎหมาย และความต่างข้อนี้สำคัญ

Figure 6 · ข้อ 2 เป็นข้อเดียวที่แก้ได้ด้วยเครื่องมือล้วน ๆ จึงควรทำก่อน

15.07

Skill atrophy — สิ่งที่ไม่มีใครพูดถึง

เมื่อ agent ทำงานบางอย่างแทนได้ดี ทีมจะเลิกฝึกทักษะนั้น ซึ่งบางกรณีดี บางกรณีอันตราย เกณฑ์แยกคือ “ทักษะนี้จำเป็นตอนที่ agent ทำไม่ได้หรือทำผิดหรือเปล่า”

ปล่อยได้ต้องรักษาไว้
จำ syntax ของภาษาที่ไม่ค่อยใช้อ่านโค้ดที่ไม่ได้เขียนเองแล้วเข้าใจ
เขียนโค้ดสำเร็จรูปซ้ำ ๆdebug ด้วยการตั้งสมมติฐานแล้วทดสอบ
จำ flag ของคำสั่งออกแบบระบบและประเมินข้อแลกเปลี่ยน
ค้นวิธีใช้ APIรู้ว่าอะไรผิดปกติเมื่อเห็นมัน
ทำไมสามข้อในคอลัมน์ขวาถึงสำคัญที่สุด

ทั้งสามคือทักษะที่ใช้ตอนตรวจงานของ agent ถ้าทีมสูญเสียมันไป คุณจะเหลือแต่คนที่กด approve ได้เร็วขึ้นแต่จับผิดไม่ได้ ซึ่งเป็นสภาพที่อันตรายกว่าการไม่ใช้ agent เลย

วิธีรักษาที่ได้ผลจริง

ให้คนในทีมผลัดกันทำงานหนึ่งชิ้นต่อสัปดาห์โดยไม่ใช้ agent เลย ไม่ใช่เพื่อประสิทธิภาพ แต่เพื่อรักษาความสามารถในการบอกว่าอะไรดีอะไรแย่ — ซึ่งเป็นสิ่งเดียวที่ทำให้การใช้ agent ปลอดภัย

15.09 · แล็บประจำโมดูล

เขียน AI engineering policy ของทีมความยาว 2 หน้า ที่บังคับใช้ได้จริง

เกณฑ์ที่ทำให้แล็บนี้ต่างจากการเขียนเอกสารทั่วไป — ทุกข้อในนโยบายต้องระบุได้ว่าบังคับด้วยอะไร ข้อที่บังคับด้วย “ความร่วมมือของทุกคน” ให้ตัดออกหรือหาวิธีบังคับ

ต้องครอบคลุมหกหัวข้อ

  1. ขอบเขต — งานประเภทไหนใช้ agent ได้ ประเภทไหนต้องมีคนอยู่ด้วยเสมอ
  2. สิทธิ์ — ระดับสิทธิ์มาตรฐาน และใครอนุมัติการขอเพิ่ม
  3. รีวิว — อะไรที่เครื่องตรวจ อะไรที่คนต้องตรวจ (ตาราง 15.05)
  4. ความรับผิดชอบ — ใครรับผิดชอบเมื่อโค้ดที่ agent เขียนทำให้เกิดปัญหา
  5. ข้อมูล — อะไรส่งเข้าโมเดลได้ อะไรห้าม และบังคับยังไง
  6. การติดตั้งของจากภายนอก — เช็คลิสต์จาก M13.04 เป็นขั้นตอนของทีม
เกณฑ์ผ่าน
  • ทุกข้อระบุกลไกบังคับได้ — hook, การตั้งค่า, gate ใน CI หรือขั้นตอนอนุมัติ
  • ยาวไม่เกินสองหน้า ถ้าเกิน แปลว่ามีข้อที่ควรเป็นเครื่องมือแทนที่จะเป็นข้อความ
  • เอาไปให้คนในทีมที่ไม่ได้เขียนอ่าน แล้วเขาบอกได้ว่าพรุ่งนี้ต้องทำอะไรต่างจากวันนี้
สัญญาณว่านโยบายจะไม่ถูกใช้

ถ้าอ่านจบแล้วรู้สึกว่า “ก็สมเหตุสมผลดี” แต่ตอบไม่ได้ว่าพรุ่งนี้ต้องเปลี่ยนอะไร แปลว่ามันเป็นเรียงความ ไม่ใช่นโยบาย นโยบายที่ดีเปลี่ยนพฤติกรรมได้ตั้งแต่วันแรก

จบหลักสูตร — จากที่นี่วนกลับไปที่ M12 ทุกไตรมาส เพราะโมเดลเปลี่ยน เครื่องมือเปลี่ยน และเวิร์กโฟลว์ที่เคยดีที่สุดเมื่อหกเดือนก่อนอาจไม่ใช่แล้ว — ชุดวัดคือสิ่งเดียวที่บอกคุณได้
