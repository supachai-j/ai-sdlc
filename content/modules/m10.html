Multi-Agent Orchestration

Multi-agent เป็นสถาปัตยกรรม ไม่ใช่ฟีเจอร์ มันมีแพตเทิร์น มีสัญญาการส่งต่อ และมีโหมดล้มเหลวเฉพาะตัว บทที่สำคัญที่สุดคือบทที่บอกว่าเมื่อไหร่มันแพ้ agent เดียว ซึ่งบ่อยกว่าที่คนคิดมาก

ใจความของทั้งโมดูล

เหตุผลที่ถูกต้องในการใช้หลาย agent มีแค่สองข้อ — กันบริบทไม่ให้ปน และทำงานที่ไม่ขึ้นต่อกันพร้อมกัน ถ้าเหตุผลของคุณไม่ใช่สองข้อนี้ คุณกำลังจ่ายแพงขึ้นเพื่อผลที่ไม่คงเส้นคงวาขึ้น

ที่มา

multi-agent เก่ากว่า LLM ประมาณ 45 ปี

เรื่องที่คนมักไม่รู้ — ปัญหาการให้หลาย agent ทำงานร่วมกันถูกศึกษามาตั้งแต่ยุค 70–80 และคำตอบที่ได้ตอนนั้น ยังใช้อธิบายว่าทำไม multi-agent สมัยนี้ถึงพังในแบบเดิม ๆ ได้อยู่เลย

สิ่งที่เปลี่ยนไปคือ agent แต่ละตัวฉลาดขึ้นมาก · สิ่งที่ไม่เปลี่ยนคือค่าใช้จ่ายในการประสานงาน

Figure 0 · เราไม่ได้กำลังคิดสถาปัตยกรรมใหม่ — เรากำลังรันสถาปัตยกรรมเก่าด้วยชิ้นส่วนที่แพงกว่ามาก

1980Contract Net — ต้นแบบของ orchestrator ที่คุณเขียนอยู่

Reid G. Smith เสนอ Contract Net Protocol ในปี 1980 เพื่อตอบคำถามว่า ระบบกระจายจะแบ่งงานกันเองได้อย่างไร กลไกคือ node ที่มีงานจะประกาศงานออกไป node อื่นที่ทำได้จะยื่นข้อเสนอ แล้วผู้ประกาศเลือกและมอบสัญญา

ถ้าอ่านแล้วรู้สึกคุ้น นั่นเพราะมันคือสิ่งที่คุณทำทุกครั้งที่เขียน orchestrator ที่แตกงานย่อยส่งให้ sub-agent สิ่งที่ Smith เขียนไว้ตั้งแต่ตอนนั้นและยังจริงอยู่คือ ค่าสื่อสารระหว่าง node อาจแพงกว่างานที่แบ่งกันทำ — ซึ่งตรงกับที่บทที่ 10.02 บอกว่าเมื่อไหร่ไม่ควรใช้ multi-agent

1980Blackboard — และปัญหาที่มันเจอก่อนเรา 45 ปี

ระบบ Hearsay-II ใช้สถาปัตยกรรม blackboard ให้ module ผู้เชี่ยวชาญหลายตัว (เสียง คำ ไวยากรณ์) อ่านและเขียนลงพื้นที่ความจำร่วมเดียวกัน แทนที่จะคุยกันตรง ๆ

ปัญหาที่พวกเขาเจอคือปัญหาเดียวกับที่ทีมสมัยนี้เจอกับ shared context — ใครควรได้อ่านอะไร และเมื่อไหร่ เพราะให้ทุกตัวเห็นทุกอย่างแล้วมันรบกวนกันเอง แต่แยกกันสนิทแล้วมันทำงานซ้ำซ้อน

บทเรียนที่ผมคิดว่าใช้ได้ทันที — งานวิจัยยุคนั้นสรุปตรงกันว่า multi-agent คุ้มเมื่อ งานย่อยแยกกันได้จริงและสื่อสารกันน้อย

ซึ่งเป็นเงื่อนไขเดียวกับที่ยังจริงในปี 2026 — และเป็นเหตุผลว่าทำไมงาน "refactor ทั้ง codebase" ถึงไม่เหมาะกับ multi-agent ทั้งที่ฟังดูเหมือนงานใหญ่ที่ควรแบ่งกันทำ

  2. Blackboard system — สถาปัตยกรรมพื้นที่ความจำร่วมจาก Hearsay-II และข้อจำกัดที่พบ wikipedia.org

10.01

เหตุผลที่ถูกต้องเพียงสองข้อ

Multi-agent เป็นสถาปัตยกรรม ไม่ใช่ฟีเจอร์ — มันมีแพตเทิร์น มีสัญญาการส่งต่อ และมีโหมดล้มเหลวเฉพาะตัวที่ agent เดียวไม่มี

ผมอยากเริ่มด้วยการตัดเหตุผลผิด ๆ ออกก่อน เพราะเหตุผลที่ถูกจริง ๆ มีแค่สองข้อ ถ้าเหตุผลของคุณไม่ใช่สองข้อนี้ คุณกำลังจ่ายแพงขึ้นเพื่อผลที่ไม่คงเส้นคงวาขึ้น

Figure 1 · ทั้งสองเหตุผลที่ถูกวัดเป็นตัวเลขได้ · ทั้งสามที่ผิดวัดไม่ได้เลย — นั่นคือวิธีแยก

  2. Building a multi-agent research system — เคสจริงที่ใช้การแยก context เป็นเหตุผลหลัก anthropic.com/engineering

10.08 · แล็บประจำโมดูล

ทำ review pipeline สามขั้น แล้ววัดว่าดีกว่า agent เดียวจริงหรือแค่แพงกว่า

แล็บนี้ต้องใช้ชุดวัดจาก M12 เพราะทั้งประเด็นคือการพิสูจน์ ไม่ใช่การสร้าง

ขั้นตอน

  1. ปลูกบั๊กที่รู้คำตอบ 15 ตัว ใน repo จริง คละความยาก
  2. แขนที่ 1 — agent เดียวที่สั่งให้หาบั๊ก
  3. แขนที่ 2 — pipeline สามขั้น review → verify → report พร้อมสัญญาที่เป็นโครงสร้าง
  4. รันทั้งสองแขนบนชุดเดียวกัน อย่างละ 3 ครั้ง
  5. วัดสี่มิติ — จับได้กี่ตัว เตือนผิดกี่ครั้ง ต้นทุนต่อบั๊กที่จับได้ และเวลาจริง
เกณฑ์ผ่าน
  • ตอบได้ด้วยตัวเลขว่าแขนไหนชนะ และชนะที่มิติไหน
  • ถ้าผลออกมาว่า agent เดียวชนะ ถือว่าผ่านเต็ม — คุณเพิ่งประหยัดเงินและความซับซ้อนให้ตัวเอง
  • ถ้าช่วงผลของสองแขนทับกัน ต้องบอกได้ว่าต้องใช้อีกกี่งานถึงจะสรุปได้
ผลที่มักเจอ

pipeline มักจับได้พอ ๆ กัน แต่เตือนผิดน้อยลงชัดเจน เพราะสเตจ verify กรองออก ถ้าผลของคุณออกมาแบบนี้ คุณค่าที่แท้จริงของแพตเทิร์นนี้อยู่ที่ความแม่นยำ ไม่ใช่ความครอบคลุม ซึ่งเปลี่ยนวิธีที่คุณควรใช้มัน
