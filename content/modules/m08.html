AI Coding Agent SDLC · Phase 02 · Module 08

Brownfield และ Legacy Code

แล็บที่เริ่มจากโฟลเดอร์ว่างสอนงานที่แทบไม่มีใครทำจริง งานจริงคือ codebase อายุหกปี ไม่มีเทสต์ ไม่มี type และคนเขียนลาออกไปแล้ว โมดูลนี้คือส่วนที่คุณจะใช้บ่อยที่สุด

7 บทเรียน2.5 ชั่วโมง1 แล็บต้องผ่าน M05 ก่อน
ใจความของทั้งโมดูล

ใน greenfield ความเสี่ยงคือทำไม่เสร็จ ใน brownfield ความเสี่ยงคือทำของที่เคยใช้ได้ให้พัง กลยุทธ์ทั้งหมดจึงกลับด้าน — สร้างตาข่ายก่อน แล้วค่อยขยับ

08.01

สร้างแผนที่ก่อน อย่าเพิ่งแก้

สัญชาตญาณแรกคือส่งงานให้ agent เลย แต่ใน codebase ที่ไม่มีใครเข้าใจ สิ่งที่ควรสั่งเป็นอย่างแรกคือ ให้มันอธิบายกลับมา

  1. แผนที่ระดับบน — โมดูลหลักมีอะไรบ้าง อะไรเรียกอะไร ทางเข้าอยู่ตรงไหน
  2. เส้นทางของฟีเจอร์ที่จะแตะ — จาก request จนถึงฐานข้อมูล ทีละไฟล์ทีละบรรทัด
  3. รายการสิ่งที่ดูแปลก — โค้ดที่ดูเหมือนตายแล้ว ชื่อที่ขัดกัน ของที่ซ้ำกันสองที่
ทำไมข้อสามถึงมีค่าที่สุด

agent ไม่มีความคุ้นเคยมาบดบัง มันจึงชี้ของแปลกที่คนในทีมมองข้ามมาสามปีเพราะชินแล้ว รายการนี้มักมีของที่คุ้มจะแก้ซ่อนอยู่ และเป็นผลพลอยได้ที่คนไม่คาดคิด

เก็บผลลัพธ์ไว้ อย่าทิ้ง

แผนที่ที่ได้ให้เขียนลงไฟล์ในโปรเจกต์ มันจะกลายเป็นบริบทถาวรตามหลัก M05.06 และทำให้ครั้งหน้าไม่ต้องเสียเงินสำรวจซ้ำ

08.02

Characterization test

เทสต์ชนิดนี้ไม่ได้ยืนยันว่าโค้ดถูก แต่ยืนยันว่าโค้ดทำเหมือนเดิม ซึ่งเป็นสิ่งที่คุณต้องการจริง ๆ ก่อนแตะของที่ไม่เข้าใจ

// ขั้นตอน — และใช่ ข้อ 3 คือการล็อกพฤติกรรมที่รู้ว่าผิดไว้ โดยตั้งใจ
1. เรียกโค้ดเดิมด้วยอินพุตหลากหลาย
2. บันทึกผลที่ได้จริง ไม่ใช่ผลที่ควรจะเป็น
3. เขียนเทสต์ที่ยืนยันผลนั้น พร้อมคอมเมนต์ว่ายังไม่ได้ตรวจว่าถูกไหม
4. ทีนี้ค่อยแก้ — ถ้าเทสต์แดง แปลว่าคุณเปลี่ยนพฤติกรรม ซึ่งอาจตั้งใจหรือไม่ก็ได้
ข้อควรระวัง

อย่าลืมคอมเมนต์ในข้อ 3 ไม่งั้นอีกหกเดือนจะมีคนเห็นเทสต์นี้แล้วคิดว่าพฤติกรรมนี้คือสิ่งที่ตั้งใจ แล้วสร้างของทับลงไป เทสต์ที่ล็อกบั๊กไว้โดยไม่มีป้ายบอก คือกับดักที่คุณวางให้ตัวเองในอนาคต

08.03

Strangler pattern ร่วมกับ agent

แทนที่จะเขียนใหม่ทั้งก้อนแล้วสลับทีเดียว ให้สร้างของใหม่ข้าง ๆ ของเก่า แล้วย้ายทราฟฟิกทีละส่วน วิธีนี้เข้ากับ agent ได้ดีเป็นพิเศษเพราะแต่ละก้าวเล็กพอที่จะตรวจได้

ขั้นagent ทำได้แค่ไหนคนต้องทำอะไร
สร้างชั้นห่อของเก่าทำได้เองตรวจว่าครอบคลุมทุกทางเข้า
เขียน implementation ใหม่ทำได้เองรีวิวตามปกติ
รันคู่กันแล้วเทียบผลทำได้เองตัดสินว่าผลต่างที่เจอรับได้ไหม
ย้ายทราฟฟิกไม่ควรตัดสินใจและกดเอง
ลบของเก่าทำได้เมื่อไม่มีทราฟฟิกแล้วยืนยันว่าเงียบจริง
08.04

ทำงานกับโค้ดที่ไม่มีเทสต์และไม่มี type

ลำดับสร้างตาข่ายที่ให้ผลเร็วที่สุดต่อความพยายาม — ทำตามลำดับ อย่ากระโดด

  1. ทำให้รันได้ก่อน — ถ้ายังตั้งโปรเจกต์ขึ้นไม่ได้ ทุกอย่างหลังจากนี้ไม่มีความหมาย
  2. เทสต์ที่ครอบเส้นทางหลักหนึ่งเส้น — ไม่ต้องครบ ขอให้มีสัญญาณ
  3. เปิดการตรวจ type แบบหลวมก่อน แล้วค่อยเข้มขึ้นเป็นโฟลเดอร์ ๆ
  4. characterization test เฉพาะบริเวณที่จะแตะ
  5. ค่อยเริ่มแก้
ข้อผิดพลาดที่พบบ่อย

พยายามเปิด type เข้มทั้งโปรเจกต์ในครั้งเดียว ได้ error หลายพันข้อ แล้วเลิก ให้เปิดเป็นโฟลเดอร์และเฉพาะที่กำลังจะแตะ — agent ทำงานได้ดีกับขอบเขตแบบนี้ และคุณเห็นความคืบหน้าจริง

08.05

อ่านประวัติเป็นบริบท

ใน codebase ที่ไม่มีเอกสาร ประวัติการเปลี่ยนแปลงคือเอกสารที่ดีที่สุดที่มี และเป็นแหล่งที่ agent เข้าถึงได้ดี

คำถามหาจากไหนบอกอะไร
โค้ดนี้ทำไมเขียนแบบนี้ประวัติของบรรทัดนั้นมักเจอว่าแก้ตาม incident
ตรงนี้แตะแล้วเสี่ยงไหมความถี่การแก้ + จำนวนคนที่แตะไฟล์ที่แก้บ่อยคือไฟล์ที่เปราะ
เคยลองแล้วล้มเหลวไหมคอมมิตที่ถูกย้อนกันไม่ให้ทำผิดซ้ำ
สัญญาณที่ใช้ได้จริง

ไฟล์ที่แก้บ่อยและมีคนแตะหลายคน คือจุดที่ควรลงทุนทำเทสต์ก่อนที่อื่น เพราะมันคือจุดที่ความเสียหายจะเกิดถี่ที่สุด สั่งให้ agent จัดอันดับให้ได้ในคำสั่งเดียว

08.06

แก้อย่างปลอดภัย — blast radius

ก่อนแตะทุกครั้ง ต้องตอบสามคำถามให้ได้ ถ้าตอบไม่ได้ แปลว่ายังไม่พร้อมแก้

  1. ถ้าพัง ใครเจอ และเจอเมื่อไหร่ — ผู้ใช้ทันที หรืองานกลางคืนสัปดาห์หน้า
  2. รู้ได้ยังไงว่าพัง — มีสัญญาณเตือนไหม หรือรอลูกค้าโทรมา
  3. ย้อนกลับยังไง และใช้เวลานานแค่ไหน
กฎที่ควรบังคับ

ถ้าตอบข้อสามไม่ได้ ห้ามแก้ ให้ไปทำแผนย้อนกลับก่อน — และถ้ามันย้อนไม่ได้จริง ๆ (เช่นงานที่แตะข้อมูล) ให้ใช้ feature flag เพื่อทำให้มันย้อนได้ นี่คือเหตุผลที่ flag มีค่ามากกว่าที่คนคิด

08.07 · แล็บประจำโมดูล

เพิ่มฟีเจอร์ใน repo โอเพนซอร์สจริงที่ไม่เคยเห็นมาก่อน

เลือก repo ที่มีอายุอย่างน้อยสองปี มีคอมมิตหลายพัน และคุณไม่เคยอ่านมาก่อน จำกัดเวลาสามชั่วโมง

ลำดับที่ต้องทำ

  1. ทำแผนที่ตามบท 08.01 ก่อนแตะโค้ดใด ๆ — เขียนลงไฟล์
  2. ตั้งโปรเจกต์ให้รันและรันเทสต์ได้
  3. เลือก issue จริงจาก repo นั้น ขนาดเล็ก
  4. เขียน characterization test รอบบริเวณที่จะแตะ
  5. แก้ พร้อมตอบสามคำถาม blast radius เป็นลายลักษณ์อักษร
เกณฑ์ผ่าน
  • เทสต์เดิมทั้งหมดยังเขียว — ข้อนี้สำคัญกว่าฟีเจอร์เสร็จ
  • มีเอกสารแผนที่ที่คนอื่นอ่านแล้วเข้าใจโครงได้
  • ตอบได้ว่าถ้าการแก้นี้ผิด จะรู้ได้ยังไงและย้อนยังไง
  • ทำไม่เสร็จก็ผ่านได้ ถ้าสามข้อบนครบ — เพราะจุดประสงค์คือฝึกวิธีเข้าหา ไม่ใช่วัดความเร็ว
สิ่งที่คนทำผิดในแล็บนี้

ข้ามข้อ 1 แล้วสั่งแก้เลย ซึ่งได้ผลบ้างในโปรเจกต์เล็ก แต่พอเจอของจริง agent จะแก้ผิดที่แล้วมั่นใจ เพราะมันเห็นไฟล์ที่ชื่อคล้ายกันสามไฟล์และเลือกผิด

เชื่อมกับโมดูลอื่น — M05 เทคนิคเดียวกันแต่กับ repo ที่คุณคุมได้ · M11.03 เทสต์ในฐานะ spec · M12.02 งานจาก brownfield คือวัตถุดิบที่ดีที่สุดของชุดวัด · M14.07 แผนย้อนกลับ
