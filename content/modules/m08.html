AI Coding Agent SDLC · Phase 02 · Module 08

Brownfield และ Legacy Code

แล็บที่เริ่มจากโฟลเดอร์ว่างสอนงานที่แทบไม่มีใครทำจริง งานจริงคือ codebase อายุหกปี ไม่มีเทสต์ ไม่มี type และคนเขียนลาออกไปแล้ว โมดูลนี้คือส่วนที่คุณจะใช้บ่อยที่สุด

7 บทเรียน2.5 ชั่วโมง1 แล็บต้องผ่าน M05 ก่อน
ใจความของทั้งโมดูล

ใน greenfield ความเสี่ยงคือทำไม่เสร็จ ใน brownfield ความเสี่ยงคือทำของที่เคยใช้ได้ให้พัง กลยุทธ์ทั้งหมดจึงกลับด้าน — สร้างตาข่ายก่อน แล้วค่อยขยับ

08.01

สร้างแผนที่ก่อน อย่าเพิ่งแก้

โมดูลนี้ผมว่าคุณจะใช้บ่อยที่สุดในหลักสูตร เพราะงานจริงไม่ได้เริ่มจากโฟลเดอร์ว่าง มันเริ่มจาก repo อายุหกปี ไม่มีเทสต์ ไม่มี type คนเขียนลาออกไปแล้ว

และกติกาจะกลับด้านจาก greenfield — ตรงนั้นความเสี่ยงคือทำไม่เสร็จ ตรงนี้ความเสี่ยงคือทำของที่เคยใช้ได้ให้พัง

Figure 1 · แผนที่ที่ได้ให้เขียนลงไฟล์ในโปรเจกต์ — มันจะกลายเป็นบริบทถาวรตาม M05.06

อย่าทิ้งผลลัพธ์

คนส่วนใหญ่ให้ agent สำรวจ อ่านคำตอบ แล้วปิด session ไป — ครั้งหน้าก็เสียเงินสำรวจซ้ำ

เขียนลงไฟล์แล้ว commit ทันที มันเป็นเอกสารที่ทั้งคนใหม่และ agent ตัวถัดไปใช้ต่อได้ และเป็นตัวอย่างที่ตรงที่สุดของ docs-as-context

อ่านเพิ่มจากต้นทาง

  1. Key points of Working Effectively with Legacy Code — สรุปแนวคิดหลักของการเข้าหาโค้ดเก่าอย่างเป็นระบบ understandlegacycode.com
  2. Common workflows — วิธีสั่งให้ agent สำรวจ codebase อย่างมีโครง docs.claude.com
08.02

Characterization test

เทสต์ชนิดนี้แปลกตรงที่มันไม่ได้ยืนยันว่าโค้ดถูก แต่ยืนยันว่าโค้ดทำเหมือนเดิม

ฟังดูไร้สาระ แต่มันคือสิ่งที่เราต้องการจริง ๆ ก่อนแตะของที่ไม่เข้าใจ — เพราะเราไม่รู้ว่าพฤติกรรมไหนตั้งใจ พฤติกรรมไหนเป็นบั๊กที่มีคนพึ่งพาอยู่แล้ว

Figure 2 · STEP 2 คือจุดที่คนมักทำผิด — บันทึกผลที่ ได้จริง ไม่ใช่ผลที่ ควรจะเป็น

โยงกับ M04.09

Kiro บังคับให้ bugfix spec ระบุช่อง "อะไรห้ามเปลี่ยน" เขียนเป็นเงื่อนไข เมื่อ X ระบบต้องยังคง Y

นั่นคือ characterization test ในรูปแบบเอกสาร — แปลงช่องนั้นเป็นเทสต์ตรง ๆ ได้เลย และถ้าคุณไม่ได้ใช้ Kiro ก็เพิ่มหัวข้อนี้ในเทมเพลตของตัวเองได้

อ่านเพิ่มจากต้นทาง

  1. Legacy Seam — จุดที่แทรกเข้าไปทดสอบได้โดยไม่ต้องรื้อโครง martinfowler.com
  2. Key points of Working Effectively with Legacy Code — ที่มาของแนวคิด characterization test understandlegacycode.com
08.03

Strangler pattern ร่วมกับ agent

แทนที่จะเขียนใหม่ทั้งก้อนแล้วสลับทีเดียว ให้สร้างของใหม่ข้าง ๆ ของเก่า แล้วย้ายทราฟฟิกทีละส่วน วิธีนี้เข้ากับ agent ได้ดีเป็นพิเศษ เพราะแต่ละก้าวเล็กพอที่จะตรวจได้

Figure 3 · agent ทำได้ 4 จาก 5 ขั้น · ขั้นที่เหลือคือขั้นที่ผิดแล้วผู้ใช้เจอทันที

ขั้นที่ 3 คือของฟรีที่คนมักข้าม

การรันของเก่ากับของใหม่คู่กันแล้วเทียบผล เป็นงานที่ agent ทำได้ดีมาก เพราะมันเป็นงานกลไกล้วน ๆ — ยิง input เดียวกันเข้าสองทาง แล้วรายงานว่าต่างตรงไหน

และมันให้ข้อมูลที่หาจากที่อื่นไม่ได้ — พฤติกรรมจริงของระบบเก่าที่ไม่มีใครเขียนไว้ หลายทีมพบว่าผลต่างที่เจอคือบั๊กของของเก่า ที่ไม่มีใครรู้มาก่อน

อ่านเพิ่มจากต้นทาง

  1. Strangler Fig Application — ต้นฉบับของรูปแบบนี้ พร้อมเหตุผลว่าทำไมการเขียนใหม่ทีเดียวถึงล้มเหลวบ่อย martinfowler.com
  2. Feature Toggle — กลไกย้ายทราฟฟิกทีละส่วนและย้อนกลับได้ทันที martinfowler.com
08.04

ทำงานกับโค้ดที่ไม่มีเทสต์และไม่มี type

สถานการณ์คลาสสิก — อยากเพิ่มเทสต์ แต่โค้ดเทสต์ไม่ได้ อยากเปิด type แต่ได้ error สี่พันข้อ แล้วก็เลยไม่ได้ทำอะไรเลย

ทางออกคือลำดับ ไม่ใช่ความพยายาม — ทำผิดลำดับแล้วจะติดตั้งแต่ก้าวแรก

Figure 4 · ลำดับนี้ให้ผลเร็วที่สุดต่อความพยายาม · agent ทำงานได้ดีกับขอบเขตแบบทีละโฟลเดอร์

อ่านเพิ่มจากต้นทาง

  1. Legacy Seam — หาจุดแทรกเพื่อทดสอบโดยไม่ต้องรื้อทั้งก้อน martinfowler.com
  2. Test Pyramid — เลือกว่าจะลงทุนเทสต์ชั้นไหนก่อนเมื่อมีเวลาจำกัด martinfowler.com
08.05

อ่านประวัติเป็นบริบท

ใน repo ที่ไม่มีเอกสาร ประวัติการเปลี่ยนแปลงคือเอกสารที่ดีที่สุดที่มี และเป็นแหล่งที่ agent เข้าถึงได้ดีมาก เพราะมันเป็นข้อความล้วน ๆ ที่ค้นได้

Figure 5 · สั่งให้ agent จัดอันดับไฟล์ตามสองสัญญาณนี้ได้ในคำสั่งเดียว

อ่านเพิ่มจากต้นทาง

  1. Code Smell — การอ่านสัญญาณจากโค้ดและประวัติของมัน martinfowler.com
  2. Common workflows — การให้ agent ใช้ประวัติเป็นแหล่งข้อมูลระหว่างสำรวจ docs.claude.com
08.06

แก้อย่างปลอดภัย — blast radius

Figure 6 · Q3 คือคำถามที่ตอบไม่ได้บ่อยที่สุด และเป็นคำถามที่สำคัญที่สุด

กฎที่ควรบังคับ

ตอบ Q3 ไม่ได้ ห้ามแก้ ให้ไปทำแผนย้อนกลับก่อน

และถ้ามันย้อนไม่ได้จริง ๆ เช่นงานที่แตะข้อมูล ให้ใช้ feature flag ทำให้มันย้อนได้ แทนที่จะยอมรับความเสี่ยงเฉย ๆ — ต่อกับรูปแบบ expand–migrate–contract ใน M07.03

อ่านเพิ่มจากต้นทาง

  2. Blue Green Deployment — อีกกลไกที่ทำให้การย้อนกลับเร็วพอจะใช้จริง martinfowler.com
08.07 · แล็บประจำโมดูล

เพิ่มฟีเจอร์ใน repo โอเพนซอร์สจริงที่ไม่เคยเห็นมาก่อน

เลือก repo ที่มีอายุอย่างน้อยสองปี มีคอมมิตหลายพัน และคุณไม่เคยอ่านมาก่อน จำกัดเวลาสามชั่วโมง

ลำดับที่ต้องทำ

  1. ทำแผนที่ตามบท 08.01 ก่อนแตะโค้ดใด ๆ — เขียนลงไฟล์
  2. ตั้งโปรเจกต์ให้รันและรันเทสต์ได้
  3. เลือก issue จริงจาก repo นั้น ขนาดเล็ก
  4. เขียน characterization test รอบบริเวณที่จะแตะ
  5. แก้ พร้อมตอบสามคำถาม blast radius เป็นลายลักษณ์อักษร
เกณฑ์ผ่าน
  • เทสต์เดิมทั้งหมดยังเขียว — ข้อนี้สำคัญกว่าฟีเจอร์เสร็จ
  • มีเอกสารแผนที่ที่คนอื่นอ่านแล้วเข้าใจโครงได้
  • ตอบได้ว่าถ้าการแก้นี้ผิด จะรู้ได้ยังไงและย้อนยังไง
  • ทำไม่เสร็จก็ผ่านได้ ถ้าสามข้อบนครบ — เพราะจุดประสงค์คือฝึกวิธีเข้าหา ไม่ใช่วัดความเร็ว
สิ่งที่คนทำผิดในแล็บนี้

ข้ามข้อ 1 แล้วสั่งแก้เลย ซึ่งได้ผลบ้างในโปรเจกต์เล็ก แต่พอเจอของจริง agent จะแก้ผิดที่แล้วมั่นใจ เพราะมันเห็นไฟล์ที่ชื่อคล้ายกันสามไฟล์และเลือกผิด
