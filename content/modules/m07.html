AI Coding Agent SDLC · Phase 02 · Module 07

Backend และงานที่แตะข้อมูล

ฝั่งหลังบ้านมีงานที่ผิดแล้วย้อนไม่ได้ ซึ่งเปลี่ยนกติกาทั้งหมด โมดูลนี้ว่าด้วยการวาง guardrail ก่อนปล่อยให้ agent แตะของที่แตะแล้วเสียหายถาวร

9 บทเรียน3 ชั่วโมง2 แล็บต้องผ่าน M04 · M05 ก่อน
ใจความของทั้งโมดูล

เกณฑ์ข้อที่สี่จาก M04.03 — “ผิดแล้วจับได้และย้อนกลับได้ไหม” — เป็นเกณฑ์ที่งาน backend หลายอย่างสอบตก และนั่นคือเส้นแบ่งว่าอะไรมอบให้ agent ทำเองได้ อะไรต้องมีคนอยู่ด้วย

07.01

Contract-first

สัญญา API ที่เขียนเป็นสคีมาให้ประโยชน์สามชั้นพร้อมกัน — เป็น spec ให้ agent เป็นเกณฑ์ตรวจอัตโนมัติ และเป็นเอกสารที่ไม่มีวันล้าสมัย เพราะถ้าล้าสมัยแล้วเทสต์จะแดง

ลำดับที่ให้ผลดีที่สุด

เขียนสัญญาก่อน → ให้ agent สร้าง type จากสัญญา → ให้เขียน implementation ที่ผ่านสัญญา ลำดับนี้ทำให้ความถูกต้องถูกตรวจโดยเครื่องตลอดทาง แทนที่จะต้องรอคนอ่าน

07.02

Layering ที่ agent ทำงานด้วยง่าย

ลักษณะagent ทำงานด้วยง่ายagent หลงทาง
ทางเข้าโค้ดทางเดียวชัดเจนเข้าได้หลายทาง ผ่าน re-export ซ้อน
ผลข้างเคียงรวมอยู่ชั้นเดียวกระจายทุกชั้น
การตั้งค่าอ่านที่เดียวตอนเริ่มอ่าน env กระจายทั่วโค้ด
ขอบเขตธุรกรรมระบุชัดว่าเริ่มและจบที่ไหนซ่อนอยู่ใน decorator หรือ middleware

สังเกตว่าทุกข้อในคอลัมน์ขวาก็ทำให้คนหลงทางเหมือนกัน โครงสร้างที่ดีสำหรับ agent มักคือโครงสร้างที่ดีอยู่แล้ว แค่ agent ไม่มีความอดทนและความคุ้นเคยมาชดเชยให้

07.03

Database migration — งานอันตรายที่สุดในหลักสูตร

Migration ต่างจากงานอื่นตรงที่มันทำลายข้อมูลได้ถาวร และเทสต์ที่เขียวไม่ได้แปลว่าปลอดภัย เพราะเทสต์รันบนฐานข้อมูลว่างที่ไม่มีข้อมูลจริง

รูปแบบที่อันตรายที่สุดสามอย่าง
  • ลบหรือเปลี่ยนชนิดคอลัมน์ในขั้นเดียว — โค้ดเก่าที่ยังรันอยู่จะพังทันที
  • เพิ่มคอลัมน์ NOT NULL โดยไม่มีค่าเริ่มต้น — ล็อกตารางและล้มบนข้อมูลจริง
  • Backfill ในไฟล์ migration เดียวกัน — ตารางใหญ่จะล็อกนานจนระบบล่ม
Guardrail ที่ต้องมีก่อนให้ agent แตะ migration
  1. บังคับรูปแบบขยาย–ย้าย–หด — เพิ่มของใหม่ ย้ายข้อมูล แล้วค่อยลบของเก่าคนละรอบ deploy
  2. ทุก migration ต้องมีทางย้อน และทางย้อนต้องถูกทดสอบ ไม่ใช่แค่มีอยู่
  3. รันกับสำเนาข้อมูลจริงขนาดใกล้เคียง ก่อนขึ้นเสมอ
  4. คนอนุมัติทุกครั้ง — งานนี้ตกเกณฑ์ข้อสี่ ไม่ควรอยู่ในกลุ่มที่ agent ทำจบเอง
07.04

Idempotency ขอบเขตธุรกรรม และ error taxonomy

สามเรื่องนี้อยู่ด้วยกันเพราะมันตอบคำถามเดียวกัน — เมื่อเกิดข้อผิดพลาดกลางทาง ระบบอยู่ในสภาพไหน ซึ่งเป็นคำถามที่ agent ตอบผิดบ่อยเพราะมันมองเห็นแค่เส้นทางที่สำเร็จ

ชนิดข้อผิดพลาดควรลองใหม่ไหมสิ่งที่ agent มักทำผิด
ข้อมูลนำเข้าไม่ถูกต้องไม่ — ลองกี่ครั้งก็ผิดใส่ retry ให้ทุกอย่างเหมือนกันหมด
ไม่มีสิทธิ์ไม่ลองใหม่จนโดนบล็อก
ปลายทางล่มชั่วคราวใช่ พร้อมหน่วงเพิ่มขึ้นลองรัว ๆ จนซ้ำเติมปลายทาง
ชนกันเพราะแก้พร้อมกันใช่ หลังอ่านค่าใหม่เขียนทับของคนอื่น

ถ้า error ในโปรเจกต์ของคุณแยกชนิดไม่ได้ agent จะเลือกกลยุทธ์ไม่ถูก การจัดชนิด error ให้ชัดจึงเป็นงาน M05 ที่ให้ผลตรงกับโมดูลนี้

07.05

Secret และ env — กฎที่ห้ามยืดหยุ่น

  • ห้ามให้ไฟล์ที่มีค่าจริงเข้าไปในบริบท — เมื่อเข้าไปแล้ว มันอยู่ในประวัติการสนทนาและย้อนไม่ได้
  • ใช้ไฟล์ตัวอย่างที่มีแต่ชื่อคีย์ ให้ agent อ่านจากตัวนั้น
  • ตั้ง deny rule ที่ระดับ hook ไม่ใช่แค่เขียนเป็นกฎใน prompt — กฎที่บังคับได้ชนะกฎที่ขอไว้
  • ถ้าหลุดแล้ว ให้ถือว่ารั่ว และหมุนคีย์ ไม่ใช่หวังว่าไม่มีใครเห็น
ทำไมถึงย้อนไม่ได้

บริบทถูกส่งไปประมวลผลแล้ว และอาจถูกเก็บใน log ของ harness ใน transcript หรือใน cache การลบข้อความออกจากหน้าจอไม่ได้ลบสิ่งที่ส่งไปแล้ว — รายละเอียดเต็มใน M13.06

07.06

Background job, queue และ retry

สามอย่างนี้ agent ออกแบบผิดเป็นประจำ เพราะรูปแบบที่ดูถูกต้องในโค้ดกลับผิดในสภาพจริงที่มีความล้มเหลว

สิ่งที่มักได้ปัญหาจริงสิ่งที่ควรได้
retry สามครั้งติดซ้ำเติมปลายทางที่กำลังล่มหน่วงเพิ่มขึ้นพร้อมสุ่ม + เพดาน
งานไม่ idempotentรันซ้ำแล้วเกิดผลซ้ำคีย์กันซ้ำต่อหนึ่งงาน
ไม่มีที่เก็บงานที่ล้มถาวรงานหายเงียบคิวสำหรับงานที่ล้ม + การแจ้งเตือน
ไม่มีเพดานเวลางานค้างกินทรัพยากรตลอดไปtimeout ที่ชัดเจนทุกงาน
07.07

Observability ตั้งแต่บรรทัดแรก

เหตุผลที่เรื่องนี้อยู่ในโมดูล implementation ไม่ใช่โมดูล operations เพราะ log คือสิ่งที่ agent ใช้ debug ตัวเองในรอบหน้า การเขียน log ที่ดีจึงเป็นการลงทุนในความสามารถของ agent โดยตรง

  • ทุก request มีรหัสที่ตามได้ตลอดเส้นทาง
  • log เป็นโครงสร้าง ไม่ใช่ประโยคที่ต้องใช้ regex แกะ
  • ตอนล้มเหลว ให้ log ค่าที่นำเข้ามาด้วย ไม่ใช่แค่ชื่อ error
  • อย่า log ค่าที่เป็นความลับ — ข้อนี้ต้องบังคับด้วยเครื่องมือ ไม่ใช่ด้วยความระวัง
07.08 · แล็บ A

สร้าง API จากสัญญา พร้อม migration ที่มีทางย้อน

  1. เขียนสัญญา API สำหรับทรัพยากรหนึ่งตัว ครบทั้ง success และ error
  2. ให้ agent สร้าง implementation ที่ผ่านการตรวจสัญญาอัตโนมัติ
  3. เพิ่มฟิลด์ใหม่โดยใช้รูปแบบ ขยาย–ย้าย–หด แยกเป็นสาม migration
  4. ทดสอบทางย้อนของทุก migration บนฐานที่มีข้อมูล ไม่ใช่ฐานว่าง
เกณฑ์ผ่าน
  • รัน migration ไปหน้าแล้วย้อนกลับ ข้อมูลเดิมต้องครบ
  • ระหว่างขั้นกลาง โค้ดเวอร์ชันเก่าต้องยังทำงานได้
07.09 · แล็บ B

ให้ agent หาบั๊กจากบันทึกอย่างเดียว

ปลูกบั๊กไว้หนึ่งตัว แล้วส่งให้ agent เฉพาะ log กับ trace ห้ามบอกว่าพังตรงไหน นี่คือการทดสอบคุณภาพ observability ของคุณ ไม่ใช่ทดสอบ agent

อ่านผลยังไง

ถ้า agent หาไม่เจอ อย่าเพิ่งสรุปว่าโมเดลไม่เก่ง ให้ถามก่อนว่าคนจะหาเจอไหมถ้ามีแค่ log ชุดนี้ ถ้าคนก็หาไม่เจอ ปัญหาอยู่ที่ log ไม่ใช่ที่ agent และคุณเพิ่งพบสิ่งที่ต้องแก้

เชื่อมกับโมดูลอื่น — M04.03 เกณฑ์ตัดสินว่างานไหนมอบให้ agent ได้ · M05.03 error taxonomy คือ error message ที่ดีในอีกรูปแบบ · M13.06 การจัดการ secret เชิงลึก · M15.02 log ชุดเดียวกันนี้ใช้ตอน incident
