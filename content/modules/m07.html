07.01

Contract-first

ฝั่ง BE มีงานที่ผิดแล้วย้อนไม่ได้ ซึ่งเปลี่ยนกติกาทั้งหมด งาน FE ผิดก็แก้ CSS ใหม่ แต่ migration ที่ลบคอลัมน์ผิดคือข้อมูลหายจริง

เพราะงั้นโมดูลนี้จะพูดเรื่อง guardrail เยอะกว่าเรื่องความเร็ว และเริ่มจากของที่ถูกที่สุด — สัญญา

07.03

Database migration — งานอันตรายที่สุดในหลักสูตร

บทนี้ผมอยากให้อ่านช้าที่สุดในโมดูล เพราะ migration ต่างจากงานอื่นตรงที่ มันทำลายข้อมูลได้ถาวร และเทสต์เขียวไม่ได้แปลว่าปลอดภัย

เหตุผลง่ายมาก — เทสต์รันบนฐานว่างที่ไม่มีข้อมูลจริง ไม่มีตารางขนาด 40 ล้านแถว และไม่มีโค้ดเวอร์ชันเก่าที่ยังรันอยู่พร้อมกัน

Figure 3 · แต่ละกล่องคือคนละ deploy — ไม่ใช่คนละบรรทัดในไฟล์เดียวกัน

Guardrail ที่ต้องมีก่อนให้ agent แตะ migration
  1. บังคับรูปแบบ expand–migrate–contract — เขียนเป็นกฎใน project memory และตรวจใน review
  2. ทุก migration ต้องมีทางย้อน และทางย้อนต้องถูกทดสอบ ไม่ใช่แค่มีอยู่
  3. รันกับสำเนาข้อมูลจริงขนาดใกล้เคียงก่อนขึ้นเสมอ — ฐานว่างไม่บอกอะไรเลยเรื่องเวลาล็อก
  4. คนอนุมัติทุกครั้ง — งานนี้ตกเกณฑ์ข้อสี่ของ M04.03 ไม่ควรอยู่ในกลุ่มที่ agent จบเอง

อ่านเพิ่มจากต้นทาง

  2. Blue Green Deployment — บริบทว่าทำไมโค้ดสองเวอร์ชันถึงรันพร้อมกันระหว่าง deploy martinfowler.com
07.04

Idempotency ขอบเขต transaction และ error taxonomy

สามเรื่องนี้อยู่ด้วยกันเพราะตอบคำถามเดียวกัน — เมื่อพังกลางทาง ระบบอยู่ในสภาพไหน ซึ่งเป็นคำถามที่ agent ตอบผิดบ่อย เพราะมันมองเห็นแต่เส้นทางที่สำเร็จ

Figure 4 · การจัดชนิด error ไม่ใช่เรื่องความสวยงาม แต่เป็นข้อมูลที่ใช้ตัดสินใจ

Idempotency คือสิ่งที่ทำให้ retry ปลอดภัย

retry จะปลอดภัยก็ต่อเมื่อการทำซ้ำไม่สร้างผลซ้ำ — ถ้าไม่มีคีย์กันซ้ำ การใส่ retry เข้าไปคือการเปลี่ยนจาก "ล้มเหลวหนึ่งครั้ง" เป็น "เก็บเงินลูกค้าสามครั้ง"

เพราะงั้นลำดับที่ถูกคือ ทำให้ idempotent ก่อน แล้วค่อยใส่ retry ไม่ใช่กลับกัน

อ่านเพิ่มจากต้นทาง

  1. Idempotent Receiver — รูปแบบการกันผลซ้ำเมื่อข้อความถูกส่งมามากกว่าหนึ่งครั้ง martinfowler.com
  2. The Twelve-Factor App — Disposability — การออกแบบให้โปรเซสถูกฆ่ากลางทางได้โดยไม่ทิ้งสภาพค้าง 12factor.net
07.05

Secret และ env — กฎที่ห้ามยืดหยุ่น

เรื่องนี้ผมเขียนเป็นกฎแข็ง ๆ ไม่มี "แล้วแต่กรณี" เพราะพอค่าลับเข้า context แล้ว มันเข้าไปแล้วจริง ๆ

มันอยู่ในสิ่งที่ส่งไปประมวลผล อาจอยู่ใน log ของ harness อยู่ใน transcript และอาจอยู่ใน cache — การลบข้อความบนหน้าจอไม่ได้ลบสิ่งที่ส่งไปแล้ว

Figure 5 · ทุกวิธีกันในคอลัมน์ขวาเป็นกลไก ไม่ใช่ความระมัดระวัง — เพราะความระมัดระวังมีวันพลาด

ต้นทุนการหมุนคีย์ต่ำมากเมื่อเทียบกับต้นทุนของการเดาผิด เพราะงั้นเวลาไม่แน่ใจ ให้หมุน รายละเอียดเชิงภัยคุกคามเต็มรูปแบบอยู่ใน M13.06

อ่านเพิ่มจากต้นทาง

  1. The Twelve-Factor App — Config — แยกการตั้งค่าออกจากโค้ด ซึ่งเป็นเงื่อนไขของทุกข้อในตาราง 12factor.net
  2. Hooks — กลไกบล็อกการอ่านไฟล์และคำสั่งที่ไม่ควรรัน docs.claude.com
  3. Identity and access management — การเขียน allow/deny rule ให้ครอบคำสั่งกลุ่มที่เสี่ยง docs.claude.com
07.06

Background job, queue และ retry

สามอย่างนี้ agent ออกแบบผิดเป็นประจำ เพราะรูปแบบที่ดูถูกต้องในโค้ด กลับผิดในสภาพจริงที่มีความล้มเหลว

Figure 6 · retry ที่ไม่มี backoff เปลี่ยนปัญหาชั่วคราวให้กลายเป็นปัญหาถาวร

ลำดับที่ห้ามสลับ

ทำให้ idempotent → ใส่ backoff → ค่อยเปิด retry

ถ้าเปิด retry ก่อนสองข้อแรก คุณไม่ได้เพิ่มความทนทาน คุณเพิ่มจำนวนครั้งที่ผลข้างเคียงเกิดซ้ำ และเพิ่มภาระให้ปลายทางที่กำลังมีปัญหาอยู่แล้ว

อ่านเพิ่มจากต้นทาง

  1. Idempotent Receiver — เงื่อนไขที่ทำให้ retry ปลอดภัย martinfowler.com
  2. Circuit Breaker — กลไกหยุดยิงเมื่อปลายทางล่ม แทนการ retry ไปเรื่อย ๆ martinfowler.com
07.07

Observability ตั้งแต่บรรทัดแรก

เหตุผลที่เรื่องนี้อยู่ในโมดูล implementation ไม่ใช่โมดูล operations — log คือสิ่งที่ agent ใช้ debug ตัวเองในรอบหน้า

การเขียน log ที่ดีจึงไม่ใช่งานฝั่ง ops แต่เป็นการลงทุนในความสามารถของ agent โดยตรง เหมือนกับ error message ใน M05.03

Figure 7 · แล็บ B ของโมดูลนี้คือการทดสอบว่า log ของคุณอยู่ฝั่งไหนของรูปนี้

วิธีอ่านผลแล็บ B ให้ถูก

ถ้า agent หาบั๊กจาก log ไม่เจอ อย่าเพิ่งสรุปว่าโมเดลไม่เก่ง ให้ถามก่อนว่า "คนจะหาเจอไหมถ้ามีแค่ log ชุดนี้"

ถ้าคนก็หาไม่เจอ ปัญหาอยู่ที่ log ไม่ใช่ที่ agent — และคุณเพิ่งพบสิ่งที่ต้องแก้ ซึ่งจะช่วยทั้งทีมตอนเกิด incident จริงด้วย ไม่ใช่แค่ช่วย agent

อ่านเพิ่มจากต้นทาง

  1. The Twelve-Factor App — Logs — log ในฐานะ event stream ที่เครื่องอ่านต่อได้ 12factor.net
  2. OpenTelemetry — Observability Primer — คำศัพท์พื้นฐานเรื่อง trace, span และการตามรอยข้ามบริการ opentelemetry.io
07.08 · แล็บ A

สร้าง API จากสัญญา พร้อม migration ที่มีทางย้อน

  1. เขียนสัญญา API สำหรับทรัพยากรหนึ่งตัว ครบทั้ง success และ error
  2. ให้ agent สร้าง implementation ที่ผ่านการตรวจสัญญาอัตโนมัติ
  3. เพิ่มฟิลด์ใหม่โดยใช้รูปแบบ ขยาย–ย้าย–หด แยกเป็นสาม migration
  4. ทดสอบทางย้อนของทุก migration บนฐานที่มีข้อมูล ไม่ใช่ฐานว่าง
เกณฑ์ผ่าน
  • รัน migration ไปหน้าแล้วย้อนกลับ ข้อมูลเดิมต้องครบ
  • ระหว่างขั้นกลาง โค้ดเวอร์ชันเก่าต้องยังทำงานได้
07.09 · แล็บ B

ให้ agent หาบั๊กจากบันทึกอย่างเดียว

ปลูกบั๊กไว้หนึ่งตัว แล้วส่งให้ agent เฉพาะ log กับ trace ห้ามบอกว่าพังตรงไหน นี่คือการทดสอบคุณภาพ observability ของคุณ ไม่ใช่ทดสอบ agent

อ่านผลยังไง

ถ้า agent หาไม่เจอ อย่าเพิ่งสรุปว่าโมเดลไม่เก่ง ให้ถามก่อนว่าคนจะหาเจอไหมถ้ามีแค่ log ชุดนี้ ถ้าคนก็หาไม่เจอ ปัญหาอยู่ที่ log ไม่ใช่ที่ agent และคุณเพิ่งพบสิ่งที่ต้องแก้

เชื่อมกับโมดูลอื่น — M04.03 เกณฑ์ตัดสินว่างานไหนมอบให้ agent ได้ · M05.03 error taxonomy คือ error message ที่ดีในอีกรูปแบบ · M13.06 การจัดการ secret เชิงลึก · M15.02 log ชุดเดียวกันนี้ใช้ตอน incident
