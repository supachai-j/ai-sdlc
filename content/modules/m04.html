Prompt ที่ดีไม่ใช่คำสั่งที่เขียนเก่ง แต่คือข้อกำหนดที่ตรวจได้ ความต่างคือ คำสั่งบอกว่าให้ทำอะไร ข้อกำหนดบอกว่าจะรู้ได้ยังไงว่าทำถูก

04.01

Spec-first — คำสั่งกับข้อกำหนดต่างกันตรงไหน

คำแนะนำที่ได้ยินบ่อยที่สุดเวลาผลลัพธ์ไม่ดีคือ “เขียน prompt ให้ดีกว่านี้” ซึ่งไม่ผิดแต่ไม่ได้บอกอะไร เพราะไม่ได้นิยามว่า “ดี” คืออะไร นิยามที่ใช้ได้จริงมีข้อเดียว — prompt ที่ดีคือข้อกำหนดที่ตรวจได้ ไม่ใช่คำสั่งที่เขียนสละสลวย

คำสั่งข้อกำหนด
รูปแบบ“แก้บั๊กตรงหน้า checkout ให้หน่อย”“เมื่อตะกร้าว่าง ปุ่มชำระเงินต้อง disabled และเทสต์ checkout.empty ต้องเขียว”
รู้ว่าเสร็จเมื่อคนดูแล้วรู้สึกว่าใช่สคริปต์ตัดสินได้
เมื่อผิดต้องอธิบายใหม่ทั้งหมดชี้ได้ว่าข้อไหนไม่ผ่าน
ส่งต่อได้ไหมไม่ได้ ความรู้อยู่ในหัวคนสั่งได้ ใครหยิบไปทำต่อก็ได้
เอาไปวัดผลได้ไหมไม่ได้ได้ทันที

ทำไมความต่างนี้ถึงใหญ่กว่าที่ดู

เมื่อคุณสั่งด้วยคำสั่ง สิ่งที่เกิดขึ้นคือ agent ต้องเดาว่าคุณหมายถึงอะไร แล้วคุณต้องดูผลเพื่อบอกว่าเดาถูกหรือเปล่า วงจรนี้ต้องมีคุณอยู่ในลูปตลอด และแต่ละรอบใช้เวลาของคุณเต็ม ๆ

เมื่อคุณสั่งด้วยข้อกำหนด agent ตรวจงานตัวเองได้ก่อนส่งกลับมา วงจรกลายเป็นว่ามันวนแก้จนผ่านเกณฑ์แล้วค่อยเรียกคุณ คุณถูกย้ายจาก “คนตรวจทุกรอบ” ไปเป็น “คนตรวจรอบสุดท้าย” ซึ่งเป็นความต่างที่ใหญ่ที่สุดในหลักสูตรนี้เมื่อวัดเป็นเวลาที่ประหยัดได้

การทดสอบที่ใช้เวลาสิบวินาที

อ่าน prompt ที่คุณกำลังจะส่ง แล้วถามว่า “ถ้าผมไม่เห็นผลลัพธ์เลย ผมเขียนสคริปต์ตัดสินว่าผ่านหรือไม่ผ่านได้ไหม”

ถ้าตอบไม่ได้ แปลว่ายังเป็นคำสั่ง และคุณกำลังจะเสียเวลาไปกับการอธิบายซ้ำ การเสียเวลาสองนาทีเติมเกณฑ์ตอนนี้ ถูกกว่าการอธิบายซ้ำสามรอบเสมอ

ข้อกำหนดที่เขียนไม่ได้ ก็มีความหมาย

บางข้อคุณจะเขียนเกณฑ์ไม่ออกจริง ๆ เช่น “ให้ UI ดูสะอาดขึ้น” เมื่อเจอแบบนี้ อย่าฝืนแปลงเป็นเกณฑ์ปลอม ๆ ให้ยอมรับว่ามันเป็น คำถามที่ต้องถามคน แล้วแยกออกไปอีกกอง

กองนี้มีค่ามาก เพราะมันคือรายการของสิ่งที่คุณกำลังจะเดาแทนผู้ใช้โดยไม่รู้ตัว ถ้ากองนี้ว่างเปล่าทุกครั้งที่คุณย่อยงาน แสดงว่าคุณไม่ได้กำลังพบความกำกวม คุณกำลังกลบมันไว้

04.02

ขนาดงานที่พอดีกับ agent

งานที่ใหญ่เกินทำให้ agent ลอยจากแผน งานที่เล็กเกินทำให้คุณเสียเวลาสั่งมากกว่าลงมือทำเอง มีสามเกณฑ์ที่บอกว่าพอดี

  • ยืนยันผลได้ในรอบเดียว — มีคำสั่งหนึ่งบรรทัดที่บอกว่าสำเร็จหรือไม่
  • อยู่ในไฟล์ที่นับได้ — ถ้าต้องแตะเกินสิบไฟล์ ให้แตกก่อน
  • อธิบายได้ในสามประโยค — ถ้าต้องเขียนหน้าเต็มถึงจะสั่งได้ แปลว่ายังไม่ได้ย่อย
อาการของงานที่ใหญ่เกิน

agent เริ่มถูกทาง ทำได้ดีสามสี่ขั้น แล้วค่อย ๆ เบี่ยงไปทำอย่างอื่นที่ดูเกี่ยวข้อง สุดท้ายได้ diff ใหญ่ที่ทำหลายอย่างพร้อมกันและรีวิวไม่ได้ นี่ไม่ใช่ความผิดของโมเดล แต่คือสัญญาณว่างานไม่ได้ถูกย่อย

04.03

งานนี้ควรให้ agent ทำไหม

ไม่ใช่ทุกงานที่คุ้มจะมอบให้ agent ใช้สี่เกณฑ์นี้ตัดสิน ถ้าตอบ “ไม่” ข้อใดข้อหนึ่ง ให้ทำเองหรือลดขนาดงานลง

เกณฑ์คำถามถ้าตอบไม่
ความซับซ้อนเป็นงานหลายขั้นที่ระบุล่วงหน้าครบไม่ได้ไหมงานง่ายเกิน เขียนเองเร็วกว่า
คุณค่าผลลัพธ์คุ้มกับต้นทุนและเวลารอไหมไม่คุ้ม ทำเอง
ความเป็นไปได้โมเดลทำงานประเภทนี้ได้จริงไหมให้ช่วยบางส่วนแทนทั้งงาน
ต้นทุนเมื่อผิดผิดแล้วจับได้และย้อนกลับได้ไหมอย่ามอบให้ทำเอง — ต้องมีคนตรวจทุกขั้น

เกณฑ์ที่สี่คือเกณฑ์ที่คนมองข้ามบ่อยที่สุด งาน migration ฐานข้อมูลตกเกณฑ์นี้เกือบทุกครั้ง ซึ่งเป็นเหตุผลว่าทำไม M07 ถึงมีบทเฉพาะเรื่องนี้

04.04

Research loop — แยกสามขั้นออกจากกัน

ความผิดพลาดที่พบบ่อยคือสั่งรวบ “ไปหาข้อมูลแล้วตัดสินใจให้หน่อย” ซึ่งทำให้ได้ข้อสรุปที่ดูมั่นใจแต่ตรวจย้อนไม่ได้ ให้แยกเป็นสามขั้นที่มีผลลัพธ์คนละแบบ

ขั้นผลลัพธ์ที่ต้องได้ใครตัดสิน
ค้นหารายการแหล่งพร้อมลิงก์และวันที่agent
สรุปข้อเท็จจริงพร้อมที่มาต่อข้อagent
ตัดสินใจทางเลือกพร้อมข้อแลกเปลี่ยนคุณ
ทำไมการแยกถึงคุ้ม

เมื่อผลของขั้นสองมีที่มาต่อข้อ คุณตรวจได้ว่าข้อไหนมีหลักฐานจริง ข้อไหนเป็นการเติมเต็มของโมเดล การรวบสามขั้นทำให้สองอย่างนี้ปนกันจนแยกไม่ออก และคุณจะเชื่อทั้งก้อนหรือทิ้งทั้งก้อน

04.05

วินัยเรื่องหลักฐาน

ข้อความสองแบบนี้หน้าตาเหมือนกันในคำตอบของ agent แต่คุณค่าต่างกันคนละโลก

// อ้างลอย — ตรวจไม่ได้ อาจจริงอาจไม่จริง
"ฟังก์ชันนี้ถูกเรียกจากสามที่ในโปรเจกต์"

// อ้างพร้อมหลักฐาน — ตรวจได้ในสิบวินาที
"ฟังก์ชันนี้ถูกเรียกจากสามที่:
   src/api/invoice.ts:88
   src/jobs/nightly.ts:41
   test/invoice.spec.ts:12"
กฎที่ควรใส่ใน project memory

ทุกข้ออ้างเกี่ยวกับ codebase ต้องมี ไฟล์:บรรทัด ทุกข้ออ้างเกี่ยวกับโลกภายนอกต้องมี URL และวันที่ที่ดึงมา ข้อไหนไม่มีหลักฐาน ให้เขียนกำกับว่าเป็นการอนุมาน กฎข้อนี้เปลี่ยนคุณภาพงาน research มากกว่ากฎอื่นใด

04.06

ADR ที่ agent ตัวถัดไปอ่านต่อได้

บันทึกการตัดสินใจไม่ได้มีไว้ให้คนอ่านอย่างเดียวอีกต่อไป มันคือบริบทถาวรที่ทำให้ agent รอบหน้าไม่ถามซ้ำและไม่รื้อของที่ตัดสินไปแล้ว โครงที่ใช้ได้จริงมีห้าส่วน

  1. บริบท — สถานการณ์ที่บังคับให้ต้องเลือก
  2. ทางเลือกที่พิจารณา — อย่างน้อยสองทาง พร้อมเหตุผลที่ตกไป
  3. สิ่งที่เลือก — ประโยคเดียว ชัดเจน
  4. ผลที่ยอมรับ — ข้อเสียที่รู้ตัวและยอมแลก
  5. เงื่อนไขที่จะทำให้ต้องทบทวน — ส่วนที่คนลืมใส่ และเป็นส่วนที่มีค่าที่สุด
ส่วนที่ห้าสำคัญเพราะอะไร

ถ้าไม่เขียนไว้ว่า “ถ้าจำนวนผู้ใช้เกินหนึ่งแสนให้กลับมาทบทวน” การตัดสินใจนี้จะกลายเป็นกฎถาวรที่ไม่มีใครกล้าแตะ ทั้งที่เหตุผลเดิมหมดอายุไปแล้ว

04.07

Plan mode และการรีวิวแผนก่อนลงมือ

ถ้าคุณจำได้อย่างเดียวจากทั้งหลักสูตร ให้จำบทนี้ เหตุผลที่มันให้ผลตอบแทนสูงที่สุด ไม่ใช่เรื่องเทคนิคเลย แต่เป็นเลขคณิตของต้นทุนการแก้ตามจังหวะที่จับได้

จังหวะที่จับข้อผิดพลาดได้ต้นทุนการแก้ใครเสียเวลา
ตอนอ่านแผนพิมพ์สองประโยคคุณ 30 วินาที
ตอนรีวิว diffอ่านโค้ดที่เขียนเสร็จแล้วทั้งหมดคุณ 15 นาที + ค่า token ที่จ่ายไปแล้ว
ตอน CI แดงรอบ CI + สลับบริบทกลับมาคุณ + สายพาน + คนที่รอ merge
ตอนขึ้นโปรดักชันincidentทั้งทีม + ลูกค้า

แผนคือสิ่งเดียวที่อ่านจบใน 30 วินาที แล้วบอกได้ว่าอีก 20 นาทีข้างหน้าจะเดินถูกทางหรือเปล่า การข้ามขั้นนี้เพื่อ “ประหยัดเวลา” คือการยืมเวลาจากตัวเองในอัตราดอกเบี้ยที่แย่มาก

อ่านแผนยังไงให้ได้ผลสามคำถามที่จับปัญหาได้เกือบหมด

  1. ไฟล์ที่มันบอกว่าจะแตะ ตรงกับที่คุณคาดไหม
    ถ้าไม่ตรง แปลว่าคุณสองคนเข้าใจโจทย์คนละอย่าง และนี่คือจุดที่ถูกที่สุดในการค้นพบ ข้อนี้จับปัญหาได้มากที่สุดในสามข้อ
  2. มีขั้นไหนที่กว้างจนแปลได้หลายแบบไหม
    ขั้นอย่าง “ปรับ logic ให้รองรับเคสใหม่” คือที่ที่การลอยจากแผนเริ่มต้น ให้ตีกลับไปให้ระบุว่าจะปรับอะไรตรงไหน
  3. มันรู้ได้ยังไงว่าเสร็จ
    ถ้าแผนไม่มีข้อนี้ ให้ตีกลับทุกครั้ง แผนที่ไม่มีเกณฑ์จบคือแผนที่จบเมื่อ agent รู้สึกว่าพอ ซึ่งไม่ตรงกับตอนที่คุณรู้สึกว่าพอ
กับดักของแผนที่ดูดี

แผนที่เขียนสวยและครบถ้วนอาจหลอกได้ เพราะความครบถ้วนของรูปแบบ ไม่ได้แปลว่าเข้าใจโจทย์ ถูก

ตัวชี้วัดที่แม่นกว่าคือรายชื่อไฟล์ ไม่ใช่ความยาวของคำอธิบาย เพราะไฟล์คือสิ่งที่พิสูจน์ว่ามันหาที่ถูกเจอแล้วจริง แผนสามบรรทัดที่ระบุไฟล์ถูก ดีกว่าแผนสามหน้าที่ระบุไฟล์ผิด

เมื่อไหร่ที่ข้ามได้

งานที่ขอบเขตชัดจนไม่มีอะไรให้ตีความ — แก้ typo เปลี่ยนค่าคงที่ เพิ่มเทสต์เคสเดียว — การขอแผนก่อนเป็นพิธีกรรมที่ไม่ให้อะไร

เส้นแบ่งที่ใช้ได้คือ “ถ้ามันเข้าใจผิด ผมจะรู้ตอนไหน” ถ้ารู้ทันทีจาก diff สั้น ๆ ก็ข้ามได้ ถ้าต้องรอเทสต์หรือรอคนอื่นบอก ให้ขอแผนก่อน

04.08 · แล็บประจำโมดูล

แปลง requirement กำกวมหนึ่งหน้าเป็น spec + task graph + ADR

ใช้ requirement จริงจากงานของคุณ ไม่ใช่ตัวอย่างที่แต่งขึ้น เพราะความกำกวมของจริงมีรสชาติที่ตัวอย่างสังเคราะห์ไม่มี

ผลลัพธ์สามชิ้น

  1. Spec — ทุกข้อต้องมีเกณฑ์ที่สคริปต์ตัดสินได้ ข้อไหนเขียนเกณฑ์ไม่ได้ ให้ย้ายไปกอง “คำถามที่ต้องถามคน”
  2. Task graph — ย่อยเป็นงานที่ผ่านเกณฑ์สามข้อในบท 04.02 พร้อมระบุว่าอะไรต้องเสร็จก่อนอะไร
  3. ADR — สำหรับทุกจุดที่คุณต้องเลือก ครบทั้งห้าส่วน โดยเฉพาะส่วนที่ห้า
เกณฑ์ผ่าน
  • ส่ง task ใบแรกให้ agent แล้วมันทำได้จบโดยคุณไม่ต้องอธิบายเพิ่มเลย
  • กอง “คำถามที่ต้องถามคน” ไม่ว่างเปล่า — ถ้าว่าง แปลว่าคุณเดาแทนผู้ใช้โดยไม่รู้ตัว
  • ADR ทุกใบมีเงื่อนไขทบทวนที่เป็นรูปธรรม ไม่ใช่ “ถ้าสถานการณ์เปลี่ยน”

เชื่อมกับโมดูลอื่น — M05 ทำให้ ADR และเอกสารกลายเป็นบริบทที่ agent ใช้ได้จริง · M11 เปลี่ยน spec เป็นเทสต์ · M12.02 ใช้งานจากแล็บนี้เป็นวัตถุดิบของ golden task set
