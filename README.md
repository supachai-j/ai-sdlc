# ai-sdlc · eval harness

เครื่องวัดผลระบบ agent ขนาดเล็กที่สุดที่ยังให้สัญญาณจริง
อ้างอิงโมดูล **M12 · Evals** ของหลักสูตร AI Coding Agent SDLC

> ความแปรปรวนระหว่างการรันสองครั้งของงานเดียวกัน มักใหญ่กว่าผลของการแก้ prompt ที่คุณเพิ่งทำ
> ถ้าไม่มีเครื่องวัด คุณกำลังอ่านสัญญาณรบกวนแล้วเรียกมันว่าการปรับปรุง

ไม่มี dependency — ใช้ `Bun.YAML` และ `Bun.Glob` ในตัว

---

## เริ่มใช้

```bash
bun evals/runner.ts --dry-run          # ตรวจไฟล์ task และ SHA โดยไม่รันจริง (ไม่เสียเงิน)
bun evals/runner.ts --repeats 3        # รันจริง
bun evals/report.ts --save             # ดูผล + เก็บ baseline พร้อมวันที่
```

รันเฉพาะบางส่วน

```bash
bun evals/runner.ts --tasks fix-a,fix-b --arms baseline --repeats 5
bun evals/report.ts 2026-09-01T10-22-31-004Z
```

## ลำดับการใช้งานจริง (สัปดาห์แรก)

1. **เลือกคำถามหนึ่งข้อที่ยังเถียงกันอยู่** เช่น “กฎใน `CLAUDE.md` บรรทัดไหนยังมีผล”
   คำถามต้องมาก่อนงาน ไม่ใช่สร้าง task ไปเรื่อยแล้วค่อยหาว่าจะถามอะไร
2. **เอา 5 งาน ไม่ใช่ 20** — 5 งานที่มีอยู่จริงชนะ 20 งานที่วางแผนแล้วไม่ได้ทำ
   ดึงจาก PR ย้อนหลังสามเดือน แล้วตรึงด้วย SHA ก่อนหน้าการแก้จริง
3. **รอบแรกห้ามใช้ LLM judge** — ถ้า 5 งานแรกหาเกณฑ์เชิงกลไม่ได้ แปลว่าเลือกงานผิด
4. **รัน 3 ครั้งต่องาน แล้วดู “ช่วง” ไม่ใช่ค่าเดียว**
5. **`--save` ทุกครั้ง** เพื่อให้มี baseline เทียบตอนเปลี่ยนโมเดล

## โครงของหนึ่ง task

ดู `evals/tasks/_template.yaml` — ทุก task ต้องมีครบห้าอย่างนี้

| ส่วน | ทำไมต้องมี |
|---|---|
| `repo` + `sha` | ตรึงสถานะ ถ้า repo เคลื่อน ผลข้ามสัปดาห์เทียบกันไม่ได้ |
| `prompt` | เขียนแบบที่จะพิมพ์จริง ไม่ใช่แบบขัดเกลาแล้ว |
| `criteria` | ต้องตัดสินได้ด้วยสคริปต์ ไม่ใช่ด้วยสายตา |
| `setup` | ตรึงสภาพแวดล้อม — ตัวแปรที่คนลืมบ่อยที่สุด |
| `tags` | เพื่อดูว่าพังเฉพาะกลุ่มไหน |

### เกณฑ์ 4 แบบ เรียงจากถูกไปแพง

```yaml
- type: cmd            # typecheck / test — ถูกที่สุด เชื่อได้สมบูรณ์
- type: before_after   # แดงก่อน เขียวหลัง — สัญญาณที่แรงที่สุดต่อบาทที่จ่าย
- type: diff           # allow / deny / max_lines
- type: budget         # max_usd / max_wall_sec / max_turns
```

> **`type: diff` ห้ามละเว้น** — ถ้าไม่จำกัดขอบเขต agent จะทำให้เทสต์เขียวด้วยการแก้ไฟล์เทสต์
> หรือเติม `skip` ชุด eval ที่ไม่จำกัด diff จะถูกโกงในที่สุดเสมอ

`before_after` จะรายงานว่าเกณฑ์ **เป็นโมฆะ** ถ้าคำสั่งผ่านตั้งแต่ก่อน agent ทำงาน —
แปลว่าคุณเลือกเทสต์ที่ไม่ได้พังอยู่จริง

## สี่มิติในรายงาน

| คอลัมน์ | บอกอะไร |
|---|---|
| `pass` | ทำงานได้ไหม |
| `per-task range` | **คอลัมน์ที่สำคัญที่สุด** — ช่วงของอัตราผ่านรายงาน ถ้าสองแขนช่วงทับกัน คุณยังไม่ได้วัดอะไร |
| `$ / run` | ขยายไปทั้งทีมไหวไหม |
| `wall p50 / p95` | ขวางจังหวะการทำงานคนไหม |
| `interv.` | อิสระจริงแค่ไหน |

รายงานยังบอกด้วยว่า **เกณฑ์ไหนไม่ให้สัญญาณ** (ผ่านหมดหรือตกหมดทุกครั้ง) ให้เอาออกหรือทำให้ยากขึ้น
และเมื่อมีสองแขน จะแสดง **รายการงานที่พลิกผล** ซึ่งมีค่ากว่าตัวเลขรวม
เพราะมันเผยว่าการปรับปรุงที่ดูดีในภาพรวม กำลังทำให้งานประเภทหนึ่งแย่ลงอย่างเป็นระบบหรือเปล่า

### ข้อจำกัดของ `interv.` — อ่านก่อนใช้ตัวเลขนี้

โหมด headless ไม่มีคนนั่งดู จึงวัด “จำนวนครั้งที่คนต้องเข้าไปช่วย” ตรง ๆ ไม่ได้
ตัวเลขนี้เป็น **proxy อัตโนมัติ** = `permission_denials` + (`is_error` ? 1 : 0)

- ✅ จับได้ — agent ขอสิทธิ์ที่ไม่ได้ให้, จบแบบผิดพลาด, timeout
- ❌ จับไม่ได้ — คนเข้าไปตอบคำถามกลางทาง, เข้าไปแก้เอง, ยอมแพ้แล้วทำมือ

ถ้าจะวัดของจริง ต้องรันแบบ interactive แล้วบันทึกด้วยมือ ตัวเลขจาก harness นี้คือ *ขอบล่าง* เสมอ

## ความปลอดภัย

`allowed_tools` ใน `evals/arms.yaml` ตั้งไว้แคบโดยตั้งใจ — มันเป็นทั้ง
ขอบเขตความปลอดภัย (M13) และ **ส่วนหนึ่งของสิ่งที่กำลังวัด** การให้สิทธิ์กว้างขึ้นคือคนละแขน

- แต่ละ run ทำงานใน `git worktree` ใหม่ใน `$TMPDIR` แล้วลบทิ้งเสมอ
- worktree กันการแก้ไฟล์ข้าม run ได้ **แต่ไม่ได้กัน bash ออกจากเครื่อง**
- อย่าตั้ง `permission_mode: bypassPermissions` นอกจากรันใน container ที่ทิ้งได้

## การดูแลชุดงาน

ชุดงานเป็นสิ่งมีชีวิต

- ทุกครั้งที่เจอความล้มเหลวจริงในงานประจำวัน **แปลงเป็น task** นั่นคือวิธีที่ชุดวัดแหลมขึ้นแทนที่จะเก่าลง
- งานที่ผ่าน 100% ทุกครั้ง ให้ย้ายไปเป็น smoke หรือเอาออก — ไม่ให้สัญญาณ
- งานที่ตกทุกครั้งเหมือนกันหมด ก็ไม่ให้สัญญาณเช่นกัน
- กันชุดหนึ่งไว้ **ไม่ใช้ปรับ prompt** ไม่งั้นจะ overfit กับชุดวัดของตัวเอง

## โครงไฟล์

```
evals/
  types.ts        โครงข้อมูล task / criteria / run record
  criteria.ts     ตัวตัดสินทั้ง 4 แบบ
  runner.ts       worktree → setup → before → agent → diff → evaluate
  report.ts       รวมผล 4 มิติ + paired comparison + หาเกณฑ์ที่ไม่ให้สัญญาณ
  arms.yaml       นิยามแขนที่จะเทียบกัน
  tasks/*.yaml    ชุดงาน
  lib/            exec / git / agent
runs/             ผลดิบรายรัน (gitignored)
baselines/        snapshot พร้อมวันที่ + เวอร์ชัน สำหรับจับ drift
```

## สิ่งที่ยังไม่มีโดยตั้งใจ

**LLM-as-judge** — เพราะ M12.03 บอกว่าเกณฑ์ deterministic ต้องมาก่อนเสมอ
เพิ่มเมื่อคุณมี 15 งานที่ใช้เกณฑ์เชิงกลได้แล้วจริง ๆ และเหลือแต่สิ่งที่วัดเชิงกลไม่ได้
ตอนเพิ่มอย่าลืม calibrate กับคำตัดสินของคนสัก 30 ชิ้นก่อนเชื่อมัน
