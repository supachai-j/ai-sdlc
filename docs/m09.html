AI Coding Agent SDLC · Phase 03 · Module 09

Tooling — MCP, Skills, Hooks, Plugins

โมดูลนี้พาคุณข้ามจากผู้ใช้เครื่องมือไปเป็นผู้สร้าง และบทที่สำคัญที่สุดคือบทท้าย ๆ ที่บอกว่า เมื่อไหร่ไม่ควรสร้าง — เพราะสคริปต์ธรรมดาชนะบ่อยกว่าที่คนคิดมาก

10 บทเรียน3.5 ชั่วโมง1 แล็บต้องผ่าน M01 · M02 · M05 ก่อน
ใจความของทั้งโมดูล

เครื่องมือทุกตัวที่คุณเพิ่ม มีต้นทุนคงที่ที่จ่ายทุกรอบ — คำอธิบายของมันกินงบบริบท และตัวเลือกที่มากขึ้นทำให้โอกาสเลือกผิดสูงขึ้น เครื่องมือที่ดีจึงต้องคุ้มค่าที่จ่ายไปนั้น

09.01

MCP คือโปรโตคอล ไม่ใช่ไลบรารี

ความเข้าใจผิดที่พบบ่อยคือคิดว่ามันเป็นแพ็กเกจที่ติดตั้งแล้วได้ความสามารถ จริง ๆ มันคือข้อตกลงว่าโปรแกรมสองตัวจะคุยกันยังไง ซึ่งแปลว่าคุณเขียนฝั่งเซิร์ฟเวอร์เองด้วยภาษาอะไรก็ได้

สิ่งที่ให้ได้คืออะไรใช้เมื่อ
Toolsสิ่งที่ agent เรียกให้ทำงานต้องการให้มันทำอะไรบางอย่าง
Resourcesข้อมูลที่ agent อ่านได้ต้องการให้มันรู้อะไรบางอย่าง
Promptsเทมเพลตคำสั่งสำเร็จรูปต้องการให้ทีมสั่งงานเหมือนกัน

คนส่วนใหญ่ใช้แต่ tools ทั้งที่ resources มักเหมาะกว่าสำหรับข้อมูลที่ agent ควรอ่านเมื่อต้องใช้ — เป็นการทำ retrieval ตามหลัก M02.08 โดยไม่เปลืองงบบริบท

09.02

Transport และ auth

รูปแบบเหมาะกับข้อควรระวัง
ผ่าน stdio (โปรเซสในเครื่อง)เครื่องมือส่วนตัว เข้าถึงไฟล์ในเครื่องรันด้วยสิทธิ์เท่าคุณ ทุกอย่างที่คุณทำได้ มันทำได้
ผ่าน HTTPบริการที่ทีมใช้ร่วมกันต้องมี auth จริง และต้องคุมว่าใครเรียกได้
ข้อที่คนประเมินต่ำเกินไป

MCP server ที่รันในเครื่องมีสิทธิ์เท่าผู้ใช้ที่รันมัน การติดตั้งจากแหล่งที่ไม่รู้จักจึงเทียบเท่ากับการรันสคริปต์ของคนแปลกหน้าด้วยสิทธิ์ตัวเอง ไม่ใช่การติดตั้งปลั๊กอินในแซนด์บ็อกซ์ — ขยายเต็มใน M13.04

09.03

คำอธิบายเครื่องมือคือ prompt

agent เลือกเครื่องมือจากคำอธิบายเท่านั้น มันไม่ได้อ่านโค้ดข้างใน คำอธิบายจึงไม่ใช่เอกสาร API แต่เป็นคำสั่งที่กำหนดพฤติกรรม

// อ่อน — agent ไม่รู้ว่าเมื่อไหร่ควรใช้ตัวนี้แทนตัวอื่น
"ค้นหาผู้ใช้"

// ดี — บอกว่าเมื่อไหร่ใช้ เมื่อไหร่ไม่ใช้ และคืนอะไร
"ค้นหาผู้ใช้จากอีเมลหรือรหัส คืนโปรไฟล์และสถานะบัญชี
 ใช้เมื่อรู้ตัวตนที่แน่นอนแล้ว
 ห้ามใช้เพื่อไล่ดูรายชื่อทั้งหมด — ใช้ list_users แทน
 ไม่พบผู้ใช้จะคืน null ไม่ใช่ error"
สามส่วนที่คำอธิบายที่ดีต้องมี

ทำอะไร → เมื่อไหร่ควรใช้และไม่ควรใช้ → คืนอะไรรวมกรณีไม่เจอ ส่วนที่สองสำคัญที่สุดเมื่อคุณมีเครื่องมือหลายตัวที่คล้ายกัน ซึ่งเป็นสาเหตุอันดับหนึ่งของการเลือกผิด

09.04

ต้นทุน token ของ tool registry

เครื่องมือทุกตัวและ schema ของมันถูกส่งเข้าโมเดลทุกรอบ ทีมที่ติด MCP server ไว้สิบตัวอาจจ่ายค่าคำอธิบายเครื่องมือหลายหมื่น token ต่อรอบ โดยที่ใช้จริงสามตัว

สามวิธีลด เรียงจากง่ายไปยาก
  1. ถอดที่ไม่ใช้ออก — ได้ผลทันที และคนมักไม่เคยตรวจว่าตัวไหนไม่เคยถูกเรียกเลย
  2. เปิดเป็นชุดตามงาน — งาน FE ไม่ต้องมีเครื่องมือฐานข้อมูล
  3. ให้โหลดเครื่องมือตามต้องการ — เก็บเป็นดัชนีแล้วดึงเฉพาะที่ต้องใช้
ผลข้างเคียงที่วัดยากกว่าเรื่องเงิน

เครื่องมือเยอะทำให้เลือกผิดบ่อยขึ้น ไม่ใช่แค่แพงขึ้น เมื่อมีเครื่องมือสามตัวที่ทำสิ่งใกล้เคียงกัน agent จะเลือกสลับไปมาระหว่างรอบ ทำให้ผลไม่คงเส้นคงวาโดยไม่มีสาเหตุที่มองเห็น

09.05

Skills — ความรู้ที่โหลดตามบริบท

Skill ต่างจาก tool ตรงที่มันไม่ใช่สิ่งที่ agent เรียก แต่เป็นความรู้ที่ถูกโหลดเข้ามาเมื่อสถานการณ์ตรง ทำให้มันเหมาะกับเวิร์กโฟลว์หลายขั้นที่มีวิธีทำเฉพาะ

ToolSkill
คืออะไรฟังก์ชันที่เรียกได้คำสั่งและขั้นตอนที่โหลดมาอ่าน
ต้นทุนตอนไม่ใช้จ่ายค่าคำอธิบายทุกรอบจ่ายแค่บรรทัด description
เหมาะกับงานเดียวที่ทำซ้ำกระบวนการหลายขั้นที่มีท่าเฉพาะ
09.06

เขียน skill ที่ trigger ถูกจังหวะ

ข้อเท็จจริงที่คนเขียน skill ครั้งแรกมักพลาด — บรรทัด description คือสิ่งเดียวที่ตัดสินว่าจะถูกโหลดหรือไม่ ตัวเนื้อหาจะถูกอ่านก็ต่อเมื่อโหลดแล้ว ดังนั้นเนื้อหาที่ดีแต่ description แย่ เท่ากับไม่มี

// โหลดไม่ตรงจังหวะ — กว้างเกินจนไม่รู้ว่าเมื่อไหร่เกี่ยว
description: ช่วยเรื่องฐานข้อมูล

// โหลดตรงจังหวะ — มีคำที่ผู้ใช้จะพิมพ์จริง และมีขอบเขตชัด
description: >
  เขียนและตรวจ migration ของฐานข้อมูลด้วยรูปแบบขยาย-ย้าย-หด
  ใช้เมื่อผู้ใช้พูดถึง migration, เพิ่ม/ลบคอลัมน์, เปลี่ยนสคีมา,
  backfill หรือถามว่าแก้ตารางยังไงให้ไม่ล็อก
  ไม่ใช่สำหรับ query ธรรมดาหรือปรับ index
วิธีทดสอบ description

เขียนคำสั่งจริงที่คนในทีมจะพิมพ์มา 10 แบบ แล้วดูว่า skill ถูกโหลดกี่แบบ ถ้าโหลดน้อยกว่า 8 ให้แก้ description ไม่ใช่แก้เนื้อหา — และนี่คือ regression test ของ skill ตามหลัก M12.05

09.07

Hooks — บังคับสิ่งที่ prompt บังคับไม่ได้

ความต่างที่เป็นแก่นของบทนี้ — prompt คือการขอ hook คือการบังคับ อะไรที่ต้องเกิดขึ้นแน่นอนทุกครั้ง ต้องเป็น hook ไม่ใช่กฎในไฟล์บริบท

จังหวะใช้ทำอะไรได้จริง
ก่อนใช้เครื่องมือบล็อกคำสั่งอันตราย · กันไม่ให้อ่านไฟล์ลับ
หลังใช้เครื่องมือจัดรูปแบบโค้ดอัตโนมัติ · รัน lint ทันทีที่แก้ไฟล์
ก่อนจบงานบังคับให้รันเทสต์ · บล็อกถ้าเทสต์แดง
ตอนรับคำสั่งเติมบริบทประจำที่ต้องมีทุกครั้ง
กฎแปลง

ไล่ดูกฎใน project memory ของคุณ ข้อไหนที่ขึ้นต้นว่า “ห้าม…” หรือ “ทุกครั้งต้อง…” ข้อนั้นควรเป็น hook เพราะกฎประเภทนี้ที่ทำตามบ้างไม่ทำบ้าง มีค่าเท่ากับไม่มี แถมยังกินงบบริบททุกรอบ

09.08

Plugins และ slash command

เมื่อคุณมี skill, hook และ MCP server ที่ใช้ได้ผลแล้ว ขั้นถัดไปคือทำให้ทั้งทีมได้ของชุดเดียวกัน เพราะประโยชน์ที่แท้จริงเกิดตอนที่ทุกคนได้พฤติกรรมเหมือนกัน ไม่ใช่ตอนที่คุณคนเดียวเก่งขึ้น

  • เวอร์ชันได้และย้อนได้ — ปฏิบัติกับมันเหมือนโค้ด เพราะมันคือโค้ด
  • มีชุดวัดกำกับ — เปลี่ยน skill แล้วต้องรันชุดวัดก่อน merge
  • slash command สำหรับงานที่ทำซ้ำ — ทำให้คนในทีมสั่งงานแบบเดียวกัน ซึ่งทำให้ผลเทียบกันได้
09.09

เมื่อไหร่ไม่ควรทำ MCP server

บทที่สำคัญที่สุดในโมดูลนี้ ทีมจำนวนมากสร้าง MCP server สำหรับสิ่งที่สคริปต์ 20 บรรทัดทำได้ดีกว่า แล้วต้องดูแลมันไปตลอด

สถานการณ์ควรใช้เพราะ
เรียกคำสั่งที่มีอยู่แล้วในเครื่องสคริปต์ + bashagent ใช้ bash เป็นอยู่แล้ว ไม่ต้องสอนอะไรใหม่
อ่านไฟล์ในโปรเจกต์ให้มันอ่านเองมีเครื่องมืออ่านไฟล์อยู่แล้ว
เวิร์กโฟลว์หลายขั้นที่มีท่าเฉพาะSkillไม่กินงบบริบทตอนไม่ใช้
ต่อกับระบบภายนอกที่มี authMCPตรงกับสิ่งที่มันถูกออกแบบมา
ให้ทั้งทีมเข้าถึงบริการเดียวกันMCP แบบ HTTPคุมสิทธิ์ที่ศูนย์กลางได้
คำถามที่ควรถามก่อนเริ่มเขียน

“ถ้าผมเขียนสคริปต์แล้วบอก agent ว่ามีสคริปต์นี้อยู่ มันจะใช้ได้ไหม” ถ้าตอบว่าได้ ให้ทำแบบนั้น เพราะสคริปต์ไม่กินงบบริบท ไม่ต้องดูแลโปรโตคอล และ debug ง่ายกว่ามาก

09.10 · แล็บประจำโมดูล

สร้าง MCP server + skill + hook ที่บังคับ convention ของทีมได้จริง

เลือก convention จริงที่ทีมคุณมีปัญหาว่าคนทำตามบ้างไม่ทำบ้าง แล้วทำให้มันบังคับได้

สามชิ้นที่ต้องส่ง

  1. Hook ที่บล็อกสิ่งที่ห้ามทำ พร้อมข้อความบอกว่าให้ทำอะไรแทน (ตามหลัก M05.03)
  2. Skill ที่ห่อเวิร์กโฟลว์หลายขั้น พร้อม description ที่ผ่านการทดสอบสิบคำสั่ง
  3. MCP server หรือสคริปต์ — และต้องอธิบายได้ว่าทำไมเลือกอย่างนั้น ตามตารางในบท 09.09
เกณฑ์ผ่าน
  • ลองละเมิด convention โดยตั้งใจ แล้ว hook ต้องบล็อกได้จริง
  • skill ถูกโหลดอย่างน้อย 8 จาก 10 คำสั่งทดสอบ
  • วัด token ของ tool registry ก่อนและหลัง แล้วอธิบายส่วนต่างได้
  • ถ้าคำตอบของชิ้นที่สามคือ “สคริปต์ก็พอ” ถือว่าผ่านเต็ม — การไม่สร้างของที่ไม่จำเป็นคือคำตอบที่ถูก

เชื่อมกับโมดูลอื่น — M02 tool registry คือส่วนหนึ่งของงบบริบท · M05.05 hook คือ guardrail ที่บังคับได้แบบเดียวกับ type · M12.05 ชุดวัดสำหรับ skill · M13.03 ภัยจาก tool poisoning
