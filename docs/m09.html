AI Coding Agent SDLC · Phase 03 · Module 09

Tooling — MCP, Skills, Hooks, Plugins

โมดูลนี้พาคุณข้ามจากผู้ใช้เครื่องมือไปเป็นผู้สร้าง และบทที่สำคัญที่สุดคือบทท้าย ๆ ที่บอกว่า เมื่อไหร่ไม่ควรสร้าง — เพราะสคริปต์ธรรมดาชนะบ่อยกว่าที่คนคิดมาก

10 บทเรียน3.5 ชั่วโมง1 แล็บต้องผ่าน M01 · M02 · M05 ก่อน
ใจความของทั้งโมดูล

เครื่องมือทุกตัวที่คุณเพิ่ม มีต้นทุนคงที่ที่จ่ายทุกรอบ — คำอธิบายของมันกินงบบริบท และตัวเลือกที่มากขึ้นทำให้โอกาสเลือกผิดสูงขึ้น เครื่องมือที่ดีจึงต้องคุ้มค่าที่จ่ายไปนั้น

09.01

MCP คือโปรโตคอล ไม่ใช่ไลบรารี

ความเข้าใจผิดที่พบบ่อยสุดคือคิดว่า MCP เป็นแพ็กเกจที่ติดตั้งแล้วได้ความสามารถ จริง ๆ มันคือข้อตกลงว่าโปรแกรมสองตัวจะคุยกันยังไง

แปลว่าคุณเขียนฝั่ง server เองด้วยภาษาอะไรก็ได้ — และแปลว่าถ้าเข้าใจโปรโตคอล คุณ debug ได้ทุกเจ้า ไม่ต้องรอ SDK

Figure 1 · ถ้าสิ่งที่คุณจะให้คือ "ข้อมูล" ไม่ใช่ "การกระทำ" ให้ดู resources ก่อน tools

อ่านเพิ่มจากต้นทาง

  1. Model Context Protocol — Introduction — โปรโตคอลคืออะไร และแยก tools / resources / prompts ยังไง modelcontextprotocol.io
  2. MCP — การต่อ MCP server เข้ากับ agent ในทางปฏิบัติ docs.claude.com
09.02

Transport และ auth

Figure 2 · ความต่างที่สำคัญไม่ใช่ความเร็ว แต่คือ สิทธิ์ที่มันได้ — ขยายเต็มใน M13.04

อ่านเพิ่มจากต้นทาง

  1. MCP — Security Best Practices — คำแนะนำด้านความปลอดภัยจากตัวสเปคเอง modelcontextprotocol.io
  2. Identity and access management — การคุมว่า server ตัวไหนทำอะไรได้บ้าง docs.claude.com
09.03

คำอธิบายเครื่องมือคือ prompt

agent เลือกเครื่องมือจากคำอธิบายเท่านั้น มันไม่ได้อ่านโค้ดข้างใน เพราะงั้นคำอธิบายไม่ใช่เอกสาร API แต่เป็นคำสั่งที่กำหนดพฤติกรรม

Figure 3 · เขียนส่วนที่ 2 ให้ครบ แล้วอาการ "หยิบผิดตัว" ใน M01.07 จะหายไปเอง

อ่านเพิ่มจากต้นทาง

  1. Writing tools for agents — หลักการเขียนคำอธิบายและ schema ที่ agent ใช้ถูก anthropic.com/engineering
  2. MCP — Introduction — โครงสร้างของ tool definition ที่ส่งไปให้โมเดล modelcontextprotocol.io
09.04

ต้นทุน token ของ tool registry

เครื่องมือทุกตัวและ schema ของมันถูกส่งเข้าโมเดลทุกรอบ — ทีมที่ติด MCP server ไว้สิบตัวอาจจ่ายค่าคำอธิบายหลายหมื่น token ต่อรอบ โดยใช้จริงสามตัว

Figure 4 · เครื่องมือเยอะไม่ได้แค่แพงขึ้น — มันทำให้ เลือกผิดบ่อยขึ้น ด้วย

เริ่มจากตรงไหน

เปิด log สองสัปดาห์ แล้วนับว่าเครื่องมือตัวไหนไม่เคยถูกเรียกเลย ถอดออกก่อนเลย — เป็นการลด context ที่ไม่แลกอะไรเลย ตรงกับคันโยกข้อ 2 ใน M03.06

อ่านเพิ่มจากต้นทาง

  1. Effective context engineering — tool registry ในฐานะส่วนหนึ่งของงบ context anthropic.com/engineering
  2. Prompt caching — ทำไม tool list ที่ไม่นิ่งถึงทำลาย cache ของทุกอย่างหลังมัน docs.claude.com
09.05

Skills — ความรู้ที่โหลดตามบริบท

Figure 5 · ถ้าสิ่งที่คุณจะให้คือ "วิธีทำ" ไม่ใช่ "ความสามารถใหม่" — skill ถูกกว่าเสมอ

อ่านเพิ่มจากต้นทาง

  1. Skills — โครงสร้างของ skill และการโหลดตามบริบท docs.claude.com
  2. Kiro — Steering — แนวคิดเดียวกันจากอีกเจ้า พร้อม inclusion mode สี่แบบ kiro.dev
09.06

เขียน skill ที่ trigger ถูกจังหวะ

ข้อเท็จจริงที่คนเขียน skill ครั้งแรกมักพลาด — บรรทัด description คือสิ่งเดียวที่ตัดสินว่าจะถูกโหลดหรือไม่

ตัวเนื้อหาจะถูกอ่านก็ต่อเมื่อโหลดแล้ว เพราะงั้นเนื้อหาดีแต่ description แย่ = เท่ากับไม่มี

Figure 6 · การทดสอบ 10 คำสั่งนี้คือ regression test ของ skill ตาม M12.05

อ่านเพิ่มจากต้นทาง

  1. Skills — โครงไฟล์ และบทบาทของ description ในการเลือกโหลด docs.claude.com
  2. Writing tools for agents — หลักการเดียวกันกับคำอธิบายเครื่องมือ anthropic.com/engineering
09.07

Hooks — บังคับสิ่งที่ prompt บังคับไม่ได้

ความต่างที่เป็นแก่นของบทนี้มีประโยคเดียว — prompt คือการขอ · hook คือการบังคับ

อะไรที่ต้องเกิดขึ้นแน่นอนทุกครั้ง ต้องเป็น hook ไม่ใช่กฎในไฟล์บริบท

Figure 7 · ย้ายกฎจาก prompt ไป hook = ได้ความแน่นอน และคืนงบ context ไปพร้อมกัน

อ่านเพิ่มจากต้นทาง

  1. Hooks — จังหวะที่ hook แทรกได้ และรูปแบบการตั้งค่า docs.claude.com
  2. Kiro — Hooks — เจ้าอื่นที่ได้ข้อสรุปเดียวกัน พร้อม trigger 11+ แบบ kiro.dev
09.08

Plugins และ slash command

เมื่อมี skill, hook และ MCP server ที่ใช้ได้ผลแล้ว ขั้นถัดไปคือทำให้ทั้งทีมได้ของชุดเดียวกัน เพราะประโยชน์ที่แท้จริงเกิดตอนที่ทุกคนได้พฤติกรรมเหมือนกัน ไม่ใช่ตอนที่คุณคนเดียวเก่งขึ้น

Figure 8 · ประโยชน์ที่มองข้ามคือ ผลเทียบกันได้ — ซึ่งเป็นเงื่อนไขของทุกอย่างใน M12

อ่านเพิ่มจากต้นทาง

  1. Plugins — การแพ็ก skill / hook / คำสั่ง ให้ทีมติดตั้งชุดเดียวกัน docs.claude.com
  2. Settings — ระดับการตั้งค่า user / project / local และลำดับทับกัน docs.claude.com
09.09

เมื่อไหร่ไม่ควรทำ MCP server

บทที่สำคัญที่สุดในโมดูลนี้ และเป็นบทที่คนอยากข้ามที่สุด

ทีมจำนวนมากสร้าง MCP server สำหรับสิ่งที่สคริปต์ 20 บรรทัดทำได้ดีกว่า แล้วต้องดูแลมันไปตลอด

Figure 9 · สคริปต์ไม่กินงบ context ไม่ต้องดูแลโปรโตคอล และ debug ง่ายกว่ามาก

คำถามที่ควรถามก่อนเริ่มเขียน

"ถ้าผมเขียนสคริปต์แล้วบอก agent ว่ามีสคริปต์นี้อยู่ มันจะใช้ได้ไหม"

ถ้าตอบว่าได้ ให้ทำแบบนั้น — และแล็บของโมดูลนี้ระบุไว้ชัดว่า ถ้าคำตอบของคุณคือ "สคริปต์ก็พอ" ถือว่าผ่านเต็ม เพราะการไม่สร้างของที่ไม่จำเป็นคือคำตอบที่ถูก

อ่านเพิ่มจากต้นทาง

  1. Building effective agents — เมื่อไหร่ที่วิธีง่ายกว่าชนะการ over-engineer anthropic.com/engineering
  2. MCP — Introduction — ขอบเขตที่โปรโตคอลนี้ตั้งใจแก้จริง ๆ modelcontextprotocol.io
09.10 · แล็บประจำโมดูล

สร้าง MCP server + skill + hook ที่บังคับ convention ของทีมได้จริง

เลือก convention จริงที่ทีมคุณมีปัญหาว่าคนทำตามบ้างไม่ทำบ้าง แล้วทำให้มันบังคับได้

สามชิ้นที่ต้องส่ง

  1. Hook ที่บล็อกสิ่งที่ห้ามทำ พร้อมข้อความบอกว่าให้ทำอะไรแทน (ตามหลัก M05.03)
  2. Skill ที่ห่อเวิร์กโฟลว์หลายขั้น พร้อม description ที่ผ่านการทดสอบสิบคำสั่ง
  3. MCP server หรือสคริปต์ — และต้องอธิบายได้ว่าทำไมเลือกอย่างนั้น ตามตารางในบท 09.09
เกณฑ์ผ่าน
  • ลองละเมิด convention โดยตั้งใจ แล้ว hook ต้องบล็อกได้จริง
  • skill ถูกโหลดอย่างน้อย 8 จาก 10 คำสั่งทดสอบ
  • วัด token ของ tool registry ก่อนและหลัง แล้วอธิบายส่วนต่างได้
  • ถ้าคำตอบของชิ้นที่สามคือ “สคริปต์ก็พอ” ถือว่าผ่านเต็ม — การไม่สร้างของที่ไม่จำเป็นคือคำตอบที่ถูก

เชื่อมกับโมดูลอื่น — M02 tool registry คือส่วนหนึ่งของงบบริบท · M05.05 hook คือ guardrail ที่บังคับได้แบบเดียวกับ type · M12.05 ชุดวัดสำหรับ skill · M13.03 ภัยจาก tool poisoning
