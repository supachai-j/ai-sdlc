AI Coding Agent SDLC · Phase 01 · Module 05

ออกแบบ Codebase ให้ Agent ทำงานได้

คุณภาพงานของ agent มาจากโครงสร้าง repo มากกว่ามาจาก prompt และความต่างที่สำคัญคือ โครงสร้างให้ผลถาวร ส่วน prompt ที่ปรับดีขึ้นให้ผลแค่ครั้งเดียว

8 บทเรียน2.5 ชั่วโมง1 แล็บต้องผ่าน M02 · M04 ก่อน
ใจความของทั้งโมดูล

ทุกครั้งที่ agent หาของไม่เจอ อ่าน error ไม่รู้เรื่อง หรือรันเทสต์ทั้งชุดเพื่อตรวจบรรทัดเดียว คุณจ่ายเงินและเวลาให้กับสิ่งที่แก้ครั้งเดียวจบได้

05.01

Legibility — อ่านรู้เรื่องสำหรับเครื่อง

codebase ที่คนอ่านรู้เรื่องกับที่เครื่องอ่านรู้เรื่อง ไม่ใช่สิ่งเดียวกัน คนเติมช่องว่างจากบริบทที่สะสมมาหลายเดือน ส่วน agent เห็นเฉพาะสิ่งที่อยู่ตรงหน้า

สิ่งที่คนทดแทนได้ด้วยความคุ้นเคยสิ่งที่ agent ต้องเห็นตรง ๆ
“ไฟล์ utils.ts น่ะเหรอ ของเก่า อย่าไปแตะ”คอมเมนต์บนหัวไฟล์ว่า deprecated ใช้อะไรแทน
“เทสต์ชุดนั้นแดงมาตั้งแต่ปีที่แล้ว ปกติ”skip พร้อมเหตุผล หรือลบทิ้ง
“ต้องรัน seed ก่อนนะ ไม่งั้นพัง”สคริปต์เดียวที่ทำให้ครบ หรือ error ที่บอก
“โฟลเดอร์นี้กำลังจะย้าย”ADR ที่บอกว่ากำลังย้ายไปไหน
การทดสอบที่ตรงที่สุด

ถ้าคุณต้องอธิบายอะไรกับ dev ใหม่ในสัปดาห์แรกซ้ำ ๆ นั่นคือสิ่งที่ agent ก็ไม่รู้เหมือนกัน และมันจะไม่ถามคุณ มันจะเดา

05.02

โครงไฟล์ที่ลดต้นทุนการค้นหา

agent จ่าย token ทุกครั้งที่หาไม่เจอ และมันหาแบบเดาจากชื่อ ไม่ใช่แบบจำที่ได้ โครงสร้างที่ดีจึงวัดได้ด้วยคำถามเดียว — “จากชื่อฟีเจอร์ เดาที่อยู่ไฟล์ถูกในครั้งแรกไหม”

  • จัดตามโดเมน ไม่ใช่ตามชนิดไฟล์ — billing/ ที่มีทั้ง logic เทสต์ และ type รวมกัน ชนะ controllers/ services/ types/ ที่กระจายเรื่องเดียวไปสามที่
  • ชื่อไฟล์บอกเนื้อหา — invoice-total.ts ชนะ helpers.ts
  • อย่ามีทางเข้าหลายทางไปที่เดียวกัน — re-export ซ้อนกันหลายชั้นทำให้ agent ตามไม่จบ
  • ไฟล์ที่ห้ามแตะต้องบอกที่ตัวมันเอง ไม่ใช่ในหัวคน
05.03

Error message คือช่องทาง feedback

นี่คือการลงทุนที่คุ้มที่สุดในโมดูลนี้ เพราะ error คือสิ่งที่ agent อ่านตอนที่มันหลงทาง และเป็นโอกาสเดียวที่คุณจะชี้ทางได้โดยไม่ต้องอยู่ตรงนั้น

// ไร้ประโยชน์ — agent ได้แต่เดา แล้วลองสุ่มแก้
Error: Invalid configuration

// มีประโยชน์ — บอกว่าอะไรผิด ที่ไหน และแก้ยังไง
Error: config.retries ต้องเป็นจำนวนเต็ม 0-10 แต่ได้ค่า "3s"
  ที่ config/worker.yaml บรรทัด 12
  ถ้าต้องการกำหนดเวลา ให้ใช้ config.timeout แทน
โครงสามส่วนที่ใช้ได้ทุก error

อะไรผิด → ที่ไหน → ทำยังไงต่อ ส่วนที่สามคือส่วนที่คนละเลย และเป็นส่วนที่เปลี่ยนการวนแก้สามรอบให้เหลือรอบเดียว

05.04

Test affordance

หลักการที่คนไม่ค่อยพูดถึง — ถ้ารันเทสต์เฉพาะจุดไม่ได้เร็ว agent จะเลิกรันแล้วเดาแทน มันไม่ได้ประกาศว่าเลิกรัน มันแค่ค่อย ๆ ข้ามไป และคุณจะเห็นผลเป็นคุณภาพที่ตกโดยไม่รู้สาเหตุ

เวลารันเทสต์เฉพาะจุดพฤติกรรมที่ได้
ต่ำกว่า 5 วินาทีรันทุกครั้งที่แก้ วนแก้เองจนเขียว
10–30 วินาทีรันบ้าง ข้ามบ้าง
เกิน 1 นาที หรือรันเฉพาะจุดไม่ได้เดาเอาแล้วบอกว่าน่าจะถูก
สิ่งที่ต้องมี

คำสั่งเดียวที่รันเทสต์ของไฟล์เดียวได้ และเสร็จในไม่กี่วินาที ถ้าโปรเจกต์ของคุณยังไม่มี นี่คือสิ่งแรกที่ควรทำ — มันให้ผลมากกว่าการปรับ prompt ทุกอย่างรวมกัน

05.05

Type และ schema เป็น guardrail ที่ถูกที่สุด

Type ทำงานต่างจากคำสั่งใน prompt ตรงที่มันบังคับได้ ไม่ใช่แค่ขอ และมันทำงานตอนที่ไม่มีใครดูอยู่

วิธีกันบังคับได้จริงไหมต้นทุนต่อครั้ง
เขียนกฎใน promptขอ — ทำตามบ้างไม่ทำบ้างจ่าย token ทุกรอบ
Type / schemaบังคับ — ผิดแล้วคอมไพล์ไม่ผ่านศูนย์
Hook / lint ruleบังคับศูนย์
รีวิวโดยคนบังคับ แต่ช้าและมีวันพลาดเวลาคน

กฎที่ควรใช้คือ — อะไรที่ทำให้เป็น type ได้ อย่าเอาไปเขียนเป็นกฎใน prompt เพราะกฎใน prompt กินงบบริบททุกรอบและยังไม่รับประกันผล

05.06

Docs-as-context

เอกสารในโปรเจกต์ที่มี agent ทำงานอยู่ มีสถานะเปลี่ยนไป มันไม่ใช่ของที่เขียนแล้วไม่มีใครอ่าน แต่เป็น input ที่ถูกอ่านทุกวัน ซึ่งเปลี่ยนวิธีเขียนไปด้วย

เอกสารเขียนแบบเดิมเขียนให้เป็นบริบท
READMEเล่าว่าโปรเจกต์ทำอะไรคำสั่งที่ต้องใช้ + ข้อจำกัดที่ไม่เห็นจากโค้ด
ADRบันทึกไว้เผื่อใครสงสัยระบุสิ่งที่ห้ามรื้อและเพราะอะไร
Runbookขั้นตอนสำหรับคนคำสั่งที่รันได้จริง + วิธีตรวจว่าสำเร็จ
Design systemภาพประกอบtoken กับ primitive ที่ระบุชื่อได้
เอกสารที่เป็นโทษ

เอกสารที่ล้าสมัยแย่กว่าไม่มีเอกสาร เพราะ agent เชื่อมันและทำตาม ถ้าดูแลไม่ไหว ให้ลบดีกว่าปล่อยไว้ — และถ้าลบไม่ได้ ให้เขียนวันที่กับสถานะไว้บนหัวไฟล์

05.07

ลำดับชั้นของไฟล์บริบท

ไฟล์บริบทมีได้หลายระดับ และการรู้ลำดับทับกันช่วยให้วางกฎถูกที่

ระดับควรใส่อะไรสิ่งที่ไม่ควรอยู่ที่นี่
Globalวิธีทำงานที่คุณต้องการเสมอทุกโปรเจกต์อะไรที่จริงเฉพาะโปรเจกต์เดียว
Projectconvention คำสั่ง ข้อห้ามของ repo นี้ความรู้ทั่วไปที่โมเดลรู้อยู่แล้ว
Directoryกฎเฉพาะโซน เช่น โฟลเดอร์ที่กำลัง migrateกฎที่ใช้ทั้ง repo
เกณฑ์วางกฎให้ถูกระดับ

ถามว่า “กฎนี้ยังจริงไหมถ้าย้ายไปอีกโปรเจกต์” — จริง ให้ขึ้น global · ไม่จริง ให้อยู่ project · จริงเฉพาะบางโฟลเดอร์ ให้ลง directory การวางสูงเกินไปทำให้กฎไปรบกวนงานที่ไม่เกี่ยว

05.08 · แล็บประจำโมดูล

Audit repo จริง แล้วทำห้าการเปลี่ยนที่ลด token ต่องานลง 30%

แล็บนี้วัดผลได้ตรง ๆ และผลมักอยู่ได้นานกว่าทุกอย่างที่คุณทำในหลักสูตรนี้

ขั้นตอน

  1. วัดตั้งต้น — เลือกงานตัวแทนสามงาน รันแล้วบันทึก token ที่ใช้ จำนวนรอบ และจำนวนไฟล์ที่ agent เปิดอ่าน
  2. หาจุดรั่ว — ดูว่ามันเปิดไฟล์อะไรบ้างก่อนจะเจอที่ถูก ทุกไฟล์ที่เปิดผิดคือหลักฐานว่าโครงสร้างหรือชื่อไม่สื่อ
  3. เลือกห้าการเปลี่ยน จากรายการนี้ — คำสั่งรันเทสต์เฉพาะจุด · แก้ error สามข้อที่เจอบ่อยให้บอกวิธีแก้ · ตั้งชื่อไฟล์ที่กำกวมใหม่ · เขียนหัวไฟล์ให้ของ deprecated · ตัด project memory ที่พิสูจน์ไม่ได้ทิ้ง
  4. วัดซ้ำด้วยงานเดิม อย่างละ 3 ครั้ง
เกณฑ์ผ่าน
  • token ต่องานลดลงอย่างน้อย 30% โดยอัตราผ่านไม่ตก
  • จำนวนไฟล์ที่เปิดผิดก่อนเจอที่ถูก ลดลงชัดเจน
  • บอกได้ว่าการเปลี่ยนไหนให้ผลมากที่สุด — เกือบทุกครั้งคือข้อ test affordance
อย่าทำพร้อมกันทั้งห้า

ทำทีละอย่างแล้ววัด ไม่งั้นคุณจะรู้ว่ารวม ๆ ดีขึ้น แต่ไม่รู้ว่าเพราะอะไร แล้วครั้งหน้าในโปรเจกต์อื่นก็ต้องเดาใหม่หมด

เชื่อมกับโมดูลอื่น — M01.07 สองในเจ็ดโหมดล้มเหลวแก้ได้ที่นี่ · M02.08 โครงสร้างที่ดีทำให้ retrieval ชนะ stuffing · M08 ใช้เทคนิคเดียวกันกับ repo ที่คุณไม่ได้เขียน · M09 เปลี่ยนกฎเป็น hook ที่บังคับได้
