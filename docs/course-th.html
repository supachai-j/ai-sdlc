กลไกภายในของ Agent

เห็นว่า agent คือลูปธรรมดาที่ห่อด้วยวิศวกรรม ไม่ใช่กล่องดำ เพื่อให้ debug ได้เมื่อมันพัง

  1. Agentic loop จริง ๆ คืออะไร และทำไมแค่นั้นก็พอ
  2. กายวิภาคของ harness — system prompt, tool registry, context assembler, permission layer, result renderer
  3. Tool-use protocol — tool_use / tool_result, parallel call, is_error และทำไมต้องส่ง result ครบใน message เดียว
  4. stop_reason ทุกค่า และการจัดการแต่ละแบบ
  5. Thinking กับ effort — adaptive thinking, ระดับ low→max, ผลต่อจำนวน tool call
  6. Permission model — allow / ask / deny, sandbox และทำไม "ปล่อยผ่านหมด" คือหนี้ทางความปลอดภัย
  7. 7 โหมดที่ agent ล้มเหลว — context ล้น, tool description กำกวม, error message อ่านไม่รู้เรื่อง, ติดลูป, ค้นเกินจำเป็น, ลอยจากแผน, ตัดข้อมูลเงียบ
  8. LABเขียน mini-harness ~150 บรรทัด — ลูป + 3 tools + permission gate
ผลลัพธ์อธิบายได้ว่าเวลา agent ทำอะไรแปลก ๆ มันเกิดที่ชั้นไหนของ harness

Context Engineering

มองบริบทเป็นงบประมาณที่ต้องบริหาร ไม่ใช่ถังที่เทใส่จนกว่าจะเต็ม

  1. Context window คืองบ ไม่ใช่พื้นที่เก็บของ — มี 1M token ก็ยังต้องบริหาร
  2. กฎ 4 ข้อของสิ่งที่ควรอยู่ในบริบท — เกี่ยวข้อง / สด / เรนเดอร์เล็ก / หากลับมาได้
  3. Attention dilution — ทำไมยัดเยอะแล้วคุณภาพตก ทั้งที่ยังไม่เต็ม window
  4. ลำดับชั้นหน่วยความจำ และอะไรควรอยู่ชั้นไหน
  5. เขียน CLAUDE.md ให้ทำงานจริง — สั้น เป็นกฎ ตรวจสอบได้ ไม่ใช่ README ฉบับสอง
  6. สามกลไกที่คนสับสน — compaction vs context editing vs memory tool
  7. Sub-agent ในฐานะเครื่องมือ context isolation ไม่ใช่แค่ทำงานขนาน
  8. Retrieval vs stuffing — เมื่อไหร่ควรให้ grep เอง เมื่อไหร่ควรแนบไปเลย
  9. LABวัด context ของงานจริง ตัดออก 40% แล้ววัดว่าคุณภาพเปลี่ยนไหม
ผลลัพธ์ลดต้นทุนต่องานได้ 30–60% โดยคุณภาพเท่าเดิมหรือดีขึ้น

เศรษฐศาสตร์ของ Token และโมเดล

ตัดสินใจเรื่องต้นทุนด้วยตัวเลข ไม่ใช่ความรู้สึกว่า "โมเดลนี้แพง"

  1. บัญชี token 4 ช่อง — input / output / cache write / cache read ราคาไม่เท่ากันและต่างกันมาก
  2. Prompt caching เชิงลึก — prefix match, ลำดับเรนเดอร์, เพดาน breakpoint, ขนาดขั้นต่ำที่จะติด cache
  3. ตัวทำลาย cache แบบเงียบ และวิธี audit ด้วย cache_read_input_tokens
  4. Model routing เชิงเศรษฐศาสตร์ — งานแบบไหนคุ้มกับโมเดลตัวไหน
  5. ต้นทุนต่องานที่เสร็จ ไม่ใช่ต่อ request
  6. Effort เป็นคันโยกแรกก่อนเปลี่ยนโมเดล และกับดักที่ cache แยก namespace ตามโมเดล
  7. Batch, task budget และการตั้งเพดานแบบที่ agent รู้ตัว
  8. LABทำ cost profile ของงานจริง 1 สัปดาห์ หา 3 คันโยกที่ประหยัดได้จริง
ผลลัพธ์ตอบได้ว่างานนี้ควรใช้โมเดลไหน effort เท่าไหร่ ด้วยข้อมูล ไม่ใช่ความเชื่อ

Requirements, Research และการย่อยงาน

เปลี่ยนความต้องการกำกวมเป็น spec ที่ agent ทำแล้วตรวจได้

  1. Spec-first — prompt ที่ดีคือข้อกำหนด ไม่ใช่คำสั่ง และต่างกันตรงไหน
  2. ขนาดงานที่พอดีกับ agent — เล็กพอที่จะยืนยันผลได้ในลูปเดียว
  3. เกณฑ์ตัดสินว่างานนี้ควรให้ agent ทำไหม — ความซับซ้อน / คุณค่า / ความเป็นไปได้ / ต้นทุนเมื่อผิด
  4. Research loop — แยก "ค้นหา" ออกจาก "สรุป" ออกจาก "ตัดสินใจ"
  5. วินัยเรื่องหลักฐาน — บังคับให้อ้างไฟล์ บรรทัด หรือ URL ทุกครั้ง
  6. ADR ที่ agent เขียนแล้ว agent ตัวถัดไปอ่านต่อได้
  7. Plan mode และการรีวิวแผนก่อนลงมือ — บทที่ให้ผลตอบแทนสูงที่สุดในหลักสูตร
  8. LABแปลง requirement กำกวม 1 หน้า เป็น spec + task graph + ADR
  9. เครื่องมือที่บังคับ spec-driven ให้เลย — กรณีศึกษา Kiro
ผลลัพธ์งานที่ต้องสั่งซ้ำลดลงชัดเจน เพราะรอบแรกมี acceptance criteria อยู่แล้ว

Backend และงานที่แตะข้อมูล

ทำงาน backend กับ agent โดยที่ migration และ data operation ไม่กลายเป็นอุบัติเหตุ

  1. Contract-first — OpenAPI / schema ในฐานะ spec ที่ตรวจได้อัตโนมัติ
  2. Layering ที่ agent ทำงานด้วยง่าย และ layering ที่ทำให้มันหลงทาง
  3. Database migration กับ agent — งานอันตรายที่สุด และ guardrail ที่ต้องมีก่อนเริ่ม
  4. Idempotency, ขอบเขต transaction และ error taxonomy ที่ agent ใช้ตัดสินใจได้
  5. การจัดการ secret และ env ตอน agent เขียนโค้ด — กฎที่ห้ามยืดหยุ่น
  6. Background job, queue, retry — สามอย่างที่ agent ออกแบบผิดเป็นประจำ
  7. Observability ตั้งแต่บรรทัดแรก — log ที่ agent ใช้ debug ตัวเองได้รอบหน้า
  8. LAB Aสร้าง API จาก OpenAPI spec พร้อม migration ที่มี rollback
  9. LAB Bให้ agent หา bug จริงจาก log อย่างเดียว ห้ามบอกว่าพังตรงไหน
ผลลัพธ์ชุด guardrail สำหรับงาน data ที่เอาไปใช้กับ repo ตัวเองได้เลย

Multi-Agent Orchestration

ใช้หลาย agent เมื่อมันชนะจริง และรู้ว่าเมื่อไหร่มันแพ้ agent เดียว

ความปลอดภัยและโมเดลภัยคุกคาม

agent ที่อ่านอินเทอร์เน็ตได้และรันคำสั่งได้ คือ attack surface ชนิดใหม่

  1. โมเดลภัยคุกคามของ coding agent — ต่างจาก web app ตรงไหน และทำไม checklist เดิมใช้ไม่ได้
  2. Prompt injection ผ่านเนื้อหาที่ agent อ่าน — issue, README, หน้าเว็บ, log, แม้แต่ชื่อไฟล์
  3. Tool poisoning และ rug-pull ใน MCP — เมื่อ description เปลี่ยนหลังติดตั้งไปแล้ว
  4. Supply chain ของ skill / plugin / MCP — สิ่งที่ติดตั้งคือโค้ดที่รันด้วยสิทธิ์ของคุณ
  5. ออกแบบขอบเขตสิทธิ์ — allowlist, deny rule, sandbox และการคุม network egress
  6. Secret handling — ทำไม .env ที่หลุดเข้า context คือการรั่วที่ย้อนกลับไม่ได้
  7. เส้นทางขโมยข้อมูลที่มองไม่เห็น — curl, git push, webhook, artifact ที่ถูกอัปโหลด
  8. Agent ที่ปล่อยรันเอง กับการคุม blast radius
  9. LABred-team เวิร์กโฟลว์ของตัวเอง ฝัง injection 5 แบบ วัดว่าติดกี่แบบ
