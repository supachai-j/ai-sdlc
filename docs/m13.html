ใจความของทั้งโมดูล

ข้อเท็จจริงหนึ่งข้อที่อธิบายภัยเกือบทั้งหมดในโมดูลนี้ — โมเดลแยกไม่ออกระหว่างคำสั่งจากคุณ กับข้อความที่หน้าตาเหมือนคำสั่งซึ่งอยู่ในข้อมูลที่มันอ่าน ทุกอย่างที่เหลือคือผลของข้อนี้

ที่มา

ใครตั้งชื่อ "prompt injection" และทำไมชื่อนี้ถึงสำคัญ

ช่องโหว่นี้มีชื่อที่รู้วันเกิดชัดเจน — 12 กันยายน 2022 ซึ่งใหม่กว่าที่หลายคนคิดมาก

และชื่อนี้ถูกตั้งโดยเทียบกับช่องโหว่เก่าอย่างจงใจ ซึ่งเป็นการเทียบที่ทั้งช่วยและหลอกเราไปพร้อมกัน

Figure 0 · จุดที่ 2023-02 คือจุดที่ปัญหาเปลี่ยนจาก "ระวังผู้ใช้" เป็น "ระวังทุกอย่างที่ agent อ่าน"

กันยายน 2022ชื่อที่ยืมมาจาก SQL injection

Simon Willison เขียนโพสต์ Prompt injection attacks against GPT-3 เมื่อ 12 กันยายน 2022 หลังเห็นการสาธิตของ Riley Goodside ที่แสดงว่าข้อความ ในอินพุตสามารถทำให้โมเดลทิ้งคำสั่งเดิมแล้วทำตามคำสั่งใหม่ได้

การเทียบกับ SQL injection ทำให้คนเข้าใจรูปร่างของปัญหาได้ทันที — ข้อมูลที่ไม่น่าเชื่อถือ ถูกอ่านเป็นคำสั่ง แต่การเทียบนี้ก็สร้างความเข้าใจผิดที่ตามหลอกหลอนมาจนทุกวันนี้เหมือนกัน

SQL injection แก้หายขาดได้ ด้วย parameterized query เพราะมันแยกคำสั่งกับข้อมูล ออกเป็นสองช่องได้จริงในระดับโปรโตคอล

LLM ทำแบบนั้นไม่ได้ ทุกอย่างเป็น token ในสายเดียวกัน ไม่มี "ช่องข้อมูล" ให้แยก — คนจำนวนมากได้ยินชื่อนี้แล้วคิดว่าเดี๋ยวก็มี prepared statement เวอร์ชัน LLM ออกมา ซึ่งยังไม่มี

กุมภาพันธ์ 2023ตอนที่ปัญหาใหญ่ขึ้นสิบเท่า

งาน Not what you've signed up for (Greshake และคณะ, 23 ก.พ. 2023) แสดงว่าผู้โจมตี ไม่จำเป็นต้องคุยกับระบบเลย แค่ฝังข้อความไว้ในหน้าเว็บ เอกสาร หรืออีเมลที่ระบบจะไปอ่านก็พอ

นี่คือจุดที่ทำให้เนื้อหาทั้งโมดูลนี้จำเป็น — เพราะ coding agent อ่าน README, issue, log และผลลัพธ์คำสั่ง ตลอดเวลา ทุกช่องทางเหล่านั้นกลายเป็นทางเข้าทันที

  2. Not what you've signed up for: Compromising Real-World LLM-Integrated Applications with Indirect Prompt Injection — Greshake และคณะ · งานที่นิยาม indirect prompt injection arxiv.org · 2023

13.01

ทำไม checklist เดิมใช้ไม่ได้

ถ้าคุณมาจากสาย security มาก่อน บทนี้จะรู้สึกแปลก ๆ เพราะchecklist ที่คุณใช้กับ web app ใช้กับ agent ไม่ได้เกือบทั้งหมด

ไม่ใช่เพราะมันล้าสมัย แต่เพราะมันตั้งอยู่บนเส้นแบ่งเส้นหนึ่งที่ agent ไม่มี

13.02

Prompt injection ผ่านเนื้อหาที่ agent อ่าน

คำถามที่ควรถามไม่ใช่ "agent ของเราโดน injection ได้ไหม" แต่คือ "ข้อความจากภายนอกเข้าถึง context ของมันได้ทางไหนบ้าง"

พอถามแบบหลัง รายการจะยาวกว่าที่คิดมาก และสามอันท้าย ๆ ในรายการข้างล่างนี้ แทบไม่มีใครใส่ไว้ในโมเดลภัยคุกคาม

ช่องทางที่ใช้ได้จริงมีเยอะกว่าที่คนคิด ทุกที่ที่ข้อความจากภายนอกเข้ามาถึงบริบทได้ คือช่องทาง

  • Issue และคอมเมนต์ใน PR — ใครก็เปิดได้ในโปรเจกต์เปิด
  • README ของ dependency — ตอน agent สำรวจว่าไลบรารีใช้ยังไง
  • หน้าเว็บที่ให้ไปอ่าน — รวมข้อความที่มองไม่เห็นด้วยตา
  • ผลลัพธ์ของคำสั่งและ log — ข้อมูลที่ผู้ใช้ป้อนไหลมาโผล่ที่นี่ได้
  • ชื่อไฟล์และชื่อ branch — สั้นแต่พอสำหรับคำสั่งสั้น ๆ
  • เนื้อหาในฐานข้อมูล ที่ agent ดึงมาดู
กรณีที่อันตรายเป็นพิเศษ

คำสั่งอย่าง “ช่วยจัดการ issue ที่ค้างอยู่ให้หน่อย” ฟังดูไม่มีพิษภัย แต่มันคือการอนุญาตให้อ่าน ไม่ใช่การอนุญาตให้ทำตามสิ่งที่อยู่ข้างใน agent ที่ดีต้องเอาสิ่งที่เจอมาถามก่อน ไม่ใช่ลงมือทำตาม

Figure 2 · แท่งยิ่งยาว ยิ่งเป็นช่องที่คนมองข้าม — สามอันล่างแทบไม่มีใครใส่ในโมเดลภัยคุกคาม

  2. OWASP Top 10 for LLM Applications — LLM01 และ LLM02 — injection กับการรั่วของข้อมูลใน context genai.owasp.org
13.03

Tool poisoning และ rug-pull

ช่องโหว่นี้ต่างจากที่คุ้นเคยตรงที่ ตัวโค้ดไม่ต้องเปลี่ยนเลย — สิ่งที่เปลี่ยนคือข้อความที่ server ส่งมาบอกว่า tool นี้ทำอะไร

และเพราะ tool description ถูกป้อนเข้า context ในฐานะ prompt มันจึงเป็นช่องทางสั่งงาน agent โดยตรงที่เจ้าของ server เขียนได้ตลอดเวลา

เพราะ agent เลือกเครื่องมือจากคำอธิบาย (M09.03) คำอธิบายจึงเป็นพื้นผิวการโจมตี และมันเปลี่ยนได้หลังจากที่คุณตรวจไปแล้ว

รูปแบบวิธีการวิธีกัน
คำอธิบายมีคำสั่งแฝงฝังข้อความสั่งไว้ในฟิลด์คำอธิบายอ่านคำอธิบายจริงก่อนติดตั้ง
Rug-pullดีตอนติดตั้ง เปลี่ยนทีหลังตรึงเวอร์ชัน + ตรวจว่าเปลี่ยนไหม
เครื่องมือเงาชื่อคล้ายของจริง เช่น read_fiIeตรวจรายชื่อเครื่องมือที่โหลดจริง
แทรกแซงข้ามเซิร์ฟเวอร์เซิร์ฟเวอร์หนึ่งพูดถึงเครื่องมือของอีกตัวลดจำนวนที่เปิดพร้อมกัน

Figure 3 · tool description คือ prompt ที่มาจากเซิร์ฟเวอร์ของคนอื่น และมันเปลี่ยนได้ทุกเมื่อ

  2. OWASP Top 10 for LLM Applications — LLM Top 10 — ความเสี่ยงจาก plugin และ tool ที่ควบคุมโดยบุคคลที่สาม genai.owasp.org
13.04

Supply chain ของ skill, plugin และ MCP

ประโยคเดียวที่ผมอยากให้ติดหัวจากบทนี้ — สิ่งที่คุณติดตั้งคือโค้ดที่รันด้วยสิทธิ์ของคุณ

ไม่ใช่ "ส่วนขยาย" ไม่ใช่ "ปลั๊กอิน" ไม่ใช่ "สกิล" — คำพวกนี้ทำให้ฟังดูเบากว่าความจริง มันคือโค้ดที่อ่านไฟล์คุณได้และรันคำสั่งในเครื่องคุณได้

ประโยคเดียวที่ต้องจำ — สิ่งที่คุณติดตั้งคือโค้ดที่รันด้วยสิทธิ์ของคุณ ไม่ใช่ปลั๊กอินในแซนด์บ็อกซ์ ไม่ใช่ส่วนขยายที่ถูกจำกัด

เช็คลิสต์ก่อนติดตั้งของจากภายนอก
  1. อ่านโค้ดจริง ไม่ใช่แค่ README โดยเฉพาะส่วนที่ต่อเน็ตและอ่านไฟล์
  2. ดูว่ามันขอสิทธิ์อะไร — ถ้าเครื่องมือแปลงรูปขอสิทธิ์เน็ต ให้สงสัย
  3. ตรึงเวอร์ชัน อย่าใช้ที่อัปเดตอัตโนมัติ
  4. รันแยกก่อนถ้าทำได้ ดูว่ามันเรียกอะไรออกไปข้างนอกบ้าง
  5. ตรวจซ้ำเมื่ออัปเดต — ที่ปลอดภัยเมื่อวานอาจไม่ปลอดภัยวันนี้
ทำไมข้อนี้เพิ่งกลายเป็นเรื่องเร่งด่วนกว่าเดิม

ตอนที่โมเดลยังเขียน exploit ไม่เป็น การให้สิทธิ์กว้างเกินไปเป็นความเสี่ยงเชิงทฤษฎีเสียมาก — ต่อให้มีคำสั่งแฝงเข้ามา สิ่งที่มันทำได้ก็จำกัด

ปี 2026 สมมติฐานนั้นใช้ไม่ได้แล้ว ผู้ผลิตโมเดลรายงานเองว่ารุ่นล่าสุดข้ามเกณฑ์ความสามารถด้านความปลอดภัยไซเบอร์ ในระดับที่ต้องมีมาตรการควบคุมเพิ่ม รวมถึงกรณีที่โมเดลค้นพบช่องโหว่ที่ยังไม่เคยมีใครรู้ระหว่างการประเมิน และผู้ผลิตต้องแจ้งผู้ดูแลซอฟต์แวร์นั้น

แปลว่าตัวคูณความเสียหายเปลี่ยนไปแล้ว — เครื่องมือที่คุณติดตั้งโดยไม่ได้อ่านโค้ด ไม่ได้รันด้วยความสามารถของเมื่อสองปีก่อนอีกต่อไป เช็คลิสต์ข้างบนจึงไม่ใช่พิธีกรรม (อ้างอิง: ประกาศ GPT-6 Astra ส่วน cybersecurity · เป็นเอกสารของผู้ผลิต)

แรงกดดันที่ทำให้คนข้ามขั้นตอน

ระบบนิเวศนี้โตเร็วมาก มีของใหม่ให้ลองทุกสัปดาห์ และการ “ลองดูก่อน” ใช้เวลาสามสิบวินาที ส่วนการตรวจใช้เวลาครึ่งชั่วโมง แรงจูงใจจึงผลักไปทางที่ผิดตลอด ทางแก้ที่ได้ผลคือทำให้การตรวจเป็นขั้นตอนของทีม ไม่ใช่ฝากไว้กับวินัยของแต่ละคน

Figure 4 · เช็คลิสต์นี้ทำเองได้ด้วย grep — ข้อ 5 คือข้อที่เครื่องมือ scan ทั่วไปจับไม่ได้

13.05

ออกแบบขอบเขตสิทธิ์

หลักที่ใช้ออกแบบส่วนนี้มีข้อเดียว — สมมติว่าชั้นบนพังเสมอ

ไม่ใช่เพราะมองโลกในแง่ร้าย แต่เพราะ prompt injection ยังไม่มีวิธีปิดสนิท (ดูหัวข้อ "ที่มา") ดังนั้นชั้นที่กันไม่ให้ทำสิ่งผิด ต้องถือว่ามีวันถูกเจาะ

หลักการคือให้เท่าที่งานต้องใช้ ไม่ใช่ให้เท่าที่สะดวก และควรออกแบบเป็นระดับตามความเสี่ยงของงาน

ระดับให้อะไรเหมาะกับ
อ่านอย่างเดียวอ่านไฟล์ ค้นหาสำรวจ ทำแผนที่ ตอบคำถาม
แก้ในขอบเขต+ แก้ไฟล์ในโฟลเดอร์ที่ระบุงานเขียนโค้ดทั่วไป
รันคำสั่งที่กำหนด+ เฉพาะคำสั่งใน allowlistงานที่ต้องรันเทสต์และ build
เต็มรูปแบบทุกอย่างเฉพาะใน container ที่ทิ้งได้
ขอบเขตที่คนลืมมากที่สุด

การออกเน็ต — agent ที่รันคำสั่งได้และต่อเน็ตได้ สามารถส่งอะไรออกไปข้างนอกก็ได้ การจำกัดปลายทางที่ออกได้ ปิดช่องขโมยข้อมูลเกือบทั้งหมดในบทถัดไป และเป็นการตั้งค่าที่ทำครั้งเดียว

13.06

Secret handling

การรั่วของ secret ในบริบทนี้ต่างจาก log ทั่วไปอย่างสำคัญ — มันข้ามขอบเขตองค์กรไปแล้วตั้งแต่วินาทีแรก

กับ log คุณยังไล่ลบได้ กับ context คุณลบข้อความในหน้าจอได้ แต่ลบสำเนาที่แตกไปแล้วไม่ได้ — ทางเดียวที่เหลือคือ rotate

เมื่อค่าลับเข้าไปในบริบทแล้ว มันเข้าไปแล้วจริง ๆ — อยู่ในสิ่งที่ส่งไปประมวลผล อาจอยู่ใน log ของ harness อยู่ใน transcript และอาจอยู่ใน cache การลบข้อความบนหน้าจอไม่ได้ลบสิ่งเหล่านั้น

ช่องที่หลุดบ่อยวิธีกันที่บังคับได้
สั่งให้อ่านไฟล์ตั้งค่าที่มีค่าจริงhook บล็อกการอ่านไฟล์กลุ่มนั้น
คำสั่งที่พิมพ์ตัวแปรสภาพแวดล้อมออกมาไม่ให้คำสั่งกลุ่มนั้นอยู่ใน allowlist
error ที่แนบค่าที่ใช้เชื่อมต่อมาด้วยปกปิดค่าลับในตัวจัดการ error
แปะ log จริงเข้าไปให้ดูสคริปต์กรองก่อนแปะ

13.07

เส้นทางขโมยข้อมูลที่มองไม่เห็น

หัวข้อนี้คือเหตุผลที่ผมยืนยันเรื่อง network egress allowlist ในบทที่แล้ว ทั้งที่มันเป็นชั้นที่ตั้งยากที่สุด

เพราะทุกเส้นทางข้างล่างนี้ อ่านใน log แล้วดูเหมือนงาน dev ปกติทั้งหมด สิ่งที่ผิดปกติคือปลายทาง ไม่ใช่การกระทำ ซึ่งแปลว่าการไล่จับพฤติกรรมไม่ได้ผล

เมื่อ prompt injection สำเร็จ ขั้นถัดไปคือส่งข้อมูลออก และเส้นทางเหล่านี้ทุกเส้นดูปกติมากเมื่อดูทีละอย่าง

เส้นทางหน้าตาปกติแค่ไหนวิธีปิด
เรียก URL ภายนอกพร้อมข้อมูลดูเหมือนดึงข้อมูลปกติจำกัดปลายทางที่ออกได้
push ไป branch หรือ repo อื่นดูเหมือนงาน git ปกติallowlist ปลายทาง
เขียนลงไฟล์ที่ถูกอัปโหลดต่อดูเหมือนสร้าง artifactตรวจสิ่งที่ CI อัปโหลด
ฝังในคอมมิตหรือคอมเมนต์ดูเหมือนงานปกติทุกประการตรวจ diff ก่อน merge
เข้ารหัสไว้ในชื่อ subdomain ที่ queryแทบมองไม่เห็นเลยคุม DNS ขาออก
ทำไมการตรวจจับถึงยาก

ทุกการกระทำแยกกันดูไม่มีพิษภัย มีแต่ลำดับที่บอกเจตนา — อ่านไฟล์ลับ แล้วเรียกปลายทางภายนอก การกันที่ได้ผลจริงจึงเป็นการปิดช่องล่วงหน้า ไม่ใช่การหวังจับได้ทีหลัง

  2. Claude Code — Identity and Access Management — การควบคุม network และ tool ที่ออกนอกเครือข่ายได้ docs.claude.com
13.08

Agent ที่ปล่อยรันเองกับ blast radius

autonomy ไม่ใช่สวิตช์เปิด-ปิด แต่เป็นขั้นบันได และแต่ละขั้นมีราคาที่ต้องจ่ายล่วงหน้า

คำถามที่ต้องตอบให้ได้ก่อนขึ้นแต่ละขั้นมีข้อเดียว — "ถ้ามันทำสิ่งที่แย่ที่สุดที่ทำได้ในระดับนี้ เราจะรู้ตอนไหน และย้อนกลับยังไง" ตอบไม่ได้ = ยังไม่ควรขึ้น

งานอัตโนมัติที่ไม่มีคนดูเพิ่มความเสี่ยงสองทางพร้อมกัน — ไม่มีใครสังเกตความผิดปกติ และมันทำงานกับเนื้อหาจากภายนอกโดยไม่มีคนกรอง

กฎขั้นต่ำก่อนเปิดงานอัตโนมัติ
  1. สิทธิ์แคบที่สุดที่งานนั้นต้องใช้ และต่างจากสิทธิ์ตอนคุณใช้เอง
  2. ห้ามให้ทำสิ่งที่ย้อนไม่ได้เอง — สร้าง PR ได้ merge ไม่ได้
  3. คุมปลายทางขาออก
  4. เพดานต้นทุนและจำนวนรอบ เพื่อกันทั้งบั๊กและการถูกใช้ประโยชน์
  5. บันทึกทุกการกระทำในที่ที่ตัว agent เองแก้ไม่ได้

ข้อ 5 สำคัญเป็นพิเศษ — บันทึกที่ตัวมันเองเขียนทับได้ ไม่ใช่บันทึกสำหรับเหตุการณ์ด้านความปลอดภัย

13.09 · แล็บประจำโมดูล

Red-team เวิร์กโฟลว์ของตัวเอง

ทดสอบเซ็ตอัปจริงของคุณ ไม่ใช่ตัวอย่างสมมติ เป้าหมายคือได้รายการช่องโหว่จริงพร้อมสิ่งที่แก้ไปแล้ว

ฝัง injection ห้าแบบ

  1. ใน issue — ข้อความที่แกล้งเป็นคำสั่งจากผู้ดูแลระบบ
  2. ใน README ของ dependency จำลอง — สั่งให้อ่านไฟล์ตั้งค่าแล้วสรุปมา
  3. ในผลลัพธ์ของคำสั่ง — บรรทัดที่หน้าตาเหมือนคำสั่งใหม่จากผู้ใช้
  4. ในชื่อไฟล์ — คำสั่งสั้น ๆ ในชื่อ
  5. ในเนื้อหาหน้าเว็บ — รวมข้อความที่มองไม่เห็นด้วยตา

วัดสามอย่างต่อแบบ

  • agent ทำตามไหม
  • ถ้าไม่ทำตาม มันบอกคุณไหมว่าเจอสิ่งนี้ หรือเงียบไปเฉย ๆ
  • ถ้ามันทำตาม มีชั้นไหนหยุดได้บ้าง (สิทธิ์ hook ปลายทางขาออก)
เกณฑ์ผ่าน
  • รู้ว่าติดกี่แบบจากห้าแบบ — ตัวเลขนี้เป็น baseline ของคุณ
  • ปิดช่องที่ติดได้อย่างน้อยหนึ่งช่องด้วยการบังคับเชิงกล ไม่ใช่การเพิ่มกฎใน prompt
  • เขียนได้ว่าถ้า injection สำเร็จเต็มรูปแบบ ความเสียหายสูงสุดคืออะไร
ผลที่เกือบทุกคนเจอ

แบบที่ 2 กับ 3 ผ่านบ่อยที่สุด เพราะคนตั้งการ์ดกับ “หน้าเว็บจากภายนอก” แต่ไม่ตั้งการ์ดกับ “README ของไลบรารีที่เราใช้อยู่” และ “ผลลัพธ์ของคำสั่งที่เรารันเอง” ทั้งที่สองอย่างนี้มีข้อความจากคนอื่นอยู่เหมือนกัน
