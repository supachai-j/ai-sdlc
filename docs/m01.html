2021–2022ยุคที่ยังแยกกันอยู่

ตอนนั้นมีสองสายที่เดินแยกกัน สายหนึ่งพยายามทำให้โมเดลคิดเก่งขึ้น — Chain-of-Thought Prompting (Wei และคณะ, ม.ค. 2022) แสดงว่าถ้าให้โมเดลเขียนขั้นตอนการคิดออกมาเป็นข้อความก่อนตอบ มันตอบโจทย์ที่ต้องใช้เหตุผลได้ดีขึ้นมาก

อีกสายพยายามทำให้มันทำอะไรได้จริง — WebGPT (Nakano และคณะ, ธ.ค. 2021) ให้โมเดลใช้ browser ค้นข้อมูลมาตอบ ส่วน MRKL Systems (Karpas และคณะ, พ.ค. 2022) เสนอสถาปัตยกรรมที่ให้โมเดลส่งงานบางอย่างออกไปให้ module ภายนอกทำ แทนที่จะพยายามทำเองทั้งหมด

แต่สองสายนี้ยังไม่ได้มาบรรจบกัน — คิดก็คิดไป ทำก็ทำไป

ตุลาคม 2022จุดที่ทุกอย่างมาเจอกัน

ReAct (Yao และคณะ) เอาสองสายนั้นมารวมในลูปเดียว — ให้โมเดลสลับระหว่างการให้เหตุผล กับการลงมือทำ แทนที่จะทำอย่างใดอย่างหนึ่ง คิดหน่อย → ทำหน่อย → เห็นผล → คิดใหม่ → ทำต่อ

ถ้าย้อนกลับไปดู Figure 1 ในบทถัดไป คุณจะเห็นว่ามันคือ ReAct เป๊ะ ๆ แค่เปลี่ยนจาก paper มาเป็น production code

ที่ผมชอบคือ idea มันเรียบง่ายมากจนดูเหมือนไม่น่าจะเป็น research paper ได้ — "ก็แค่ให้มันคิดสลับกับทำ" แต่ก่อนหน้านั้นไม่มีใครทำแบบนี้

2023 เป็นต้นมาจากงานวิจัยมาเป็นของที่ใช้จริง

Toolformer (Schick และคณะ, ก.พ. 2023) ไปอีกขั้นด้วยการให้โมเดลเรียนรู้เองว่าควรเรียก tool ตอนไหน แทนที่จะต้องบอกในprompt ทุกครั้ง

หลังจากนั้นสิ่งที่เกิดขึ้นส่วนใหญ่ไม่ใช่งานวิจัยแล้ว แต่เป็นงานวิศวกรรม — ทำ tool calling ให้เป็น API ที่มีสัญญาชัดเจน ทำ permission layer ทำ context management ทำโปรโตคอลกลางอย่าง MCP เพื่อให้ tool จากคนละเจ้าคุยกันได้

ห้าชั้นของ harness ที่เราจะดูกันในบท 01.02 ทั้งหมดเป็นของที่เกิดในยุคนี้ ไม่มีชั้นไหนอยู่ใน paper ต้นฉบับเลย มันคือสิ่งที่ต้องเพิ่มเข้ามาเมื่อเอาของจาก paper ไปใช้กับงานจริง

ทำไมประวัติถึงมีประโยชน์กับการ debug

เพราะมันบอกว่าส่วนไหนเป็นแก่นและส่วนไหนเป็นของที่เราใส่เข้าไปเอง

ลูป ReAct เป็นแก่น — แทบไม่พัง ส่วนอีก 5 ชั้นเป็นวิศวกรรมของแต่ละเจ้า — พังได้และพังบ่อย เวลาเจอปัญหา ให้เดาชั้นนอกก่อนเสมอ นี่คือเหตุผลที่ผมบอกในบทถัดไปว่า "โมเดลไม่เก่งพอ" ควรเป็นข้อสรุปสุดท้าย ไม่ใช่ข้อแรก

01.01

Agentic loop จริง ๆ คืออะไร

เอาแบบนี้นะ ถ้าเพื่อนถามผมว่า agent คืออะไร ผมจะตอบว่า — มันคือโปรแกรมที่ถามโมเดลว่า "จะทำอะไรต่อ" แล้วก็ทำตามนั้น วนไปเรื่อย ๆ จนโมเดลบอกว่าพอแล้ว

แค่นั้นจริง ๆ ครับ ไม่มีอะไรมากกว่านี้ ที่มันดูฉลาดจนน่าตกใจ ไม่ได้มาจากความซับซ้อนของโปรแกรม แต่มาจากการที่มันวนลูปนี้หลาย ๆ รอบ

ลูปนี้มีแค่สามขั้น ถาม → ทำ → บอกผล แล้ววนกลับไปถามใหม่

รูปที่ 1 · ลูปทั้งหมดของ agent เส้นสีส้มคือส่วนที่ทำให้มันดูฉลาด — มันได้ลองใหม่พร้อมข้อมูลที่เพิ่งได้มา

messages = [คำสั่งของคุณ]
while True:
    reply = model(messages, tools)      # ขั้น 1 — ถาม
    messages.append(reply)
    if reply.stop_reason != "tool_use":
        break                           # โมเดลไม่ขออะไรแล้ว จบ
    results = [run(call) for call in reply.tool_calls]   # ขั้น 2 — ทำ
    messages.append(results)            # ขั้น 3 — บอกผล

มาดูของจริงสั่งงานหนึ่งงาน เกิดอะไรขึ้นบ้าง

สมมติคุณพิมพ์ว่า “ฟังก์ชัน calculateTotal คำนวณผิดตอนตะกร้าว่าง ช่วยแก้ที” สิ่งที่เกิดขึ้นจริงหลังบ้านเป็นแบบนี้

รอบโมเดลขอโปรแกรมทำ
1ค้นคำว่า calculateTotalรัน grep ได้มา 3 บรรทัด
2ขอเปิดไฟล์ total.tsอ่านมา 120 บรรทัด
3ขอเปิดไฟล์เทสต์อ่านมาอีก 80 บรรทัด
4ขอแก้ไฟล์เขียนทับ สำเร็จ
5ขอรันเทสต์รัน ได้ผลมา 40 บรรทัด
6ไม่ขออะไรแล้ว บอกว่าแก้เสร็จออกจากลูป

จุดที่คนพลาดกันเยอะทุกรอบคุณส่งของเดิมไปใหม่ทั้งหมด

ตรงนี้แหละที่คนตกใจกันตอนรู้ — รอบที่ 6 ไม่ได้ส่งแค่ผลเทสต์นะครับ มันส่งทุกอย่างตั้งแต่รอบ 1 ไปใหม่หมด

คำสั่งของคุณ ผล grep ไฟล์ทั้งไฟล์ เทสต์ทั้งไฟล์ diff ที่แก้ ผลเทสต์ — ไปพร้อมกันอีกรอบ เพราะโมเดลไม่ได้จำอะไรได้เลย ต้องบอกใหม่ทุกครั้ง

รูปที่ 2 · แถบสีน้ำเงินคือของเดิมที่ถูกส่งซ้ำ สังเกตว่ามันโตขึ้นเรื่อย ๆ ส่วนของใหม่แต่ละรอบเล็กนิดเดียว

แปลว่าอะไรกับกระเป๋าเงินคุณ

ไฟล์ที่เปิดตอนรอบ 2 สมมติ 5,000 token คุณไม่ได้จ่ายครั้งเดียวนะ คุณจ่ายในรอบ 2, 3, 4, 5, 6 — ห้าครั้ง

งานที่วน 20 รอบก็คือจ่ายค่าไฟล์นั้นเกือบยี่สิบครั้ง นี่คือเหตุผลที่ M03 พูดเรื่อง cache เยอะมาก และทำไม M02 ถึงบอกว่าบริบทคืองบประมาณ ไม่ใช่ถังที่เทใส่ได้เรื่อย ๆ

เรื่องที่เข้าใจผิดกันบ่อย“มันจำได้ว่าเมื่อกี้ทำอะไร”

ไม่ได้จำครับ จำไม่ได้เลยสักนิด ที่มันดูเหมือนจำได้ เพราะโปรแกรมส่งประวัติทั้งหมดกลับเข้าไปให้ทุกครั้งต่างหาก

ฟังดูเป็นเรื่องเล็ก แต่มันเปลี่ยนวิธีคิดเยอะ — ถ้าข้อมูลไม่ได้อยู่ในกองที่ส่งไป มันไม่รู้ และถ้าเราตัดของเก่าทิ้ง มันลืมทันทีเหมือนไม่เคยเกิดขึ้น

พอเข้าใจข้อนี้ อาการอย่าง “คุยไปนาน ๆ แล้วมันเริ่มลืมสิ่งที่ตกลงกันไว้” จะเลิกดูลึกลับ กลายเป็นเรื่องที่เดาได้และแก้ได้

แล้วอะไรทำให้ agent ตัวหนึ่งเก่งกว่าอีกตัว

ในเมื่อลูปเหมือนกันหมด ความต่างมาจากสามอย่างรอบ ๆ ลูป และทั้งสามอย่างอยู่ในมือคุณ

  • เครื่องมือที่ให้ — ตัวที่รันเทสต์ได้ ตรวจงานตัวเองได้ ตัวที่รันไม่ได้ต้องเดาเอา
  • ข้อมูลที่ใส่ให้ — มันเห็นเท่าที่เราส่งไป ไม่มากไม่น้อยกว่านั้น
  • ขอบเขตที่วางไว้ — อะไรทำเองได้ อะไรต้องหยุดถาม

ทั้งหลักสูตรนี้คือการเล่นกับสามอย่างนี้ให้เป็นระบบ ไม่มีอย่างที่สี่จริง ๆ

ลองเองสัก 5 นาที

สั่งงานเล็ก ๆ กับ agent ที่คุณใช้อยู่ แล้วนับว่ามันเรียกเครื่องมือกี่ครั้งกว่าจะจบ เอาจำนวนรอบคูณขนาดบริบทคร่าว ๆ ดู ตัวเลขที่ได้มักทำให้คนอึ้ง และเป็นแรงจูงใจที่ดีที่สุดสำหรับ M02

01.02

กายวิภาคของ harness

ลูปในบทที่แล้วคือแก่น แต่ของที่คุณใช้จริงไม่ใช่ลูปเปล่า ๆ มันมีอีกห้าชั้นห่อไว้รอบนอก เราเรียกทั้งก้อนนี้ว่า harness

ที่ต้องรู้จักทั้งห้าชั้นไม่ใช่เพื่อความรู้รอบตัวนะครับ แต่เพราะ เวลามันทำอะไรแปลก ๆ คำถามที่ช่วยได้คือ "อาการนี้มาจากชั้นไหน" ไม่ใช่ "ทำไมโมเดลมันโง่จัง" — คำถามแรกพาไปเจอทางแก้ คำถามหลังพาไปเปลี่ยนโมเดลซึ่งมักไม่ใช่สาเหตุ

รูปที่ 3 · ลูปอยู่ตรงกลาง มีห้าชั้นห่อไว้ ชั้นสีส้มคือชั้นที่คนเจอปัญหาบ่อยที่สุด

ชั้นทำอะไรพังแล้วอาการเป็นยังไง
1 · System promptบอกบทบาทกับกฎทำผิด convention เดิม ๆ ทุกครั้งเหมือนกันหมด
2 · Tool registryรายการเครื่องมือหยิบเครื่องมือผิดตัวซ้ำ ๆ
3 · Context assemblerเลือกว่าจะส่งอะไรลืมของที่เพิ่งคุย วนทำงานเดิม
4 · Permissionอนุญาตหรือห้ามค้างรออนุมัติ หรือทำสิ่งที่ไม่ควรทำ
5 · Result rendererแปลงผลเป็นข้อความมั่นใจแต่ผิด

ชั้นที่ 3ชั้นที่คนบ่นถึงมากที่สุด

ชั้นนี้ตอบคำถามว่า “รอบนี้จะส่งอะไรเข้าไปบ้าง” ซึ่งฟังดูง่าย แต่พอคุยกันยาว ๆ จนใกล้เต็มที่ มันต้องเลือกว่าจะตัดอะไร สรุปอะไร เก็บอะไร

อาการคลาสสิกคือ “คุยไปสักพักมันเริ่มลืม” กับ “มันวนทำสิ่งที่ทำไปแล้ว” ทั้งคู่คือชั้นนี้ตัดของที่ยังต้องใช้ทิ้งไป M02 ทั้งโมดูลคือการจัดการชั้นนี้

ชั้นที่ 5ชั้นที่โดนโทษน้อยที่สุด แต่ผิดบ่อยที่สุด

ชั้นนี้ผมอยากเล่าให้ฟังหน่อย เพราะมันหลอกคนได้เก่งมาก

สมมติ agent สั่งรันเทสต์ แล้ว output ออกมา 3,000 บรรทัด เทสต์ที่แดงอยู่บรรทัดที่ 2,400 แต่ harness ตัดเหลือแค่ 200 บรรทัดแรกก่อนส่งเข้าโมเดล

โมเดลก็เลยเห็นแต่เทสต์ที่ผ่าน แล้วสรุปอย่างมั่นใจว่าเรียบร้อยดี คุณจะเห็นเป็น "มันตอบผิดแบบมั่นใจ" แล้วก็สรุปว่าโมเดลไม่เก่ง

แต่จริง ๆ โมเดลสรุปถูกแล้วนะ ถูกต้องตามข้อมูลที่มันได้รับ — ปัญหาอยู่ที่ท่อ ไม่ได้อยู่ที่คนอ่าน

เวลาเจอปัญหา ให้ไล่ตามนี้
  1. มันเห็นข้อมูลถูกไหม — ชั้น 3 กับ 5
  2. มันมีเครื่องมือที่เหมาะไหม — ชั้น 2
  3. มันโดนห้ามอะไรอยู่หรือเปล่า — ชั้น 4
  4. กฎที่เราให้ไปขัดกันเองไหม — ชั้น 1

สังเกตว่า “โมเดลไม่เก่งพอ” ไม่อยู่ในลิสต์ เพราะมันควรเป็นข้อสรุปสุดท้ายหลังตัดสี่ข้อบนทิ้งแล้ว และจากประสบการณ์ มันแทบไม่เคยเป็นคำตอบจริง ๆ

01.03

Tool-use protocol และกฎที่ห้ามผิด

เวลาเราพูดว่า "agent เรียก tool" มันชวนให้เข้าใจผิดนิดนึง เพราะโมเดลไม่ได้เรียกอะไรเลย

สิ่งที่มันทำได้อย่างเดียวคือ generate text ออกมา แล้วบังเอิญ text นั้นเป็น structured block ที่บอกว่า "อยากให้รัน read_file ด้วย path นี้นะ" — คนที่รันจริงคือโปรแกรมของเรา

ฟังดูเป็นเรื่องความหมาย แต่มันสำคัญ เพราะแปลว่าเราคุมทุกอย่างที่เกิดขึ้นจริง โมเดลได้แค่ "ขอ" เท่านั้น

Figure 4 · โมเดลส่ง tool_use พร้อม id · โปรแกรมรันจริง · ส่ง tool_result กลับโดยอ้าง id เดิม

กฎข้อ 11 reply มีหลาย tool call ได้

ถ้างานไม่ depend กัน โมเดลจะขอมาพร้อมกันเลย เช่นขอเปิด 3 ไฟล์รวดเดียว แทนที่จะเปิดทีละไฟล์แล้วรอผล อันนี้ดีมาก เพราะลดจำนวน round trip ซึ่งลดทั้งเวลาและเงิน (ย้อนไปดู Figure 2 — จำนวนรอบ × ขนาด context คือบิลของเรา)

กฎข้อ 2ต้องส่ง result กลับครบทุกตัวใน message เดียว

อันนี้คือกฎที่ผิดแล้วไม่มีใครรู้เลย และผมอยากให้จำที่สุดในบทนี้

ถ้าโมเดลขอมา 3 อย่าง เราต้องรวม result ทั้ง 3 ไว้ใน message เดียวแล้วส่งกลับ ห้ามแยกส่งทีละอัน 3 ครั้ง

ถามว่าถ้าแยกส่งจะเป็นไง — มันไม่ error นะ ไม่มีอะไรแดง แต่ conversation structure จะกลายเป็นว่า "ขอ 3 ได้กลับมาทีละอัน" แล้วรอบต่อ ๆ ไปโมเดลจะเรียนรู้จาก pattern นั้น ว่าขอพร้อมกันแล้วไม่เวิร์ก แล้วค่อย ๆ เลิกขอแบบ parallel

อาการที่เห็นคือ agent ที่ตอนแรกเร็ว แล้วช้าลงเรื่อย ๆ ใช้ round เยอะขึ้น บิลแพงขึ้น โดยหาสาเหตุไม่เจอ — เป็น bug ที่ debug ยากมากถ้าไม่รู้ว่าต้องมองหาอะไร

กฎข้อ 3tool ที่ fail ต้องส่ง result กลับ ห้ามเงียบ

สัญชาตญาณของ dev คือเจอ error ก็ throw แล้วจบ แต่ในลูปนี้การไม่ส่ง result กลับ ทำให้ conversation เสียสภาพ — มี tool_use ที่ไม่มีคู่ แล้วโมเดลจะเดาเอาว่าเกิดอะไรขึ้น

ที่ถูกคือส่งกลับพร้อม flag ว่า error แล้วให้โมเดลตัดสินใจเอง ซึ่งมันทำได้ดีกว่าที่คิดเยอะ ถ้า error message บอกอะไรที่ใช้ได้

Error message = ช่องทาง teach agent ที่ถูกที่สุดที่มี

เทียบสองอันนี้ อันแรกทำให้มันเดาสุ่มแล้ว retry 3 รอบ อันหลังทำให้แก้ถูกในรอบเดียว

// ทำให้วนแก้ไปเรื่อย
ENOENT: no such file or directory

// ทำให้แก้ถูกทันที
ENOENT: ไม่พบ src/billing/index.ts
  ไฟล์ใน dir นี้: total.ts, tax.ts, discount.ts
  ถ้าต้องการ entry point ของ billing ให้ใช้ total.ts

cost ของการเขียนแบบหลัง = ครั้งเดียว · payoff = ทุกครั้งที่ใครก็ตาม (คนหรือ agent) เจอมัน เรื่องนี้เป็นแกนของ M05 ทั้งโมดูล

Engineering noteเคสจริงที่เจอบ่อยเวลาเขียน harness เอง

ถ้าคุณเขียน tool runner เอง มี 3 อย่างที่มักลืมและกัดทีหลัง

  • Timeout ต่อ tool call — คำสั่งที่ hang จะทำให้ทั้ง loop ค้าง ตั้ง timeout แล้วส่งกลับเป็น error result ดีกว่าปล่อยค้าง
  • Truncate output แล้วต้องบอกด้วย — ถ้าตัด output ให้ต่อท้ายว่า [truncated 2,860 more lines] ไม่งั้นเข้าเคส Layer 5 ที่เล่าไปในบทที่แล้ว
  • รัน parallel จริง ๆ — ถ้าโมเดลขอ 3 อย่างแล้วเรารัน sequential เราเสียประโยชน์ของกฎข้อ 1 ไปฟรี ๆ ใช้ Promise.all ไปเลย

01.04

stop_reason ทุกค่า และการจัดการแต่ละแบบ

ทุกครั้งที่โมเดลตอบกลับ มันแนบค่ามาด้วยตัวนึงชื่อ stop_reason บอกว่าทำไมถึงหยุดพูด ค่าเล็ก ๆ ตัวเดียวนี่แหละคือ debug info ที่ดีที่สุดที่เรามี

แล้วก็เป็นจุดที่ code ส่วนใหญ่เขียนผิดด้วย เพราะคนมักเขียนว่า "ไม่ใช่ tool_use ก็แปลว่าเสร็จ" ซึ่งไม่จริง

Figure 5 · แยกทุก branch ให้ครบ โดยเฉพาะ max_tokens ที่หน้าตาเหมือนคำตอบปกติทุกอย่าง

ตัวที่อันตรายสุดmax_tokens กับไฟล์ที่เขียนไม่จบ

ทุก request มีเพดานว่า generate ได้ยาวสุดเท่าไร พอชนเพดาน มันไม่ได้สรุปให้จบนะ มันหยุดกลางประโยค แล้วแนบ max_tokens มาบอก 

// bug คลาสสิก — กลืน max_tokens เงียบ ๆ
if (reply.stop_reason === "tool_use") {
    runTools(reply)
} else {
    done(reply)          // ← max_tokens ก็มาตกที่นี่ แล้วถูกนับว่าเสร็จ
}

// ที่ควรเป็น
switch (reply.stop_reason) {
    case "tool_use":    runTools(reply); break
    case "max_tokens":  throw new IncompleteOutput(reply)   // ← ต้องแยก
    case "refusal":     escalateToHuman(reply); break
    case "pause_turn":  continueTurn(reply); break
    case "end_turn":    done(reply); break
}

เคสที่เจอบ่อยสุดคือสั่งให้เขียนไฟล์ยาว ๆ แล้วได้ไฟล์ที่ขาดครึ่ง หรือให้ generate JSON config แล้วได้ JSON ที่ parse ไม่ผ่าน แล้ว step ถัดไปก็ทำงานต่อบนของที่ไม่สมบูรณ์ — นี่คือที่มาของอาการ "มันเขียนไฟล์มาแล้วพัง" จำนวนมากที่คนโทษว่าโมเดลสะเพร่า

end_turn ก็มีกับดักนะ

end_turn บอกว่าโมเดลพูดจบ ไม่ได้บอกว่างานสำเร็จ agent อาจตอบว่า "ผมแก้ไม่ได้ครับ ต้องให้คนดู" แล้วจบด้วย end_turn เหมือนกัน

การตัดสินว่า "สำเร็จ" ต้องมาจากเกณฑ์ของเรา ไม่ใช่จากค่านี้ — typecheck ผ่านไหม test เขียวไหม diff อยู่ใน scope ไหม เรื่องนี้คือหัวใจของ M12 เลย

  2. Context windows — ความสัมพันธ์ระหว่าง input, output และเพดานความยาว docs.claude.com
01.05

Thinking และ effort

โมเดลรุ่นใหม่ "คิดก่อนตอบ" ได้ คือมัน generate reasoning ออกมาก่อน แล้วค่อยตอบจริง ส่วนนี้นับเป็น output token ที่เราจ่ายเหมือนกันนะ ไม่ได้ฟรี

คนส่วนใหญ่เข้าใจว่า effort สูง = ฉลาดขึ้น ซึ่งไม่ผิด แต่พลาดประเด็นที่สำคัญกว่า — มันเปลี่ยน "วิธีทำงาน" ไม่ใช่แค่ "คุณภาพ" แล้ววิธีทำงานที่เปลี่ยนไปมีผลกับทั้งเวลาและบิล

Figure 6 · effort เปลี่ยน pattern การทำงาน ไม่ใช่แค่ IQ — และมันคือ knob ที่ควรหมุนก่อนเปลี่ยน model

Prompt cruftคำสั่งที่เคยช่วย แต่ตอนนี้กลายเป็นตัวถ่วง

สมัยที่โมเดลยังไม่คิดเองก่อนตอบ การเขียนใน prompt ว่า "think step by step" ช่วยได้จริง แล้วมันก็กลายเป็นคำแนะนำมาตรฐานที่ copy ต่อ ๆ กันมาจนถึงทุกวันนี้

แต่กับโมเดลที่มี thinking อยู่แล้ว คำสั่งแบบนี้ไม่ช่วย และหลายเคสทำให้แย่ลง เพราะไปแทรกแซง process ที่ทำงานดีอยู่แล้ว บวกกับกิน context ทุกรอบ

นี่คือตัวอย่างของสิ่งที่ M12.08 เรียกว่า prompt cruft — คำสั่งหมดอายุที่ยังอยู่เพราะไม่มีใครกล้าลบ เนื่องจากพิสูจน์ไม่ได้ว่าไม่จำเป็น

ลำดับการ debug คุณภาพที่ถูกต้อง
  1. Context — มันเห็นข้อมูลครบไหม มีของรกปนไหม · ฟรี และมักได้ผลมากสุด
  2. Effort — ปรับได้ทันที ไม่ต้องแก้ code · ยังอยู่ใน cache namespace เดิม แต่ถ้าเปลี่ยนกลางบทสนทนา messages cache จะหลุด
  3. Model — แพงสุด กระทบมากสุด และทำให้ cache ที่สะสมมาใช้ไม่ได้

คนส่วนใหญ่กระโดดข้อ 3 ก่อน ซึ่งนอกจากแพงแล้วยังทำให้ไม่รู้ว่าปัญหาจริงคืออะไร — ถ้าเปลี่ยน model แล้วดีขึ้น เราก็ยังไม่รู้ว่าเพราะ model เก่งกว่า หรือเพราะ context เราห่วยมาตลอด

อ่านเพิ่มจากต้นทาง

  1. Extended thinking — thinking ทำงานยังไง และ token ส่วนนี้ถูกคิดเงินยังไง docs.claude.com
  2. Claude Code best practices — แนวทางใช้งานจริง รวมเรื่องเลือกระดับความพยายามให้เหมาะกับงาน anthropic.com/engineering
01.06

Permission model

Layer 4 เป็นชั้นเดียวในห้าชั้นที่มีหน้าที่ "ปฏิเสธ" ชั้นอื่นทำให้ agent ทำงานได้ ชั้นนี้ทำให้มันทำงานได้ เท่าที่ควร

แล้วเพราะมันขวางทางเป็นครั้งคราว คนเลยมองว่าเป็นความรำคาญที่ต้องกำจัด — ซึ่งเป็นการมองผิดที่ราคาแพงมาก

Figure 7 · allowlist ได้ความลื่นไหลของ bypass โดยไม่ต้องรับความเสี่ยงของมัน

ทำไม allowlist ถึงชนะทั้งสองขั้ว

ask ปลอดภัยแต่ทำให้ต้องนั่งกด approve จนเลิกใช้ · bypass สะดวกแต่ให้สิทธิ์เท่า shell ทางออกจริงอยู่ตรงกลาง — ระบุไปเลยว่าคำสั่งกลุ่มไหนรันได้โดยไม่ต้องถาม

ผลคือ agent ทำงานลื่นตลอด happy path — edit code, run test, ดู diff, แก้ต่อ — โดยไม่ต้องขออนุญาตเลย แต่ถ้าจะทำอะไรนอกกรอบ เช่น curl ออกเน็ต หรือ git push มันต้องหยุดถาม

เรื่องที่คนไม่ค่อยพูดถึง — เหตุผลที่คนเปิด bypass มักไม่ใช่ความประมาทนะ แต่เป็นความหงุดหงิดสะสม โดนถามครั้งที่สิบในเช้าวันเดียวแล้วก็กดปิดไป

ประเด็นคือความเสี่ยงไม่ได้อยู่ที่ agent จะ "คิดชั่ว" แต่อยู่ที่มันอ่านเนื้อหาจากภายนอก — GitHub issue ที่ใครก็เปิดได้ · README ของ dependency · หน้าเว็บที่เราให้ไปอ่าน — แล้วในนั้นมีข้อความที่หน้าตาเหมือน instruction ฝังอยู่

ในโหมด bypass ไม่มีอะไรกั้นระหว่างข้อความนั้นกับ shell ของคุณเลย M13 ลงรายละเอียดว่าช่องทางพวกนี้มีอะไรบ้างและปิดยังไง

Permission เป็นส่วนหนึ่งของสิ่งที่เรากำลังวัด

agent ที่รัน test ได้ กับตัวที่รันไม่ได้ คือคนละระบบกัน ตัวแรก verify งานตัวเองได้ ตัวหลังต้องเดา

เวลาเทียบสอง workflow ตาม M12 ถ้า permission ต่างกัน เรากำลังเทียบของที่ต่างกันมากกว่าที่ตั้งใจ — เพราะงั้นต้องระบุ allowlist เป็นส่วนหนึ่งของนิยาม arm ที่ทดสอบ ไม่ใช่ปล่อยให้เป็นค่า default ของใครของมัน

  2. Settings — ตั้ง permission ระดับ user / project / local ยังไง docs.claude.com

01.07

เจ็ดโหมดที่ agent ล้มเหลว

หลังจากดูปัญหาที่คนเจอจริงมาเยอะพอสมควร ผมพบว่า failure เกือบทั้งหมดตกอยู่ใน 7 แบบนี้

ประโยชน์ของการจำได้ไม่ใช่การท่องจำนะ แต่คืออาการแต่ละแบบชี้ไปคนละ layer ทำให้เราเลิกเดาแล้วเริ่ม diagnose ได้

Figure 8 · จับคู่อาการกับที่ที่ต้องไปแก้ · สังเกตว่ามีแค่ 3 ใน 7 ที่แก้ที่ harness ที่เหลือแก้ที่ codebase หรือ process

3 แบบที่เจอบ่อยสุดแยกออกจากกันยังไง

Context ล้น — ลายเซ็นชัดมาก ทำถูกช่วงแรก แล้วเริ่มถามสิ่งที่ตอบไปแล้ว หรือแก้ไฟล์ที่เพิ่งแก้กลับเป็นแบบเดิม จุดสังเกตคืออาการแย่ลงตามความยาวของ session ถ้าเปิด session ใหม่แล้วหาย นั่นแหละใช่ — เป็น test ที่ใช้เวลา 10 วินาทีและแม่นที่สุด

ค้นเกินจำเป็น — ดูเผิน ๆ เหมือนความขยัน แต่จริง ๆ คือ signal ว่า repo structure ไม่สื่อ ทุกไฟล์ที่มันเปิดผิดก่อนเจอไฟล์ที่ถูก คือหลักฐานว่าชื่อหรือที่อยู่เดาไม่ได้ ข้อดีคือวัดเป็นตัวเลขได้ตรง ๆ — นับจำนวนไฟล์ที่เปิดก่อนเจอที่ถูก แล้วใช้เป็น metric ว่าการปรับ repo ตาม M05 ได้ผลจริงไหม

ตัดข้อมูลเงียบ — วินิจฉัยยากสุด เพราะไม่มีอาการภายนอกเลย ผลลัพธ์ดู reasonable น้ำเสียงมั่นใจ แต่ข้อสรุปผิด วิธีจับคือตรวจสิ่งที่มันเห็น ไม่ใช่สิ่งที่มันพูด — ดู raw output ของคำสั่งที่มันรัน แล้วเทียบกับที่มันสรุป ช่องว่างตรงนั้นคือคำตอบ

01.08 · แล็บประจำโมดูล

เขียน mini-harness ~150 บรรทัด

เป้าหมายไม่ใช่ได้เครื่องมือใช้งาน แต่คือทำลายความรู้สึกว่ามันเป็นเวทมนตร์ เมื่อคุณเขียนลูปเองแล้ว ทุกอาการแปลก ๆ หลังจากนี้จะมีที่ทางให้ชี้

ข้อกำหนดต้องมีครบทั้งห้าข้อ

  1. ลูป while ที่วนจนกว่า stop_reason จะไม่ใช่ tool_use และแยกกรณี max_tokens ออกมาชัด ๆ
  2. เครื่องมือสามตัว — อ่านไฟล์ เขียนไฟล์ และรันคำสั่ง
  3. Permission gate ที่เป็น allowlist ไม่ใช่ ask ทุกครั้ง
  4. รองรับ tool call หลายตัวในหนึ่งคำตอบ และส่งผลกลับครบใน message เดียว
  5. นับและพิมพ์จำนวน token กับต้นทุนสะสมทุกรอบ
เกณฑ์ผ่าน
  • สั่งงานที่ต้องใช้เครื่องมือสามรอบขึ้นไปแล้วทำสำเร็จ
  • จงใจให้เครื่องมือ error หนึ่งครั้ง แล้ว agent แก้ทางได้เองโดยไม่ค้าง
  • ตั้งเพดาน token ต่ำจนโดนตัด แล้ว harness ต้องรายงานว่าโดนตัด ไม่ใช่ทำเป็นว่าจบ

เชื่อมกับโมดูลอื่น — M02 ลงลึกที่ชั้น context assembler · M03 เอาตัวนับ token จากแล็บนี้ไปทำบัญชีจริง · M05 แก้สองในเจ็ดโหมดล้มเหลวด้วยการปรับ repo · M13 ต่อยอดชั้น permission เป็นโมเดลภัยคุกคามเต็มรูปแบบ
