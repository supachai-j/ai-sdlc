AI Coding Agent SDLC · Phase 00 · Module 01

กลไกภายในของ Agent

Agent ไม่ใช่กล่องดำ มันคือลูป while ธรรมดาที่ห่อด้วยวิศวกรรมหลายชั้น โมดูลนี้แกะทีละชั้นเพื่อให้เวลามันทำอะไรแปลก ๆ คุณชี้ได้ว่าเกิดที่ชั้นไหน

8 บทเรียน2.5 ชั่วโมง1 แล็บไม่มีข้อกำหนดก่อนหน้า
ใจความของทั้งโมดูล

คนที่ debug agent ไม่เป็น ไม่ใช่เพราะไม่เก่ง แต่เพราะไม่มีแบบจำลองในหัวว่าข้างในมีอะไรบ้าง เมื่อมีแล้ว ปัญหาที่เคยดูลึกลับจะกลายเป็นคำถามว่า “ชั้นไหนพัง”

01.01

Agentic loop จริง ๆ คืออะไร

ตัดทุกอย่างออกจนเหลือแก่น agent คือลูปเดียว โมเดลตอบกลับมาพร้อมคำขอใช้เครื่องมือ โปรแกรมรันเครื่องมือนั้น ส่งผลกลับเข้าไป แล้ววนใหม่จนกว่าโมเดลจะบอกว่าจบ

messages = [user_request]
while True:
    reply = model(messages, tools)
    messages.append(reply)
    if reply.stop_reason != "tool_use":
        break                      # จบงาน หรือถูกตัด หรือถูกปฏิเสธ
    results = [run(call) for call in reply.tool_calls]
    messages.append(results)       # ต้องส่งกลับ "ครบทุกตัว" ใน message เดียว

แค่นี้จริง ๆ ความสามารถทั้งหมดที่เห็นมาจากสามอย่างที่ประกอบเข้ามารอบลูปนี้ — เครื่องมือที่ให้ บริบทที่ใส่ และขอบเขตสิทธิ์ที่วางไว้ ไม่มีเวทมนตร์อื่น

ผลที่ตามมาทันที

ทุกอย่างที่ agent “รู้” ในรอบถัดไป มาจาก messages ล้วน ๆ ถ้าข้อมูลไม่ได้อยู่ในนั้น มันไม่รู้ และถ้ามันอยู่ในนั้นเยอะเกินไป คุณจ่ายเงินและจ่ายความสนใจของโมเดลไปกับสิ่งที่ไม่เกี่ยว

01.02

กายวิภาคของ harness

สิ่งที่คุณใช้จริงไม่ใช่ลูปเปล่า แต่เป็น harness ที่ห่อลูปนั้นไว้ห้าชั้น การรู้ชั้นทั้งห้าคือเครื่องมือ debug ที่ดีที่สุดในโมดูลนี้

ชั้นหน้าที่อาการเมื่อชั้นนี้มีปัญหา
System promptบอกว่าเป็นใคร ทำอะไรได้ กฎอะไรห้ามข้ามพฤติกรรมโดยรวมเพี้ยน ไม่ทำตาม convention ของทีม
Tool registryรายการเครื่องมือ + schema + คำอธิบายเลือกเครื่องมือผิด หรือส่ง argument ผิดซ้ำ ๆ
Context assemblerประกอบ messages ที่จะส่งเข้าโมเดลแต่ละรอบลืมของที่เพิ่งทำ วนทำงานเดิม ต้นทุนพุ่ง
Permission layerตัดสินว่าคำขอไหนรันได้ค้างรออนุมัติ หรือ (แย่กว่า) ทำสิ่งที่ไม่ควรทำ
Result rendererแปลงผลของเครื่องมือเป็นข้อความที่โมเดลอ่านโมเดลตีความผลผิด เพราะผลถูกตัดหรือจัดรูปแย่
ชั้นที่คนโทษน้อยที่สุดแต่ผิดบ่อยที่สุด

Result renderer — เวลาคำสั่งคืน output 20,000 บรรทัดแล้ว harness ตัดเหลือ 200 บรรทัดแรก โมเดลจะสรุปจากส่วนที่เห็น แล้วมั่นใจเต็มที่ว่าเข้าใจครบ อาการคือ “มันตอบผิดแบบมั่นใจ” ซึ่งคนมักโทษว่าโมเดลโง่ ทั้งที่ปัญหาอยู่ที่ท่อ

01.03

Tool-use protocol และกฎที่ห้ามผิด

โมเดลไม่ได้ “เรียกฟังก์ชัน” มันผลิตบล็อกข้อมูลที่บอกว่าอยากเรียกอะไรด้วย argument อะไร แล้วโปรแกรมของคุณเป็นคนรัน ผลลัพธ์ถูกส่งกลับเป็นบล็อกคู่กันที่อ้าง id เดิม

  • หนึ่งคำตอบมีหลาย tool call ได้ — โมเดลขอหลายอย่างพร้อมกันเมื่อมันไม่ขึ้นต่อกัน ให้รันขนานแล้วรวมผล
  • ต้องส่งผลกลับครบทุกตัวใน message เดียว — ถ้าแยกส่งทีละอัน โมเดลจะค่อย ๆ เลิกขอแบบขนาน เพราะเรียนรู้ว่ามันไม่ได้ผลดี ประสิทธิภาพตกโดยไม่มีใครสังเกต
  • เครื่องมือที่ล้มเหลวต้องส่งผลกลับพร้อมธง error ห้ามเงียบ — การไม่ส่งผลกลับทำให้ลูปเสียสภาพ และโมเดลจะเดาว่าเกิดอะไรขึ้น
ทำไม error ที่ส่งกลับถึงมีค่ากว่าที่คิด

ข้อความ error คือช่องทางสอน agent ที่ถูกที่สุดที่มี ENOENT เปล่า ๆ บอกอะไรไม่ได้ แต่ ENOENT: ไม่พบ src/billing/index.ts — ไฟล์ในโฟลเดอร์นี้คือ invoice.ts, tax.ts ทำให้รอบถัดไปมันแก้ถูกเลย เรื่องนี้เป็นแกนของ M05

01.04

stop_reason ทุกค่า และการจัดการแต่ละแบบ

ค่าที่บอกว่าทำไมโมเดลหยุดพูด เป็นข้อมูล debug ที่ดีที่สุดชิ้นเดียว และเป็นสิ่งที่โค้ดต้องแยกกรณีให้ครบ

ค่าแปลว่าต้องทำอะไร
end_turnพูดจบตามปกติออกจากลูป
tool_useขอใช้เครื่องมือรันแล้วส่งผลกลับ วนต่อ
max_tokensชนเพดานความยาว ถูกตัดกลางคันห้ามถือว่าเป็นคำตอบ — ต้องขอต่อหรือขยายเพดาน
pause_turnงานฝั่งเซิร์ฟเวอร์ยังไม่จบส่งกลับเข้าไปให้ทำต่อ
refusalถูกปฏิเสธด้วยเหตุผลด้านความปลอดภัยจัดการแยก อย่าลอง retry ซ้ำ ๆ
บั๊กคลาสสิก

โค้ดที่เช็คแค่ stop_reason == "tool_use" แล้ว else ถือว่าเสร็จ จะกลืน max_tokens เงียบ ๆ ผลคือได้คำตอบที่ถูกตัดครึ่ง แล้วเอาไปใช้ต่อเหมือนสมบูรณ์ นี่คือแหล่งของ “ไฟล์ที่เขียนไม่จบ” จำนวนมาก

01.05

Thinking และ effort

โมเดลรุ่นใหม่คิดก่อนตอบได้ และคุมความลึกได้ผ่านระดับ effort ผลของมันไม่ใช่แค่ “ฉลาดขึ้น” แต่เปลี่ยนรูปแบบการทำงานด้วย

  • effort ต่ำ — tool call น้อยลงและรวบมากขึ้น คำพูดนำสั้นลง เหมาะกับงานซ้ำ ๆ ที่รู้ขั้นตอนแล้ว และเหมาะกับ sub-agent
  • effort สูง — สำรวจมากขึ้น ตรวจสอบตัวเองมากขึ้น คุ้มกับงานที่ผิดแล้วแพง
  • ห้ามสั่งให้ “คิดทีละขั้น” กับโมเดลที่คิดเองอยู่แล้ว — คำสั่งแบบนั้นเป็นมรดกจากยุคก่อน และตอนนี้กลายเป็นตัวรบกวน เรื่องนี้กลับมาอีกครั้งใน M12.08
ลำดับการปรับที่ถูก

เจอปัญหาคุณภาพ ให้ไล่ตามลำดับนี้ — บริบท → effort → โมเดล คนส่วนใหญ่กระโดดไปข้อสามก่อน ซึ่งแพงที่สุดและมักไม่ใช่สาเหตุ

01.06

Permission model

ชั้นสิทธิ์คือสิ่งเดียวที่กั้นระหว่าง “ผู้ช่วยที่มีประโยชน์” กับ “โปรแกรมที่รันคำสั่งอะไรก็ได้บนเครื่องคุณ” มันไม่ใช่ความรำคาญที่ต้องปิด แต่เป็นส่วนหนึ่งของการออกแบบ

โหมดใช้เมื่อความเสี่ยง
askงานสำรวจ งานที่ยังไม่ไว้ใจต่ำ แต่ขัดจังหวะ
acceptEditsงานแก้ไฟล์ในขอบเขตที่รู้แล้วปานกลาง — แก้ไฟล์ได้เอง
allowlist เฉพาะคำสั่งโหมดที่ควรใช้เป็นค่าเริ่มต้นของทีมต่ำและคาดเดาได้
bypassเฉพาะใน container ที่ทิ้งได้สูงมาก — เท่ากับให้ shell เต็ม
หนี้ที่มองไม่เห็น

การเปิดโหมดผ่านทุกอย่างเพราะ “รำคาญ prompt” คือการกู้ยืมความเร็ววันนี้ด้วยความเสี่ยงพรุ่งนี้ และดอกเบี้ยจะมาเก็บตอนที่ agent อ่านเนื้อหาจากอินเทอร์เน็ตที่มีคำสั่งฝังอยู่ — ดู M13

01.07

เจ็ดโหมดที่ agent ล้มเหลว

เกือบทุกความล้มเหลวที่เจอในงานจริงตกอยู่ในเจ็ดแบบนี้ จำให้ได้แล้วเวลาเจอปัญหาจะวินิจฉัยได้เร็วขึ้นมาก

โหมดอาการที่เห็นชั้นที่ต้องแก้
บริบทล้นลืมสิ่งที่เพิ่งตกลง วนทำงานเดิมcontext assembler
คำอธิบายเครื่องมือกำกวมเลือกผิดตัวซ้ำ ๆtool registry
error อ่านไม่รู้เรื่องแก้วนไปวนมาไม่ตรงจุดcodebase (M05)
ติดลูปทำสามอย่างสลับกันไม่จบเพดาน turn + เกณฑ์จบงาน
ค้นเกินจำเป็นอ่าน 40 ไฟล์ก่อนแก้ 1 บรรทัดโครงสร้าง repo (M05)
ลอยจากแผนเริ่มถูก แล้วค่อย ๆ ทำอย่างอื่นแผนที่ตรวจได้ (M04)
ตัดข้อมูลเงียบมั่นใจแต่ผิดresult renderer
01.08 · แล็บประจำโมดูล

เขียน mini-harness ~150 บรรทัด

เป้าหมายไม่ใช่ได้เครื่องมือใช้งาน แต่คือทำลายความรู้สึกว่ามันเป็นเวทมนตร์ เมื่อคุณเขียนลูปเองแล้ว ทุกอาการแปลก ๆ หลังจากนี้จะมีที่ทางให้ชี้

ข้อกำหนดต้องมีครบทั้งห้าข้อ

  1. ลูป while ที่วนจนกว่า stop_reason จะไม่ใช่ tool_use และแยกกรณี max_tokens ออกมาชัด ๆ
  2. เครื่องมือสามตัว — อ่านไฟล์ เขียนไฟล์ และรันคำสั่ง
  3. Permission gate ที่เป็น allowlist ไม่ใช่ ask ทุกครั้ง
  4. รองรับ tool call หลายตัวในหนึ่งคำตอบ และส่งผลกลับครบใน message เดียว
  5. นับและพิมพ์จำนวน token กับต้นทุนสะสมทุกรอบ
เกณฑ์ผ่าน
  • สั่งงานที่ต้องใช้เครื่องมือสามรอบขึ้นไปแล้วทำสำเร็จ
  • จงใจให้เครื่องมือ error หนึ่งครั้ง แล้ว agent แก้ทางได้เองโดยไม่ค้าง
  • ตั้งเพดาน token ต่ำจนโดนตัด แล้ว harness ต้องรายงานว่าโดนตัด ไม่ใช่ทำเป็นว่าจบ

เชื่อมกับโมดูลอื่น — M02 ลงลึกที่ชั้น context assembler · M03 เอาตัวนับ token จากแล็บนี้ไปทำบัญชีจริง · M05 แก้สองในเจ็ดโหมดล้มเหลวด้วยการปรับ repo · M13 ต่อยอดชั้น permission เป็นโมเดลภัยคุกคามเต็มรูปแบบ
