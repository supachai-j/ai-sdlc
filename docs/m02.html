Context Engineering

ทักษะที่แยกคนใช้ agent เป็นกับไม่เป็นได้ชัดที่สุด และเป็นทักษะเดียวที่ให้ผลตอบแทนสูงกว่าการเปลี่ยนโมเดล การมี context window ใหญ่ไม่ได้ยกเลิกวินัยข้อนี้ มันแค่ทำให้ค่าเสียหายมาช้าลง

ใจความของทั้งโมดูล

บริบทคืองบประมาณ ไม่ใช่ถัง ทุก token ที่ใส่เข้าไปมีต้นทุนสองชั้น — เงินที่จ่าย และความสนใจของโมเดลที่ถูกดึงไปจากสิ่งที่สำคัญกว่า

02.01

Context window คืองบ ไม่ใช่พื้นที่เก็บของ

ตอน context window ยังเล็ก ทุกคนบริหารบริบทโดยอัตโนมัติเพราะไม่มีทางเลือก พอมันขยายเป็นหลักล้าน คนจำนวนมากสรุปว่าปัญหาจบแล้ว — ยัดทุกอย่างเข้าไปได้เลย ข้อสรุปนี้ผิด และเหตุผลไม่มีข้อไหนเกี่ยวกับขนาด window เลย

เหตุผลที่หนึ่งคุณจ่ายทุกรอบ ไม่ใช่ครั้งเดียว

ย้อนกลับไปที่ M01.01 — บริบททั้งกองถูกส่งใหม่ทุกครั้งที่วนลูป ไฟล์ที่คุณแนบไปตอนต้นไม่ได้ถูกจ่ายครั้งเดียว มันถูกจ่ายซ้ำทุกรอบจนจบงาน

สถานการณ์บริบทจำนวนรอบtoken ที่ส่งจริงรวม
แนบไฟล์ที่ต้องใช้จริง20K15300K
แนบทั้งโฟลเดอร์เผื่อไว้120K151.8M

ต่างกันหกเท่าจากการตัดสินใจเดียวตอนเริ่ม และผู้ใช้จะไม่รู้สึกอะไรเลยระหว่างทาง เพราะไม่มีตัวเลขวิ่งให้เห็น

เหตุผลที่สองคุณภาพตกก่อนที่ window จะเต็ม

นี่เป็นข้อที่ขัดสัญชาตญาณที่สุด ถ้าเรามองบริบทเป็นถัง การใส่ของเพิ่มไม่ควรทำให้ของที่มีอยู่แย่ลง แต่บริบทไม่ใช่ถัง มันคือสิ่งที่โมเดลต้องกระจายความสนใจไปทั่ว ยิ่งมีของไม่เกี่ยวเยอะ กฎสำคัญของคุณยิ่งต้องแข่งกับเสียงรบกวน บทถัดไปเจาะเรื่องนี้โดยเฉพาะ

เหตุผลที่สามเวลาตอบช้าลงตามขนาด แล้วคูณด้วยจำนวนรอบ

บริบทใหญ่ทำให้แต่ละรอบใช้เวลานานขึ้น และ agent วนหลายรอบ ผลคือความช้าถูกคูณ ซึ่งสำคัญมากกับงานที่คนนั่งรออยู่ เพราะคนจะเลิกใช้เครื่องมือที่ต้องรอสามนาทีต่อคำสั่ง ต่อให้ผลลัพธ์ดีก็ตาม

คำถามที่เปลี่ยนวิธีคิดทั้งโมดูล

เวลาจะใส่อะไรเข้าบริบท คนส่วนใหญ่ถามว่า “สิ่งนี้อาจมีประโยชน์ไหม” ซึ่งคำตอบเกือบทุกครั้งคือ “อาจจะ” และนั่นทำให้บริบทบวมขึ้นเรื่อย ๆ

คำถามที่ถูกคือ “ถ้าตัดสิ่งนี้ออก งานจะพังไหม” คำถามนี้ตอบยากกว่า แต่บังคับให้คุณคิดถึงสิ่งที่จำเป็นจริง ไม่ใช่สิ่งที่สบายใจกว่าถ้ามี

ข้อดีที่ window ใหญ่ให้จริง

ไม่ได้แปลว่า window ใหญ่ไม่มีประโยชน์ ประโยชน์จริงของมันคือคุณไม่พังกลางทาง — งานที่แต่ก่อนต้องตัดบทสนทนาทิ้งกลางคัน ตอนนี้ทำจนจบได้ แต่นั่นคือ “ไม่พัง” ไม่ใช่ “ไม่ต้องบริหาร” มันเปลี่ยนเพดานจากที่เคยชนบ่อย เป็นชนไม่บ่อย ส่วนต้นทุนกับคุณภาพยังขึ้นกับวินัยของคุณเหมือนเดิม

02.02

กฎสี่ข้อของสิ่งที่ควรอยู่ในบริบท

กฎหมายความว่าตัวอย่างที่ละเมิด
เกี่ยวข้องถ้าตัดออกแล้วคำตอบเปลี่ยน จึงควรอยู่แนบทั้งโฟลเดอร์เพราะไม่แน่ใจว่าไฟล์ไหนเกี่ยว
สดสะท้อนสถานะปัจจุบัน ไม่ใช่ของเมื่อ 20 รอบก่อนผลของไฟล์ที่ถูกแก้ไปแล้วยังค้างอยู่
เรนเดอร์เล็กสื่อความหมายเท่าเดิมด้วย token น้อยลงแปะ JSON เต็มทั้งที่ต้องการแค่สามฟิลด์
หากลับมาได้ไม่ต้องอยู่ในบริบทถ้า agent หามันเจอเมื่อต้องใช้แนบเอกสาร API ทั้งเล่มแทนที่จะให้ grep เอา

กฎข้อสี่คือข้อที่คนมองข้ามมากที่สุด และเป็นข้อที่ประหยัดได้มากที่สุด — ถ้า agent หาข้อมูลเจอได้ในสองวินาที การแนบมันไปล่วงหน้าคือการจ่ายเงินซื้อสิ่งที่ได้ฟรี

02.03

Attention dilution

ปรากฏการณ์ที่คุณภาพตกเมื่อบริบทยาวขึ้นทั้งที่ยังไม่เต็ม window เป็นเรื่องที่คนสังเกตเห็นกันเยอะ แต่ตีความผิดกันเกือบทั้งหมด คำอธิบายที่ได้ยินบ่อยคือ “โมเดลเหนื่อย” หรือ “มันเบลอ” ซึ่งเป็นการอธิบายเชิงอุปมาที่พาไปสู่ทางแก้ที่ผิด

สิ่งที่เกิดขึ้นจริงตรงไปตรงมากว่านั้น — โมเดลต้องหาว่าอะไรในกองข้อความเกี่ยวข้องกับงานตรงหน้า เมื่อกองใหญ่ขึ้นและมีของไม่เกี่ยวมากขึ้น งานนั้นยากขึ้น กฎที่คุณเขียนไว้ตอนต้นบทสนทนา ตอนนี้ต้องแข่งความสนใจกับผลลัพธ์เครื่องมือหกหมื่น token ที่ใช้ไปแล้วและไม่เกี่ยวอะไรอีกเลย

ทางแก้ที่คนเลือก และทำไมมันทำให้แย่ลง

เมื่อ agent เริ่มไม่ทำตามกฎ ปฏิกิริยาแรกของเกือบทุกคนคือย้ำกฎอีกครั้ง — พิมพ์ซ้ำ เขียนตัวใหญ่ ใส่คำว่า “สำคัญมาก” เพิ่มเข้าไปในไฟล์บริบท

แต่การย้ำคือการเพิ่มบริบท ซึ่งทำให้อัตราส่วนของสัญญาณต่อเสียงรบกวนแย่ลงไปอีก คุณกำลังเติมน้ำเพื่อแก้ปัญหาน้ำจืดเกินไป ทางแก้ที่ถูกคือตรงกันข้าม — ตัดของที่ไม่ใช้แล้วออก เพื่อให้กฎที่มีอยู่กลับมาเด่นขึ้นเอง

อาการที่บอกว่าเป็นเรื่องนี้

  • ทำถูกช่วงแรกของบทสนทนา แล้วค่อย ๆ เพี้ยน — อาการแย่ลงตามความยาว
  • เริ่มบทสนทนาใหม่ด้วยคำสั่งเดิมแล้วทำถูกทันที นี่คือหลักฐานที่ชัดที่สุด
  • ลืมข้อจำกัดที่ตกลงกันไว้ตอนต้น ทั้งที่มันยังอยู่ในบริบท
  • วนกลับไปทำสิ่งที่ทำไปแล้ว หรือถามสิ่งที่ตอบไปแล้ว

ข้อที่สองคือการทดสอบที่แม่นที่สุดและใช้เวลาสิบวินาที ถ้าเริ่มใหม่แล้วหาย ปัญหาไม่ได้อยู่ที่ prompt ไม่ได้อยู่ที่โมเดล แต่อยู่ที่กองบริบทที่สะสมมา

ทดสอบได้ในสิบนาที

เอางานจริงที่คุณทำซ้ำได้ รันสองแบบ — แบบที่หนึ่งปล่อยบริบทสะสมตามปกติ แบบที่สองตัดผลเครื่องมือเก่าที่ใช้เสร็จแล้วออกก่อนแต่ละรอบ แล้ววัดด้วยเกณฑ์เดียวกัน

คนส่วนใหญ่คาดว่าแบบที่สองจะแย่กว่าเพราะข้อมูลน้อยกว่า ผลที่ได้จริงมักเท่ากันหรือดีกว่า พร้อมกับต้นทุนที่ลดลงชัดเจน นี่คือแล็บของโมดูลนี้ และเป็นแล็บที่เปลี่ยนวิธีทำงานของคนได้มากที่สุด

02.04

ลำดับชั้นหน่วยความจำ

ข้อมูลแต่ละประเภทควรอยู่คนละชั้น การวางผิดชั้นคือสาเหตุของทั้งความสิ้นเปลืองและการลืม

ชั้นอายุควรใส่อะไรต้นทุน
System promptถาวรบทบาท กฎที่ห้ามข้ามจ่ายทุกรอบ แต่ cache ได้
Project memoryข้ามเซสชันconvention ของ repo คำสั่ง buildจ่ายทุกรอบ cache ได้
Sessionในบทสนทนาสิ่งที่เพิ่งตัดสินใจ ผลที่เพิ่งได้โตเรื่อย ๆ ต้องบริหาร
Retrievalตามคำขอโค้ดและเอกสารที่ค้นเมื่อต้องใช้จ่ายเฉพาะตอนใช้
External KBข้ามโปรเจกต์ความรู้ที่ยืนยันแล้ว ใช้ซ้ำได้จ่ายเฉพาะตอนดึง
กฎการวางชั้น

ยิ่งข้อมูลใช้บ่อยและเปลี่ยนน้อย ยิ่งควรอยู่ชั้นบน ยิ่งใช้นาน ๆ ครั้งและใหญ่ ยิ่งควรอยู่ชั้นล่างและดึงเมื่อต้องใช้ ที่ผิดบ่อยคือเอาสิ่งที่ใช้นาน ๆ ครั้งไปแปะไว้ชั้นบนเพราะกลัวลืม

02.05

เขียนไฟล์บริบทโปรเจกต์ให้ทำงานจริง

ไฟล์บริบทประจำโปรเจกต์ถูกส่งเข้าโมเดลทุกรอบของทุกงาน ทำให้มันเป็นของที่แพงที่สุดต่อบรรทัด ในทั้งระบบ บรรทัดหนึ่งในไฟล์นี้มีต้นทุนสูงกว่าบรรทัดเดียวกันที่เขียนไว้ใน README หลายพันเท่า เพราะ README ถูกอ่านเมื่อจำเป็น ส่วนไฟล์นี้ถูกอ่านเสมอ

เมื่อคิดแบบนี้ เกณฑ์ว่าอะไรควรอยู่ในไฟล์จะเปลี่ยนไปทันที

ควรมีไม่ควรมี และเพราะอะไร
คำสั่งรันเทสต์เฉพาะจุดคำอธิบายว่าโปรเจกต์นี้ทำอะไร — อ่านจากโค้ดได้
convention ที่ฝืนความเคยชินทั่วไปconvention มาตรฐานที่โมเดลรู้อยู่แล้ว
สิ่งที่ห้ามแตะ และเพราะอะไรประวัติการตัดสินใจแบบเล่าเรื่อง — ควรอยู่ใน ADR
ที่อยู่ของสิ่งที่หายากสิ่งที่ grep หาเจอในสองวินาที
ข้อจำกัดที่มองไม่เห็นจากโค้ดคำอธิบายเครื่องมือมาตรฐาน

การทดสอบต่อบรรทัด

วิธีที่ตรงที่สุดในการตัดสินว่าบรรทัดหนึ่งควรอยู่ไหม คือถามว่า “ถ้าลบบรรทัดนี้ จะมีงานไหนที่ทำผิดไป”

ถ้านึกงานนั้นออกได้ชัด ๆ ให้เก็บไว้ ถ้านึกไม่ออก แสดงว่าคุณไม่รู้ว่ามันทำอะไร และในเมื่อคุณกำลังจ่ายค่ามันทุกรอบ การไม่รู้ว่ามันทำอะไรคือเหตุผลที่ดีพอจะลบ

สุสานของกฎ — ปรากฏการณ์ที่เกิดกับทุกทีม

กลไกมันเรียบง่ายและหลีกเลี่ยงยาก ทุกครั้งที่ agent ทำผิดหนึ่งครั้ง มีคนเพิ่มกฎหนึ่งข้อ เพราะการเพิ่มใช้เวลาสิบวินาทีและรู้สึกว่าได้แก้ปัญหาแล้ว

แต่ไม่มีใครลบ เพราะการลบต้องพิสูจน์ว่าไม่จำเป็น ซึ่งพิสูจน์ไม่ได้ถ้าไม่มีชุดวัด ผ่านไปหกเดือนได้ไฟล์สี่ร้อยบรรทัดที่ทุกคนกลัวจะแตะ ทั้งที่ครึ่งหนึ่งอาจไม่มีผลอะไรเลย และอีกส่วนหนึ่งอาจกำลังทำให้แย่ลงด้วยซ้ำ

ทางออกทางเดียวคือชุดวัดที่พิสูจน์ได้ว่ากฎไหนมีผล ซึ่งเป็นเนื้อหาของ M12.05 โดยตรง จนกว่าจะมีสิ่งนั้น ไฟล์นี้จะโตทางเดียว

เขียนกฎยังไงให้ทำตามได้จริง

กฎที่กำกวมไม่ได้ถูกละเลยเพราะ agent ดื้อ แต่เพราะมันตีความได้หลายแบบ เทียบสองแบบนี้ 

// ตีความได้หลายแบบ ทำตามบ้างไม่ทำบ้าง
- เขียนเทสต์ให้ครอบคลุม
- อย่าทำให้โค้ดซับซ้อนเกินจำเป็น
- ระวังเรื่อง performance

// ตรวจได้ ไม่ต้องตีความ
- ทุก export ใหม่ต้องมีเทสต์ที่ครอบทั้งเคสปกติและเคสว่าง
- ห้ามเพิ่ม dependency ใหม่โดยไม่ถามก่อน
- query ที่วนใน loop ต้องเปลี่ยนเป็น batch — ห้าม N+1

ข้อสังเกตสำคัญ — กฎในกลุ่มหลังหลายข้อควรกลายเป็น lint rule หรือ hook แทนที่จะเป็นข้อความ เพราะกฎที่บังคับด้วยเครื่องมือไม่กินงบบริบทเลยและไม่มีวันถูกลืม M09.07 ว่าด้วยเรื่องนี้

02.06

สามกลไกที่คนสับสน

เมื่อบริบทเริ่มยาว มีสามทางเลือกที่ทำงานคนละแบบ และคนมักใช้ผิดตัว

กลไกทำอะไรเหมาะเมื่อเสียอะไร
Compactionสรุปย่อประวัติเก่าให้สั้นลงบทสนทนายาวที่ยังต้องรู้ว่าเคยทำอะไรรายละเอียดที่ถูกสรุปทิ้ง
Context editingลบผลเครื่องมือเก่าออกทั้งก้อนผลที่ใช้แล้วและไม่ต้องใช้อีกของนั้นหายไปเลย
Memory toolเขียนออกไปเก็บนอกบริบทข้อสรุปที่ต้องใช้ข้ามเซสชันต้องดึงกลับเองเมื่อจะใช้
วิธีเลือกให้ถูก

ถามว่า “ของชิ้นนี้จะต้องใช้อีกไหม” — ไม่ต้องใช้แล้วก็ ลบ · ต้องรู้ว่าเคยเกิดแต่ไม่ต้องรู้รายละเอียดก็ สรุป · ต้องใช้อีกแน่ ๆ แต่ไม่ใช่ตอนนี้ก็ เขียนออกไป

02.07

Sub-agent ในฐานะเครื่องมือกันบริบท

คนส่วนใหญ่มอง sub-agent เป็นเรื่องความเร็ว แต่ประโยชน์ที่แน่นอนกว่าคือมันมีบริบทของตัวเอง งานที่ต้องอ่านเยอะแต่สรุปสั้น เหมาะกับ sub-agent มากที่สุด เพราะบริบทหลักได้รับแค่ข้อสรุป ไม่ใช่กองข้อมูลดิบ

เกณฑ์ตัดสิน

ถ้าอัตราส่วน “ข้อมูลที่ต้องอ่าน : ข้อสรุปที่ต้องใช้” สูงกว่าราว 10 ต่อ 1 ให้แยกเป็น sub-agent เกือบทุกครั้ง ถ้าใกล้ 1 ต่อ 1 การแยกมีแต่เพิ่มต้นทุนกับความไม่แน่นอน — ขยายเต็มใน M10

02.08

Retrieval หรือ stuffing

ทางเลือกระหว่าง “แนบไปเลย” กับ “ให้มันหาเอง” ตัดสินด้วยสามตัวแปร ไม่ใช่ความรู้สึก

ตัวแปรเอียงไปทาง stuffingเอียงไปทาง retrieval
ความแน่ใจว่าต้องใช้แน่ใจว่าใช้ทุกครั้งใช้บ้างไม่ใช้บ้าง
ขนาดเล็ก (ไม่กี่พัน token)ใหญ่
ความง่ายในการหาหายาก ชื่อไม่สื่อหาง่ายด้วย grep

ข้อสังเกตสำคัญ — ตัวแปรที่สามอยู่ในมือคุณ การทำให้ codebase ค้นง่ายขึ้นคือการเปลี่ยนสมการนี้อย่างถาวร ซึ่งเป็นเหตุผลว่าทำไม M05 ถึงให้ผลตอบแทนสูง

02.09 · แล็บประจำโมดูล

ตัดบริบท 40% แล้ววัดว่าคุณภาพเปลี่ยนไหม

แล็บนี้ออกแบบมาให้ผลลัพธ์ขัดกับสัญชาตญาณ คนส่วนใหญ่คาดว่าตัดแล้วแย่ลง แต่บ่อยครั้งผลออกมาเท่าเดิมหรือดีขึ้น พร้อมกับต้นทุนที่ลดลงชัดเจน

ขั้นตอน

  1. เลือกงานจริงที่คุณทำซ้ำได้ และมีเกณฑ์ตัดสินเชิงกล
  2. วัดบริบทตั้งต้น — นับ token แยกเป็นหมวด: system, project memory, ผลเครื่องมือ, ไฟล์ที่แนบ
  3. ตัดออก 40% โดยเลือกจากหมวดที่ใหญ่ที่สุดก่อน และเลือกตามกฎข้อสี่ (หากลับมาได้)
  4. รันทั้งสองแบบ อย่างละ 5 ครั้ง แล้วเทียบทั้งอัตราผ่านและต้นทุน
  5. ถ้าคุณภาพไม่ตก ให้ตัดอีก 40% แล้ววัดซ้ำ จนกว่าจะเริ่มตก — นั่นคือขอบของจริง
เกณฑ์ผ่าน
  • รู้ตัวเลขจริงว่าบริบทของงานนี้แบ่งเป็นหมวดละกี่ token
  • หาขอบที่คุณภาพเริ่มตกได้ พร้อมบอกว่าตัดอะไรออกแล้วพัง
  • ถ้าคุณภาพไม่ตกเลยแม้ตัดไปมาก ถือว่าผ่าน — และคุณเพิ่งพบว่าจ่ายเกินมานาน
ข้อควรระวังในการอ่านผล

รันละครั้งไม่พอ ความแปรปรวนของลูปจะกลบผลของการตัด ถ้ายังไม่ได้อ่าน M12.01 ให้ข้ามไปอ่านก่อนสรุปอะไรจากแล็บนี้

เชื่อมกับโมดูลอื่น — M03 เปลี่ยนการตัดบริบทเป็นตัวเลขเงิน · M05 ทำให้ retrieval ถูกลงอย่างถาวร · M10 ใช้ sub-agent เป็นกำแพงกันบริบทเต็มรูปแบบ · M12 คือเครื่องมือที่ทำให้แล็บนี้เชื่อถือได้
