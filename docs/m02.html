AI Coding Agent SDLC · Phase 00 · Module 02

Context Engineering

ทักษะที่แยกคนใช้ agent เป็นกับไม่เป็นได้ชัดที่สุด และเป็นทักษะเดียวที่ให้ผลตอบแทนสูงกว่าการเปลี่ยนโมเดล การมี context window ใหญ่ไม่ได้ยกเลิกวินัยข้อนี้ มันแค่ทำให้ค่าเสียหายมาช้าลง

9 บทเรียน3 ชั่วโมง1 แล็บต้องผ่าน M01 ก่อน
ใจความของทั้งโมดูล

บริบทคืองบประมาณ ไม่ใช่ถัง ทุก token ที่ใส่เข้าไปมีต้นทุนสองชั้น — เงินที่จ่าย และความสนใจของโมเดลที่ถูกดึงไปจากสิ่งที่สำคัญกว่า

02.01

Context window คืองบ ไม่ใช่พื้นที่เก็บของ

เมื่อ window ขยายจากหลักแสนเป็นหลักล้าน คนจำนวนมากสรุปว่าปัญหาบริบทจบแล้ว ยัดทุกอย่างเข้าไปได้เลย ข้อสรุปนี้ผิดด้วยเหตุผลสามข้อที่ไม่เกี่ยวกับขนาด window

  1. คุณจ่ายทุกรอบ — บริบทถูกส่งซ้ำทุกครั้งที่วนลูป งานที่วน 30 รอบกับบริบท 200K คือการส่ง 6 ล้าน token
  2. คุณภาพตกก่อนที่ window จะเต็ม — ดูบทถัดไป
  3. เวลาตอบช้าลงตามขนาด — บริบทใหญ่ทำให้แต่ละรอบนานขึ้น และ agent วนหลายรอบ
กรอบคิดที่ใช้ได้ทั้งโมดูล

ถามทุกครั้งว่า “ถ้าตัดสิ่งนี้ออก งานจะพังไหม” ไม่ใช่ “สิ่งนี้อาจมีประโยชน์ไหม” คำถามแรกทำให้บริบทกระชับ คำถามหลังทำให้บริบทบวม เพราะเกือบทุกอย่างอาจมีประโยชน์

02.02

กฎสี่ข้อของสิ่งที่ควรอยู่ในบริบท

กฎหมายความว่าตัวอย่างที่ละเมิด
เกี่ยวข้องถ้าตัดออกแล้วคำตอบเปลี่ยน จึงควรอยู่แนบทั้งโฟลเดอร์เพราะไม่แน่ใจว่าไฟล์ไหนเกี่ยว
สดสะท้อนสถานะปัจจุบัน ไม่ใช่ของเมื่อ 20 รอบก่อนผลของไฟล์ที่ถูกแก้ไปแล้วยังค้างอยู่
เรนเดอร์เล็กสื่อความหมายเท่าเดิมด้วย token น้อยลงแปะ JSON เต็มทั้งที่ต้องการแค่สามฟิลด์
หากลับมาได้ไม่ต้องอยู่ในบริบทถ้า agent หามันเจอเมื่อต้องใช้แนบเอกสาร API ทั้งเล่มแทนที่จะให้ grep เอา

กฎข้อสี่คือข้อที่คนมองข้ามมากที่สุด และเป็นข้อที่ประหยัดได้มากที่สุด — ถ้า agent หาข้อมูลเจอได้ในสองวินาที การแนบมันไปล่วงหน้าคือการจ่ายเงินซื้อสิ่งที่ได้ฟรี

02.03

Attention dilution

ปรากฏการณ์ที่คุณภาพตกลงเมื่อบริบทยาวขึ้น ทั้งที่ยังไม่เต็ม window เกิดเพราะคำสั่งสำคัญของคุณต้องแข่งความสนใจกับข้อมูลรอบข้างที่ไม่เกี่ยว

อาการที่คนตีความผิด

“พอคุยไปนาน ๆ มันเริ่มโง่ลง” — ไม่ใช่ว่าโมเดลเหนื่อย แต่กฎสำคัญของคุณที่เขียนไว้ตอนต้น ตอนนี้จมอยู่ใต้ผลลัพธ์เครื่องมือ 60,000 token คนมักแก้ด้วยการเพิ่มคำสั่งย้ำ ซึ่งทำให้แย่ลงเพราะเพิ่มบริบทอีก วิธีที่ถูกคือตัดของที่ไม่ใช้ทิ้ง

ทดสอบได้ในสิบนาที

เอางานเดิม รันสองแบบ — แบบเต็มบริบท กับแบบตัดผลเครื่องมือเก่าที่ไม่เกี่ยวออก แล้ววัดด้วยเกณฑ์เดียวกัน คนส่วนใหญ่ประหลาดใจกับผล และนี่คือแล็บของโมดูลนี้

02.04

ลำดับชั้นหน่วยความจำ

ข้อมูลแต่ละประเภทควรอยู่คนละชั้น การวางผิดชั้นคือสาเหตุของทั้งความสิ้นเปลืองและการลืม

ชั้นอายุควรใส่อะไรต้นทุน
System promptถาวรบทบาท กฎที่ห้ามข้ามจ่ายทุกรอบ แต่ cache ได้
Project memoryข้ามเซสชันconvention ของ repo คำสั่ง buildจ่ายทุกรอบ cache ได้
Sessionในบทสนทนาสิ่งที่เพิ่งตัดสินใจ ผลที่เพิ่งได้โตเรื่อย ๆ ต้องบริหาร
Retrievalตามคำขอโค้ดและเอกสารที่ค้นเมื่อต้องใช้จ่ายเฉพาะตอนใช้
External KBข้ามโปรเจกต์ความรู้ที่ยืนยันแล้ว ใช้ซ้ำได้จ่ายเฉพาะตอนดึง
กฎการวางชั้น

ยิ่งข้อมูลใช้บ่อยและเปลี่ยนน้อย ยิ่งควรอยู่ชั้นบน ยิ่งใช้นาน ๆ ครั้งและใหญ่ ยิ่งควรอยู่ชั้นล่างและดึงเมื่อต้องใช้ ที่ผิดบ่อยคือเอาสิ่งที่ใช้นาน ๆ ครั้งไปแปะไว้ชั้นบนเพราะกลัวลืม

02.05

เขียน CLAUDE.md ให้ทำงานจริง

ไฟล์บริบทประจำโปรเจกต์ถูกส่งเข้าโมเดลทุกรอบ มันจึงเป็นของที่แพงที่สุดต่อบรรทัดในระบบ และควรถูกปฏิบัติแบบนั้น

ควรมีไม่ควรมี
คำสั่งรันเทสต์เฉพาะจุดคำอธิบายว่าโปรเจกต์นี้ทำอะไร (อ่านจากโค้ดได้)
convention ที่ฝืนความเคยชินทั่วไปconvention มาตรฐานที่โมเดลรู้อยู่แล้ว
สิ่งที่ห้ามแตะ และเพราะอะไรประวัติการตัดสินใจแบบเล่าเรื่อง
ที่อยู่ของสิ่งที่หายากสิ่งที่ grep หาเจอในสองวินาที
สุสานของกฎ

ทุกครั้งที่ agent ทำผิดหนึ่งครั้ง มีคนเพิ่มกฎหนึ่งข้อ ผ่านไปหกเดือนได้ไฟล์ 400 บรรทัดที่ไม่มีใครกล้าลบ เพราะไม่มีใครรู้ว่าบรรทัดไหนยังจำเป็น ทางออกเดียวคือชุดวัดที่พิสูจน์ได้ว่ากฎไหนมีผล — M12.05

02.06

สามกลไกที่คนสับสน

เมื่อบริบทเริ่มยาว มีสามทางเลือกที่ทำงานคนละแบบ และคนมักใช้ผิดตัว

กลไกทำอะไรเหมาะเมื่อเสียอะไร
Compactionสรุปย่อประวัติเก่าให้สั้นลงบทสนทนายาวที่ยังต้องรู้ว่าเคยทำอะไรรายละเอียดที่ถูกสรุปทิ้ง
Context editingลบผลเครื่องมือเก่าออกทั้งก้อนผลที่ใช้แล้วและไม่ต้องใช้อีกของนั้นหายไปเลย
Memory toolเขียนออกไปเก็บนอกบริบทข้อสรุปที่ต้องใช้ข้ามเซสชันต้องดึงกลับเองเมื่อจะใช้
วิธีเลือกให้ถูก

ถามว่า “ของชิ้นนี้จะต้องใช้อีกไหม” — ไม่ต้องใช้แล้วก็ ลบ · ต้องรู้ว่าเคยเกิดแต่ไม่ต้องรู้รายละเอียดก็ สรุป · ต้องใช้อีกแน่ ๆ แต่ไม่ใช่ตอนนี้ก็ เขียนออกไป

02.07

Sub-agent ในฐานะเครื่องมือกันบริบท

คนส่วนใหญ่มอง sub-agent เป็นเรื่องความเร็ว แต่ประโยชน์ที่แน่นอนกว่าคือมันมีบริบทของตัวเอง งานที่ต้องอ่านเยอะแต่สรุปสั้น เหมาะกับ sub-agent มากที่สุด เพราะบริบทหลักได้รับแค่ข้อสรุป ไม่ใช่กองข้อมูลดิบ

เกณฑ์ตัดสิน

ถ้าอัตราส่วน “ข้อมูลที่ต้องอ่าน : ข้อสรุปที่ต้องใช้” สูงกว่าราว 10 ต่อ 1 ให้แยกเป็น sub-agent เกือบทุกครั้ง ถ้าใกล้ 1 ต่อ 1 การแยกมีแต่เพิ่มต้นทุนกับความไม่แน่นอน — ขยายเต็มใน M10

02.08

Retrieval หรือ stuffing

ทางเลือกระหว่าง “แนบไปเลย” กับ “ให้มันหาเอง” ตัดสินด้วยสามตัวแปร ไม่ใช่ความรู้สึก

ตัวแปรเอียงไปทาง stuffingเอียงไปทาง retrieval
ความแน่ใจว่าต้องใช้แน่ใจว่าใช้ทุกครั้งใช้บ้างไม่ใช้บ้าง
ขนาดเล็ก (ไม่กี่พัน token)ใหญ่
ความง่ายในการหาหายาก ชื่อไม่สื่อหาง่ายด้วย grep

ข้อสังเกตสำคัญ — ตัวแปรที่สามอยู่ในมือคุณ การทำให้ codebase ค้นง่ายขึ้นคือการเปลี่ยนสมการนี้อย่างถาวร ซึ่งเป็นเหตุผลว่าทำไม M05 ถึงให้ผลตอบแทนสูง

02.09 · แล็บประจำโมดูล

ตัดบริบท 40% แล้ววัดว่าคุณภาพเปลี่ยนไหม

แล็บนี้ออกแบบมาให้ผลลัพธ์ขัดกับสัญชาตญาณ คนส่วนใหญ่คาดว่าตัดแล้วแย่ลง แต่บ่อยครั้งผลออกมาเท่าเดิมหรือดีขึ้น พร้อมกับต้นทุนที่ลดลงชัดเจน

ขั้นตอน

  1. เลือกงานจริงที่คุณทำซ้ำได้ และมีเกณฑ์ตัดสินเชิงกล
  2. วัดบริบทตั้งต้น — นับ token แยกเป็นหมวด: system, project memory, ผลเครื่องมือ, ไฟล์ที่แนบ
  3. ตัดออก 40% โดยเลือกจากหมวดที่ใหญ่ที่สุดก่อน และเลือกตามกฎข้อสี่ (หากลับมาได้)
  4. รันทั้งสองแบบ อย่างละ 5 ครั้ง แล้วเทียบทั้งอัตราผ่านและต้นทุน
  5. ถ้าคุณภาพไม่ตก ให้ตัดอีก 40% แล้ววัดซ้ำ จนกว่าจะเริ่มตก — นั่นคือขอบของจริง
เกณฑ์ผ่าน
  • รู้ตัวเลขจริงว่าบริบทของงานนี้แบ่งเป็นหมวดละกี่ token
  • หาขอบที่คุณภาพเริ่มตกได้ พร้อมบอกว่าตัดอะไรออกแล้วพัง
  • ถ้าคุณภาพไม่ตกเลยแม้ตัดไปมาก ถือว่าผ่าน — และคุณเพิ่งพบว่าจ่ายเกินมานาน
ข้อควรระวังในการอ่านผล

รันละครั้งไม่พอ ความแปรปรวนของลูปจะกลบผลของการตัด ถ้ายังไม่ได้อ่าน M12.01 ให้ข้ามไปอ่านก่อนสรุปอะไรจากแล็บนี้

เชื่อมกับโมดูลอื่น — M03 เปลี่ยนการตัดบริบทเป็นตัวเลขเงิน · M05 ทำให้ retrieval ถูกลงอย่างถาวร · M10 ใช้ sub-agent เป็นกำแพงกันบริบทเต็มรูปแบบ · M12 คือเครื่องมือที่ทำให้แล็บนี้เชื่อถือได้
