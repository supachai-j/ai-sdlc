Context Engineering

ทักษะที่แยกคนใช้ agent เป็นกับไม่เป็นได้ชัดที่สุด และเป็นทักษะเดียวที่ให้ผลตอบแทนสูงกว่าการเปลี่ยนโมเดล การมี context window ใหญ่ไม่ได้ยกเลิกวินัยข้อนี้ มันแค่ทำให้ค่าเสียหายมาช้าลง

ที่มา

ทำไมถึงมี context window ตั้งแต่แรก

คำถามที่ผมว่าน่าสนใจคือ — ทำไมโมเดลถึงต้องมีขีดจำกัดด้วย? ทำไมไม่ให้มันอ่านได้ไม่จำกัดไปเลย

คำตอบอยู่ในสถาปัตยกรรมที่ทุกอย่างวางอยู่บน และมันย้อนกลับไปถึงปี 2017

Figure 0 · จากข้อจำกัดทางสถาปัตยกรรม → ทางออกเชิงเทคนิค → การค้นพบว่าทางออกนั้นไม่พอ → กลายเป็นวินัยที่ต้องฝึก

2017ต้นกำเนิดของข้อจำกัด

Attention Is All You Need (Vaswani และคณะ, มิ.ย. 2017) เสนอสถาปัตยกรรม transformer ซึ่งเป็นฐานของโมเดลภาษาแทบทั้งหมดที่เราใช้ทุกวันนี้ หัวใจของมันคือกลไก attention ที่ให้ทุก token มองเห็นทุก token อื่นได้

ข้อดีคือมันจับความสัมพันธ์ระยะไกลได้ดีมาก แต่ราคาของมันคือ ยิ่งข้อความยาว ต้นทุนยิ่งโตเร็วกว่าเชิงเส้น เพราะทุก token ต้องเทียบกับทุก token

เพราะงั้น context window ไม่ได้เป็นขีดจำกัดที่ใครตั้งขึ้นมาเพื่อกวนใจเรา — มันเป็นผลโดยตรงจากวิธีที่โมเดลทำงาน และเป็นเหตุผลว่าทำไมการขยาย window ถึงเป็นงานยากที่ต้องใช้เทคนิคเฉพาะ ไม่ใช่แค่เพิ่มตัวเลขในไฟล์ config

2020ทางออกแรก — อย่ายัด ให้ดึงเอา

Retrieval-Augmented Generation (Lewis และคณะ, พ.ค. 2020) เสนอไอเดียที่ตอนนี้ฟังดูธรรมดามาก แต่ตอนนั้นเป็นการเปลี่ยนกรอบคิด — แทนที่จะพยายามให้โมเดลรู้ทุกอย่างหรือใส่ทุกอย่างเข้าไป ให้ค้นเฉพาะชิ้นที่เกี่ยวกับคำถามตรงหน้า แล้วใส่เฉพาะชิ้นนั้น

สังเกตไหมครับว่านี่คือกฎข้อ 4 ในบท 02.02 เป๊ะ ๆ — "re-findable"

คือไอเดียนี้อายุ 5 ปีแล้ว แต่คนยังทำผิดกันอยู่ทุกวัน เพราะพอ window ใหญ่ขึ้น คนก็เลิกคิดเรื่องนี้ไปเลย ทั้งที่เหตุผลเดิมยังอยู่ครบ

2023การค้นพบที่เปลี่ยนวิธีคิด

พอ window เริ่มใหญ่ขึ้นจริง ๆ คำถามใหม่ก็ตามมา — ถ้าใส่ได้เยอะแล้ว ยังต้องเลือกอยู่ไหม

Lost in the Middle (Liu และคณะ, ก.ค. 2023) วัดเรื่องนี้อย่างเป็นระบบ แล้วพบว่า โมเดลใช้ข้อมูลที่อยู่ต้นและท้ายของ context ได้ดีกว่าข้อมูลที่อยู่ตรงกลางอย่างมีนัยสำคัญ

ความหมายคือ "ใส่เข้าไปได้" ไม่เท่ากับ "โมเดลจะใช้มันได้ดี" ซึ่งเป็นรากของบท 02.03 ทั้งบท และเป็นเหตุผลว่าทำไมการยัดของเพิ่มถึงไม่ใช่ทางแก้

2025ตอนที่มันได้ชื่อ

ก่อนหน้านี้เราเรียกทุกอย่างรวม ๆ ว่า prompt engineering ซึ่งเน้นที่ "เขียนคำสั่งยังไง" แต่พอ agent วนหลายรอบและ context สะสมเอง ปัญหาก็เปลี่ยนไป — มันไม่ใช่เรื่องถ้อยคำในคำสั่งอีกต่อไป แต่เป็นเรื่องบริหารทั้งกองที่ส่งเข้าไปในแต่ละรอบ

คำว่า context engineering เลยถูกใช้แยกออกมา เพื่อชี้ว่านี่เป็นคนละงานกัน และเป็นงานที่ต้องคิดเชิงระบบ ไม่ใช่เชิงถ้อยคำ

สรุปเส้นเรื่องทั้งหมดในสามบรรทัด
  1. 2017 — สถาปัตยกรรมทำให้เกิดขีดจำกัด
  2. 2020 — เราแก้ด้วยการดึงเฉพาะที่เกี่ยว
  3. 2023 — พบว่าต่อให้ขยายขีดจำกัด การเลือกก็ยังจำเป็นอยู่ดี

เพราะงั้นเวลามีคนบอกว่า "window ใหญ่แล้ว ไม่ต้องคิดเรื่องนี้แล้ว" — เขากำลังข้ามข้อ 3 ซึ่งเป็นข้อที่มีหลักฐานรองรับชัดที่สุด

02.01

Context window คืองบ ไม่ใช่พื้นที่เก็บของ

ตอน context window ยังเล็ก ทุกคนบริหาร context กันอัตโนมัติเพราะไม่มีทางเลือก พอมันขยายเป็นหลักล้าน คนก็สรุปว่า "จบแล้ว ยัดเข้าไปเลย"

ผมเข้าใจนะว่าทำไมคิดแบบนั้น แต่มันไม่จบ และเหตุผลทั้ง 3 ข้อไม่มีข้อไหนเกี่ยวกับขนาด window เลย

Figure 1 · เหตุผลข้อแรก — context ถูกส่งซ้ำทุก round ตามที่เห็นใน M01 Figure 2

เหตุผลข้อ 2คุณภาพตกก่อน window เต็ม

อันนี้ขัดสัญชาตญาณสุด ถ้ามอง context เป็นถัง การใส่ของเพิ่มไม่ควรทำให้ของเดิมแย่ลง แต่มันไม่ใช่ถัง — บทถัดไปเจาะเรื่องนี้โดยเฉพาะ พร้อมงานวิจัยที่วัดผลไว้แล้ว

เหตุผลข้อ 3ช้าลง แล้วคูณด้วยจำนวน round

context ใหญ่ทำให้แต่ละ round นานขึ้น และ agent วนหลาย round ความช้าเลยถูกคูณ สำคัญมากกับงานที่คนนั่งรออยู่ เพราะคนจะเลิกใช้เครื่องมือที่ต้องรอ 3 นาทีต่อคำสั่ง ต่อให้ผลลัพธ์ดีก็ตาม — นี่เป็นเหตุผลที่ workflow ตายบ่อยกว่าเรื่องคุณภาพเสียอีก

คำถามที่เปลี่ยนวิธีคิดทั้งโมดูล

เวลาจะใส่อะไรเข้า context คนมักถามว่า "อันนี้อาจมีประโยชน์ไหม" ซึ่งคำตอบเกือบทุกครั้งคือ "อาจจะ" แล้ว context ก็บวมขึ้นเรื่อย ๆ

คำถามที่ถูกคือ "ถ้าตัดอันนี้ออก งานจะพังไหม" ตอบยากกว่า แต่บังคับให้คิดถึงสิ่งที่จำเป็นจริง ไม่ใช่สิ่งที่ใส่ไว้แล้วสบายใจ

แล้ว window ใหญ่ดียังไง

ไม่ได้บอกว่าไม่มีประโยชน์นะครับ ประโยชน์จริงคือ "ไม่พังกลางทาง" — งานที่แต่ก่อนต้องตัด session ทิ้งกลางคัน ตอนนี้ทำจนจบได้

แต่นั่นคือ "ไม่พัง" ไม่ใช่ "ไม่ต้องบริหาร" มันย้ายเพดานจากที่เคยชนบ่อย เป็นชนไม่บ่อย ส่วนต้นทุนกับคุณภาพยังขึ้นกับวินัยเราเหมือนเดิม

02.03

Attention dilution

อาการ "คุยไปนาน ๆ แล้วมันเริ่มโง่ลง" คนเจอกันทุกคน แต่ตีความผิดกันเกือบหมด คำอธิบายที่ได้ยินบ่อยคือ "โมเดลมันเหนื่อย" หรือ "มันเบลอ" ซึ่งเป็นการอธิบายเชิงอุปมา ที่พาไปสู่ทางแก้ที่ผิด

ของจริงตรงกว่านั้นเยอะ — โมเดลต้องหาว่าอะไรในกอง message เกี่ยวกับงานตรงหน้า พอกองใหญ่ขึ้นและมีของไม่เกี่ยวเยอะขึ้น งานนั้นก็ยากขึ้น กฎที่เราเขียนไว้ตอนต้น ตอนนี้ต้องแข่งความสนใจกับ tool output 60K token ที่ใช้ไปแล้วและไม่เกี่ยวอะไรอีกเลย

Figure 3 · กฎของเราไม่ได้หายไปไหน มันแค่กลายเป็นสัดส่วนที่เล็กลงเรื่อย ๆ ของทั้งกอง

ทางแก้ที่คนเลือก และทำไมมันทำให้แย่ลง

พอ agent เริ่มไม่ทำตามกฎ ปฏิกิริยาแรกของเกือบทุกคนคือย้ำกฎอีกที — พิมพ์ซ้ำ ใส่ตัวใหญ่ เติม "สำคัญมาก!!" เข้าไปใน CLAUDE.md

แต่การย้ำคือการ เพิ่ม context ซึ่งทำให้ signal-to-noise แย่ลงไปอีก เหมือนเติมน้ำเพื่อแก้ปัญหาน้ำจืดเกินไป ทางแก้ที่ถูกคือตรงข้าม — ตัดของที่ไม่ใช้ออก เพื่อให้กฎที่มีอยู่กลับมาเด่นเอง

มีงานวิจัยรองรับ

เรื่องนี้ไม่ใช่แค่ความรู้สึกจากสนาม มีงานวิจัยที่วัดไว้ชัด — Lost in the Middle ของ Liu และคณะ พบว่าโมเดลใช้ข้อมูลที่อยู่ต้นและท้ายของ context ได้ดีกว่าข้อมูลที่อยู่ตรงกลาง อย่างมีนัยสำคัญ

ผลเชิงปฏิบัติที่เอาไปใช้ได้ทันที — อะไรที่สำคัญ อย่าปล่อยให้ไปอยู่กลางกอง กฎสำคัญควรอยู่ใน system prompt (ต้น) หรือย้ำใกล้ ๆ คำถามล่าสุด (ท้าย) ไม่ใช่ฝังอยู่ใน message ที่ 12 จาก 30

Test ที่ใช้เวลา 10 วินาที และแม่นที่สุด

เจออาการแปลก ให้เปิด session ใหม่แล้วสั่งคำสั่งเดิม

ถ้าทำถูกทันที = ปัญหาไม่ได้อยู่ที่ prompt ไม่ได้อยู่ที่ model แต่อยู่ที่กอง context ที่สะสมมา ถ้ายังผิดเหมือนเดิม = ไปดู Layer 1 หรือ Layer 2 ตาม M01.07

  2. Effective context engineering for AI agents — แนวทางจัดการเมื่อ context ยาวขึ้น anthropic.com/engineering
02.04

ลำดับชั้นหน่วยความจำ

ข้อมูลแต่ละประเภทควรอยู่คนละชั้น การวางผิดชั้นคือสาเหตุของทั้งความสิ้นเปลืองและการลืม

Figure 4 · เส้นประคือเส้นแบ่งที่สำคัญที่สุด — เหนือเส้นจ่ายทุก round ใต้เส้นจ่ายเฉพาะตอนใช้

กฎการวางชั้น

ยิ่งใช้บ่อยและเปลี่ยนน้อย → ยิ่งควรอยู่ชั้นบน · ยิ่งใช้นาน ๆ ครั้งและใหญ่ → ยิ่งควรอยู่ชั้นล่าง

ที่ผิดบ่อยคือเอาของที่ใช้นาน ๆ ครั้งไปแปะไว้ชั้นบนเพราะกลัวลืม เช่นเอา API doc ทั้งเล่มใส่ CLAUDE.md ผลคือจ่ายค่ามันทุก round ของทุกงาน ทั้งที่ใช้จริงเดือนละครั้ง

Engineering noteวิธีเช็คว่าวางชั้นถูกไหม

เอา CLAUDE.md ของคุณมาไล่ทีละบรรทัด แล้วถามว่า "บรรทัดนี้ถูกใช้ในกี่เปอร์เซ็นต์ของงานที่ทำ"

  • เกิน 80% → อยู่ถูกที่แล้ว
  • 20–80% → พิจารณาย้ายไป directory-scoped file ที่โหลดเฉพาะโซนนั้น
  • ต่ำกว่า 20% → ย้ายออกไปเป็นไฟล์ที่ agent อ่านเมื่อต้องใช้ แล้วเขียนใน CLAUDE.md แค่บรรทัดเดียวว่าไฟล์นั้นอยู่ไหน

บรรทัดเดียวที่ชี้ทางไปหาของ ถูกกว่าการแปะของทั้งก้อนไว้ตลอดเวลาเสมอ

02.06

สามกลไกที่คนสับสน

พอ context เริ่มยาว มี 3 ทางเลือกที่ทำงานคนละแบบ และคนใช้ผิดตัวกันบ่อยมาก

Figure 6 · สี่กลไกทำคนละอย่าง — สรุป / ลบ / ย้ายออก / จดแล้วค้นย้อนได้ · เลือกจากว่าจะได้ใช้อีกไหม

กลไกทำอะไรเหมาะเมื่อเสียอะไร
Compactionสรุปย่อประวัติเก่าsession ยาวที่ยังต้องรู้ว่าเคยทำอะไรรายละเอียดที่ถูกสรุปทิ้ง
Context editingลบ tool result เก่าทั้งก้อนผลที่ใช้แล้วและไม่ต้องใช้อีกของนั้นหายไปเลย
Memory toolเขียนออกไปเก็บนอก contextข้อสรุปที่ต้องใช้ข้าม sessionต้องดึงกลับเองเมื่อจะใช้
Notes + searchable historyจด note ข้าม window และค้น window เก่าย้อนได้งานยาวที่ยังไม่รู้ว่าจะต้องย้อนดูอะไรต้องเก็บของเก่าไว้ ซึ่งมีต้นทุนฝั่งระบบ

กลไกที่ 4จดไว้ แล้วค้นของเก่าย้อนได้

สามกลไกแรกมีจุดอ่อนร่วมกันข้อหนึ่ง — พอตัดสินใจไปแล้วก็ย้อนไม่ได้ สรุปแล้วรายละเอียดหาย ลบแล้วหายเลย เขียนออกไปแล้วถ้าไม่ได้จดสิ่งที่ถูกก็ดึงกลับไม่ได้

ปัญหาคือตอนที่ต้องตัดสินใจ เรามักยังไม่รู้ว่าอีกสิบรอบข้างหน้าจะต้องใช้อะไร เช่นตอน debug ยาว ๆ เหตุผลว่า "ทำไมวิธีที่ 3 ถึงไม่เวิร์ก" อาจสำคัญมากตอนรอบที่ 20 แต่ตอนสรุปรอบที่ 8 มันดูเหมือนของที่ตัดได้

แนวทางใหม่ที่เริ่มเห็นในเครื่องมือปี 2026 คือให้ agent จด note สะสมข้าม window และเก็บ window เก่าไว้ให้ค้นย้อนได้ — ถ้ามันนึกได้ทีหลังว่าต้องการอะไร ก็ไปค้นเอาจากของเก่า แม้สิ่งนั้นจะไม่ได้อยู่ใน note ก็ตาม

มองอีกมุมคือมันเอาแนวคิด retrieval มาใช้กับ "ประวัติของตัวเอง" แทนที่จะใช้กับ codebase อย่างเดียว

ซึ่งถ้าย้อนไปดูกฎข้อ 4 ในบท 02.02 (re-findable) — นี่คือการทำให้ประวัติการสนทนา กลายเป็นของที่ "หากลับมาได้" แทนที่จะเป็นของที่ต้องแบกไว้ทั้งกองหรือทิ้งไปเลย

แล้วมันแทนสามอันแรกไหม

ไม่ — มันแก้ปัญหาคนละข้อ ถ้ารู้แน่ว่าของชิ้นนั้นไม่ต้องใช้แล้ว ลบยังถูกกว่าเสมอ เพราะการเก็บไว้ให้ค้นได้ก็มีต้นทุนของมัน กลไกที่ 4 มีค่าตอนที่เราไม่รู้ว่าจะต้องใช้อะไร ซึ่งเป็นสถานการณ์ของงานยาวที่ยังไม่จบ ไม่ใช่ของงานที่รู้ขอบเขตแล้ว

Sub-agent ในฐานะเครื่องมือกันบริบท

คนส่วนใหญ่มอง sub-agent เป็นเรื่อง "ทำงานขนาน = เร็วขึ้น" แต่ประโยชน์ที่แน่นอนกว่าคือมันมี context ของตัวเอง

02.09 · แล็บประจำโมดูล

ตัดบริบท 40% แล้ววัดว่าคุณภาพเปลี่ยนไหม

แล็บนี้ออกแบบมาให้ผลลัพธ์ขัดกับสัญชาตญาณ คนส่วนใหญ่คาดว่าตัดแล้วแย่ลง แต่บ่อยครั้งผลออกมาเท่าเดิมหรือดีขึ้น พร้อมกับต้นทุนที่ลดลงชัดเจน

ขั้นตอน

  1. เลือกงานจริงที่คุณทำซ้ำได้ และมีเกณฑ์ตัดสินเชิงกล
  2. วัดบริบทตั้งต้น — นับ token แยกเป็นหมวด: system, project memory, ผลเครื่องมือ, ไฟล์ที่แนบ
  3. ตัดออก 40% โดยเลือกจากหมวดที่ใหญ่ที่สุดก่อน และเลือกตามกฎข้อสี่ (หากลับมาได้)
  4. รันทั้งสองแบบ อย่างละ 5 ครั้ง แล้วเทียบทั้งอัตราผ่านและต้นทุน
  5. ถ้าคุณภาพไม่ตก ให้ตัดอีก 40% แล้ววัดซ้ำ จนกว่าจะเริ่มตก — นั่นคือขอบของจริง
เกณฑ์ผ่าน
  • รู้ตัวเลขจริงว่าบริบทของงานนี้แบ่งเป็นหมวดละกี่ token
  • หาขอบที่คุณภาพเริ่มตกได้ พร้อมบอกว่าตัดอะไรออกแล้วพัง
  • ถ้าคุณภาพไม่ตกเลยแม้ตัดไปมาก ถือว่าผ่าน — และคุณเพิ่งพบว่าจ่ายเกินมานาน
ข้อควรระวังในการอ่านผล

รันละครั้งไม่พอ ความแปรปรวนของลูปจะกลบผลของการตัด ถ้ายังไม่ได้อ่าน M12.01 ให้ข้ามไปอ่านก่อนสรุปอะไรจากแล็บนี้
