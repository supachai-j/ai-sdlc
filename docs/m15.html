15.01

Runbook ที่ agent อ่านแล้วทำได้

ลองนึกถึง runbook ที่ทีมคุณมีอยู่ตอนนี้ แล้วถามตัวเองว่า ถ้าให้ agent ทำตามคำต่อคำ มันจะทำได้ไหม

คำตอบเกือบทุกทีมคือไม่ได้ ไม่ใช่เพราะเขียนไม่ดี แต่เพราะ runbook สำหรับคน เว้นช่องว่างไว้ให้คนเติมเอง — "ตรวจดูว่าคิวปกติไหม" คนอ่านแล้วรู้ว่าปกติแปลว่าอะไร เพราะเคยเห็นตอนไม่ปกติมาแล้ว

ช่องว่างพวกนี้คือความรู้ที่ค้างอยู่ในหัวคนเก่า และมันไม่ได้หายไปไหน แค่ไม่เคยถูกเขียนลงกระดาษ เพราะไม่มีใครบังคับให้เขียน

การเขียน runbook ให้ agent ทำตามได้ คือการบังคับตัวเองให้ตอบคำถามที่เลี่ยงมาตลอด — "ปกติ" คือ p99 เท่าไร · "แปลก ๆ" วัดจากอะไร · ก่อนเรียกคนต้องลองอะไรมาแล้วบ้าง

15.02

Log triage และ incident response

ตอนเกิด incident มันมีสภาวะหนึ่งที่อันตรายมากและเกิดขึ้นแทบทุกครั้ง — คนอยู่ใต้ความกดดันและอยากได้คำตอบเร็ว

ซึ่งเป็นสภาวะที่คนเชื่อคำตอบที่ฟังดูมั่นใจโดยไม่ตรวจง่ายที่สุด และ agent ผลิตคำตอบที่ฟังดูมั่นใจได้ตลอดเวลาโดยไม่เหนื่อย

สิ่งที่ agent ทำได้ดีมากตอนตี 3 คืองานที่คนทำช้าและพลาดง่าย — ดึง log จากห้าที่มาเรียงตามเวลา หาว่า deploy ไหนลงก่อนเกิดเหตุ นับว่า error ตัวไหนโผล่ถี่ขึ้นผิดปกติ งานพวกนี้ มอบให้ได้เต็มที่และคุ้มมาก

สิ่งที่ห้ามมอบคือการตัดสินใจ และเหตุผลไม่ใช่เรื่องความสามารถ แต่เป็นเรื่อง ความรับผิดชอบ — คนที่ประกาศว่า incident จบแล้วต้องเป็นคนที่รับผลถ้ามันยังไม่จบ

กฎที่ใช้ได้จริงคือบังคับกฎเดิมจาก M04.05 — ทุกข้อสรุปต้องชี้หลักฐานได้ ถ้าชี้ไม่ได้ให้เรียกว่าสมมติฐาน และให้มันเสนอมา หลายข้อพร้อมกัน ไม่ใช่ข้อเดียว เพราะคำตอบเดียวชวนให้ทีมไล่ตามทางนั้นทางเดียว

15.03

Documentation automation ที่ไม่กลายเป็นขยะ

เอกสารอัตโนมัติล้มเหลวด้วยรูปแบบเดียวกันเสมอ — เดือนแรกสวยมาก เดือนที่สามไม่มีใครเชื่อ เดือนที่หกยังอยู่ในโปรเจกต์เพื่อหลอก agent ตัวถัดไป

เกณฑ์ที่แยกเอกสารที่มีชีวิตออกจากขยะมีข้อเดียว — มันพังได้ไหมเมื่อมันผิด

ถ้าเอกสาร API ถูกสร้างจากสคีมาและมีเทสต์เทียบ พอโค้ดเปลี่ยนแล้วเอกสารไม่ตรง build จะแดง นั่นคือเอกสารที่มีชีวิต แต่ถ้ามันถูก generate ครั้งเดียวแล้ว commit ทิ้งไว้ มันจะเริ่มโกหกเงียบ ๆ ตั้งแต่ commit ถัดไป

ประเภทสร้างอัตโนมัติได้ไหมกลไกที่ทำให้ไม่เน่า
เอกสาร APIได้สร้างจากสคีมา เทสต์แดงถ้าไม่ตรง
บันทึกการเปลี่ยนแปลงได้สร้างจากคอมมิต
ตัวอย่างการใช้งานได้ต้องรันได้จริงใน CI
เอกสารสถาปัตยกรรมช่วยร่างคนตรวจ + มีวันหมดอายุ
ADRไม่เป็นบันทึกการตัดสินใจของคน

แถวล่างสุดสำคัญที่สุด — ADR ไม่ควรให้ agent เขียน เพราะคุณค่าของมันคือบันทึกว่า คนตัดสินใจอะไรและตอนนั้นคิดอะไรอยู่ ถ้าให้ agent เขียน คุณจะได้สรุปสิ่งที่โค้ดทำ ซึ่งอ่านจากโค้ดก็ได้อยู่แล้ว

Figure 3 · ถ้าเอกสารไม่ได้ผูกกับสิ่งที่ build ตรวจได้ มันจะเน่าตามกำหนดเวลาเสมอ

15.04

Trust calibration

คำถามที่ทีมถามผมบ่อยที่สุดในหัวข้อนี้คือ "แล้วเมื่อไหร่ถึงเชื่อมันได้" ซึ่งเป็นคำถามที่ตอบไม่ได้ในรูปแบบที่ถาม เพราะความไว้ใจไม่ใช่ตัวเลขเดียว

มันต่างกันตามประเภทงาน และควรมาจากข้อมูลของทีมคุณเอง ไม่ใช่จากที่คนอื่นบอกในทวิตเตอร์

ตัวแปรที่ตัดสินไม่ใช่ว่างานยากแค่ไหน แต่คือตรวจผลง่ายแค่ไหนและ ผิดแล้วเสียหายแค่ไหน refactor ที่มีเทสต์คุมครบตรวจได้ในไม่กี่วินาที ส่วนข้ออ้างเรื่อง API ที่ฟังดูสมเหตุสมผลอาจใช้เวลาตรวจนานกว่าเขียนเองเสียอีก

ระดับหมายความว่าเลื่อนขึ้นได้เมื่อ
ตรวจทุกบรรทัดอ่าน diff ทั้งหมดก่อนรับงานประเภทนี้ผ่านชุดวัดสม่ำเสมอ
ตรวจแบบสุ่มดูละเอียดบางส่วนอัตราพลาดต่ำต่อเนื่องหลายสิบงาน
เชื่อ gateดูแค่ผลของ gategate มี precision สูงพิสูจน์แล้ว
ตรวจย้อนหลังดูเป็นชุดรายสัปดาห์งานที่ผิดแล้วเสียหายต่ำและย้อนได้

คอลัมน์ขวาคือเหตุผลที่ M12 ต้องมาก่อนบทนี้

เพราะมันเปลี่ยนบทสนทนาจาก "ผมว่ามันเชื่อได้แล้วนะ" เป็น "งานประเภทนี้ผ่าน 47 จาก 50 ในสามเดือน และสามที่ไม่ผ่าน gate จับได้ทั้งหมด" — ประโยคหลังเถียงกันต่อได้ ประโยคแรกเถียงไม่ได้

15.05

วัฒนธรรม code review เมื่อ diff โตขึ้นสิบเท่า

ปฏิกิริยาแรกของเกือบทุกทีมเมื่อ diff โตขึ้นสิบเท่าคือ พยายามรีวิวให้เร็วขึ้น ซึ่งเป็นทางที่ไปไม่รอด เพราะความเร็วในการอ่านของคนไม่ได้เพิ่มขึ้นตาม

สิ่งที่ต้องเปลี่ยนไม่ใช่ความเร็ว แต่คือเป้าของการรีวิว

เรื่องรูปแบบ การตั้งชื่อ type สัญญาระหว่างฟังก์ชัน และขอบเขตของ diff — ทั้งหมดนี้เครื่องตรวจได้และตรวจได้ดีกว่าคน ถ้ายังใช้สายตาคนตรวจอยู่ แปลว่าคุณกำลังจ่ายเวลาที่แพงที่สุดในทีมไปกับงานที่ถูกที่สุด

สิ่งที่เหลือให้คนคือคำถามที่เครื่องตอบไม่ได้ — โจทย์นี้ถูกต้องหรือเปล่า · มันสมมติอะไรไว้โดยไม่ได้เขียน · เทสต์กำลังทดสอบสิ่งที่ถูกต้องไหม · และมีผลกระทบอะไรที่ diff ไม่แสดง

สังเกตว่าสองข้อที่หนาที่สุดเป็นคำถามเรื่องความถูกต้องของเป้าหมาย ไม่ใช่ความถูกต้องของโค้ด และมันมีค่าเพิ่มขึ้นเรื่อย ๆ เมื่อโค้ดถูกผลิตเร็วขึ้น

15.06

Attribution license และความเสี่ยงเชิงกฎหมาย

ขอออกตัวก่อนว่าผมไม่ใช่นักกฎหมาย และหัวข้อนี้ไม่ใช่คำแนะนำทางกฎหมาย สิ่งที่ผมให้ได้คือเช็คลิสต์ว่าต้องไปถามอะไรบ้าง ซึ่งต่างกันมากและความต่างนี้สำคัญ

เหตุผลที่ต้องมีหัวข้อนี้เลยคือ สามเรื่องข้างล่างนี้มาถึงในรูปของ incident เสมอถ้าไม่จบในนโยบายก่อน — และตอนมาเป็น incident มันแพงกว่ามาก

สิ่งที่ควรทำเป็นนโยบาย
  • ระบุในคอมมิตว่าสร้างโดย agent และใครอนุมัติ — สำคัญตอนตรวจสอบย้อนหลัง
  • สแกน license ของ dependency ที่ agent เพิ่มเข้ามา เป็น gate ใน CI
  • กำหนดว่าโค้ดของลูกค้าส่งเข้าโมเดลได้แค่ไหน — ข้อนี้มักถูกกำหนดโดยสัญญาที่มีอยู่แล้ว
  • เก็บบันทึกว่าใครใช้อะไรกับงานไหน ในระดับที่ตอบผู้ตรวจสอบได้

เรื่องเหล่านี้ต่างกันไปตามเขตอำนาจและตามสัญญาที่องค์กรคุณมีอยู่ หลักสูตรนี้ให้เช็คลิสต์ที่ต้องเอาไปคุยกับฝ่ายกฎหมาย ไม่ใช่คำแนะนำทางกฎหมาย และความต่างข้อนี้สำคัญ

ในสามเรื่องนี้ ข้อ สแกน license เป็นข้อเดียวที่แก้ได้ด้วยเครื่องมือล้วน ๆ จึงควรทำก่อน — agent ไม่รู้ว่าองค์กรคุณห้าม copyleft และมันจะไม่มีวันรู้ เว้นแต่คุณจะทำให้ CI เป็นคนบอก

Figure 6 · ข้อ 2 เป็นข้อเดียวที่แก้ได้ด้วยเครื่องมือล้วน ๆ จึงควรทำก่อน

15.07

Skill atrophy — สิ่งที่ไม่มีใครพูดถึง

หัวข้อนี้คนไม่ค่อยพูดถึงเพราะมันฟังดูเหมือนบ่นเรื่องเทคโนโลยี แต่ผมคิดว่ามันเป็น ความเสี่ยงระยะยาวที่ใหญ่ที่สุดในโมดูลนี้

เกณฑ์ที่ผมใช้แยกว่าทักษะไหนปล่อยได้ทักษะไหนต้องรักษามีข้อเดียว — "ทักษะนี้จำเป็นตอนที่ agent ทำไม่ได้หรือทำผิดหรือเปล่า"

การจำ syntax ของภาษาที่ไม่ค่อยใช้ · จำ flag ของคำสั่ง · ค้นวิธีใช้ API · เขียนโค้ดสำเร็จรูปซ้ำ ๆ — ปล่อยได้หมด ไม่มีใครกลับไปท่องหน้า man page แล้วชีวิตดีขึ้น

ส่วนที่ต้องรักษาคือสามอย่างที่ใช้ตอนตรวจงานของ agent — อ่านโค้ดที่ไม่ได้เขียนเองแล้วเข้าใจจริง · debug ด้วยการตั้งสมมติฐานแล้วทดสอบ · และรู้ว่าอะไรผิดปกติเมื่อเห็นมัน

ถ้าทีมสูญเสียสามอย่างนี้ไป คุณจะเหลือแต่คนที่กด approve ได้เร็วขึ้นแต่จับผิดไม่ได้ ซึ่งเป็นสภาพที่อันตรายกว่าการไม่ใช้ agent เลย เพราะโค้ดไหลเข้าเร็วขึ้นโดยไม่มีด่าน

ทางปฏิบัติที่ผมเห็นว่าได้ผลจริงไม่ใช่การห้ามใช้เครื่องมือ แต่คือ กันงานบางประเภทไว้ให้ทำเองโดยตั้งใจ

เช่น incident ทุกครั้งให้คนไล่หาสาเหตุเองก่อน 30 นาที หรือให้ junior เป็นคนอ่าน PR ของ agent แล้วอธิบายให้ทีมฟังว่ามันทำอะไร — ได้ทั้งงานและได้ทั้งการฝึก

แผน rollout ในองค์กร

ขั้นตอนสามขั้นนี้ฟังดูเหมือนสามัญสำนึก แต่องค์กรจำนวนมากทำสลับลำดับ และเกือบทุกครั้งที่สลับ มันสลับแบบเดียวกัน

คนเริ่มที่ Policy เพราะเป็นขั้นที่เขียนได้เร็วที่สุดและดูเหมือนได้ทำอะไรแล้ว

ผลของการเริ่มที่ Policy คือได้กฎที่อิงจากความกลัวและข่าวที่อ่านเจอ ไม่ใช่จากสิ่งที่ทีมเจอจริง กฎพวกนั้นมักเข้มเกินในเรื่องที่ไม่เป็นปัญหา และหลวมเกินในเรื่องที่เป็นปัญหาจริง เพราะยังไม่มีใครเคยเจอมัน

Pilot ต้องมาก่อนเสมอ เพราะมันเป็นสิ่งเดียวที่บอกได้ว่ากฎข้อไหนจำเป็นจริง และเกณฑ์ผ่านของ Pilot ต้องเป็นตัวเลขจากชุดวัด ไม่ใช่ความเห็นของทีมที่ทดลอง ซึ่งเป็นทีมที่กระตือรือร้นที่สุดและจะบอกว่าดีเสมอ

เกณฑ์ผ่านของอีกสองขั้นก็ต้องคมพอกัน — Policy ผ่านเมื่อกฎถูกบังคับด้วยเครื่องมือ ไม่ใช่ด้วยเอกสาร · Platform ผ่านเมื่อติดตั้งแล้วทุกคนได้พฤติกรรมเหมือนกันจริง ไม่ใช่แค่ได้ไฟล์ config เหมือนกัน

15.09 · แล็บประจำโมดูล

เขียน AI engineering policy ของทีมความยาว 2 หน้า ที่บังคับใช้ได้จริง

เกณฑ์ที่ทำให้แล็บนี้ต่างจากการเขียนเอกสารทั่วไป — ทุกข้อในนโยบายต้องระบุได้ว่าบังคับด้วยอะไร ข้อที่บังคับด้วย “ความร่วมมือของทุกคน” ให้ตัดออกหรือหาวิธีบังคับ

ต้องครอบคลุมหกหัวข้อ

  1. ขอบเขต — งานประเภทไหนใช้ agent ได้ ประเภทไหนต้องมีคนอยู่ด้วยเสมอ
  2. สิทธิ์ — ระดับสิทธิ์มาตรฐาน และใครอนุมัติการขอเพิ่ม
  3. รีวิว — อะไรที่เครื่องตรวจ อะไรที่คนต้องตรวจ (ตาราง 15.05)
  4. ความรับผิดชอบ — ใครรับผิดชอบเมื่อโค้ดที่ agent เขียนทำให้เกิดปัญหา
  5. ข้อมูล — อะไรส่งเข้าโมเดลได้ อะไรห้าม และบังคับยังไง
  6. การติดตั้งของจากภายนอก — เช็คลิสต์จาก M13.04 เป็นขั้นตอนของทีม
เกณฑ์ผ่าน
  • ทุกข้อระบุกลไกบังคับได้ — hook, การตั้งค่า, gate ใน CI หรือขั้นตอนอนุมัติ
  • ยาวไม่เกินสองหน้า ถ้าเกิน แปลว่ามีข้อที่ควรเป็นเครื่องมือแทนที่จะเป็นข้อความ
  • เอาไปให้คนในทีมที่ไม่ได้เขียนอ่าน แล้วเขาบอกได้ว่าพรุ่งนี้ต้องทำอะไรต่างจากวันนี้
สัญญาณว่านโยบายจะไม่ถูกใช้

ถ้าอ่านจบแล้วรู้สึกว่า “ก็สมเหตุสมผลดี” แต่ตอบไม่ได้ว่าพรุ่งนี้ต้องเปลี่ยนอะไร แปลว่ามันเป็นเรียงความ ไม่ใช่นโยบาย นโยบายที่ดีเปลี่ยนพฤติกรรมได้ตั้งแต่วันแรก

จบหลักสูตร — จากที่นี่วนกลับไปที่ M12 ทุกไตรมาส เพราะโมเดลเปลี่ยน เครื่องมือเปลี่ยน และเวิร์กโฟลว์ที่เคยดีที่สุดเมื่อหกเดือนก่อนอาจไม่ใช่แล้ว — ชุดวัดคือสิ่งเดียวที่บอกคุณได้
