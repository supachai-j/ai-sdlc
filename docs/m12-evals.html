12.01

ทำไม “รู้สึกว่าดีขึ้น” ถึงเชื่อไม่ได้

เริ่มด้วยความจริงที่ไม่ค่อยมีใครพูด — งาน agent เดิม รันสองครั้ง ได้ผลคนละแบบได้ โดยที่คุณไม่ได้แตะ prompt เลย

และขนาดของความแปรปรวนนี้มักใหญ่กว่าผลของการแก้ prompt ส่วนใหญ่ ซึ่งแปลว่าเวลาคุณแก้แล้วรันหนึ่งครั้งแล้วรู้สึกว่าดีขึ้น สิ่งที่คุณเห็นอาจเป็นเสียงรบกวนล้วน ๆ

งาน agent หนึ่งงานไม่ได้เดินเส้นทางเดียวทุกครั้ง ลูปแตกต่างกันได้จากลำดับการเรียก tool ผลลัพธ์ที่ tool คืนกลับมาไม่เหมือนเดิม ไฟล์ที่มันเลือกอ่านก่อน–หลัง และการที่บริบทสะสมต่างกัน ผลคือรันงานเดิมสองครั้งอาจได้ diff คนละแบบ แม้จะไม่แตะ prompt เลย

ปัญหาคือขนาดของความแปรปรวนนี้ มักใหญ่กว่าผลของการแก้ prompt ทั่วไป เมื่อคุณแก้ prompt แล้วรันหนึ่งครั้งแล้วรู้สึกว่าดีขึ้น สิ่งที่คุณสังเกตเห็นอาจเป็นความแปรปรวนล้วน ๆ

ตัวแปรกวนสามอย่างที่ปนกันเสมอเวลาเปรียบเทียบด้วยความรู้สึก

  • คุณเปลี่ยนมากกว่าหนึ่งอย่าง — แก้ prompt พร้อมกับเพิ่มไฟล์เข้า context พร้อมกับเปลี่ยนวิธีตั้งคำถาม
  • งานไม่เหมือนเดิม — รอบสองคุณลองกับงานที่ง่ายกว่า หรือกับ repo ที่สะอาดกว่า
  • คุณเองเปลี่ยน — รอบสองคุณตั้งใจกว่า ตอบคำถามของ agent ดีกว่า และเข้าไปช่วยแก้ระหว่างทางโดยไม่นับ

n = 1 คือเกร็ดเล่าสู่กันฟัง ไม่ใช่ผลการวัด ก่อนจะเชื่ออะไรเกี่ยวกับการเปลี่ยนแปลง ให้รันงานเดิมซ้ำอย่างน้อย 5 ครั้งทั้งก่อนและหลัง แล้วดูว่าช่วงของผลสองชุดทับกันหรือไม่ ถ้าทับ แปลว่าคุณยังไม่รู้อะไรเลย

องค์ประกอบของชุดสัดส่วนที่ใช้ได้จริง

ขั้นต่ำที่เริ่มมีประโยชน์คือ 20 งาน และเริ่มเชื่อผลได้จริงราว 40–60 งาน กระจายตามประเภทงานที่ทีมทำจริง ไม่ใช่ตามที่คิดว่าน่าจะเป็น — ดึงจาก backlog หรือ PR ย้อนหลังสามเดือน

  • Bugfix ~40% — วัดง่ายที่สุด เพราะมีเทสต์ที่ควรเปลี่ยนจากแดงเป็นเขียว
  • Feature เล็ก ~25% — วัดด้วยเทสต์ที่เขียนไว้ล่วงหน้า
  • Refactor ~20% — วัดด้วย “เทสต์เดิมต้องยังเขียวทั้งหมด” บวกเกณฑ์เชิงโครงสร้าง
  • Investigation ~15% — งานที่ผลลัพธ์เป็นคำตอบ ไม่ใช่โค้ด ต้องใช้ judge
งานที่ต้องคัดทิ้ง
  • ง่ายเกิน — ผ่าน 100% ทุกครั้ง ไม่ให้สัญญาณ เอาออกหรือเลื่อนไปเป็น smoke test
  • ยากเกิน — ตกทุกครั้งเหมือนกันหมด ก็ไม่ให้สัญญาณเช่นกัน
  • ไม่ deterministic — พึ่ง network จริง เวลาปัจจุบัน หรือ service ภายนอกที่เปลี่ยนได้
  • อยู่ในข้อมูลฝึกแน่ ๆ — เช่น bug ดังใน repo โอเพนซอร์สที่มีคำตอบเต็มอินเทอร์เน็ต
กรณีศึกษา · อ่าน benchmark ของผู้ผลิตยังไง

ทักษะสร้าง task set กับทักษะอ่าน task set ของคนอื่น เป็นเรื่องเดียวกัน ลองใช้หน้าประกาศโมเดลของผู้ผลิตเป็นแบบฝึก — เอาหน้าไหนก็ได้ที่มีตารางเทียบคะแนน แล้วไล่ถาม 4 ข้อนี้

  1. ใครเป็นคนรัน — คะแนนของคู่แข่งในตาราง ผู้ผลิตรันเองหรือเอามาจากที่คู่แข่งประกาศ
  2. รันด้วย config อะไร — effort เท่าไร มี tool อะไรให้ จำกัดจำนวน turn ไหม
  3. eval ถูกดัดแปลงไหม — บางครั้ง footnote จะบอกว่าปรับ task หรือปรับวิธีให้คะแนน
  4. เลือกมาโชว์กี่ตัวจากกี่ตัว — benchmark ที่ไม่ปรากฏในตาราง มักมีความหมายพอ ๆ กับตัวที่ปรากฏ

ตัวอย่างที่ชัดคือประกาศ GPT-6 Astra ของ OpenAI (2026) ซึ่งเปิดเผยเงื่อนไขพวกนี้ไว้ใน footnote อย่างตรงไปตรงมา — มีทั้งกรณีที่ผู้ผลิตรันคะแนนคู่แข่งเอง กรณีที่ปรับ eval แล้วระบุไว้ กรณีที่คะแนนต่ำของรุ่นก่อนเกิดจากเพดานจำนวน turn ไม่ใช่ความสามารถ และกรณีที่คะแนนคู่แข่งบางตัวมาจากเวอร์ชันที่มี safeguard น้อยลง

ที่น่าสนใจกว่าคือ — ในตารางเดียวกันนั้น index ของบุคคลที่สามให้ผลไม่ตรงกับ benchmark ที่ถูกเลือกมาโชว์ ซึ่งเป็นภาพของ benchmark selection ที่ชัดเจนโดยไม่ต้องกล่าวหาใคร

ผมไม่ได้จะบอกว่าเขาโกงนะครับ ตรงข้ามเลย — การที่ footnote บอกเงื่อนไขครบขนาดนั้นถือว่าโปร่งใสกว่าค่าเฉลี่ยของวงการมาก

ประเด็นคือ ต่อให้โปร่งใสเต็มที่ ตัวเลขก็ยังตอบคำถามของคุณไม่ได้อยู่ดี เพราะ task set ของเขาไม่ใช่งานของคุณ — และนั่นคือเหตุผลทั้งหมดที่โมดูลนี้ยืนยันว่าต้องมีชุดวัดของตัวเอง

12.03

เกณฑ์ deterministic มาก่อนเสมอ

บทนี้มีกฎข้อเดียวที่ทีมส่วนใหญ่ทำกลับด้าน — คนมักเริ่มที่ LLM-as-judge เพราะมันดูฉลาดกว่าและยืดหยุ่นกว่า

แต่เกณฑ์ที่ deterministic ไม่มีอคติ ไม่มีค่าใช้จ่ายต่อรอบ และไม่เถียงกับคุณ มันตอบคำถามส่วนใหญ่ได้ในราคาเศษเสี้ยว ใช้ชั้นบนเมื่อชั้นล่างตอบไม่ได้เท่านั้น

ความผิดพลาดที่พบบ่อยที่สุดตอนเริ่มทำ eval คือกระโดดไปใช้ LLM ตัดสินทันที ทั้งที่เกณฑ์ส่วนใหญ่ผลักลงมาเป็นเกณฑ์เชิงกลได้ ซึ่งถูกกว่า เร็วกว่า และไม่มีความเห็น

ลำดับชั้นไล่จากถูกไปแพง — ใช้ชั้นที่ต่ำที่สุดที่ตอบคำถามได้

ชั้นเกณฑ์ต้นทุนเชื่อถือได้
1คอมไพล์ / lint / typecheck ผ่านแทบเป็นศูนย์สมบูรณ์
2เทสต์ที่มีอยู่เดิมยังเขียวทั้งหมดต่ำสมบูรณ์
3เทสต์เป้าหมาย แดงก่อน → เขียวหลังต่ำสมบูรณ์
4diff แตะเฉพาะไฟล์ที่อนุญาต / ไม่เกิน N บรรทัดต่ำสมบูรณ์
5ต้นทุนและเวลาไม่เกินเพดานต่ำสมบูรณ์
6static analysis / security scan ไม่พบของใหม่ปานกลางสูง
7LLM judge ตาม rubricสูงต้อง calibrate
8คนตัดสินสูงมากสูง แต่ไม่ scale
เกณฑ์ที่ทรงพลังที่สุดต่อบาทที่จ่าย

“เทสต์ต้องแดงก่อนแก้ และเขียวหลังแก้” — สำหรับงาน bugfix เกณฑ์นี้แทบพิสูจน์ความถูกต้องได้เอง เพราะมันปิดทั้งช่องที่ agent แก้ไม่ตรงจุด และช่องที่ agent แก้เทสต์แทนที่จะแก้โค้ด

# โครงเกณฑ์หนึ่งงาน — เป็นสคริปต์ ไม่ใช่คำบรรยาย
task: fix-null-deref-in-invoice-total
repo_sha: 8f3a91c
prompt: "invoice total คำนวณผิดเมื่อไม่มี line item — แก้ให้ถูก"
criteria:
  - type: cmd     cmd: "pnpm typecheck"                 expect: exit 0
  - type: cmd     cmd: "pnpm test --filter invoice"     expect: exit 0

12.04

LLM-as-Judge ที่ใช้ได้จริง

ประโยคที่อยากให้จำจากบทนี้ — judge เป็นเครื่องมือวัดชิ้นหนึ่ง และเครื่องมือวัดทุกชิ้นต้องถูก calibrate ก่อนใช้

คนส่วนใหญ่เอา judge มาใช้เลยแล้วเชื่อตัวเลขที่มันผลิต โดยไม่เคยวัดว่ามันตรงกับคนแค่ไหน ซึ่งถ้าตรงต่ำ ตัวเลขทุกตัวหลังจากนั้นก็ไม่มีความหมาย

เมื่อเหลือแต่สิ่งที่วัดเชิงกลไม่ได้ — คุณภาพของคำอธิบาย ความสมเหตุสมผลของสถาปัตยกรรม ความชัดของรายงาน — จึงค่อยใช้ LLM ตัดสิน แต่ต้องรู้ว่ามันมีอคติเป็นระบบ ไม่ใช่สุ่ม

อคติ 4 แบบที่ต้องออกแบบรับมือ ไม่ใช่หวังว่าจะไม่เกิด

อคติอาการวิธีรับมือ
Position biasเลือกตัวเลือกแรก (หรือหลัง) บ่อยเกินจริงรันสองลำดับแล้วเฉลี่ย ถ้าผลกลับกันให้ถือว่าเสมอ
Verbosity biasให้คะแนนคำตอบยาวสูงกว่า ทั้งที่เนื้อเท่ากันใส่เกณฑ์ความกระชับใน rubric อย่างชัดเจน
Self-preferenceโมเดลชอบผลงานของตัวเองใช้ judge คนละตัวกับ executor
Leniency driftตัดสินหลวมขึ้นเมื่อ rubric กำกวมเกณฑ์ต้องเป็นคำถามใช่/ไม่ใช่ ไม่ใช่คะแนน 1–10
กฎการเลือก judge

Judge ต้องมีความสามารถเท่ากับหรือมากกว่าตัวที่ถูกตัดสินเสมอ การใช้โมเดลเล็กตัดสินผลงานโมเดลใหญ่เพื่อประหยัด คือการเอาไม้บรรทัดที่สั้นกว่าของจริงไปวัด

การออกแบบ rubricแตกเป็นข้อย่อยแบบไบนารี

คะแนน 1–10 ให้ผลที่ไม่คงเส้นคงวา เพราะโมเดลไม่มีนิยามร่วมว่า 7 ต่างจาก 8 อย่างไร แตกเป็นคำถามที่ตอบได้แค่ใช่หรือไม่ แล้วนับจำนวนข้อที่ผ่าน จะเสถียรกว่ามาก

ขั้นตอนที่คนข้ามแล้วเสียใจทีหลัง

Calibrate judge ก่อนใช้ — ให้คนตัดสิน 30 ชิ้นด้วยมือ แล้ววัดว่า judge เห็นตรงกับคนกี่เปอร์เซ็นต์ ถ้าต่ำกว่า 80% แปลว่า rubric ยังกำกวม ต้องแก้ rubric ไม่ใช่แก้ judge และควรรายงานอัตราความสอดคล้องนี้ควบคู่ไปกับผลเสมอ เพราะมันคือความน่าเชื่อถือของเครื่องวัด

วัดสี่มิติพร้อมกัน

กับดักของบทนี้คือการวัดมิติเดียวแล้วดีใจ — ความถูกต้องขึ้น 12% ฟังดูดีมาก จนกว่าจะเห็นว่าต้นทุนขึ้นสามเท่าและช้าลงสองเท่าครึ่ง

ที่สำคัญคือ ตัวเลขสี่ช่องนั้นยังตัดสินไม่ได้ว่าคุ้มไหม จนกว่าจะรู้ว่าเวลาของคนในทีมแพงแค่ไหน ซึ่งเป็นตัวเลขที่ทีมส่วนใหญ่ไม่เคยคำนวณ

12.07

A/B การเปลี่ยนเวิร์กโฟลว์

บทนี้มีคำตอบหนึ่งที่คนไม่ชอบ แต่ผมคิดว่าต้องพูด — "ยังบอกไม่ได้" เป็นผลลัพธ์ที่ใช้ได้

ผลต่างระดับ 2–3% ต้องการจำนวนรอบมากกว่าที่คนส่วนใหญ่ยอมรัน การยอมรับว่ายังสรุปไม่ได้ ดีกว่าเชื่อผิดแล้วเอาไปตัดสินใจต่อ

เมื่อมีเครื่องวัดแล้ว คำถามอย่าง “sub-agent ช่วยจริงไหม” หรือ “effort สูงคุ้มไหม” เลิกเป็นเรื่องความเห็น แต่ต้องออกแบบการทดลองให้ถูก ไม่งั้นจะได้ตัวเลขที่ดูน่าเชื่อแต่ผิด

หลักสามข้อที่ทำให้ผลเชื่อได้

  1. เปลี่ยนทีละอย่าง — ถ้าเปลี่ยนทั้ง prompt และโมเดลพร้อมกัน คุณจะไม่มีวันรู้ว่าอันไหนมีผล
  2. ใช้ paired design — รันทั้งสองแบบบนชุดงานเดียวกัน แล้วเทียบเป็นรายงาน วิธีนี้ให้กำลังทางสถิติสูงกว่าการสุ่มแยกกลุ่มมาก เพราะตัดความแปรปรวนระหว่างงานออกไป
  3. รันซ้ำต่องาน — อย่างน้อย 3 ครั้งต่องานต่อแบบ แล้วใช้ค่ากลาง เพื่อกดความแปรปรวนของลูปลง
ขนาดตัวอย่างที่ต้องมี

ที่ระดับ pass rate ราว 70% การจะแยกความต่าง 10 จุด ออกจากความบังเอิญได้ ต้องใช้ราว 40–60 งานต่อแบบ ถ้ามีน้อยกว่านั้น สิ่งที่คุณเห็นคือความแปรปรวน ยิ่งความต่างที่ต้องการจับเล็กลง ยิ่งต้องการงานมากขึ้นอย่างรวดเร็ว

สิ่งที่มีค่ากว่าตัวเลขรวม

รายการงานที่พลิกผล — งานที่เดิมตกแล้วผ่าน และงานที่เดิมผ่านแล้วตก ตัวเลขรวมบอกว่าเปลี่ยนไปเท่าไหร่ แต่รายการที่พลิกบอกว่าเปลี่ยนอะไร และบ่อยครั้งเผยว่าการปรับปรุงที่ดูดีในภาพรวม กำลังทำให้งานประเภทหนึ่งแย่ลงอย่างเป็นระบบ

12.08

Drift — เมื่อของเดิมแย่ลงโดยไม่มีใครแตะ

โหมดล้มของบทนี้เงียบที่สุดในโมดูล — ไม่มี PR ไม่มี commit ไม่มี alert

ทีมจะรู้สึกแค่ว่า "ช่วงนี้มันงี่เง่าขึ้นนะ" ซึ่งเป็นความรู้สึกที่เถียงกันไม่จบ เพราะไม่มีเส้นฐานให้ชี้

เวิร์กโฟลว์ที่ปรับจนดีกับโมเดลหนึ่ง ไม่ได้แปลว่าจะดีกับโมเดลถัดไป และรูปแบบความเสื่อมที่พบบ่อยที่สุดไม่ใช่โมเดลแย่ลง แต่คือคำสั่งที่เคยช่วยกลายเป็นตัวถ่วง

Prompt cruftคำสั่งที่หมดอายุแล้วแต่ยังอยู่

  • คำสั่งให้คิดเป็นขั้นตอนทีละข้อ — บนโมเดลที่คิดเองอยู่แล้ว กลายเป็นการรบกวน
  • โครง scaffolding ที่ละเอียดยิบ — บนโมเดลใหม่ทำให้ผลแย่ลง เพราะไปจำกัดวิธีที่มันถนัดกว่า
  • คำสั่งแก้ปัญหาเฉพาะของโมเดลเก่า — ปัญหาหายไปแล้ว แต่คำสั่งยังกินบริบทอยู่
  • ตัวอย่าง few-shot ที่สะท้อนสไตล์เดิม — ดึงผลลัพธ์กลับไปหาพฤติกรรมรุ่นก่อน
อาการที่มองไม่เห็นถ้าไม่มีชุดวัด

ทีมอัปเกรดโมเดล ทุกคนรู้สึกว่า “ก็ดีขึ้นนะ” แต่จริง ๆ งานบางประเภทถดถอยลง เพราะ prompt ที่เขียนไว้สำหรับโมเดลเก่ายังบังคับพฤติกรรมเดิมอยู่ กว่าจะรู้ตัวคือสามเดือนถัดมา ตอนที่มีคนบ่นว่า “ช่วงนี้มันงี่เง่าลง”

12.09 · แล็บประจำโมดูล

สร้าง eval harness 20 งาน แล้วใช้มันยุติข้อถกเถียงจริงหนึ่งข้อ

เป้าหมายของแล็บนี้ไม่ใช่การได้เครื่องมือสวย ๆ แต่คือการเปลี่ยนคำถามที่ทีมเถียงกันด้วยความเห็น ให้กลายเป็นคำถามที่มีคำตอบพร้อมตัวเลข

ขั้นตอนทำตามลำดับ อย่าข้ามขั้น 1

  1. เลือกคำถามก่อนสร้างเครื่องมือ — เช่น “review sub-agent ของเราช่วยจริงไหม” หรือ “effort สูงคุ้มกับงาน bugfix ไหม” คำถามต้องเป็นเรื่องที่ทีมยังเถียงกันอยู่จริง
  2. ดึง 20 งานจาก PR ย้อนหลัง 3 เดือน ตรึงด้วย git SHA ตามสัดส่วนใน 12.02
  3. เขียนเกณฑ์ — อย่างน้อย 15 งานต้องใช้เกณฑ์ deterministic ล้วน เหลือไม่เกิน 5 งานที่ใช้ judge
  4. Calibrate judge กับ 30 ตัวอย่างที่คนตัดสินไว้ ถ้าตรงกันต่ำกว่า 80% ให้กลับไปแก้ rubric
  5. รัน paired A/B — สองแบบบนชุดเดียวกัน 3 ครั้งต่องานต่อแบบ
  6. รายงานสี่มิติ พร้อมรายการงานที่พลิกผล
เกณฑ์ผ่านแล็บ
  • ตอบคำถามที่ตั้งไว้ได้ด้วยตัวเลข พร้อมระบุว่ามั่นใจแค่ไหนและเพราะอะไร
  • ถ้าผลออกมาว่า “ยังบอกไม่ได้” ถือว่าผ่านเช่นกัน — ตราบใดที่บอกได้ว่าต้องมีอีกกี่งานถึงจะตอบได้
  • ชุดงานรันซ้ำได้จากคำสั่งเดียว โดยไม่ต้องเซ็ตอัปด้วยมือ
โหมดล้มเหลวของ eval harness เอง
  • Overfitting — ปรับ prompt จนชนะชุดวัดของตัวเอง แต่ไม่ดีขึ้นกับงานจริง กันด้วยชุดที่กันไว้ไม่ใช้ปรับ
  • ลืมตรึงสภาพแวดล้อม — dependency ขยับแล้วผลข้ามสัปดาห์เทียบกันไม่ได้
  • ชุดที่เอียง — งานส่วนใหญ่มาจากส่วนเดียวของ codebase แล้วสรุปเหมารวมทั้งระบบ
  • ปล่อยให้เก่า — ไม่เติมงานจากความล้มเหลวจริง สุดท้ายวัดสิ่งที่ไม่มีใครทำแล้ว

เชื่อมกับโมดูลอื่น — M03 ให้วิธีคิดต้นทุนที่ใช้ในมิติที่สอง, M10 ใช้แล็บนี้เป็นเครื่องตัดสินว่า multi-agent คุ้มจริงหรือแค่แพงกว่า, M11 ใช้เกณฑ์เดียวกันนี้วัด precision และ recall ของ review agent, และ M14 เอาชุด smoke ไปแขวนไว้บนสายพาน CI เป็น quality gate
