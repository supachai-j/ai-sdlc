AI Coding Agent SDLC · Phase 03 · Module 10

Multi-Agent Orchestration

Multi-agent เป็นสถาปัตยกรรม ไม่ใช่ฟีเจอร์ มันมีแพตเทิร์น มีสัญญาการส่งต่อ และมีโหมดล้มเหลวเฉพาะตัว บทที่สำคัญที่สุดคือบทที่บอกว่าเมื่อไหร่มันแพ้ agent เดียว ซึ่งบ่อยกว่าที่คนคิดมาก

8 บทเรียน3 ชั่วโมง1 แล็บต้องผ่าน M02 · M03 · M12 ก่อน
ใจความของทั้งโมดูล

เหตุผลที่ถูกต้องในการใช้หลาย agent มีแค่สองข้อ — กันบริบทไม่ให้ปน และทำงานที่ไม่ขึ้นต่อกันพร้อมกัน ถ้าเหตุผลของคุณไม่ใช่สองข้อนี้ คุณกำลังจ่ายแพงขึ้นเพื่อผลที่ไม่คงเส้นคงวาขึ้น

10.01

เหตุผลที่ถูกต้องเพียงสองข้อ

เหตุผลได้อะไรวัดยังไง
กันบริบทงานที่อ่านเยอะแต่สรุปสั้น ไม่ทำให้บริบทหลักบวมtoken ของ agent หลักลดลง
ขนานได้จริงเวลารวมลดลงเวลาจริงลดลง ไม่ใช่แค่ต้นทุนเพิ่ม
เหตุผลที่ฟังดูดีแต่ผิด
  • “แบ่งงานให้ผู้เชี่ยวชาญเฉพาะทาง” — โมเดลเดียวกันทำได้ทั้งคู่ การแบ่งบทบาทไม่ได้เพิ่มความสามารถ แค่เพิ่มค่าส่งต่อ
  • “เลียนแบบทีมจริง” — โครงสร้างองค์กรมนุษย์แก้ปัญหาการสื่อสารของมนุษย์ ไม่ใช่ของโมเดล
  • “หลายหัวดีกว่าหัวเดียว” — จริงเฉพาะเมื่อมีความเป็นอิสระจริง ซึ่งต้องออกแบบ ไม่ได้มาเอง
10.02

Pattern 1 — Orchestrator / Worker

ตัวกลางถือแผนและบริบทรวม ตัวลูกได้รับงานที่นิยามชัดพร้อมบริบทเท่าที่จำเป็น แล้วส่งผลสรุปกลับ

กฎที่ทำให้แพตเทิร์นนี้ได้ผล
  • ตัวลูกไม่ควรเห็นบริบทเต็มของตัวกลาง — ถ้าเห็น คุณเสียประโยชน์ข้อกันบริบทไปทั้งหมด
  • ตัวลูกคืนข้อสรุป ไม่ใช่ข้อมูลดิบ — ถ้าคืนดิบ บริบทตัวกลางก็บวมเหมือนเดิม
  • ตัวลูกใช้ effort ต่ำกว่าได้ เพราะงานถูกนิยามมาแล้ว — จุดประหยัดสำคัญตาม M03.06
10.03

Pattern 2 — Pipeline

แต่ละสเตจรับ input ที่นิยามไว้ ทำงานหนึ่งอย่าง แล้วส่ง output ที่นิยามไว้ต่อ จุดแข็งคือตรวจได้ทีละสเตจ ซึ่งทำให้ debug ได้จริง ต่างจากแพตเทิร์นอื่นที่พังแล้วไม่รู้ว่าพังตรงไหน

// สัญญาระหว่างสเตจต้องเป็นโครงสร้าง ไม่ใช่ข้อความอิสระ
review  → { findings: [{ file, line, claim, severity }] }
verify  → { findings: [{ ..., verdict: "confirmed" | "false-positive", evidence }] }
report  → { confirmed: [...], summary }
ทำไมสัญญาที่เป็นโครงสร้างถึงสำคัญ

ถ้าสเตจส่งข้อความอิสระต่อกัน คุณจะตรวจไม่ได้ว่าสเตจไหนเริ่มเพี้ยน และไม่มีทางเขียนเกณฑ์เชิงกลมาตรวจกลางทาง โครงสร้างที่ชัดทำให้ pipeline กลายเป็นสิ่งที่วัดได้ตามหลัก M12.03

10.04

Pattern 3 — Fan-out / Fan-in

แตกงานที่ไม่ขึ้นต่อกันออกไปทำพร้อมกัน แล้วรวมผล เหมาะกับงานอย่างตรวจไฟล์ 40 ไฟล์ด้วยเกณฑ์เดียวกัน

จุดที่ระเบิด — การรวมผล

ถ้าตัวลูก 40 ตัวคืนผลยาว ๆ กลับมา บริบทตอนรวมจะใหญ่กว่าตอนที่ไม่แตกเสียอีก ต้องบังคับให้ตัวลูกคืนผลตามรูปแบบที่กำหนดและมีเพดานความยาว ไม่งั้นแพตเทิร์นนี้ทำร้ายตัวเอง

เกณฑ์ตัวเลข

ถ้าอัตราส่วน “ข้อมูลที่ต้องอ่าน : ข้อสรุปที่ต้องใช้” สูงกว่าราว 10 ต่อ 1 การแตกคุ้ม ถ้าใกล้ 1 ต่อ 1 อย่าแตก — เกณฑ์เดียวกับ M02.07

10.05

Pattern 4 — Judge / Critic

แพตเทิร์นที่ให้ผลชัดที่สุดในบรรดาสี่แบบ และเป็นแบบเดียวที่ความเป็นอิสระคือทั้งหมดของคุณค่า

กฎเหล็กสามข้อ
  1. ตัวตรวจต้องไม่เห็นเหตุผลของตัวเขียน — ถ้าเห็น มันจะเห็นด้วยตาม ไม่ใช่ตรวจ
  2. ตัวตรวจต้องเก่งเท่าหรือมากกว่าตัวเขียน — ใช้โมเดลเล็กตรวจงานโมเดลใหญ่คือการเอาไม้บรรทัดสั้นไปวัด
  3. ห้ามให้ตัวเดียวกันทั้งเขียนและตรวจ — แม้จะสั่งให้ “ทบทวนอีกครั้ง” ก็ไม่ใช่การตรวจอิสระ

ข้อสองกับข้อสามเป็นเหตุผลเดียวกับที่ M12.04 กำหนดว่า judge ต้องแรงกว่าหรือเท่า และเป็นหลักการเดียวกับการมีคนรีวิวที่ไม่ใช่คนเขียน

10.06

Handoff protocol

ต้องส่งต่อห้ามส่งต่อ
งานที่นิยามชัดพร้อมเกณฑ์เสร็จประวัติการสนทนาทั้งหมด
ข้อจำกัดที่ห้ามละเมิดทางที่เคยลองแล้วไม่สำเร็จ (เว้นแต่จะบอกว่าห้ามลองซ้ำ)
รูปแบบผลลัพธ์ที่ต้องคืนความเห็นของ agent ตัวก่อนหน้า
ไฟล์หรือขอบเขตที่แตะได้ผลเครื่องมือดิบที่ยังไม่ได้กลั่น
Context pollution

การส่งประวัติทั้งหมดต่อไปให้ตัวถัดไป เป็นความผิดพลาดที่พบบ่อยที่สุด มันทำลายเหตุผลข้อแรกของการใช้ multi-agent ทั้งหมด และยังพาความเข้าใจผิดของตัวก่อนหน้าไปด้วย ทำให้ความผิดพลาดสะสมแทนที่จะถูกจับ

10.07

เมื่อ multi-agent แพ้ single agent

บทที่สำคัญที่สุดในโมดูล และเป็นบทที่คนข้ามเพราะขัดกับความตื่นเต้น

อาการสาเหตุทำอะไร
ต้นทุนพุ่งหลายเท่าแต่ผลเท่าเดิมงานไม่ได้อ่านเยอะ แค่แบ่งเฉย ๆกลับไปใช้ตัวเดียว
ผลไม่คงเส้นคงวาระหว่างรอบสัญญาส่งต่อหลวมทำสัญญาให้เป็นโครงสร้าง
debug ไม่ได้ว่าพังตรงไหนไม่มีการตรวจกลางทางเปลี่ยนเป็น pipeline ที่ตรวจทีละสเตจ
ตัวลูกทำงานทับกันขอบเขตไม่ชัดระบุไฟล์ที่แต่ละตัวแตะได้
เวลารวมไม่ได้ลดลงงานขึ้นต่อกันจริง ขนานไม่ได้ยอมรับว่าเป็นงานลำดับ
คำถามเดียวที่ควรถามก่อนแตกงาน

“ถ้าผมทำด้วย agent เดียว มันจะพังตรงไหน” ถ้าตอบไม่ได้อย่างเจาะจง แปลว่ายังไม่มีเหตุผลที่จะแตก และคุณควรวัดก่อนตามแล็บของโมดูลนี้

10.08 · แล็บประจำโมดูล

ทำ review pipeline สามขั้น แล้ววัดว่าดีกว่า agent เดียวจริงหรือแค่แพงกว่า

แล็บนี้ต้องใช้ชุดวัดจาก M12 เพราะทั้งประเด็นคือการพิสูจน์ ไม่ใช่การสร้าง

ขั้นตอน

  1. ปลูกบั๊กที่รู้คำตอบ 15 ตัว ใน repo จริง คละความยาก
  2. แขนที่ 1 — agent เดียวที่สั่งให้หาบั๊ก
  3. แขนที่ 2 — pipeline สามขั้น review → verify → report พร้อมสัญญาที่เป็นโครงสร้าง
  4. รันทั้งสองแขนบนชุดเดียวกัน อย่างละ 3 ครั้ง
  5. วัดสี่มิติ — จับได้กี่ตัว เตือนผิดกี่ครั้ง ต้นทุนต่อบั๊กที่จับได้ และเวลาจริง
เกณฑ์ผ่าน
  • ตอบได้ด้วยตัวเลขว่าแขนไหนชนะ และชนะที่มิติไหน
  • ถ้าผลออกมาว่า agent เดียวชนะ ถือว่าผ่านเต็ม — คุณเพิ่งประหยัดเงินและความซับซ้อนให้ตัวเอง
  • ถ้าช่วงผลของสองแขนทับกัน ต้องบอกได้ว่าต้องใช้อีกกี่งานถึงจะสรุปได้
ผลที่มักเจอ

pipeline มักจับได้พอ ๆ กัน แต่เตือนผิดน้อยลงชัดเจน เพราะสเตจ verify กรองออก ถ้าผลของคุณออกมาแบบนี้ คุณค่าที่แท้จริงของแพตเทิร์นนี้อยู่ที่ความแม่นยำ ไม่ใช่ความครอบคลุม ซึ่งเปลี่ยนวิธีที่คุณควรใช้มัน
