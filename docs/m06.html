AI Coding Agent SDLC · Phase 02 · Module 06

Frontend Implementation

ฝั่งหน้าบ้านมีปัญหาเฉพาะตัวที่ฝั่งหลังบ้านไม่มี — โค้ดที่ผิดอาจดูถูกในสกรีนช็อต โมดูลนี้ว่าด้วยการปิดช่องนั้นด้วยลูปตรวจที่ agent ทำเองได้

9 บทเรียน3 ชั่วโมง2 แล็บต้องผ่าน M04 · M05 ก่อน
ใจความของทั้งโมดูล

งาน FE ที่มอบให้ agent แล้วได้ผลดี คืองานที่มีภาษากลางให้อ้างอิง — design token ชื่อ component และเกณฑ์ที่ตรวจอัตโนมัติได้ ถ้าไม่มีสามอย่างนี้ คุณกำลังสั่งด้วยคำบรรยายความรู้สึก

06.01

ลำดับที่ข้ามไม่ได้

token → component → page → flow ลำดับนี้ไม่ใช่เรื่องความเป็นระเบียบ แต่เป็นเรื่องของการที่แต่ละขั้นให้คำศัพท์กับขั้นถัดไป

ขั้นให้อะไรกับขั้นถัดไปถ้าข้าม
Tokenชื่อสี ระยะ ขนาดตัวอักษรagent ใส่ค่าดิบกระจายทั่วโปรเจกต์
Componentชื่อชิ้นส่วนที่อ้างอิงได้เขียน markup ซ้ำทุกหน้า สไตล์ไม่ตรงกัน
Pageโครงหน้าและสถานะflow ต่อไม่ติด state หาย
Flowเส้นทางผู้ใช้ที่ทดสอบได้ทุกหน้าถูกแต่ต่อกันไม่ได้
06.02

Design system ในฐานะบริบท

การส่งภาพอย่างเดียวทำให้ agent ต้องเดาค่าจากพิกเซล ผลคือค่าที่ใกล้เคียงแต่ไม่ตรง และกระจายไปทั่วจนเก็บกวาดยาก

// สิ่งที่ควรอยู่ในบริบท — ชื่อที่อ้างอิงได้
--space-1..6, --color-surface/ink/accent, --radius-none
Button(variant: primary|ghost, size: sm|md)
Card, Field, Toast   // ชื่อ component ที่มีอยู่แล้ว

// สิ่งที่ไม่ควรเป็นแหล่งข้อมูลเดียว
screenshot.png       // ใช้เทียบผลได้ แต่ห้ามใช้เป็นที่มาของค่า
กฎเดียวที่ต้องจำ

ภาพใช้สำหรับตรวจ ไม่ใช่สำหรับกำหนด ค่าที่กำหนดต้องมาจาก token ที่มีชื่อ เพราะชื่อคือสิ่งที่ agent อ้างถึงได้ในรอบถัดไป และคือสิ่งที่รีวิวได้

06.03

เส้นแบ่ง server/client ที่พลาดบ่อยที่สุด

เฟรมเวิร์กสมัยใหม่แยกโค้ดที่รันบนเซิร์ฟเวอร์กับบนเบราว์เซอร์ และเส้นนี้คือจุดที่ agent พลาดมากที่สุดในงาน FE ทั้งหมด

  • เอา state หรือ event handler ไปไว้ฝั่งเซิร์ฟเวอร์ — พังตอน build ไม่ใช่ตอนเขียน
  • ลากทั้งหน้าไปเป็นฝั่ง client เพื่อให้ผ่าน — ผ่านจริง แต่เสียประโยชน์ทั้งหมดของการเรนเดอร์ฝั่งเซิร์ฟเวอร์
  • ดึงข้อมูลผิดชั้น — ทำให้เกิด waterfall ที่ช้าแต่ไม่มี error
  • ใช้ของที่มีเฉพาะเบราว์เซอร์ในโค้ดที่รันสองที่ — พังเฉพาะบางเส้นทาง
วิธีกันที่ได้ผลกว่าการเขียนกฎ

ใส่ไว้ใน project memory ว่า “ถ้าต้องเปลี่ยน component จาก server เป็น client ให้หยุดแล้วอธิบายเหตุผลก่อน” — เพราะการเปลี่ยนนี้มักเป็นการหลบปัญหา ไม่ใช่การแก้ปัญหา และเป็นจุดที่คนควรตัดสิน

06.04

State และ data fetching

สองเรื่องนี้อยู่ด้วยกันเพราะความผิดพลาดส่วนใหญ่เกิดที่รอยต่อของมัน — ข้อมูลถูกดึงผิดที่ แล้ว state ก็เลยอยู่ผิดที่ตามไปด้วย

แพตเทิร์นagent ทำถูกagent ชอบทำผิด
ดึงข้อมูลใกล้จุดที่ใช้ใช่ ถ้าบอกโครงไว้ชัดยกไปไว้ชั้นบนสุดแล้วส่งผ่านหลายชั้น
แยก server state กับ UI stateทำได้เมื่อมีตัวอย่างในโปรเจกต์ยัดทุกอย่างลง state ก้อนเดียว
จัดการสถานะกำลังโหลดและผิดพลาดเขียนได้ครบถ้าอยู่ใน specทำแต่ทางที่สำเร็จถ้าไม่ได้สั่ง
ทำให้ข้อมูลสดหลังแก้ไขทำได้รีเฟรชทั้งหน้าแทนที่จะอัปเดตเฉพาะจุด
อาการที่ไม่มี error แต่ช้าลงเรื่อย ๆ

เมื่อ agent วางการดึงข้อมูลเป็นลำดับที่ต้องรอกันไปเรื่อย ๆ หน้าจะทำงานถูกทุกอย่างแต่ช้าขึ้นทุกครั้งที่เพิ่มของ ไม่มีอะไรแดง ไม่มีเทสต์แตก และไม่มีใครสังเกตจนกว่าจะมีคนบ่น ให้ใส่เพดานเวลาโหลดเป็นเกณฑ์ในเทสต์ ตามหลักเดียวกับ budget ใน M03

สิ่งที่ควรใส่ใน project memory

ระบุให้ชัดว่าโปรเจกต์นี้ใช้อะไรจัดการ server state และห้ามเพิ่มตัวใหม่โดยไม่ถาม — ไม่งั้น agent จะเลือกวิธีที่มันคุ้นเคยที่สุด ซึ่งอาจเป็นคนละตัวกับที่ทีมใช้อยู่ แล้วคุณจะได้สองระบบในโปรเจกต์เดียว

06.05

Visual verification loop

นี่คือสิ่งที่ทำให้งาน FE กับ agent เปลี่ยนจาก “ส่งไปแล้วลุ้น” เป็นลูปปิดที่มันตรวจงานตัวเองได้ก่อนถึงมือคุณ

  1. agent เขียนโค้ด
  2. รันเซิร์ฟเวอร์ เปิดหน้าในเบราว์เซอร์
  3. ถ่ายภาพหน้าจอ และอ่าน console กับ network
  4. เทียบกับ spec แล้วบอกว่าข้อไหนไม่ตรง
  5. แก้ แล้ววนใหม่จนผ่าน
สิ่งที่ต้องบังคับให้ตรวจ ไม่ใช่แค่ดูภาพ
  • console ต้องไม่มี error — ข้อนี้จับบั๊กได้มากกว่าการดูภาพ
  • ตรวจอย่างน้อยสองความกว้างหน้าจอ
  • ตรวจสถานะ empty และ error ไม่ใช่แค่สถานะที่มีข้อมูลครบ
06.06

Accessibility เป็นเกณฑ์ที่ตรวจอัตโนมัติได้

ข้อดีของการวางเรื่องนี้เป็น acceptance criteria คือมันเป็นหนึ่งในไม่กี่เรื่องคุณภาพ UI ที่เครื่องตัดสินได้จริง จึงเอาไปเป็นเกณฑ์ในชุดวัดได้ตรง ๆ

  • ทุก control ที่กดได้ต้องเข้าถึงด้วยคีย์บอร์ดและมี focus ที่มองเห็น
  • ทุกภาพมี alt ทุก input มี label ที่ผูกกัน
  • คอนทราสต์ผ่านเกณฑ์ทั้งธีมสว่างและมืด
  • ลำดับหัวข้อไม่ข้ามระดับ

สี่ข้อนี้ตรวจได้ด้วยเครื่องมืออัตโนมัติ ใส่เข้า CI แล้วมันจะกลายเป็นสิ่งที่ agent ต้องทำให้ผ่าน ไม่ใช่สิ่งที่หวังว่ามันจะนึกถึง

06.07

UI ที่ผ่านสายตาแต่พังจริง

อาการทำไมสกรีนช็อตจับไม่ได้วิธีจับ
Hydration ไม่ตรงภาพนิ่งดูปกติ พังตอนโต้ตอบอ่าน console
Layout ขยับตอนโหลดถ่ายหลังโหลดเสร็จเลยไม่เห็นวัด layout shift
State ค้างข้ามหน้าเห็นทีละหน้าเลยไม่รู้เทสต์ที่เดินหลายหน้า
สถานะไม่มีข้อมูลตอนทดสอบมีข้อมูลเสมอบังคับ fixture ว่าง
ข้อความยาวจนล้นข้อความทดสอบสั้นเสมอfixture ที่มีข้อความยาว
รูปแบบที่เจอซ้ำ

สี่ในห้าข้อข้างบนมีสาเหตุเดียวกัน — ข้อมูลทดสอบสวยเกินจริง การเตรียม fixture ที่มีเคสว่าง เคสยาว และเคสพัง ให้ผลมากกว่าการเขียนกฎเพิ่มใน prompt

06.08 · แล็บ A

สร้าง component library จาก design token

  1. กำหนด token ให้ครบก่อน — สี ระยะ ตัวอักษร มุม เงา พร้อมชื่อที่ใช้อ้างอิงได้
  2. ให้ agent สร้าง 5 component จาก token โดยห้ามใช้ค่าดิบ
  3. ตรวจด้วยเกณฑ์เชิงกล — grep หาค่าสีดิบในไฟล์ component ต้องได้ศูนย์
  4. ทุก component ต้องผ่านการตรวจ accessibility อัตโนมัติ
เกณฑ์ผ่าน

เกณฑ์ “ไม่มีค่าดิบ” ตรวจด้วย grep ได้ ทำให้แล็บนี้เอาไปใส่ชุดวัดของ M12 ได้ทันทีโดยไม่ต้องใช้คนตัดสิน

06.09 · แล็บ B

สร้าง flow สามหน้าพร้อมรอบ visual verification

  1. เขียน spec ของ flow ให้ทุกข้อตรวจได้ (ใช้วิธีจาก M04.01)
  2. ให้ agent สร้างครบสามหน้าพร้อมสถานะ loading, empty, error
  3. บังคับให้มันเปิดเบราว์เซอร์ตรวจเอง ทั้งจอกว้างและจอแคบ
  4. ให้มันรายงานว่า spec ข้อไหนยังไม่ผ่าน ก่อนที่คุณจะดู
จุดที่แล็บนี้มักล้ม

agent จะรายงานว่า “ผ่านหมด” ทั้งที่ยังไม่ผ่าน วิธีกันคือให้มันแปะภาพและบรรทัด console มาเป็นหลักฐานต่อข้อ ตามวินัยหลักฐานใน M04.05 ไม่ใช่ให้สรุปลอย ๆ

เชื่อมกับโมดูลอื่น — M05 design token คือรูปแบบหนึ่งของ docs-as-context · M11 ขยาย visual verification เป็น E2E ที่ไม่ flaky · M12.03 เกณฑ์ grep และ a11y คือตัวอย่างที่ดีของเกณฑ์เชิงกล
