AI Coding Agent SDLC · Phase 05 · Module 14

CI/CD และ Agent ในสายพาน

บนเครื่องคุณมีคนคอยกดอนุมัติและสังเกตความผิดปกติ บนสายพานไม่มีทั้งสองอย่าง โมดูลนี้ว่าด้วยการเอา agent ขึ้นสายพานโดยที่ยังมีจุดหยุดที่มนุษย์ควบคุม และบิลไม่บาน

8 บทเรียน2.5 ชั่วโมง1 แล็บต้องผ่าน M11 · M12 · M13 ก่อน
ใจความของทั้งโมดูล

สิ่งที่เปลี่ยนเมื่อ agent ขึ้นสายพานไม่ใช่เทคนิค แต่คือไม่มีคนอยู่ในลูป ทุกอย่างที่คุณเคยแก้ด้วยการสังเกตแล้วกด Ctrl-C ต้องกลายเป็นกฎที่เขียนไว้ล่วงหน้า

14.01

agent ใน CI ต่างจากบนเครื่องอย่างไร

บนเครื่องใน CI
เมื่อไม่แน่ใจถามแล้วรอต้องตัดสินใจเองหรือล้ม — รอคือค้าง
เมื่อทำผิดทางคุณเห็นแล้วหยุดทำจนจบแล้วคุณเห็นผลทีหลัง
สิทธิ์เท่าคุณควรแคบกว่ามาก
ต้นทุนคุณเห็นตัวเลขวิ่งซ่อนอยู่จนบิลมา
ความล้มเหลวคุยกันต่อได้ต้องล้มให้ชัดและมี exit code
กฎข้อแรกของ agent ใน CI

ไม่แน่ใจต้องล้ม ไม่ใช่เดา — ให้ออกด้วยรหัสที่บอกว่าต้องมีคนดู ดีกว่าปล่อยให้มันเดาแล้วสร้าง PR ที่ดูดีแต่ผิด เพราะอย่างหลังกินเวลาคนมากกว่าและกัดกร่อนความเชื่อถือ

14.02

PR automation และเส้นที่ไม่ควรข้าม

งานให้ agent ทำเหตุผล
เขียนคำอธิบาย PR จาก diffได้เลยย้อนได้ ผิดแล้วแก้ง่าย
รีวิวและคอมเมนต์ได้ ถ้าผ่าน verificationดู M11.07
แก้ตามคอมเมนต์รีวิวได้ ถ้าคนอนุมัติ diffคนยังเป็นคนตัดสิน
สร้าง PR ใหม่จาก issueได้ แต่เป็นร่างเนื้อหา issue คือข้อมูลไม่น่าเชื่อถือ (M13.02)
Mergeไม่ย้อนยาก และเป็นจุดที่ความรับผิดชอบต้องอยู่กับคน
Deploy โปรดักชันไม่เหตุผลเดียวกัน แต่หนักกว่า
เส้นที่มักถูกข้ามทีละนิด

เริ่มจาก “ให้ merge เฉพาะ PR ที่แก้ typo” แล้วขยายเป็น “เฉพาะที่เทสต์ผ่าน” แล้วกลายเป็น merge เกือบทุกอย่าง ให้ตั้งเส้นเป็นกฎที่บังคับด้วยการตั้งค่า ไม่ใช่ข้อตกลงที่พูดกันไว้

14.03

Quality gate ที่บล็อกได้จริง

Gate ที่ทำงานได้ต้องเรียงจากถูกและแน่นอนไปหาแพงและมีความเห็น ถ้าเรียงกลับกัน คุณจะจ่ายค่า LLM เพื่อตรวจโค้ดที่คอมไพล์ไม่ผ่าน

ลำดับGateบล็อกไหม
1คอมไพล์ / lint / typecheckบล็อก
2เทสต์เดิมทั้งหมดบล็อก
3ขอบเขต diff และขนาดบล็อก
4สแกนความปลอดภัยและ secretบล็อก
5รีวิวโดย LLM ที่ผ่าน verificationบล็อกเฉพาะระดับสูง
6ความเห็นเชิงคุณภาพอื่น ๆคอมเมนต์เท่านั้น
กฎที่ทำให้ gate อยู่รอด

Gate ที่บล็อกต้องมี อัตราเตือนผิดต่ำมาก ถ้ามันบล็อกผิดสัปดาห์ละครั้ง คนจะหาทางข้าม และภายในเดือนเดียวมันจะกลายเป็นของประดับ ให้เริ่มจากโหมดเตือนอย่างเดียว วัด precision ตามวิธีใน M11.08 แล้วค่อยเปลี่ยนเป็นบล็อกเมื่อตัวเลขดีพอ

14.04

ทำ agent ให้เป็น CLI ที่เขียนสคริปต์ครอบได้

agent ที่ใช้ในสายพานต้องมีพฤติกรรมเหมือนเครื่องมือ unix ทั่วไป ไม่ใช่แอปที่ต้องมีคนนั่งดู

  • โหมดไม่โต้ตอบ — รับงานเข้า คืนผลออก ไม่ถามกลับ
  • ผลลัพธ์เป็นโครงสร้าง — ให้สคริปต์อ่านต่อได้ ไม่ใช่ข้อความสวย ๆ สำหรับคน
  • exit code ที่มีความหมาย — สำเร็จ / ล้มเหลว / ต้องมีคนดู ต้องแยกกันได้
  • เพดานเวลาและต้นทุน ที่บังคับจากภายนอก ไม่ใช่หวังว่ามันจะพอดี
  • ทุกอย่างที่ต้องใช้ระบุผ่านพารามิเตอร์ ไม่พึ่งสถานะจากรอบก่อน
การทดสอบง่าย ๆ

ถ้าคุณเขียนสคริปต์ครอบมันแล้วตัดสินใจอัตโนมัติจากผลได้ แปลว่าพร้อมขึ้นสายพาน ถ้ายังต้องมีคนอ่านผลก่อนถึงจะรู้ว่าเกิดอะไรขึ้น แปลว่ายังไม่พร้อม

14.05

งานอัตโนมัติตามเวลา

งานที่รันเองตามตารางมีประโยชน์จริง — ไล่ dependency ที่ล้าสมัย สรุป error ที่เพิ่มขึ้น เตรียมร่างแก้ให้ issue ที่ค้าง แต่ต้องมี guardrail ครบก่อนเปิด

เช็คลิสต์ก่อนเปิดงานตามเวลา
  1. ผลลัพธ์เป็นร่างเสมอ — สร้าง PR หรือ issue ไม่ใช่เปลี่ยนของจริง
  2. เพดานต้นทุนต่อรอบ และการแจ้งเตือนเมื่อชน
  3. สิทธิ์แยกจากของคุณ และแคบกว่า
  4. ปุ่มปิดที่กดได้ทันที โดยไม่ต้องแก้โค้ด
  5. บันทึกที่ตัวมันแก้ไม่ได้ — ตาม M13.08
ความเสี่ยงที่มากับความสม่ำเสมอ

งานที่รันทุกคืนได้ผลดี 60 คืนติด จะไม่มีใครอ่านผลของคืนที่ 61 นี่คือกลไกเดียวกับที่ทำให้ระบบเตือนภัยที่แม่นมาก ๆ กลายเป็นเสียงพื้นหลัง ทางแก้คือให้มันเงียบเมื่อไม่มีอะไร และส่งเสียงเฉพาะเมื่อมีของจริง

14.06

ต้นทุน CI ที่บานเพราะ agent

สาเหตุทำไมโตเร็ววิธีคุม
รันทุก pushPR เดียวมี 20 pushรันตอนเปิด PR และตอนขอรีวิว
รีวิวทั้งไฟล์ทุกครั้งจ่ายซ้ำสิ่งที่ไม่เปลี่ยนส่งเฉพาะ diff และบริบทรอบ ๆ
cache ไม่ติดใน CIสภาพแวดล้อมใหม่ทุกครั้งทำ prefix ให้นิ่ง (M03.03)
ลองใหม่อัตโนมัติล้มเพราะ prompt แล้วลองอีก 3 ครั้งแยกความล้มเหลวชั่วคราวกับถาวร
งานตามเวลาที่ลืมปิดจ่ายทุกคืนโดยไม่มีใครดูวันหมดอายุที่ต้องต่ออายุ
ตัวเลขที่ควรติดแดชบอร์ด

ดอลลาร์ต่อ PR ที่ merge — ตัวเดียวจับได้ทั้งห้าสาเหตุ และเป็นตัวที่อธิบายให้ผู้บริหารเข้าใจได้ในประโยคเดียว

14.07

Rollback และ incident เมื่อคอมมิตมาจาก agent

เมื่อของพังแล้วคอมมิตนั้นเขียนโดย agent คำถามเดิม ๆ ตอบยากขึ้น — ใครเข้าใจเจตนา ใครรับผิดชอบ และจะกันไม่ให้เกิดซ้ำยังไง

สิ่งที่ต้องมีในทุกคอมมิตที่ agent เขียน
  • ระบุว่าสร้างโดย agent และคนไหนเป็นผู้อนุมัติ
  • ลิงก์กลับไปยังงานหรือ issue ต้นทาง
  • คำอธิบายเจตนา ไม่ใช่แค่สรุปว่า diff เปลี่ยนอะไร — สิ่งที่ diff เปลี่ยนอ่านเอาเองได้ สิ่งที่อ่านไม่ได้คือทำไม

เรื่องความรับผิดชอบไม่ใช่เรื่องเทคนิค — คนที่อนุมัติคือคนที่รับผิดชอบ เสมอ และการทำให้ข้อนี้ชัดตั้งแต่ต้นสำคัญกว่าเครื่องมือใด ๆ ในโมดูลนี้ รายละเอียดเชิงองค์กรอยู่ใน M15

14.08 · แล็บประจำโมดูล

ตั้ง PR review bot พร้อม gate ที่บล็อกเมื่อพบ finding ระดับสูง

  1. ทำ gate 1–4 ก่อน (เชิงกลล้วน) แล้วยืนยันว่าบล็อกได้จริง
  2. เพิ่ม review agent ในโหมดเตือนอย่างเดียว — ยังไม่บล็อก
  3. รันคู่ขนานกับการรีวิวของคนสองสัปดาห์ เก็บทุก finding
  4. วัด precision ตามวิธีของ M11.08
  5. เปิดโหมดบล็อกเฉพาะระดับสูง ก็ต่อเมื่อ precision ของระดับนั้นสูงพอ
  6. ใส่เพดานต้นทุนและวัดดอลลาร์ต่อ PR ที่ merge
เกณฑ์ผ่าน
  • gate เชิงกลบล็อกได้จริง ทดสอบด้วยการจงใจส่งของที่ควรถูกบล็อก
  • มีตัวเลข precision ของ finding ระดับสูงก่อนเปิดโหมดบล็อก
  • ทีมยอมรับว่า gate นี้ไม่ขวางทาง — ถามจริง อย่าเดาแทน
  • ถ้าผลวัดบอกว่ายังไม่ควรเปิดโหมดบล็อก ถือว่าผ่าน — การไม่เปิดของที่ยังไม่พร้อมคือคำตอบที่ถูก

เชื่อมกับโมดูลอื่น — M03 ต้นทุนที่บานใน CI · M11 เครื่องมือรีวิวที่เอามาแขวนบน gate · M12 ชุด smoke ที่รันในสายพาน · M13.08 guardrail ของงานอัตโนมัติ · M15 ความรับผิดชอบและวัฒนธรรม
